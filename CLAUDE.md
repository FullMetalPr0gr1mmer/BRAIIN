# CLAUDE.md — Braiin Station Engineering Standard

> This file is the **single, authoritative engineering standard** for Braiin Station. If code and this document disagree, this document wins until amended in a reviewed PR.

## 1. Project Summary

**Braiin Station** is a production, single-platform creative-agency system with four parts (*the project's name; the public brand is data — "Braiin Statiion" since UI v2, read from `site_profile` by every page, title, feed and JSON-LD node, so a rename is a CMS edit. No displayed string may spell it; `tests/e2e/served-html.e2e.ts` gates the old spelling*):

1. **Public site** — bilingual EN/AR (RTL) marketing/portfolio site for **28 services in 5 disciplines**, fully CMS-driven sections (toggleable, re-orderable, styleable, per-section error isolation). Each service detail page opens with its **own clip** — a window of the showreel until Stream (EXC-009, KAN-20) — and a case block. **Gaming** (the teaser) and **Merchandise** were retired on 2026-09-27: archived, restorable, their URLs 301 to the nearest new page.
2. **AI Style-Finder** — lead-gen quiz app. **Logic deferred**: ship the **module boundary + security/cost envelope only** (proxy, rate limits, spend cap, Zod wrappers around a `501` stub).
3. **Creative Knowledge blog** — SEO/GEO/AEO content engine.
4. **Admin / CMS** — authenticated, 5 roles: **Admin, Content Creator, SEO, Developer, Sales** (Sales added in Admin v2 C10a, owner decision A4, 2026-10-03). RBAC enforced **server-side from scratch**.

The 5 disciplines and 28 services (Round 2, 2026-09-27 — the `disciplines` table, `services.discipline_id`, migration 0028):
- **Branding** — Logo Design · Business Cards · Letterhead · Brand Guidelines · Stationery · Packaging · PowerPoint Templates · Company Profile
- **Production** — Motion Graphics · Animation · Montage / Video Editing · Photography / Videography · Model Booking · Music, VO & SFX
- **Marketing** — Marketing Strategy · Content Strategy · Advertising · Social Media · Campaigns · Content Creation · Copywriting
- **Website Development** — Hosting · Domain · SEO / GEO / AEO
- **Events & Exhibitions** — Venue Booking · 3D Design · Booth Production · Booth Installation

*(Launched with 14. Retired 2026-09-27: Gaming (teaser) and Merchandise; Branding, Photography, Event Planning and Web Development became disciplines or merged services. Retired slugs 301 by a code-owned map, `src/lib/services/retired.ts`. Since Round 3 the admin's `redirects` table reaches the edge too — every save rebuilds the tenant's map into KV `site:redirects` — and is consulted only after a 404: live page > code map > table > 404.)*

## 2. Locked Decisions (confirmed 2026-06-10)

- **Build:** GREENFIELD / fresh. Every `[reuse]`-tagged feature is **built new**. RBAC from scratch.
- **Stack:** Astro + React admin (islands) + Supabase (Postgres, Auth, Edge Functions, Storage) + Tiptap. **TypeScript strict.** Zod for all content + form input.
- **Hosting/adapter:** **Cloudflare Workers — not Pages** (the Astro Cloudflare adapter dropped Pages support) via the Astro Cloudflare adapter, deployed by `ci.yml`'s `deploy` job after every gate — **never** dashboard-connected Workers Builds, which ships whatever lands on the branch (locked as "Workers Builds" on 2026-06-10; see the deploys amendment below). Cloudflare WAF, Stream, image transforms/cache, MENA edge. On-demand `/admin`; static-first public shell.
- **Tenancy:** **SINGLE-TENANT at launch, TENANT-READY schema.** `tenant_id` + tenant-scoped RLS on **every** table from day 1.
- **i18n:** path-based `/` (EN) + `/ar/` (AR). hreflang + `x-default`, per-language self-referential canonicals, both languages in sitemap, complete AR metadata/OG.
- **Analytics canonical source:** **first-party self-hosted analytics is the single source of truth** (PDPL-friendly, consent-gated, no double-write). GA4 secondary, behind consent.
- **AI Style-Finder (deferred):** server-side proxy, per-IP/session rate limits + spend caps; default model = **latest Claude (Opus/Sonnet 4.x)**.
- **Search:** Postgres FTS in v1 with **explicit Arabic-tokenisation validation**; swap-ready behind one accessor.
- **Jurisdiction:** Saudi Arabia (`.sa`) — **PDPL applies**.

### Central tension (the load-bearing architecture)
Static, cacheable shell **+** Server Islands (`server:defer`) **+** on-demand `/admin` **+** on-demand revalidation / Live Content Collections (a published edit **never triggers a full rebuild**) **+** Content Layer API **+** tag-based edge cache invalidation tied to publish.

#### Render tiers
| Tier | What | Astro setting | Cache |
|---|---|---|---|
| **A — Static shell** | All indexable content (`/services/*`, `/portfolio/*`, `/creative-knowledge/*`, `/about/*`, `/ar/*` twins) | `output:'server'`, route opts in with `prerender = true` (implemented as long-`s-maxage` edge-cached SSR) | Edge-cached, purge-by-tag on publish |
| **B — Server Islands** | ONLY non-indexable dynamic holes | `server:defer` | Per-island `Cache-Control` + `cacheHint.tags` |
| **C — SSR Worker** | `/admin/**`, Style-Finder dynamic API | `prerender = false` | `private, no-store` |

**Indexable-content rule (hard):** indexable content lives in Tier A. Reviewers reject PRs that hydrate indexable content client-side. **Publish = cache event, not a rebuild.** Cache-Tag scheme `tenant:<tid>`, `route:<name>`, `<entity>:<slug>`, `<entity>:all`, `locale:<en|ar>` (≤30 tags/purge, ≤30k/24h). Adapter locks: `imageService:'cloudflare-binding'`, `sessionKVBindingName`/`imagesBindingName`. All DB access via the Supavisor transaction-mode pooler.

## 3. THE FOUR PILLARS (hard requirements, in priority order)

**Absolute order: 1) Security 2) Performance 3) SEO/GEO/AEO 4) Scalability.** Higher pillar wins. **Never weaken authz/CSP/consent to hit a perf budget — file an exception.**

### Pillar 1 — Security
- [ ] Authorization in **two independent server layers that must both pass**: Postgres RLS (primary) + `assertCap()` (secondary). React `can()` is UX only.
- [ ] Every table: `tenant_id uuid not null`, RLS `ENABLE` + `FORCE`; every policy `USING`/`WITH CHECK` includes `tenant_id = app.effective_tenant_id()` (the JWT tenant, else the single launch tenant — the anon fence; there is no `auth.current_tenant_id()`).
- [ ] Grants are **stated, never inherited** from Supabase's default privileges (revoke, then grant exactly): staff (`authenticated`) only read rollups (never raw telemetry: `analytics_events` and `web_vitals` are the service role's alone, 0071), the search/consent/notification ledgers, `tenants`, `profiles` and the help guides (`help_articles`); their one write there is the users screen's column UPDATE on `profiles.role`/`is_active`/`display_name` (never `profiles.is_owner`, which only an operator or `public.transfer_ownership` sets, 0055), which RESTRICTIVE policies on every staff write to `profiles` (`profiles_live_update`/`_insert`/`_delete`) also hold to a live Admin, `app.role_manages_users(app.live_role())`, so a demoted, deactivated or locked Admin's unexpired token changes no one, itself included (0050), and reading anyone's profile but your own needs the same (`profiles_live_read`, 0055); the service role and definer functions write the rest (0030, 0037, 0046).
- [ ] Role + `tenant_id` via the Custom Access Token Hook from `app_metadata` (never `user_metadata`). On a role, activity or tenant change, every session of that person is revoked in the database (`profiles_revoke_sessions`, an AFTER UPDATE trigger on `profiles`, 0055: no refresh is possible and the admin turns them away at their next request) and the Worker rejects a token whose claims disagree with the profile (§2). An access token already issued keeps its old role at PostgREST until it expires (up to an hour) on the tables with no live check (`docs/admin-v2/deviations.md`, Residual risks). The account owner (`profiles.is_owner`, one per tenant, set by an operator, launch runbook §3) cannot be demoted, deactivated, moved or deleted by anyone (`app.tg_profiles_owner_guard`, and a 422 in the Worker first), and hands ownership on only by their own action (`public.transfer_ownership`).
- [ ] Publish/archive/delete gated by RESTRICTIVE RLS, not hidden buttons.
- [ ] `leads.budget`/`timeline`, the notes thread (which replaced `internal_notes`; that field and the never-written `ip_inet` are dropped, C14b) and the contact ciphertext restricted to **Admin + Developer**, and to **Sales one lead at a time** (Admin v2 C10a: through the reveal, and the notes thread under a limit of the same size, never a list, an export or a notification), leaving the database only through the Worker's audited paths: a staff token SELECTs the safe lead columns only (column GRANT, 0033), and the gated ones are read as the service role by the per-lead reveal (`leads.pii` + live recheck + a rate limit of 60 an hour per person and 300 per tenant + an audit row written first, fail-closed; one path, `src/lib/crm/reveal.ts`) and the export lockdown, the only two paths that return them to a person. Two server-side processes read them too, and return nothing: the signed `notify-lead` hook (§10), which decrypts only for recipients holding `leads.pii` and `export.csv` (`receivesLeadPiiUnasked`: Admin, Developer; never Sales) and stores field names, never values, and the daily index backfill (0035, `src/lib/crm/indexBackfill.ts`), which decrypts the e-mail, phone and budget in memory and stores only blind indexes and score-signal names (it writes nothing for a batch the key decrypts none of, and logs counts only). The role-checked decrypt path is the gate of record, and `tests/lib/leadGrants.spec.ts` names every reader. Every lead row is also behind a RESTRICTIVE live check, `app.live_role()` (the profile's role, `is_active`, `locked_until` and tenant, read at query time and required to equal the token's role), so a demoted, deactivated or locked token reads nothing even through the API directly. The notes thread (`lead_notes`, 0034) is read and added to through one door, `/api/admin/leads/[id]/notes` (`leads.pii`, live recheck, a read limit of 60 an hour per person and 300 per tenant for every reader, the reveal's limiter and numbers (`lead-notes-read`, C10a, owner decision 2026-10-19: Sales holds `leads.pii` and a note can quote a budget), an audit row written before the thread is read; a note's author is the session's user; a note is append-only). The legacy `internal_notes` field is gone with its mirror (the leads contract: C14a's code, then C14b's migration); the notes the mirror wrote stay in the thread as notes (source `legacy`), append-only and deleted like any other. No staff token inserts or deletes a lead (0030): a lead added by hand arrives through `public.crm_ingest_lead` as the service role (`leads.manage` + `leads.pii`, live recheck, a limit of 60 an hour per person and 300 per tenant, `source` and the adding person set on the server), and erasing one is `crm.erase`, **Admin only**: live recheck, a limit of 20 an hour per person and 50 per tenant, an attempt audit row written first (fail-closed), then `public.crm_erase_lead` as the service role, which checks the acting profile itself, live, through `app.role_crm_erase`, and deletes the lead with its notes and timeline, then an outcome audit row; deleting one note is the same gate without the limit, through `public.crm_delete_lead_note`, its outcome row saying whether the note was found (0041). Staff UPDATE on leads stays a column grant: the pipeline's columns (0041; the legacy pair withdrawn by 0097, then dropped by C14b), never the ciphertext, the retention date, the score or the indexes. E-mail and phone are also blind-indexed for exact-match lookups (HMAC under the labelled `crm-index/v1` derivation of `LEAD_PII_ENC_KEY`, tenant-salted, no new secret, 0035); the indexes and the score's reasons are never readable by staff tokens: the reasons (three of which name the budget band and the timeline) reach a person only through the CRM's per-lead reveal, which names `score_signals` in its audit row (C4a), never through the export (the legacy panel's `?pii=1` reveal is gone since C14a). The score itself is readable by lead workers, who all hold `leads.pii`, and with the points in `crm_settings.scoring` it can imply the band (with the default points, any score above 65 includes `budget_200k_plus`); the points are Admin's to set (`crm.settings`, C9a, audited), and points that weigh one budget signal alone make every lead's score name it — accepted while every lead worker holds `leads.pii`; a role that works leads without it sees no score in bulk until the points are fenced (C9a as-built). Content Creator and SEO get **no** lead access. `leads_safe` is granted to all `authenticated` and is SECURITY INVOKER: a GRANT cannot tell the app roles apart (all five share one Postgres role), so RLS decides its rows.
- [ ] Secrets via `astro:env` (`context:"server", access:"secret"`); service-role key, `ANTHROPIC_API_KEY`, signing keys, `LEAD_PII_ENC_KEY`, `AUDIT_HMAC_KEY` never `PUBLIC_*`/client-bundled.
- [ ] **Strict CSP with per-request nonce and NO `'unsafe-inline'`** (`style-src` nonce-based — theme = CSS custom properties, Tiptap class-based with `style=` stripped; `data:`/`blob:` dropped from `img-src` and the sanitizer). `frame-ancestors 'self'`; `connect-src 'self'` covers the same-origin RUM beacon + Sentry tunnel. HSTS preload, nosniff, Referrer-Policy, Permissions-Policy, COOP/CORP. Report-Only one cycle, then enforce. Don't call CSP "strict" while shipping `'unsafe-inline'` — it ships without it. `frame-src` adds `'self'` on `/admin/**` responses only (the page editor frames `/admin/preview`), and a preview render sends `form-action 'none'` and a `connect-src` of exactly the API endpoints that write nothing (`READ_ONLY_ENDPOINTS`, as absolute URLs); a public response never frames its own origin (Admin v2 R9). GA4 (Admin v2 U15): `GA4_CSP_SOURCES` (`script-src https://www.googletagmanager.com/gtag/`, a path, because the host also serves `gtm.js`, whose containers anyone can configure; `connect-src` that host, `https://*.google-analytics.com` and `https://*.analytics.google.com`; `img-src` that host and `https://*.google-analytics.com`; no Ads host, no `frame-src`) join a response's policy only when its page carries the GA4 loader: the `GA4_NOTICE_READY` switch on, a saved measurement id, a public page route answered publicly. Every other response, the admin's and a preview's included, lists no Google host. Its Report-Only cycle, with the policy enforced (`CSP_REPORT_ONLY` false): the loader reports each Google address the browser refuses to `system_logs` (`ga4-csp`, the origin and path, never the query), and a source joins only in a reviewed PR. Residual, signed off with the notice: `connect-src`/`img-src` accept a hit for any GA property, so script injected into a GA4 page could send what it reads to another property; it needs an injection foothold first, and public pages carry no nonced element to borrow.
- [ ] Sessions in `httpOnly; Secure; SameSite=Lax` (`__Host-`) cookies. "Keep me signed in" (on by default, Admin v2 F7) gives the session cookie Max-Age 7 days, rewritten at each token refresh, so the browser drops it 7 days after the admin was last used; unticked, it is a browser-session cookie. That bounds the cookie, not the session: the refresh token in it stays valid at Supabase Auth until a sign-out or a password reset revokes it, or Auth's own session limits end it (a hosted-project setting: owner item O-24, launch runbook §2c), so a copied cookie value outlives the 7 days. The admin also enforces the tenant's session length (`admin_security_settings.session_max_days`, 1 or 7 days, the Users screen's Security card, Admin v2 U12a) on every request it serves, from the token's newest `amr` time; Supabase Auth still honours the refresh token at its own endpoints until O-24's settings bound it, and an issued access token at PostgREST until it expires on tables without a live check. `getUser()` signature verification. CSRF: double-submit `__Host-csrf` or same-origin check on all mutations.
- [ ] Edge Functions verify JWT against JWKS. `postMessage` explicit `targetOrigin`, origin+source checked, Zod envelope, tokens as CSS custom properties only.
- [ ] Tiptap sanitised on write AND render; never `set:html` unsanitised. Every public form Zod-validated server-side, its body capped first: a write to a public `/api/*` route over 128 KB is a 413 from the middleware before any handler reads it (`PUBLIC_API_BODY_LIMIT`, H14), except the three routes that bound their own (the Join multipart, the signed lead hook, the page password). The **anon search endpoint is NOT captcha-gated** — edge rate-limit + Zod cap (≤64 chars, no control chars) + **`websearch_to_tsquery` (never raw `to_tsquery`)** + per-query `statement_timeout` + capped rows.
- [ ] **AI Style-Finder = server-side proxy, no exceptions** (even at the `501` stub): per-IP+session rate limit, daily USD spend cap in DO + alert, prompt-injection hardening, answer-hash cache — tested now.
- [ ] **Lead PII:** envelope-encrypt `phone`/`email`/`budget`; gate server-side; audit-log every view/export; retention purge. PDPL.

## 4. THE 7-POINT DEFINITION OF DONE

> **No feature is "done" until ALL seven hold. Verbatim and non-negotiable.**

1. **Server-side authorized** — RLS + Edge/API `assertCap()`; never UI-only.
2. **Within performance budget** — meets §6; CI perf gates green.
3. **Server-rendered if indexable** — rankable/citable content in Tier A HTML.
4. **Accessible (WCAG 2.2 AA)** — axe zero violations on themed output; keyboard + RTL + reduced-motion. *Known open deviation: **EXC-007** — no pause control for the autoplaying loops (WCAG 2.2.2, Level A): the hero/slogan loops, the marquee, every UI v2 banner/in-view loop and the Round 2 card, explorer and service-hero clips. A header control was built and removed on 2026-09-29 at the owner's decision (mockup parity), which re-signed the widened scope; the `body.motion-paused` wiring (`src/lib/client/motion.ts`) stays so restoring it is one button. axe cannot detect this — a green a11y run is not evidence of 2.2.2 compliance.* *Pillar 2 deviation: **EXC-009** — background video is a self-hosted MP4, not Stream, until KAN-20 — since Round 2 also the discipline card clips, the explorer clip and the service hero loops, each a `preview_video_path` window (`disciplines`, `services`, 0028), and since Admin v2 E10 (2026-10-31) the Video section block an editor adds (a `clip.path` window, at most eight Galleries and Videos a page; `tests/admin/section-blocks.e2e.ts` holds it to the same battery, touch included); "zero video bytes before intersection" is CI-asserted by `tests/e2e/media-bytes.e2e.ts`. The mp4 is served through the Worker (`src/worker.ts`, `assets.run_worker_first: ["/media/*"]`) with byte ranges (206/416, `tests/e2e/media-range.e2e.ts`) so clip windows seek — the static-assets path ignores `Range`, and every window played the reel from 0.*
5. **Tested** — unit + integration + e2e **+ per-role authz** (incl. `other_tenant`=deny).
6. **Observable** — errors → Sentry + `system_logs`; high-value/PII endpoints audit-logged; RUM beacons.
7. **Documented** — schema/loader/component documented; this CLAUDE.md amended if the standard changed.

## 7. Security Non-Negotiables (summary)

- **Server-side authz on every read/write** — RLS + `assertCap()`; live-recheck on RLS-bypassing privileged endpoints.
- **Secrets never client-side** — `astro:env`; stored as Cloudflare **Worker Secrets**.
- **CSP/headers** — one policy, one **primary** enforcement point (`src/middleware.ts`; `CSP_REPORT_ONLY` in `src/lib/http/securityHeaders.ts` is the single switch), backstopped by `src/worker.ts` and `public/_headers` (§2 amendment, 2026-10); per-request-nonce CSP with **no `'unsafe-inline'`** (nonce-based `style-src`, no `data:` images), `frame-ancestors 'self'`, `connect-src 'self'` (same-origin RUM + Sentry), HSTS preload; `frame-src 'self'` on `/admin/**` only, and a preview render's `connect-src` narrowed to `READ_ONLY_ENDPOINTS`; Google's GA4 hosts only on a public page that carries the GA4 loader (Admin v2 U15, §3). Report-Only one cycle, then enforce.
- **PII handling** — envelope-encrypt lead `phone`/`email`/`budget`/`timeline`; gate of record = role-checked decrypt path (Admin/Developer), which returns values to a person only after `leads.pii`, a live recheck and a fail-closed audit row (the two server-side readers that return nothing, the signed `notify-lead` hook and the daily index backfill, are named with every other reader in `tests/lib/leadGrants.spec.ts`); staff tokens read the safe lead columns only (column GRANT, 0033) behind a RESTRICTIVE live check, with `leads_safe` (SECURITY INVOKER — RLS, not its GRANT, decides its rows) as defense-in-depth.
- **Consent (PDPL)** — first-party store (`__Host-consent` + `consent_log`) and **one `hasConsent(category)` gate** (`packages/consent/gate.ts`) gating telemetry ingest, RUM beacon, GA4 injection (`analytics`: the same-origin loader `public/scripts/ga4.js` reads the gate's cookie as `hasConsent` does, at the current `CONSENT_VERSION`, requests gtag.js only after a yes and after the page's `load`, with every advertising signal denied, and on withdrawal denies consent mode, sets Google's off switch and clears the `_ga` cookies; Admin v2 U15), third-party video facade. Default denied; categories functional/analytics/marketing; cookie inventory (Google's `_ga` and `_ga_<id>`: host-only, 180 days, set only after analytics consent while GA4 loads) + lawful basis + withdrawal/DSAR documented. GA4 loads in production only once `GA4_NOTICE_READY` is `"true"` in `wrangler.jsonc`'s `vars`, which waits for the owner's sign-off of the notice that names Google; `tests/lib/ga4Switch.spec.ts` refuses that switch without the notices and the banner naming Google in both languages, a new consent version, the integrations guide and a control that reopens the banner (launch runbook §2e). (Full spec: architecture §4.12.)
- **Audit log** — append-only + HMAC-hash-chained by a `BEFORE INSERT` trigger (key in Vault, hourly R2 anchor, verifier pages on mismatch); no UPDATE/DELETE.
- **AI proxy** — server-side only; per-IP/session limits + spend cap + alert; binding around the `501` stub.
- **Export lockdown** — `export-backup`/`export-csv`: auth + role∈{Admin,Developer} + live-recheck + 3/hr/user + pre-dump audit + tenant scope + `no-store`. The activity log's CSV follows it too (`export.csv` + `audit.view`, its own rate-limit op, attempt and outcome rows, field names only and no `detail` values; U13). Job applications are never in either (`FORBIDDEN_BACKUP_TABLES`; RLS also returns Developer zero rows).
- **Recruitment consent** — the Join form's two checkboxes (`packages/consent/recruitment.ts`: required "this application", optional "future roles") are a separate namespace from `hasConsent`; the version shown is stored on the application row.
- **Anon tenant fence + maintenance pre-cache check** — server-resolved tenant; Worker-level maintenance before cache lookup.
- **CSRF + sessions** — double-submit `__Host-csrf` or same-origin check; `getUser()` verification.

## 8. Conventions

### TypeScript & validation
`strict` + `noUncheckedIndexedAccess` + `exactOptionalPropertyTypes`. One Zod schema per shape in `packages/schemas`, imported by site, admin, Edge Functions. Zod is the single content boundary. `scripts/zod-pure.mjs` (R13) marks each zod chain in `packages/schemas` `/* @__PURE__ */` in `astro build`'s **client** environment only (vitest, `astro dev` and the server bundle never run it), so an unused schema leaves the admin chunks; it is an allow-list that fails the build on anything else, and requires zod 3. So a schema module has **one named `import { z } from 'zod'`** (no other value import of zod, no second `z` binding), **holds schemas only** (each chain a factory, then allow-listed schema-building methods, in a value position), and makes **no parse and no effect at module level** or anywhere else (`parse`/`safeParse`, `setErrorMap`, `describe`/`meta`/`register` are refused); a new zod method joins the allow-list only after checking it builds without effects.

### Data model & schema
- Every table: `id`, `tenant_id NOT NULL`, timestamps, `created_by`/`updated_by`; RLS `ENABLE`+`FORCE` on creation; `WITH CHECK (tenant_id = app.effective_tenant_id())`.
- Tenant + role from `app_metadata`; `updated_at` trigger-set.
- One lifecycle enum `content_status('draft','scheduled','published','archived')`; a teaser is `published + is_teaser=true`, never a 5th status (`is_teaser` is unused since the Gaming teaser was retired, 2026-09-27).
- Bilingual rule (scalar → `_ar`; rich-text/array → locale-keyed JSONB).
- Tiptap as sanitised JSON + derived sanitised-HTML cache.
- `audit_log` append-only; separate from `system_logs`.
- Leads PII (`budget`/`timeline` and the notes thread; `internal_notes` and `ip_inet` dropped by C14b) gated to Admin/Developer, and to Sales one lead at a time through the reveal (C10a); staff tokens SELECT the safe lead columns only (0033), so a column added to `leads` stays unreadable by staff until a migration grants it.

### i18n / Commit-PR rules
Path-based `/` + `/ar/`; reciprocal hreflang + `x-default`→EN; AR meta/OG Zod-required. **CI gate order (pillar-priority):** typecheck/lint → schema-validation → authz → unit/integration → perf-budgets → seo-schema → a11y → visual-regression → supply-chain. A table joins it only with its snapshot, capture (R4) and guard (R5) triggers in the same migration (one stated exception: `team_members` keeps no history and captures nothing until owner item O-12 decides redaction, PDPL; it is guarded), and every column of a registry table is classified (`supabase/tests/snapshot_coverage.test.sql`). The switch-on flag is `app.release_tenants` (empty; no API role reads or writes it; `app.releases_enabled()` reads it).
  - `content_drafts`: one shared pending change per entity, payload untrusted. Staff read drafts; since R3 they may write them (0062 grants INSERT, UPDATE and DELETE), the Worker only through `public.write_drafts` (SECURITY INVOKER), and a direct PostgREST write by a staff token meets the same policies, CHECKs and lock, so nothing `write_drafts` checks is a security property: a draft is written only while its tenant's releases are on and the writer's profile is live (RESTRICTIVE `content_drafts_live_*`: active, unlocked, the token's role; discards need only the live check; a singleton's draft is keyed by its tenant, `app.draft_key_ok`). The permissive policies say who stages what: staged only by the entity's author roles (`app.can_author`), removals by its delete roles (`app.can_stage_delete`), archives by Admin. Its one trigger, the draft lock (`app.tg_draft_lock`, BEFORE): a draft claimed by a scheduled release is out of reach of every staff token (with RLS), and a draft's id, version (old + 1 on every update), author and provenance (`origin_kind`, `origin_release_id`, since 0062: only a restore writes them) are the database's, so a `{draftId, draftVersion}` a publish names never names other content. `content_releases`: staff read, the service role writes, nobody deletes. `content_release_items`: append-only; no API role holds a privilege on its id sequence. Every reference to a release is tenant-fenced (a composite key).
  - Every registry table but `team_members` snapshots into `content_versions` (singletons through `app.tg_snapshot_singleton`), and a snapshot carries `release_id` only while the release token of its own transaction is valid (`app.current_release_id()`).
  - Stated exceptions to the every-table rules of §3 and §8: the registry is global configuration (no tenant column, and its staff read policy has no tenant predicate; the `app.deployment` precedent); `app.release_tenants` is keyed by the tenant with no actor columns; `content_release_items`, an append-only ledger like `audit_log`, has `actor_id` + `created_at` instead of `created_by`/`updated_by`; `app.release_link_pending` (0066) is internal per-statement state (a case study's link sets before a statement first changed them, keyed by the transaction), RLS forced with no policy and no privilege for any API role, so it has no `id`, `updated_at` or actor columns.
- **R2, the release registry in TypeScript (no migration).** `src/lib/release/registry.ts` mirrors `app.release_entities` row for row and binds each type to its resource, singleton or entity-SEO config (the site-profile and SEO-defaults singletons live in `src/lib/admin/singletons/`, the entity-SEO mapping in `src/lib/admin/entitySeo.ts`; `tests/lib/releaseRegistry.spec.ts` reads every migration's registry rows and fails on a type, table, area, order or column that differs; a migration that adds a registry row must add its TS entry). Every release-managed config declares `fields` (payload key → the columns it can emit), built from the same key map as its `toRow` (`tests/lib/resourceFields.spec.ts`; `toRow` itself is unchanged, `tests/lib/releaseOffWrites.spec.ts`). Who may publish an item is derived from `ROLE_CAPS` in `src/lib/release/caps.ts` (pure, client-safe): the area's caps (content: write cap + `content.publish`), plus the remove cap for a delete or archive; the derived release publish matrix is in architecture §3.4, proven by `tests/authz/releaseMatrix.spec.ts`. `src/lib/release/overlay.ts` is the one place payloads are merged, staged patches derived (no `published_at`, no per-item schedule, immediate columns split off), no-ops dropped and conflicts found.
- **R3a, staged writes in the resource kernel (0062, inert until R14).** With `public.releases_enabled(p_tenant)` true (read once per request by the route kernel, `ctx.releasesEnabled()`; false for any tenant but the caller's; an error is a 500, never a guess), every write through the resource kernel (`collectionRoutes`, `itemRoutes`, `reorderRoute`) to a release-managed table becomes a pending change in `content_drafts` (`src/lib/release/staged.ts`, written through `src/lib/release/drafts.ts`): a create gets a Worker-allocated id, an edit sends `version` (no draft yet) or `draftId` + `draftVersion` (409 `draft-conflict`, `draft-published`, `draft-discarded`, `scheduled`), a change equal to live is dropped, and the base is each column's live value when first changed, read over the whole writable allowlist. Stage time runs the status capabilities and `assertWritable` (since R6 over live with every other pending change laid over it, the saved item's own draft left out); publish runs `assertPublishable`. `persist`, `afterWrite` and `afterDelete` never run when staged. Reads lay the pending change over live (`overlayRow`, `overlayList`). Media and Style-Finder configs never stage. With releases off nothing changes but one flag read per request on a release-managed route (`tests/lib/stagedKernel.spec.ts`). As built: `docs/admin-v2/as-built/R3a.md`.
- **R3b, staged singletons and entity SEO, the intake switch, the draft endpoints (no migration, inert until R14).** With releases on, `singletonRoutes` stages the two release-managed singletons, `site_profile` and `seo_defaults` (`src/lib/release/stagedSingleton.ts`: the pending change is keyed by the tenant, a first save is a pending create over the config's defaults, `guardWrite` still runs first on the whole save), and `/api/admin/entity-seo` stages through `src/lib/release/stagedEntitySeo.ts` (a full replace that always stores its target; with no row yet, a pending create under a Worker-allocated id, one per target). The other singletons never ask the flag. The job-application switch is never staged: a staged save that would change it is 422 and one that sends it unchanged is let through; it has its own immediate endpoint, `PATCH /api/admin/site-profile/intake` (Admin: `applications.manage` and `settings.general`, `guardWrite`, the 0019 trigger; no version; audited only when it moves), whatever the flag. Draft endpoints (`src/lib/release/draftEndpoints.ts`): `GET /api/admin/releases/pending` (the changes the caller may read, by stored metadata only, with `publishableByMe`, `requiredCaps`, `waitingFor` and counts by area), `DELETE /api/admin/drafts/[id]?version=n`, `POST /api/admin/drafts/discard` (mine, at most 200 a request, or selected, all or nothing) and `POST /api/admin/drafts/[id]/resolve` (keep mine or use the live version, per column). Each admits any role that stages (or reads) something, then checks every draft against its own type in the Worker (a discard needs the type's author capabilities, a resolve what publishing it needs) and in the database (`public.write_drafts`); a refusal names the drafts. With releases off every singleton and entity-SEO route is what it was but for one flag read per request on site profile, SEO defaults and entity SEO (a failed read is a 500, as in R3a; `tests/lib/releaseOffWrites.spec.ts`). As built: `docs/admin-v2/as-built/R3b.md`.
- **R4, applying a release (0051, inert: it refuses every tenant whose releases are off).** `public.apply_release` (SECURITY INVOKER, EXECUTE for the service role only, and it refuses any other `current_user`, `postgres` included) applies up to 60 pending changes (`RELEASE_MAX_ITEMS`) in one transaction under a per-tenant advisory lock, as the publisher: it reads their live profile (active, unlocked, role equal to the one named, a CMS role; the tenant comes from the profile, never from a parameter), checks each draft is still the one they saw (409 `pending-changed`), checks each live row against the draft's base column by column as the column's own type, before any write (409 `conflict`), then sets their claims and `SET LOCAL ROLE authenticated`, so RLS, every RESTRICTIVE publish/archive/delete gate, CHECKs and guard triggers bind as for that person; it restores the claims and the role and clears the release token before it returns, on an error too. Writable columns come only from `app.release_entities`: every identifier in its dynamic SQL is the registry's, quoted with `%I`, and every value is bound (`tests/lib/releaseApplySql.spec.ts` pins the shape). A publish fails fast (one error, 422, nothing kept); a dry run collects every change's outcome and keeps nothing, not even a number. Creates and updates apply in registry order (a unique flag cleared before it is set), then the self-references, then removals in reverse order. `published_at` is stamped on a first publish and never rewritten (a row a restore brings back keeps the date it had when it was removed: R10 restates `apply_release` in 0104). The release is numbered and its `release.publish` audit row written, as the publisher, in the same transaction. `app.tg_release_capture` records before/after images of every registry row a release changes, cascades between registry tables included (not `team_members`, owner item O-12, and nothing outside a release); `portfolio_children` items record a project's link sets, which `save_portfolio` and the apply both write through `app.apply_portfolio_children`. `public.record_release_purge` (the service role) records a release's cache purge. As built: `docs/admin-v2/as-built/R4.md`.
- **R5, the release guard and complete capture (0066, inert while releases are off).** Every registry table (`team_members` included) and both case-study link tables carry `<table>__release_guard`, the first BEFORE trigger (`app.tg_release_guard`, SECURITY DEFINER): for a tenant with releases on, any API write outside the release of its own transaction is refused (42501), whatever its depth (no `pg_trigger_depth` exemption, so a trigger reached by a staff request is refused too), except a write with no SET ROLE and no staff claim (migrations, seeds, the runbook, pg_cron, Auth), the service role's with no staff claim, and an update of the registry's immediate columns only (`accepting_applications`, `page_visibility.password_version`). The guard runs before RLS's WITH CHECK, so for a role RLS binds (`authenticated`, `anon`) a row naming a tenant other than the caller's is refused without reading that tenant's switch: the refusal's words never tell another tenant's state. Writes outside a release in such a tenant are recorded as system items (`content_release_items` with no release and no draft), and a case study's link sets as one `portfolio_children` item per case study per statement (the sets kept when the statement first touches it, in `app.release_link_pending`, against the sets after it), cascades from a project or service removal included, so a restore sees every change since a version; `team_members` is guarded but captures nothing (O-12, an R14 blocker in `docs/admin-v2/deviations.md`). No API role may TRUNCATE a guarded table (`tests/lib/noTruncate.spec.ts`). `media_usage()` v4 counts pending changes as references, so a hard delete waits for them (the media drawer's "Used in" and the delete's refusal say each one is a pending change, with no link); `dashboard_attention` v4 lists scheduled-today (Riyadh), late, failed and not-purged releases and pending changes untouched for 30 days (the dashboard reads those apart, with an exact count, so they never crowd the content kinds out of its capped read); `app.publish_scheduled()` skips tenants with releases on. As built: `docs/admin-v2/as-built/R5.md`.
- **R6, publishing a release (no migration; inert: both routes answer 409 `releases-off` while releases are off).** `POST /api/admin/releases` publishes a selection of at most 60 pending changes with an optional note of at most 280 characters (owner item O-4; per-area, all ticked, is the dialog's default, R12); `POST /api/admin/releases/validate` runs the same check and, when the Worker finds nothing to fix, `apply_release` as a dry run. In order (`src/lib/release/endpoints.ts`, `validate.ts`, `apply.ts`): the drafts as the person saw them (409 `pending-changed`); per change every capability its publish needs (`requiredCaps`, a null is a refusal; 403 names the drafts and who could publish them); `liveRecheck`; each change re-derived from its untrusted payload, its base taken from the draft as stored; then the rules over the state the selection leaves (`src/lib/release/overlayDb.ts`): every link a change writes held to the publisher's tenant (`src/lib/release/links.ts`, held equal to the migrations' foreign keys; a pending new item left out is a dependency, `requires`), a change whose parent the release removes refused, the entity's `assertWritable` and, for a row live afterwards, `assertPublishable`. A rule that reads rows reads through `ctx.db` when given (a staged save passes `pendingDb`, live with every other pending change laid over it, the saved item's own draft left out); without it the rule sends the queries it always sent (`tests/lib/overlayDb.spec.ts`). The apply runs through the service client, as the publisher; its refusals are mapped to changes and fields, never in the database's words, and a busy database (55P03, 40P01, 40001, 57014) or no answer at all is a 503 with Retry-After, unless the Worker finds the apply committed anyway, when the after-effects run. After the commit, never fatal, the after-effects (R7 below: the edge snapshots rebuilt as the system, and the release's purge, a logged no-op recorded `skipped` until a cache zone exists, O-3). As built: `docs/admin-v2/as-built/R6.md`.
- **R7, the purge seam and the minute cron (0103, kept on the merge train above U9's 0102; inert: releases are off and no cache zone is set up, O-3).** `src/lib/http/purge.ts` is the one module that purges the cache: by Cache-Tag through the zone API (`CF_ZONE_ID`, public, and `CF_CACHE_PURGE_TOKEN`, a Worker secret, both optional; unset is "Not set up": `skipped`, nothing sent or read), at most 30 tags a request (more, or a tag the API cannot take, is `tenant:default`), at most 30,000 tags in 24 hours, taken in the database before anything is sent (`public.cache_purge_take` over `cache_purge_log`: RLS FORCEd with no policy, the service role alone holds either), one retry after jitter on a network error or a 5xx, a breaker in the isolate, never throwing. The cache it purges is the Tier A cache the Worker itself reads and fills through the Cache API, to be built (O-3, KAN-20) in `src/middleware.ts` after the maintenance and page-visibility checks, never a layer whose hits skip them (a named precondition: the R7 as-built's Open); Workers Cache and Astro's route cache stay off until the seam has their backend, and a Cache API lookup anywhere else is refused (`tests/lib/cacheLayer.spec.ts`). A composed Tier A page stamps its route's tags plus what its rendered sections read (`SECTION_READS`, `src/lib/sections/reads.ts`; every route's own list in `src/lib/http/routeTags.ts`, each within 30, `team:all` on the blog); every Tier A response also carries `media:all` (`ALWAYS_TAGS`, `src/lib/http/cacheTags.ts`: every head renders the default share image, a media row), and the sitemap, llms.txt, the RSS feeds and the web manifests (U9) carry `tenant:default`, so a collapsed purge reaches every tagged response. After a publish, each step never fatal (`src/lib/release/afterEffects.ts`): the redirect map and the page-visibility snapshot rebuilt as the system (the service client, the release's tenant) when the release changed them or renamed or removed a page; the release's tags (`src/lib/release/tags.ts`: every item's tags before and after, a section's page and an SEO row's target in one read, the sitemap and llms.txt for any change to a type they list, `tenant:default` for what it cannot resolve; `tests/lib/releaseTags.spec.ts` holds each to a route that stamps it) purged and recorded on the release; `release.purge` audited when a request was sent. A media save that moves a column a public page renders (alt, the file, the kind, the dimensions: `mediaChangeIsPublic`, never tags, folder or the name alone) purges `media:all`, and page-visibility and page-password saves their page's tags, through the same seam. The minute cron (`* * * * *`, `src/lib/cron/releases.ts`) takes what published releases still owe through `public.claim_release_purges` (the service role's: one tenant's due releases, SKIP LOCKED, leased five minutes, so two runs never act on one release twice): a failed purge retried with backoff up to 10 attempts (then the dashboard's `purge_failed`), and a release whose after-effects never ran rebuilt and purged whole. Scheduled releases fire there from R11. A publish's check reads the live rows and the links of every table in one request each (`public.release_read_rows`: SECURITY INVOKER, CMS staff of their own tenant only, registry tables and `media_assets` only, keyed by `id` or, for the two singletons only, by tenant, at most 2,000 ids a call): a clean publish touching every registry type is 26 subrequests, under the Free plan's 50 (O-16). As built: `docs/admin-v2/as-built/R7.md`.

- **R10, versions, history and restore (0104; inert: no version exists while releases are off).** A site version is a published `content_releases` row; the state at version N is the ledger's, read in one call (`public.release_as_of`, SECURITY INVOKER, EXECUTE `authenticated` only: per entity changed after vN, by a release or out of band, its earliest before-image and whether it exists now; team members never, O-12). `GET /api/admin/releases` lists the versions and `GET /api/admin/releases/[id]` shows one version's changes, each listed only in an area the person reads, consent records as "changed" only. A restore never writes the live site: `POST /api/admin/releases/[id]/restore` (`{pageId?}`: one page and its sections) and `POST /api/admin/history/restore` (one numbered snapshot; its area must be read) stage the state as pending changes through `write_drafts` under the person's RLS (only what differs from live; a row removed since comes back with its own id and link sets; a quote's consent record is never restored, a quote removed since never comes back, and none is published without consent recorded now), refused whole when one has a pending change, the person cannot publish one (P-2, H12's archived rule included), an image no longer reads, a link names something gone, an address is now another item's, it is more than one release, or its reads would pass the request's 50 subrequests (P-15, counted before any is sent, so a restore never stops halfway); the status is the first reason's, and every refused item is named under every reason (by type alone in an area the person does not read). - **R11, scheduled releases and the two switches (0112, a placeholder number; inert: `apply_release` refuses `schedule` and `fire` for a tenant whose releases are off).** `POST /api/admin/releases` with `scheduleAt` (an ISO time with its offset, 2 minutes to 366 days ahead; never a rollback) runs every check of a publish, then `apply_release` in `schedule` mode: the person live, the drafts as they saw them, the changes as a dry run as them, then the validated changes stored on a `scheduled` release, their drafts claimed (read-only to every staff token) and `release.schedule` audited, in one transaction. `PATCH /api/admin/releases/[id]` (`{version, scheduleAt}`) and `DELETE …?version=n` move or cancel it, version-checked, for a person who may publish every change it holds (P-2, H12's archived rule included: an edit that keeps a row archived live archived is an Admin's, the row's status read live in both layers), re-read live, and checked again in the database (`public.reschedule_release`, `public.unschedule_release`: the service role only, the person's live profile, the registry's author and delete roles, the tenant's release lock, audited); a moved release goes live as the person who moved it. The minute cron (`src/lib/cron/releases.ts`) claims one due release a minute (`public.claim_scheduled_releases`: SKIP LOCKED and a two-minute lease), re-checks the scheduler live against `ROLE_CAPS`, and fires it through `apply_release` in `fire` mode as them (the release and the switch re-read under the tenant's lock: one no longer scheduled or not due is left alone, so a second run is a no-op), then its after-effects as the system (R7's); a minute that fires a release spends itself on it (the purge retries wait a minute), and every path of the minute stays within 37 subrequests. A fire that cannot go live fails closed: `failed` with a code, never a message (`public.fail_scheduled_release`, its drafts released; a release a person moved to a later time since the claim is left as it is), a `cron:releases` error line, the dashboard's `release_failed` row and the bell's `releases` kind for the roles that publish one of its areas; one that goes live more than five minutes late is a `cron:releases` warning saying by how much. The runbook's switches, `app.enable_releases(tenant, operator, fallback_scheduler)` and `app.disable_releases(tenant, operator, discard_pending default false)`, are the owner's alone (no API role holds EXECUTE; a switched role or a role claim is refused), audited (`releases.enable`, `releases.disable`) and refused while a release is publishing (the apply's lock, taken without waiting): on converts the rows `app.publish_scheduled()` would have published (scheduled, with a time; anything else scheduled is left as it is) into `legacy_schedule` releases (as their last editor, else the fallback), then writes the baseline version and the flag; off is refused while changes are pending or releases scheduled unless the discard is named, with which legacy schedules go back to their rows and everything else pending is thrown away. `app.publish_scheduled()` acts only for a tenant with releases off and a scheduled release only for one with them on, and the switch moves both in one transaction under row locks, switching on with those tables write-locked, so the two never both act and a row scheduled meanwhile is never stranded. As built: `docs/admin-v2/as-built/R11.md`.

## 11. When In Doubt

> **Flag and propose, rather than ship something that fails a pillar.**

If a task seems to require weakening Security, Performance, SEO, or Scalability — or you cannot satisfy all 7 DoD points — stop, write down the conflict, and propose options (including a documented exception with an owner and expiry).
