- **Lane:** Releases (Wave 4)
- **Design:** [releases.md](../releases.md) §4.1 to §4.5, §5.4, §8 edge cases 1 to 3, 13, 16 to 19,
  22, slice R6; the README's Track REL ("Publish"), P-2, P-15; owner defaults O-3 and O-4 (plan

- **Migration:** none (departure 1)
- **PR:** number at review (branch `feat/r6-publish`)

## Plan (written before the build)

- **Scope.** `POST /api/admin/releases` (publish now) and `POST /api/admin/releases/validate`
  (the Worker's checks plus the database's dry run). Per change: `requiredCaps` through the
  Worker's capability check (a null is a 403), `liveRecheck`, the payload re-parsed with the
  entity's schema and `toRow` (`derivePatch`), `assertWritable` and, for a row that is live
  afterwards, `assertPublishable`, both over the state the release leaves. Cross-change
  checks: dependencies (a link to a pending create left out), a link into another tenant, a
  change whose parent the release removes, the R3b leftovers, warnings. Then
  `public.apply_release` through the service client, its refusals mapped to items and fields;
  after commit, never fatal: the KV syncs and the purge as a logged no-op (O-3). Per-area
  publish with every item ticked is the client's (R12); the server takes any selection of at
  most 60 changes and a note of at most 280 characters (O-4, P-15).
- **The overlay-aware database** (`src/lib/release/overlayDb.ts`), the rules that read rows
  reading through it, releases off sending exactly today's queries.
- **Tests.** `tests/lib/overlayDb.spec.ts`, `tests/lib/releasePublish.spec.ts`,
  `tests/lib/releaseLinks.spec.ts`, rows in `tests/authz/cases/releases.ts`; the releases-off
  proof is the existing call-for-call specs staying unchanged.

## What was built

Releases stay off for every tenant (`app.release_tenants` is empty until R14). With them off
both new routes answer 409 `releases-off` after the flag read and read nothing else, and every
existing route behaves as on `main`: the rules that now read through the overlay-aware
database are given none on the legacy path and send the queries they always sent
(`tests/lib/overlayDb.spec.ts` pins them call by call), and `releaseOffWrites.spec.ts`'s
snapshot, `stagedKernel.spec.ts`, `redirectResource.spec.ts`, `serviceResources.spec.ts` and
`contentResources.spec.ts` are unchanged and green.

### The routes (`src/pages/api/admin/releases/index.ts`, `validate.ts`)

Kernel `content.publish` (the label) with `anyCap` = `RELEASE_ANY_CAP` (R2), body
`PublishRequestSchema` (R1: 1 to 60 changes `{draftId, draftVersion}`, each once, an optional
note of at most 280 characters with no control character, `kind`). One handler
(`src/lib/release/endpoints.ts`), in order:

1. `kind: 'rollback'` is 422 (R10 builds restore; nothing can name a version yet).
2. Releases off: 409 `releases-off` ("Publishing is switched off: every save goes live at once.").
3. The drafts, under the publisher's RLS (`loadSelection`): any missing, moved or claimed by a
   scheduled release is 409 `pending-changed` listing them.
4. Per change, every capability its publish needs (`requiredCaps` from the stored status, so an
   archive needs `content.archiveDelete`; null, a removal no role publishes, is refused): a 403
   names the drafts, the first capability missing, and who could publish each (`waitingFor`).
5. `liveRecheck(auth)` (a demoted, deactivated or locked person is 403 at once).
6. The check over the state the selection leaves (`checkSelection`, below).
7. Validate: the report, and when the Worker found nothing to fix, `apply_release` in
   `dry_run`, its refusals and conflicts laid on the changes (`dryRun: 'ran'`); otherwise the
   report with `dryRun: 'skipped'`. Publish: 422 `validation` with the report unless it is
   clean, then `apply_release` in `publish`.

### The check (`src/lib/release/validate.ts`)

- **Each change re-derived** from its untrusted payload (`derivePatch`, A3-13). The base sent
  is the draft's own, as stored, for exactly the columns written: the raw PostgREST values
  (microsecond timestamps included), which R4 compares typed (R3a's note). Reported, never
  sent: a payload that no longer reads (`unreadable`), a rule the schema states (`invalid`),
  a column without a base (`base-missing`), a change that changes nothing (`nothing`), a live
  row gone under an edit or a removal (`removed`), and R3b's two leftovers (`exists-live`): a
  singleton create whose row an immediate path has since created, and an entity-SEO create
  whose page gained search settings by another path. An entity-SEO edit naming a page other
  than its row's is `target` (R2's note for R4).
- **The state the selection leaves**: the selected changes as layers over live
  (`layeredDb` with `fixedLayers`), read through a per-request memo (`memoDb`).
- **Links** (`src/lib/release/links.ts`, R4 review 9, R5 decision D11): every column a change
  writes that names another row must name a row of the publisher's tenant as the release
  leaves it (`link`), or a pending new item, which, when the selection leaves it out, is a
  dependency (`requires`: the draft and its version, for the dialog to tick, and an error
  until it is ticked). A row the release removes refuses every change that still points at it
  (`parent-removed`: edge case 3 for a cascade, and a restrict or set-null link that would
  break or quietly clear). A team member's account link is checked with the service client
  (ids only): staff read no profile but their own. `tests/lib/releaseLinks.spec.ts` holds the
  list equal to the foreign keys the migrations declare on the allowlisted columns, ON DELETE
  included, and complete (every `*_id` column of every registry allowlist).
- **The entity's own rules** over the merged row: `assertWritable`, and `assertPublishable` when
  the row is live afterwards (`isLive`, now exported from `resource.ts`): bilingual, placeholder,
  consent, poster alt, the discipline a service needs, section content, the sample rating.
  Entity SEO: the Arabic meta. Page visibility: the home page stays public, a page never sends
  its visitors to itself (the legacy save's rules).
- **Warnings** (never block): a published service whose discipline the release leaves
  unpublished (`hidden-by-discipline`).

### The overlay-aware database (`src/lib/release/overlayDb.ts`, `layers.ts`)

`OverlayDb` = `exists`, `list`, `first`. `liveDb` is today's queries; `layeredDb` lays a set
of changes over it (a removal gone, an edit judged on its new values, joining or leaving a
filtered read by them, a new row there); `memoDb` keeps answers and takes primed ones.
`assertLinkInTenant`, the redirect chain read and `liveRouteRefusal` read through `ctx.db`
when given, `liveDb` otherwise; the portfolio poster-alt read uses `db` when given and its old
query otherwise. Staged saves (R3a, R3b) now pass `pendingDb`: live with every pending change
of the tenant laid over it, loaded per table on first need, `exists` asking live first (so a
save linking to a live row reads no draft). That closes R3a's D5: a link to a pending create,
or a redirect from a slug a pending change renames, is no longer refused at stage time.

### The apply and after (`src/lib/release/apply.ts`)

- `serviceClient().rpc('apply_release', ApplyRequestSchema.parse(…))` with `p_actor`,
  `p_role`, the items, the note, `p_kind: 'publish'`; the call is aborted after 25 s
  (`APPLY_TIMEOUT_MS`; the function's own `statement_timeout` of 20 s is what PostgREST hoists
  into its transaction, R4's open item).
- Refusals: `BR403` is 403; `BR409` `pending-changed` is 409 naming the drafts, `conflict` is
  409 with the report (each change's columns, for Keep mine / Use the live version); `BR422`
  is 422 with the report (`refused` per change, its field from the entity's named constraints
  and refusals, else from the column; `base-missing` named); `55000` (releases switched off
  meanwhile) is 409 `releases-off`; 55P03, 40P01, 40001 and 57014 are 503 `busy` with
  `Retry-After: 5`, never "refused" (R4 review 6); anything else, 22023 included, is a 500
  the kernel logs. The database's own message text is never answered.
- After the commit, each never fatal: a release with redirects rebuilds the edge map
  (`syncRedirectsToEdge`, the publisher's client); a release with a page-visibility change,
  published by a role holding `maintenance.manage`, rebuilds the visibility snapshot; the
  purge is a logged no-op (`system_logs` info `release:purge`, "No cache zone yet (KAN-20)")
  recorded `skipped` through `record_release_purge`, whose failure is logged too.
- The answer: `{release: {id, number}, items, warnings, purge: 'skipped', kvSynced?}`
  (`PublishResultSchema`). The audit row is `release.publish`, written by the apply inside its
  transaction (R4); a refused publish changes nothing and writes none.

### Shapes (`packages/schemas/release.ts`)

`RELEASE_ISSUE_CODES`, `RELEASE_WARNING_CODES`, `ReleaseIssueSchema`, `ReleaseWarningSchema`,
`ReleaseCheckItemSchema`, `ReleaseCheckSchema`, `PublishResultSchema`.

## Departures from the design, each with its reason

1. **No migration** (the placeholder 0090 is released). Everything runs on 0051, 0062 and
   0066. The one SQL candidate, a database-side tenant fence on link columns, stays the
   Worker's, as R5's brief decided (D11: single tenant at launch; a catalog-driven fence is a
   separate change, or composite keys if multi-tenant arrives). The time cap is the caller's
   without SQL (above).
2. **The rules read through `ctx.db` only when given**, rather than every caller passing one.
   The legacy path is then the old code path, query for query, which is the cheapest proof
   that releases off changes nothing; `liveDb` reproduces the same queries for the staged and
   publish paths.
3. **The dry run runs only when the Worker found nothing to fix.** A dry run over a selection
   with a change it cannot send would report what the missing change causes (a link to an
   item left out, a refused foreign key), not what is wrong; the dialog fixes the Worker's
   errors first, then sees the database's.
4. **The page-visibility snapshot is rebuilt only for a release carrying a visibility change**
   (published by a `maintenance.manage` holder), not for every page change as the plan said.
   The snapshot is built from what the publisher's client reads, and Content Creator reads no
   `page_visibility` row: a rebuild after their page publish would have written an EMPTY
   snapshot and made every hidden page public (found in the self-review; the test fails
   without the fix). A page's new slug reaches the edge as it does for a save today, by the
   daily re-sync; R7 may run a rebuild as the system after every page release.
5. **No `release.purge` audit row.** The activity log reads every `release.` action as a
   publish (`auditLabels`, prefix), so a purge row would read "Published a version" twice.
   The purge is recorded on the release (`record_release_purge`) and in `system_logs`; R7,
   which makes the purge real, adds its row with its own words.
6. **No nav-href warning** ("a menu link to an unpublished page", §4.2 step 5): a link's href is
   a path, and mapping paths to rows is R7's route map. Only the discipline warning is built.
7. **No e2e** (`releases-publish.e2e.ts`): it needs the e2e workflow to switch releases on after
   seeding, which is R14's (README rollout step 1). The endpoint is proven over the PostgREST
   stand-in and the apply by R4's pgTAP.
8. **No help guide.** R6 adds no screen (the publish dialog and the savebar are R12's), so there
   is no `PAGE_GUIDES` entry to attach one to; R12 writes the publishing guide with its screens.
9. **A claimed pending create named by a link** is reported as a dependency like any other; the
   dialog cannot tick it (claimed drafts are refused). R11, which claims drafts, words it.

## Self-review

Read once for security and authorization, once for correctness and the standard. Fixed:
the visibility rebuild above (departure 4, `releasePublish.spec.ts` "a page change by a
Content Creator never rebuilds the visibility snapshot" fails without it); a link to a selected
new item that could not be read now adds no second, misleading "not on this site" error.
Checked: every read is tenant-scoped to the caller (the authz suite's other-tenant sweep covers
both routes); no database message or payload value reaches a response or an audit row; the
service client is used only for the apply, the purge record, the live re-read and the account
link's existence (ids only).

  Creator's archive 403 naming the draft and `waitingFor: ['admin']`; SEO and Developer on a
  service; a stale role; a singleton removal; rollback 422; the dry run's request (patch, the
  stored base untouched); bilingual on the merged row; an unreadable change; another tenant's
  client; a dependency and its tick; a page removed with its section changed; a redirect with
  and without the rename; R3b's two leftovers; the discipline warning; the poster's Arabic alt;
  the dry run's refusal mapped without its words; a conflict with live and base; a clean
  publish (purge skipped, logged, recorded); a redirect release (KV synced, a failed purge
  record only logged); the visibility rebuild (never for a Content Creator's page, yes for a
  visibility change); 422 before any apply; BR403, BR409 (both), BR422 (both), the four busy
  codes, 55000, an unexpected 22023 as a 500 without its words; and a 60-change release of
  linked services in at most 12 reads (P-15).
- `tests/lib/overlayDb.spec.ts` (11): the legacy queries call by call; the layered view;
  pending creates and renames at stage time; the memo.
- `tests/lib/releaseLinks.spec.ts` (3): the link list against the migrations.
- `tests/authz/cases/releases.ts`: publish and validate per area (a service change, archive and
  removal; identity; a theme; entity SEO; SEO defaults; a redirect and its removal; page
  visibility) with the release publish matrix's roles, and releases off (every CMS role through
  the gate, 409); 22 cases, `caseManifest.ts` updated.

  §5, architecture §3.4 and §9.3 are unchanged, and the admin bundle sum is 312.9 KB, as on
  `main`.

## Deploying

No migration: the Worker deploys alone. Everything it calls (0051's `apply_release` and
`record_release_purge`, 0062's `releases_enabled`) is in production.
