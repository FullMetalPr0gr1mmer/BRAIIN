# H16: a stale token writes nothing (the general stale-token fix)

- **Lane:** hotfix (security lane)
- **Design:** none as a slice. The known gap recorded since the Join review (2026-10-01): RLS
  reads the role from the access token, a token lives up to an hour, and a demoted,
  deactivated or locked person's token kept its old rights at PostgREST on every table no live
  check covered. Closed so far for `job_applications` (0029), `leads` and the CRM (0033 on),
  `profiles` (0050, 0055) and each table built since with its own RESTRICTIVE live policy.
- **PR:** the `fix/h16-stale-tokens` branch, cut from main d48e287d (PR number at review)
- **Migration:** `0129_live_staff_writes.sql` (placeholder; the merge train renumbers it)

## Plan (written before the build)

### What the brief asked, against what main already holds

The brief was written from the 2026-10-01 note. Three of its four parts were found partly or
wholly built by later slices; this slice builds what is left and corrects the standard.

**(a) The session check compares the token's own claims.** Already built by U12a (#70):
`resolveAuthContext` decodes the claims of the very token `getUser(token)` verified
(`src/lib/auth/claims.ts`) and a role or tenant that differs from the profile is
`DENY_REVOKE`; `tests/lib/authContext.spec.ts` ("a stale or too-old session is REVOKED",
including "even when the auth server's current record already shows the new role") guards it.
Nothing to build. The CLAUDE.md §2 amendment's sentence is true since U12a; what it still says
wrongly is that this alone closes the database layer (part d).

**(b) Revoke sessions on a role, tenant, active or lock change.** Already built for role,
activity and tenant by U12a's `profiles_revoke_sessions` (0055, AFTER UPDATE, SECURITY
DEFINER): it deletes every `auth.sessions` and `auth.refresh_tokens` row of the person, for
every writer (the users screen, the service role, an operator, a direct API call), in the same
transaction as the change. That is stronger than the Supabase admin API the brief names: the
admin API's `signOut` takes the user's own JWT, not an id, so it cannot end a colleague's
sessions at all, and a best-effort call after the write could fail where the trigger cannot.
Kept as is. Planned here:
- the users PATCH's audit row says whether the change ended the person's sessions
  (`sessionsEnded`), so the audit trail records the revocation the trigger made;
- **a lock does not revoke** (U12a's decision, kept, and pinned by `users_security.test.sql`):
  a lock is the sign-in lockout, which anyone who knows a staff address can trip with five wrong
  passwords. Deleting sessions on a lock would hand anyone a "sign this person out everywhere"
  button. What a lock must stop, a locked token's writes, is closed by part (c): the live check
  reads `locked_until` at query time, and the Worker already refuses a locked profile's session
  (`profileVerdict`) and signs it out at its next request. Recorded as a departure and an
  owner question.

**(c) A RESTRICTIVE live check on every staff-writable table.** The gap that is really open.
An inventory over the replayed schema (every public table where `authenticated` holds a write
privilege, table-wide or on a column) found 28 tables whose staff writes rely on the token's
role alone:

`ai_config`, `ai_questions`, `ai_styles`, `audit_log`, `blog_posts`, `categories`,
`certifications`, `clients`, `disciplines`, `entity_seo`, `faq_items`, `media_assets`,
`navigation`, `page_sections`, `pages`, `partner_logos`, `portfolio`, `portfolio_media`,
`portfolio_services`, `redirects`, `sectors`, `seo_defaults`, `service_cases`, `services`,
`statistics`, `system_logs`, `team_members`, `testimonials`.

Every other staff-writable table already carries one (`admin_role_defaults`,
`admin_security_settings`, `admin_user_prefs`, `analytics_goals`, `content_drafts`,
`crm_settings`, `custom_themes`, `form_settings`, `job_applications`, `lead_stages`, `leads`,
`page_visibility`, `profiles`, `site_appearance`, `site_integrations`, `site_profile`,
`site_settings`, `template_copy`). One SECURITY DEFINER RPC writes on the JWT role alone:
`public.update_media_meta` (0020, SEO's "meta only" media write). Storage is service-role only
(0029, 0045); no view is writable by staff; the `app` schema is not exposed.

The fix, one migration:
1. Three RESTRICTIVE policies per table, `TO authenticated`, one per write command
   (`<table>_live_insert`, `_live_update`, `_live_delete`), each
   `tenant_id = app.effective_tenant_id() and (select app.live_role()) is not null`.
   `app.live_role()` (0033) is non-null only when the profile named by the token's `sub` is
   active, unlocked, in the token's tenant and holds exactly the token's role, so when it is
   non-null the JWT role the existing permissive policies read IS the live role: the
   capability rules stay where they are and are now evaluated on a role the database has just
   confirmed. One generic predicate, no per-capability helper needed.
   - Reads are untouched (no SELECT policy is added), so anon's and every reader's view of
     published content is byte-identical, and no anon policy changes.
   - All three commands on every table, even where `authenticated` lacks the grant today
     (as 0050 did): a grant added by mistake is then not enough on its own.
   - Cost: `(select app.live_role())` is an InitPlan, evaluated once per statement (one
     primary-key lookup on `profiles`), never per row; measured with EXPLAIN (below).
   - Not affected: the service role (BYPASSRLS), SECURITY DEFINER functions (they run as
     their owner, which the `TO authenticated` policies do not name: `publish_scheduled`, the
     snapshot and capture triggers), the access-token hook, pg_cron. Invoker RPCs
     (`save_portfolio`, `apply_portfolio_children`, `write_drafts`) are held by the policies of
     the tables they write, which is the point. *(Corrected at review, H16-SEC-3: this line
     first named `apply_release` as a definer. It is an invoker and runs under the new
     policies; see "Review fixes".)*
2. `public.update_media_meta` restated with the live check (42501 for a stale token, as for a
   non-staff one), `search_path` pinned to `''` with every name qualified, grants stated.
3. Postconditions: the exact policy on each of the 28 tables; a catalog-wide rule that every
   public table where `authenticated` holds a write privilege has a RESTRICTIVE live policy
   for each command it can run (so a future table without one fails its own migration's
   replay and this suite); the function's settings, body and grants.

pgTAP (`supabase/tests/live_staff_writes.test.sql`): personas admin, content_creator, seo,
developer, sales, anon and another tenant's admin, plus, for each of the five staff roles, a
demoted, a deactivated and a locked token. For every one of the 28 tables, an UPDATE, a
DELETE and an INSERT (a copy of a fixture row) is tried by every persona, each attempt rolled
back on its own: the live writers write exactly as the JWT policies allow, and no stale token
writes a row. Plus the catalog checks and `update_media_meta`.

**(d) The standard.** CLAUDE.md §2's "session invalidation" amendment and §3 (Pillar 1) say
exactly what holds after this slice: the Worker rejects a stale token (U12a), a role, activity
or tenant change deletes every session (0055), every staff write is live-checked at the
database, and what stays open (below).

### Residual gaps (recorded honestly)

- **Reads by a stale token.** Until it expires (at most an hour, the access-token lifetime) a
  demoted, deactivated or locked token still READS at PostgREST what its old role could read on
  the tables without a live read check: content with its drafts (`content_drafts`), history
  (`content_versions`) and releases, media metadata, redirects, the SEO rows, `system_logs`
  (scrubbed of PII), `ai_config`, `site_settings` (technical keys, the maintenance IP
  allowlist among them), `site_profile`, `site_appearance`, `custom_themes`, `form_settings`,
  `template_copy`, `page_visibility`, the CRM's stages and scoring points (`lead_stages`,
  `crm_settings`), the consent, notification and search ledgers, `health_probes`, `tenants`
  and the read-only rollups. These read live: `leads`, `lead_events`, `job_applications`,
  other people's `profiles`, `audit_log`, `site_integrations`, `admin_role_defaults`,
  `admin_security_settings`, `admin_user_prefs`, `analytics_goals`, `team_notes` and
  `help_articles` (inventory over the replayed catalog at review: RESTRICTIVE SELECT or ALL
  policies calling `app.live_role()` or `app.is_live_admin()`, plus the two whose only read
  policy is live). *(Corrected at review, H16-SEC-2 and H16-C2: this paragraph first said "the
  CRM" and "the admin settings" read live; `lead_stages`, `crm_settings`, `site_settings` and
  the appearance, form, template and visibility settings do not.)* Closing reads too would
  need a live SELECT on each table written beside its public published-row policies; left for
  a follow-up and listed for the owner.
- **A lock does not end sessions** (part b): the locked token writes nothing and the Worker
  signs it out at its next click, but an idle session survives the lock and its refresh token
  works again once the lock passes.
- **A token minted before 2FA was required** keeps its role at PostgREST until it expires
  (U17, O-25); its writes are now live-checked like any other token's, which does not test the
  assurance level.

## As built

**The migration** (`0129_live_staff_writes.sql`, expand only):
1. 84 RESTRICTIVE policies, three per table on the 28 above, `TO authenticated`, one per
   write command, each `tenant_id = app.effective_tenant_id() and (select app.live_role()) is
   not null`. Made by one loop over a spelt-out list (so the migration does what it says on
   every database); `drop policy if exists` first, so a re-run is harmless.
2. `public.update_media_meta` restated: `app.live_role() is null` is refused with the same
   42501 as a non-staff role; `search_path` pinned to `''` (was `public, app, pg_temp`) with
   every name qualified; body, signature, result columns and error codes otherwise 0020's;
   grants stated (authenticated alone, as before).
3. The roles guide, `roles-and-access`, put at revision 4 (H11's catalog moves it to 5): its
   "One limit to know" paragraph now says a pass already handed out can no longer change
   anything, and until it runs out can still read what its role could in settings, media,
   the system logs and content. Both languages; every other block, and every other guide,
   unchanged (`tests/lib/helpCentre.spec.ts`).
4. Postconditions: the 84 policies' exact shape; the catalog rule (every public table where
   `authenticated` holds a write privilege, table-wide or on a column, has a RESTRICTIVE
   policy for authenticated, on that command or ALL, that calls `app.live_role()` or
   `app.is_live_admin()`); `update_media_meta`'s settings, body and grants; the guide in the
   catalog and in every tenant; `app.live_role()` still a pinned definer for authenticated.

**The cost** (EXPLAIN VERBOSE of a staff UPDATE over every `page_sections` row of a tenant, in
the replay): `app.live_role()` appears only as the `Output:` of InitPlans (one for USING, one
for WITH CHECK), and the row filter reads `(InitPlan n).col1 IS NOT NULL`. So it runs once or
twice per statement, whatever the row count, each time one primary-key lookup on `profiles`
(`p.id = sub`) inside a definer; no index is needed beyond the primary key.
`live_staff_writes.test.sql` asserts that shape.

**The Worker** (`src/pages/api/admin/users/[id].ts`): the audit row of a role or activity
change carries `sessionsEnded` (true when the role or Can sign in actually changed, which is
when 0055's trigger deleted the person's sessions in the same statement); the answer's
`signedOut` is the same value. `tests/lib/usersPatch.spec.ts` (its three new cases fail without
the change).

**pgTAP** (`supabase/tests/live_staff_writes.test.sql`, 186 as built, 193 after the review

## Departures from the brief, and why

- **(a) needed no build.** U12a had already made `resolveAuthContext` compare the profile with
  the verified token's own claims (DENY_REVOKE on a mismatch), with its tests. The brief was
  written from the 2026-10-01 note.
- **(b) is the database trigger, not the admin API.** 0055's `profiles_revoke_sessions`
  already deletes every session and refresh token on a role, activity or tenant change, for
  every writer, in the same transaction. Supabase's admin `signOut` takes the user's own JWT,
  not an id, so it cannot end a colleague's sessions; a best-effort call after the write would
  be weaker than the trigger. "Audited": the users PATCH's audit row now records
  `sessionsEnded`.
- **A lock does not revoke sessions** (the brief asked for it): U12a's decision, kept, because
  the lock is the sign-in lockout and anyone who knows a staff address can trip it; revoking on
  it would let anyone sign a colleague out everywhere. A locked token writes nothing (the live
  check reads `locked_until`) and the Worker signs it out at its next request. Owner question
  below.
- **`audit_log` is in the list.** 0050 let a stale token's insert through ("bound, not
  refused") for the minutes when the Worker's view and the token's could differ; since U12a the
  Worker refuses such a session before it writes anything, and refusing it keeps "a stale token
  writes nothing" true without exception. One legitimate path did insert with a token that had
  just gone stale (found at review, H16-C1): the password form's fifth wrong current password
  locks the account inside the request, then audited the refusal with the same token. That
  row is now written with the service role (`writeAuditAsService`); see "Review fixes".
- **No new `app.role_*` helper.** The live predicate is "the live role is not null": where it
  is not null it equals the token's role, so the existing permissive policies (each already a
  capability rule) decide on a confirmed role. One generic predicate keeps 84 policies uniform
  and the catalog rule simple.
- **Reads are not live-checked here** (the brief scoped (c) to writes): recorded as the
  residual gap.

## Rollback

Expand only. To undo the database half: drop the 84 `<table>_live_{insert,update,delete}`
policies (the list in the migration) and restate `update_media_meta` from 0020; the guide may
stay or be put back at revision 5. Nothing in the Worker depends on 0129; the `sessionsEnded`
key is additive (the activity log reads no detail key).

## Owner questions

- **The lock.** Keep "a lock ends no session" (as U12a decided), or revoke on a lock too,
  accepting that anyone who knows a staff address can then sign that person out everywhere
  (the brief's ask)?
- **The read window.** Accept that a stale token reads, for up to an hour, what its old role
  could on the tables without a live read (drafts, media metadata, redirects, SEO rows,
  `system_logs`, `ai_config`, the CRM's stages and scoring points, and `site_settings`, whose
  maintenance IP allowlist a demoted Admin or Developer could still read), or shorten
  `jwt_expiry` (900 s), or schedule live reads on some of them (`site_settings` first).
