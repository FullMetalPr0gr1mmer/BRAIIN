## Plan (written before the build)

- **Scope:** Sales gets `leads.manage`, `leads.pii` (one lead at a time: the existing reveal,
  live-rechecked, 60/h per person and 300/h per tenant, audited fail-closed) and `analytics.read`.
  Nothing else. No new screen.
- **Migration A** (0092): `alter type public.app_role add value if not exists 'sales'`, alone.
- **Migration B** (0093): `app.is_member()` for `audit_insert`; `role_works_leads` and
  `role_analytics_read` gain `sales`; a RESTRICTIVE non-staff block on the tables whose public
  rows `authenticated` reads more columns of than anon; the sample lock's trusted context becomes
  "no role claim"; the legacy UPDATE on `leads(status, internal_notes)` revoked; the people
  directory serves Sales the assignable lead workers; help guides for any live member;
  postconditions.
- **Files:** `src/lib/auth/types.ts`, `packages/schemas/admin.ts`, `src/lib/authz/matrix.ts`,
  `capLabels.ts`, the dashboard and quick-action defaults, the users drawers, `notify-lead`,
  `leadFields.ts`, the lead PATCH (schema, write, route), CLAUDE.md §1/§3/§5/§8/§9/§10,
  architecture §3.4/§3.6/§9, the runbook, the guide file.
- **Tests:** `supabase/tests/rls_sales_role.test.sql` (new, catalog-driven); the endpoint cases
  (Sales allowed exactly where its caps say); `matrix.spec` parsing both docs with six cells;
  the role tables of every unit suite that iterates `ROLES`; the admin e2e staff gains Sales.

## What was built

**The database.**
- 0092 holds the one `ALTER TYPE`; 0093 uses the value (55P04).
- `app.is_member()` (the five roles, by the claim; not a definer, `search_path = ''`, EXECUTE
  for `authenticated` and `service_role`). It is called by **no function** and used by one policy,
  `audit_insert`, which is now `tenant_id = app.effective_tenant_id() and app.is_member() and
  actor_id = (select auth.uid())`. 0050's actor trigger already stamps `actor_id`; the policy now
  agrees with it, so a token with a role claim and no subject writes no audit row.
- `app.role_works_leads` → admin, developer, sales; `app.role_analytics_read` → the five roles.
  Every other helper is unchanged (pinned for `sales` in the migration's postconditions, the
  pgTAP and `sqlHelpers.spec`).
- **The non-staff block**: `testimonials_staff_columns`, `service_cases_staff_columns`,
  `media_assets_staff_columns`, each RESTRICTIVE FOR SELECT TO authenticated, the tenant first,
  then `app.is_staff()`. Sales reads none of their rows (a quote's consent record, a case's
  schedule and placeholder flag, a file's folders, tags and provider reference).
- `app.tg_testimonial_sample_lock()` trusts "no role claim" (`request.jwt.claims` has no
  `app_metadata.role`), not "not staff". A claim that is not JSON raises.
- `revoke update (status, internal_notes) on public.leads from authenticated`: staff UPDATE is
  exactly the pipeline's nine columns.
- `app.staff_directory()`: CMS staff as before; a member who is not staff, while its own live
  role works leads, gets the active, unlocked lead workers only. `crm_people` and
  `public.staff_directory` read it, unchanged.
- `help_articles_member_read`: any live member reads its tenant's guides (the Worker's
  `mayRead` decides which it shows).
- `admin_role_defaults_read` (0060) restated (pre-merge review): the tenant, a live member,
  then its own role's preset or, for an Admin, every role's. It required `app.is_staff()`, so
  the preset an Admin saved for Sales was silently ignored (Sales read zero rows).

**The Worker and the screens.**
- `ROLES`, `RoleSchema` and `ROLE_CAPS` gain `sales`; `CMS_ROLES` names the four
  `app.is_staff()` roles for code and tests that mean CMS staff.
- PATCH `/api/admin/leads/[id]` refuses `status` with a 422 naming it ("A lead moves by its stage

- `notify-lead`: recipients are every role holding `leads.manage` (crm.md D8); the decrypted

- Users & roles: each role's one line (`ROLE_DESCRIPTIONS`) under the picker in the invite and

- The dashboard: Sales's default layout (key numbers, quick actions, latest inquiries, leads by

- Sales's sidebar: Dashboard, Leads, Website stats. Its search finds nothing (it opens no
  searchable entity); its bell shows new leads and the maintenance notice.

## Departures from the design

1. **disciplines is not blocked.** The plan's catalog rule would block every table whose public
   rows `authenticated` reads more columns of; blocking `disciplines` hides every published
   service from Sales (`services_discipline_published` reads the discipline under the caller's
   RLS) and breaks its leads' interest labels and the leads filters. Its extra columns are
   bookkeeping (schedule, version, timestamps, staff ids). Named in the migration and the pgTAP.
2. **Sales reads the website stats** (`analytics.read`): the README's matrix and the plan say so
   (prototype parity); crm.md §2.1 and §10 said no. The README wins.
3. **No `role_lead_pii` helper.** `leads.pii` reaches the database only through the service-role
   reveal; no policy needs it, so `sqlHelpers.spec`'s one-helper-per-capability rule adds none.
4. **The dashboard link's caps stay `['analytics.read']`**, not crm.md's `['analytics.read',
   'leads.manage']`: the dashboard API is `analytics.read`, which Sales holds; a link a
   leads-only role could see would open a 403.
5. **The topbar search is not hidden for Sales** (crm.md §10, UX only): the palette also offers
   navigation and quick actions. Its search simply finds nothing for Sales.
6. **notify-lead's PII gate is `leads.pii` and `export.csv`**, not `leads.pii` alone: with Sales
   holding `leads.pii`, the old rule would decrypt a new lead's details for Sales in every
   notification, around the one-lead-at-a-time reveal (O-6).
7. **No PAGE_GUIDES entry for the guide.** `/admin/leads` already opens `working-with-leads`
   from its head (one guide per screen; `personal-data` is the precedent of a guide reached from
   the help centre and the screen's list, not the head).
8. **The roles guide (`roles-and-access`) is revised here.** It said "four roles"; once H11
   reached main, 0093 puts it again (five roles, a Sales line in both languages).

## Self-review

Two lenses over the diff (security/authz/PII; correctness/tests/standard). Found and fixed:
- `notify-lead` would have decrypted every new lead for Sales (fixed: `receivesLeadPiiUnasked`,
  with a unit test that fails without it).
- A legacy-status PATCH would have reached the database as a 42501 (a 500) after the revoke
  (fixed: the schema refuses it with a 422; tests for admin, developer and sales).
- The comparison table of the catalog test sat in `public` and compared itself (fixed: a temp
  table).

## Owner decisions (2026-10-19)

  and leads 70), revision 0; `roles-and-access` is put again at revision 1 (as 0069 left it)
