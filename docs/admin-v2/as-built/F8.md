## What was built

- **Preferences.** `public.admin_user_prefs`, one row per person: the bell's read watermark
  (`notifications_seen_at`), the muted kinds (`notifications.muted`), and the dashboard layout
  and quick actions U1 will fill. Self only in RLS (the caller's own row, in the token's tenant)
  behind a RESTRICTIVE `app.live_role()` check, so a demoted, deactivated or locked token reads
  and writes nothing, its own row included. Staff hold SELECT, INSERT on the preference
  columns plus the key (`tenant_id`, `user_id`, which RLS holds to their own) and UPDATE on
  the preference columns only; no DELETE. A BEFORE trigger owns the version (it moves only when a
  preference does, so marking the bell read never causes a 409), the stamps and the watermark,
  which moves forward only and never past the database's `now()`, and it refuses to hand a row
  to another person. A row's tenant is its person's in the database itself, not only in RLS:
  the key to the profile is composite, `(tenant_id, user_id)` to `profiles (tenant_id, id)`, ON
  DELETE and ON UPDATE CASCADE, so no writer (the service role included) can file a row under
  another tenant, and a profile moved to another tenant takes its row along, its bell afresh.
  `GET`/`PUT /api/admin/me/preferences` (version 0 before the first save, 409 on a stale one).
- **The people directory (P-7).** `app.staff_directory()`: every active member of the token's
  tenant (id, display name, role, and whether the person can take work now), for a live CMS
  staff member only, never an e-mail, executable by no API role. Read through
  `public.staff_directory(p_tenant)` (id, name, role: for the screens that name people, U13
  first) and `public.crm_people(p_tenant)`, restated over it with 0036's exact answer (the
  assignable lead workers, for a live lead worker). Both are empty unless the tenant the
  Worker names is the token's.
- **Renaming yourself.** `public.update_my_profile(p_tenant, p_display_name)`: a SECURITY
  DEFINER that writes one column of the caller's own row after its own live check (profiles
  stays Admin-write only), under the schema's rules applied again: trimmed of what
  JavaScript's `trim()` removes, at most 80 characters (code points), no Unicode control or
  format character (Cc, Cf: bidi overrides and isolates, zero-width characters). The trim set
  and the refused class are listed as code points in the migration, and
  `tests/lib/personalLayer.spec.ts` compares them with the schema's `.trim()` and
  `/[\p{Cc}\p{Cf}]/u` over every code point. It writes the `profile.update` audit row (the
  field's name only) in the same transaction, so a direct PostgREST call is audited too and
  a rename whose row cannot be written does not happen; `PATCH /api/admin/me` and the no-JS
  page add no row of their own. An Admin can also rename anyone, themselves included, on the
  users screen (its own audited path), under the same rule.
- **One display-name rule for every writer.** `app.display_name_ok()` is the rule (at most 80
  characters, no control or format character); `update_my_profile` applies it after the trim,
  and the trigger `profiles_display_name_rule` (BEFORE INSERT OR UPDATE OF `display_name` on
  `profiles`) applies it to every other writer: the users screen's Admin session through
  PostgREST (0037's column grant), an Admin token calling the API directly, the service role's
  invite, seeds and operators (23514). The users screen's schemas (`UserInviteSchema`,
  `UserUpdateSchema`, `PATCH /api/admin/users/[id]`) share `DisplayNameValueSchema` with the
  rename, so the Worker refuses the same names first (422).
- **Changing your password.** `POST /api/admin/me/password` (`src/lib/admin/account.ts`):
  refused before anything is tried while the account is locked (and when the lockout store is
  unreachable: fail closed); the current password re-authenticates as the session's e-mail,
  and a wrong one counts toward the same 5-in-15-minutes lockout as the sign-in form (the
  fifth answers 423). Only GoTrue's `invalid_credentials` counts: a rate limit, an outage, a
  network error or a captcha refusal is a 502 that counts nothing. Then `updateUser` sets the
  new password, sending the current one again as `current_password` (so the route keeps
  working once the auth server requires it, O-24), and `signOut({ scope: 'others' })` ends
  every other session (GoTrue's update has already ended them, keeping the session that
  made it; the route's own call does not rely on that). A refused current password (locked
  or wrong) and the change are audited; a new password the auth server refuses (too weak,
  the same) or cannot set changes nothing and writes no audit row (a failure is logged to
  `system_logs`). No password reaches an audit row, a log line or a response. These are the
  Worker's checks: see "Residual risk".
- **The bell.** A derived feed (`src/lib/admin/notifications/`, one module per kind, registered
  in `index.ts`): new inquiries (`leads.manage`: name and interest only), new job applications
  (`applications.manage`: the role applied for only), services and posts going live today
  (`services.write` or `blog.write`), and maintenance turned on or off (everyone; a link only
  for `maintenance.manage`). A source runs only for a role `ROLE_CAPS` shows it to, so Content
  Creator and SEO never query leads or applications, not even for a count, and RLS applies the
  rule again. At most 30 items, 10 per source, 14 days back. The same loader gives the shell's
  unread count (every admin render, labels skipped) and the drawer's list (on open), so the
  dot and the list cannot disagree. `GET /api/admin/notifications`, `POST
  /api/admin/notifications/seen`.
- **"Going live today" is the Riyadh day.** The source reads `services` and `blog_posts`
  (status scheduled, `scheduled_for` between the Riyadh day's two midnights), not the
  dashboard's `dashboard_attention` view, whose `current_date` is UTC's and filed tomorrow's
  00:00 to 03:00 Riyadh items under "today" every evening. An item counts as new from the
  later of the day's start and its own `updated_at`, so one scheduled after the person marked
  the bell read lights it again. One more read than the view (two tables), for Admin and
  Content Creator only. The dashboard's banner still reads the view's UTC day; the dashboard
  slice (U1) owns it.
- **"Mark all as read" marks what was shown.** The feed carries `asOf`, the moment its list
  was read (the loader's now, or a later `since` a fast clock stamped). The drawer posts it
  back and the no-JS page carries it in a hidden field; the route refuses a body without one,
  holds it to the Worker's now, and the database holds it to its own. An item that arrived
  while the drawer was open stays new.
- **The environment pill.** `public.admin_environment(p_tenant)` over `app.deployment`:
  production reads "Live", staging "Staging", development "Local", and an unmarked database
  shows no pill. An answer is cached per isolate for 10 minutes; no answer is never cached,
  because NULL is also what a caller who is not live gets (a token locked a moment ago), and
  caching it would hide the pill from every member on the isolate.
- **The shell.** The topbar's bell (a link to `/admin/notifications`; its name carries the
  unread count, the dot is `hidden` at zero) and the sidebar's account chip (a link to
  `/admin/account`), each opened by `AdminChrome` as a native modal `<dialog>` drawer with JS.
  The account drawer and page share one `AccountPanel`: name, password, e-mail ("Not set up"),
  what you can do (`CAP_LABELS`, `src/lib/authz/capLabels.ts`, plain lines from `ROLE_CAPS`),
  admin language, Sign out. The drawer renders the panel the first time it opens and keeps it
  mounted after; until then the server renders an empty dialog, so the forms and the
  capability lines cost no CPU on every admin render (the island's props still carry the
  view, which the drawer needs to open without a request). The no-JS pages post their forms
  to themselves with the double-submit field and redirect (303). `/admin/notifications`
  hands the feed it loaded (and the maintenance snapshot) to the layout (`preload`), so the
  shell's count and badge come from that one read instead of a second run of the loader.
- **The no-JS pages' forms.** What a post to `/admin/account` or `/admin/notifications`
  does is `src/lib/admin/personalForms.ts` (`accountFormPost`, `notificationsFormPost`),
  not frontmatter: each page answers 403 through `mayPostPersonalForm` (an active member,
  the JSON routes' `analytics.read`) before reading the form, and each outcome answers what
  its JSON twin answers: a refused name 422, a session that may no longer rename 403, a
  wrong current password 422 and the fifth 423, an auth server that cannot answer 502 (the
  page answered 422 before), a form the page does not render 400.
- **Tests.** pgTAP over admin, content_creator, seo, developer, anon, another tenant and three
  stale tokens (demoted, deactivated, locked), plus the service role against the composite key
  (a row under another tenant, a move to one, a row handed to another person), a profile that
  moves or goes, and the display-name rule for the Admin path and the service role (a name
  stored before the rule written with the trigger off, then the sign-in's writes and an
  unchanged save over it); the migration's postconditions run under both grant regimes and,
  for MAINTAIN, only on PostgreSQL 17; `tests/lib/notifications.spec.ts` (per role),
  `accountPassword.spec.ts` (the lockout interplay, and the local auth server's settings),
  `personalLayer.spec.ts` (with the definer's name rules against the schema's, code point by
  code point), `personalForms.spec.ts` (both pages' posts); endpoint cases in
  `tests/authz/cases/account.ts` and `notifications.ts`; both pages in the per-role sweep
  (`EXTRA_LINKS`); `tests/admin/personal.e2e.ts` (axe with each drawer open, focus return, a
  rename from the drawer and from the no-JS page, the triggers as links without JS, a long
  unbroken name in a bell row, "Mark all as read" sending the list's time).

## Departures from the design, and why

- **The display-name rule is a trigger, not a CHECK.** A CHECK, even one added NOT VALID, is
  tested on every UPDATE of the row, not only when the name changes. A name stored before 0044
  that breaks the rule (the users screen allowed 120 characters and format characters, and
  production's names could not be read from here) would then make every write to that profile
  fail, the sign-in's lockout RPCs (0009) included: its owner could not sign in. The trigger
  tests a name when it is written and differs from the stored one, so such a name stays until
  its next change, which must meet the rule. The migration counts the names that break it (a
  NOTICE with a number, never a name); a later migration can add a CHECK once that count is
  zero. The users screen's limit narrows from 120 characters to 80, the rename's.
- **The preferences key is composite.** ui.md §6 names `user_id` (PK, FK profiles); the key to
  the profile is `(tenant_id, user_id)` to `profiles (tenant_id, id)` instead, so the database
  holds the row's tenant to its profile's for every writer, not only RLS for staff. It rests on
  `profiles_tenant_id_id`, UNIQUE `(tenant_id, id)`, which 0041 (C3) adds for the leads'
  assignee and applies first in production; 0044 adds the same constraint where it is absent
  (this branch's CI until C3 merges). 0041 drops and re-adds that constraint, so it must apply
  before 0044, as the numbering already requires (docs/admin-v2/migrations.md); a file after
  0044 that re-adds it must drop `admin_user_prefs_profile_fk` first.

- **Migration 0044, `0044_personal_layer.sql`.** The ledger reserved 0039 and the design names
  `00NN_admin_user_prefs.sql`; the Wave 1 plan renumbered F8 to 0044, and the file holds more
  than the preferences table. The ledger row is moved to 0044.
- **`public.update_my_profile`, not `app.update_my_profile()`.** The Worker calls it through
  the API with the caller's token, and only `public` is exposed. It takes the tenant like
  `crm_people` does, so a handler that forgot to scope is refused rather than guessed.
- **`app.staff_directory()` is reached only through wrappers.** It is executable by no API
  role; `public.staff_directory` and `public.crm_people` are the two doors. Locked people stay
  in the directory (they are still members), marked as not assignable. P-7's Sales branch
  ("only assignable lead workers") arrives with the Sales role (C10a) as a branch of the
  directory, not a second one. `public.staff_directory` has no caller yet: U13 is its first.
- **`admin_user_prefs` is keyed by the person, with no `id`, `created_by` or `updated_by`.**
  One row per person, written through the API only by that person; the key would repeat the
  owner, as in `site_settings` and `crm_settings` (keyed by their tenant). The dashboard
  columns are created now (one expand for the table), but the PUT schema refuses them until
  U1 adds its fields.
- **"Mark all as read" is a watermark.** No per-item read state is stored (there is no event
  table to hang it on). A clicked row is marked read in that drawer only, the others keep
  their dot (the mockup's bug fixed, as §2.8 asks); the next load shows what is newer than the
  watermark as new.
- **The maintenance item needs a stamp.** The KV snapshot and `site_settings.maintenance` now
  carry `changedAt`, stamped by the maintenance switch when `active` flips and kept when only
  the allowlist changes. A switch recorded before F8 has no stamp and no item (the topbar badge
  still says it is on); the item never names who flipped it (the activity log does).
- **No muting screen, and no "Notifications preferences" row in the account drawer.** The
  muted kinds are stored and honoured, and the API accepts them, but the screen is U11's; the
  account drawer gains its link then.
- **"Edit profile" is inline.** The prototype's account drawer rows ("Edit profile: name,
  photo, password") open the forms in place: the name and the password are sections of the
  drawer. No photo: avatars are initials until uploads (U3). The 2FA row stays hidden until
  U17. Changing the e-mail needs delivery (SMTP, O-2), so its row says "Not set up".
- **No topbar slot registry.** Wave 0 built none (W0-c, "No pending links and no topbar
  slots"), so F8 edits `Topbar.astro` and `Sidebar.astro` directly; U16's help button merges
  after it. The drawers mount in `AdminChrome`, the shell's one island.
- **Sign out moved into the account drawer and page.** The sidebar's `<details>` account menu
  (and the layout's script behind it) is gone; the chip is a link. `POST
  /api/admin/auth/logout` and the page's form share `endSession()`. The admin harness's
  sign-in check now reads the chip's role label.
- **A private drawer, not the kit's.** The general Drawer is F4b's, built in parallel; the
  shell's two drawers use a private `ChromeDrawer` with the kit's class names (`.drw`), so
  F4b's can replace it without touching `admin.css`.
- **Password rules.** At least 10 characters and at most 72 bytes (bcrypt reads no more), typed
  twice, not the current one; GoTrue's own policy may ask for more and its `weak_password` is
  named. A successful re-authentication does not reset the failure count (`registerSuccess` is
  the sign-in's; leaving the count is the cautious side).
- **Not driven end to end: Sign out and the password change.** Each role's e2e session is
  shared by the whole run, and both would end it. Their rules are unit-tested, through the real
  route and lockout module.
- **Page-only frames in a screen sheet.** `.acct-page`, `.ntf-page` and `.ntf-page__actions`
  are in `public/styles/admin/personal.css`; the drawers' content (`.drw`, `.list`, `.li`,
  `.empty`, `.acct`) can render on any page (both drawers open from every page), so it is in
  `admin.css`, ported from the prototype's rules.
- **The bell is a link, not a button.** ui.md §2.2 draws `<button aria-label="Notifications,
  N unread">`; the bell is `<a href="/admin/notifications" data-open="notifications">` with
  the same name, as the account chip is a link to `/admin/account`, so without JS it still
  leads somewhere (P-1's no-JS twins). With JS a plain click opens the drawer; a click with a
  modifier opens the page in a new tab.
- **`/admin/notifications` is an addition.** AV-05's deliverables name `/admin/account` as
  the only no-JS page. The bell's link needed somewhere to go, so the list has its own page:
  server-rendered, the same `NotificationList`, "Mark all as read" as a form, in the per-role
  sweep's extras.
- **The drawer is full width below 560px, not 600px.** ui.md §2.3 says "full width under
  600px"; the CSS is `min(560px, 100vw)`, so the panel takes the whole width exactly where a
  560px panel no longer fits, and between 560 and 600px a strip of scrim still shows it is a
  drawer you can click away. The prototype never goes full width (`min(560px, 92vw)`); the
  `100vw` is the design's phone rule.

## Residual risk: a password changed at Supabase Auth itself (owner item O-24)

- **The gap.** The re-authentication, the lockout count, the 10-character floor, the other
  sessions signed out and the audit rows are the Worker's. Supabase Auth's `PUT
  /auth/v1/user` is public (the project URL and the anon key ship to every browser), and with
  a session's access token alone (an unlocked machine's devtools, a copied
  `__Host-braiin-auth` cookie) it sets a new password: no current password (GoTrue's
  default), no lockout count, GoTrue's own minimum length (6 unless set), and no row in the
  app's hash-chained `public.audit_log` (GoTrue records the change only in its own auth audit
  log, as `user_updated_password`). GoTrue then signs out every other session of that user,
  so the real owner's other devices are signed out too: only the session that made the
  change stays signed in, and the real owner is locked out of their account. The gap
  predates F8; the sign-in lockout has the same edge (GoTrue's `/token` counts nothing toward
  it; GoTrue's own per-IP rate limit applies).
- **What F8 does about it.** The route sends `current_password` and counts GoTrue's
  `current_password_invalid` as a wrong try, so it works with the setting on or off. The
  separate re-authentication stays: until the auth server requires the current password it
  is the only check, and the fresh session it starts is why Secure password change never
  asks this route for an e-mailed code. Locally (`supabase/config.toml`, pinned by
  `tests/lib/accountPassword.spec.ts`): `minimum_password_length = 10` and `[auth.email]
  secure_password_change = true`, so a session older than 24 hours cannot change its
  password at the auth server without that code. Neither makes a password change depend on
  SMTP (O-2). Requiring the current password has no CLI key (2.118), so the local stack and
  CI run without it and prove the Worker's path only.
- **The owner's action (O-24, launch runbook §2a), for staging and production.** Require the
  current password (Management API `security_update_password_require_current_password`),
  minimum length 10 (`password_min_length`), Secure password change on
  (`security_update_password_require_reauthentication`). A direct call then needs the current
  password. A direct call still counts no lockout, and a direct change is audited only in
  GoTrue's own log (`user_updated_password`), never in `public.audit_log`, so a stolen token
  can still be used to guess the current password there, outside the Worker's lockout: O-24
  asks the owner to accept that remainder. Recorded in [deviations.md](../deviations.md)
  with its owner, expiry (F8's production push, at the latest 2026-11-30), close condition
  and a compensating control the owner may choose (not built): alert on a
  `user_updated_password` with no matching `auth.password_change` row in `public.audit_log`.
