## What was built

- **Preferences.** `public.admin_user_prefs`, one row per person: the bell's read watermark
  (`notifications_seen_at`), the muted kinds (`notifications.muted`), and the dashboard layout
  and quick actions U1 will fill. Self only in RLS (the caller's own row, in the token's tenant)
  behind a RESTRICTIVE `app.live_role()` check, so a demoted, deactivated or locked token reads
  and writes nothing, its own row included. Staff hold SELECT and column INSERT/UPDATE on the
  preference columns only; no DELETE. A BEFORE trigger owns the version (it moves only when a
  preference does, so marking the bell read never causes a 409), the stamps, the key, and the
  watermark, which moves forward only and never past the database's `now()`.
  `GET`/`PUT /api/admin/me/preferences` (version 0 before the first save, 409 on a stale one).
- **The people directory (P-7).** `app.staff_directory()`: every active member of the token's
  tenant (id, display name, role, and whether the person can take work now), for a live CMS
  staff member only, never an e-mail, executable by no API role. Read through
  `public.staff_directory(p_tenant)` (id, name, role: for the screens that name people, U13
  first) and `public.crm_people(p_tenant)`, restated over it with 0036's exact answer (the
  assignable lead workers, for a live lead worker). Both are empty unless the tenant the
  Worker names is the token's.
- **Renaming yourself.** `public.update_my_profile(p_tenant, p_display_name)`: a SECURITY
  DEFINER that writes one column of the caller's own row after its own live check (profiles
  stays Admin-write only), trimmed, at most 80 characters, no control characters (Zod also
  refuses Unicode format characters, bidi overrides included). `PATCH /api/admin/me`, audited
  as `profile.update` with the field name only.
- **Changing your password.** `POST /api/admin/me/password` (`src/lib/admin/account.ts`):
  refused before anything is tried while the account is locked (and when the lockout store is
  unreachable: fail closed); the current password re-authenticates as the session's e-mail,
  and a wrong one counts toward the same 5-in-15-minutes lockout as the sign-in form (the
  fifth answers 423); then `updateUser` sets the new password and `signOut({ scope: 'others' })`
  ends every other session. The refusal and the change are both audited; no password reaches
  an audit row, a log line or a response.
- **The bell.** A derived feed (`src/lib/admin/notifications/`, one module per kind, registered
  in `index.ts`): new inquiries (`leads.manage`: name and interest only), new job applications
  (`applications.manage`: the role applied for only), services and posts going live today
  (`services.write` or `blog.write`), and maintenance turned on or off (everyone; a link only
  for `maintenance.manage`). A source runs only for a role `ROLE_CAPS` shows it to, so Content
  Creator and SEO never query leads or applications, not even for a count, and RLS applies the
  rule again. At most 30 items, 10 per source, 14 days back. The same loader gives the shell's
  unread count (every admin render, labels skipped) and the drawer's list (on open), so the
  dot and the list cannot disagree. `GET /api/admin/notifications`, `POST
  /api/admin/notifications/seen`.
- **The environment pill.** `public.admin_environment(p_tenant)` over `app.deployment`:
  production reads "Live", staging "Staging", development "Local", and an unmarked database
  shows no pill. Cached per isolate (10 minutes for an answer, 1 minute for none).
- **The shell.** The topbar's bell (a link to `/admin/notifications`; its name carries the
  unread count, the dot is `hidden` at zero) and the sidebar's account chip (a link to
  `/admin/account`), each opened by `AdminChrome` as a native modal `<dialog>` drawer with JS.
  The account drawer and page share one `AccountPanel`: name, password, e-mail ("Not set up"),
  what you can do (`CAP_LABELS`, `src/lib/authz/capLabels.ts`, plain lines from `ROLE_CAPS`),
  admin language, Sign out. The no-JS pages post their forms to themselves with the
  double-submit field and redirect (303).
- **Tests.** pgTAP over admin, content_creator, seo, developer, anon, another tenant and three
  stale tokens (demoted, deactivated, locked); `tests/lib/notifications.spec.ts` (per role),
  `accountPassword.spec.ts` (the lockout interplay), `personalLayer.spec.ts`; endpoint cases in
  `tests/authz/cases/account.ts` and `notifications.ts`; both pages in the per-role sweep
  (`EXTRA_LINKS`); `tests/admin/personal.e2e.ts` (axe with each drawer open, focus return, a
  rename from the drawer and from the no-JS page, the triggers as links without JS).

## Departures from the design, and why

- **Migration 0044, `0044_personal_layer.sql`.** The ledger reserved 0039 and the design names
  `00NN_admin_user_prefs.sql`; the Wave 1 plan renumbered F8 to 0044, and the file holds more
  than the preferences table. The ledger row is moved to 0044.
- **`public.update_my_profile`, not `app.update_my_profile()`.** The Worker calls it through
  the API with the caller's token, and only `public` is exposed. It takes the tenant like
  `crm_people` does, so a handler that forgot to scope is refused rather than guessed.
- **`app.staff_directory()` is reached only through wrappers.** It is executable by no API
  role; `public.staff_directory` and `public.crm_people` are the two doors. Locked people stay
  in the directory (they are still members), marked as not assignable. P-7's Sales branch
  ("only assignable lead workers") arrives with the Sales role (C10a) as a branch of the
  directory, not a second one. `public.staff_directory` has no caller yet: U13 is its first.
- **`admin_user_prefs` is keyed by the person, with no `id`, `created_by` or `updated_by`.**
  One row per person, written through the API only by that person; the key would repeat the
  owner, as in `site_settings` and `crm_settings` (keyed by their tenant). The dashboard
  columns are created now (one expand for the table), but the PUT schema refuses them until
  U1 adds its fields.
- **"Mark all as read" is a watermark.** No per-item read state is stored (there is no event
  table to hang it on). A clicked row is marked read in that drawer only, the others keep
  their dot (the mockup's bug fixed, as §2.8 asks); the next load shows what is newer than the
  watermark as new.
- **The maintenance item needs a stamp.** The KV snapshot and `site_settings.maintenance` now
  carry `changedAt`, stamped by the maintenance switch when `active` flips and kept when only
  the allowlist changes. A switch recorded before F8 has no stamp and no item (the topbar badge
  still says it is on); the item never names who flipped it (the activity log does).
- **No muting screen, and no "Notifications preferences" row in the account drawer.** The
  muted kinds are stored and honoured, and the API accepts them, but the screen is U11's; the
  account drawer gains its link then.
- **"Edit profile" is inline.** The prototype's account drawer rows ("Edit profile: name,
  photo, password") open the forms in place: the name and the password are sections of the
  drawer. No photo: avatars are initials until uploads (U3). The 2FA row stays hidden until
  U17. Changing the e-mail needs delivery (SMTP, O-2), so its row says "Not set up".
- **No topbar slot registry.** Wave 0 built none (W0-c, "No pending links and no topbar
  slots"), so F8 edits `Topbar.astro` and `Sidebar.astro` directly; U16's help button merges
  after it. The drawers mount in `AdminChrome`, the shell's one island.
- **Sign out moved into the account drawer and page.** The sidebar's `<details>` account menu
  (and the layout's script behind it) is gone; the chip is a link. `POST
  /api/admin/auth/logout` and the page's form share `endSession()`. The admin harness's
  sign-in check now reads the chip's role label.
- **A private drawer, not the kit's.** The general Drawer is F4b's, built in parallel; the
  shell's two drawers use a private `ChromeDrawer` with the kit's class names (`.drw`), so
  F4b's can replace it without touching `admin.css`.
- **Password rules.** At least 10 characters and at most 72 bytes (bcrypt reads no more), typed
  twice, not the current one; GoTrue's own policy may ask for more and its `weak_password` is
  named. A successful re-authentication does not reset the failure count (`registerSuccess` is
  the sign-in's; leaving the count is the cautious side).
- **Not driven end to end: Sign out and the password change.** Each role's e2e session is
  shared by the whole run, and both would end it. Their rules are unit-tested, through the real
  route and lockout module.
- **Page-only frames in a screen sheet.** `.acct-page`, `.ntf-page` and `.ntf-page__actions`
  are in `public/styles/admin/personal.css`; the drawers' content (`.drw`, `.list`, `.li`,
  `.empty`, `.acct`) renders on every page, so it is in `admin.css`, ported from the
  prototype's rules.

## Measured

- Admin eager JS per screen 107.4 KB gz (F4a measured 103.9; the drawers, the account panel
  and the notification list ride `AdminChrome`), the size-limit sum 228.27 KB of 300, the
  public routes 25.51 KB of 100, unchanged. Contrast gate: three new pairs (the form outcome,
  the bell's dot, a list row's icon), all pass.
- Subrequests per admin render, at most: the profile row, one KV read shared by the badge and
  the bell, the environment (cached), the preferences row, three bell sources, and the menu's
  counts. The bell never polls (P-15).
