## As built

**The session check** (`src/lib/auth/context.ts`, `src/lib/auth/claims.ts`). The Worker
compares the profile with the claims of the access token the request carries, decoded after
the auth server verified that very token, instead of with `getUser()`'s user record (the
account's current `app_metadata`, which the users screen rewrites together with the profile,
so the two always agreed and a stale token was never seen). A token minted before a role,
activity or tenant change is revoked at its next request. It also enforces the tenant's
session length (`admin_security_settings.session_max_days`, 1 or 7 days, 7 when unset)
from the newest sign-in time the token's `amr` records. The middleware signs a revoked
session out at the auth server (`scope: 'local'`, best effort) before clearing its cookies.

**The database's half.** `profiles_revoke_sessions`, an AFTER UPDATE OF role, is_active,
tenant_id trigger on `profiles` (only when one of them changes): a definer that deletes every
`auth.sessions` row of the person (their refresh tokens and amr claims cascade) and the
refresh tokens no session names. It fires for every writer (the users screen, a direct API
call, the service role, an operator). GoTrue then answers `session_not_found` to the next
`getUser()`, so the admin finds no session at the person's next click, and their next
sign-in mints a token the hook stamps with the new role. `profiles_live_read` (RESTRICTIVE,
TO authenticated, the tenant predicate first): reading anyone's profile but your own needs
`app.role_manages_users(app.live_role())`, beside H10's three live write policies.

**The account owner.** `profiles.is_owner` (no grant names it), at most one per tenant
(`profiles_one_owner`), set by the runbook (§3a), never by the migration and never claimable.
`app.tg_profiles_owner_guard` (invoker, BEFORE INSERT OR UPDATE OR DELETE): the owner cannot
be deleted (an `auth.users` cascade included); a row that is, or becomes, the owner must be an
active Admin and cannot move tenant; only an operator or a definer may set or clear the marker.
The lockout columns stay writable (the sign-in's RPCs lock the owner like anyone). The users
PATCH answers 422 (`field: owner-protected`) before the database, and maps the guard's 42501
`owner_protected` to the same 422. `public.transfer_ownership(p_tenant, p_to)`: the caller
a live Admin of the token's tenant and its owner (42501 otherwise), the target another
active, unlocked Admin of the tenant (22023 otherwise); the old marker cleared before the new
one is set, both rows locked, and the audit row (`user.ownership_transfer`) written in the
same transaction. `POST /api/admin/users/[id]/owner` checks the caller is the owner first
(a 422 for anyone else), then calls it.

**The Security card.** `public.admin_security_settings` (one row per tenant, created by the
first save; RLS ENABLE + FORCE; Admin by the JWT and, RESTRICTIVE, by the live role; staff
read, insert the key and the two settings, update the two settings; the service role reads;
no DELETE; version, actor and updated_at triggers; immediate, so not in the release registry).
`GET/PUT /api/admin/users/security` (`users.manage`, live recheck, version 0 creates the row,
a stale version or a racing insert is a 409, audited `user.security_update` with field names).
The invite POST refuses an address outside the allowed domain (422 on `email`, exact domain:
a subdomain is another domain).

**Colleagues' e-mails.** `public.staff_accounts(p_tenant)`: e-mail, invited, confirmed, last
sign-in and the owner flag from `auth.users`, for a live Admin of the token's tenant only,
at most 200 rows; `GET /api/admin/users` joins it to the profiles (read through RLS) and
derives Active / Removed / Locked / Invited.

**The screen.** `/admin/users` on the kit: the people table (DataTable), the edit drawer
(name, role, Can sign in, the sign-out warning, Remove access and Make account owner, both
confirmed), today's invite on a card, the Security card (Segmented, SaveStatus), and the
read-only Roles & permissions matrix, server-rendered from `ROLE_CAPS` and `CAP_LABELS`
(`src/lib/authz/roleMatrix.ts`) in its own focusable scroll region. `public/styles/admin/users.css`.

**The roles guide** (`app.help_article_set()` restated from 0046, only `roles-and-access`
rewritten): a role change or switching someone off ends every sign-in on every device; the
hour an issued pass still lasts at the database directly, on what does not check the account
each time; the account owner; the Security card.

## Departures from the brief, and why

- **The helper is H10's.** `app.role_manages_users` landed in 0050; 0055 reuses it, and the
  profiles policy set it asserts includes H10's three write policies.
- **`getSession()` first, then `getUser(token)`.** The brief kept `getUser()` first and read
  the token afterwards. `getUser()` loads the session itself (refreshing it when near expiry)
  and then verifies it; doing the two steps in this order makes the claims decoded exactly the
  token the auth server just verified, never a second load that might refresh again (a
  second subrequest, a different token). supabase-js's own `getClaims()` does the same for a
  project on symmetric keys. Same subrequest count as before.
- **The setting's read falls back, the profile's does not.** The brief embedded the setting in
  the profile read and failed both closed. A failure of the embed alone (0055 not yet applied
  when the Worker deploys, a stale schema cache) would then sign every member out, so the
  profile is read again alone and the 7-day default applies (the cookie's own lifetime),
  logged once per isolate. An unreadable profile still revokes.
- **Five minutes of clock allowance** on `exp` and on the session age (`CLOCK_SKEW_SECONDS`),
  so a Worker clock ahead of the auth server's never ends a valid session.
- **The owner guard also covers INSERT**, and its rule is "a row that is or becomes the owner
  is an active Admin of its tenant" rather than "an UPDATE of the owner may not demote": the
  service role could otherwise insert a profile that is already an owner, and an operator
  marking a non-Admin would have frozen that row. An operator may clear the marker and
  demote in one statement (the marker rule already limits clearing it to operators).
- **The revocation deletes the sessions first**, then the refresh tokens no session names
  (GoTrue's foreign keys cascade the rest).
- **The postconditions exercise the privilege** (`delete from auth.sessions where false`, the
  same for refresh tokens, a read of `auth.users`) besides `has_table_privilege`, and check
  the definers' owner bypasses RLS (so a delete on an RLS-enabled auth table cannot silently
  delete nothing).
- **The invite stays a card** (email and role, as today); the invite drawer, pending invites,
  Resend, Cancel and the "Not set up" switch are U12b's. D5 (no e-mail in the invite's audit
  detail) is left with them, where the brief's §6.2 places it.
- **Another role reaches the page and sees only the refusal**: the server renders the cards
  and the matrix for `users.manage` holders only, and the island's table shows the API's 403
  (the refusals e2e).
- **The directory fails soft**: if `staff_accounts` cannot be read, the list shows the people
  without e-mails rather than an error.
- **No e-mail edit**, as the brief says (the drawer shows it).
- **The Security card does not use F5a's `useEntitySave`** (merged while this slice was
  built). The hook drives editors declared by a `uiSchema` field list against the resource and
  singleton PATCH routes; this card is two settings on its own versioned PUT
  (`/api/admin/users/security`), saved at once. It keeps the same contract by hand: the
  version it read, a 409 that keeps the input and says someone else changed it, SaveStatus.
  Moving it onto the hook means a singleton target for the route; left for a later slice.

## Rollback

**Expected once, not a fault:** on the first request after this deploy, every admin session signed in more than 7 days ago (the default session length) is signed out, the owner's included, because the session length is now counted from the original sign-in (before U12a a session refreshed at least weekly lived on indefinitely). Staff are asked to sign in again once; tell them before the deploy. Only being signed out again at every click after a fresh sign-in means a fault, and that is what the rollback below is for.

The session check is the one change that can lock everyone out if it is wrong. Its tests
(`tests/lib/authContext.spec.ts`: every role's happy path, a token minted before and after a
role change, the claims GoTrue issues, clock skew both ways, the setting's fallback;
`tests/lib/claims.spec.ts`; and the e2e, which reads a real token off its cookie) pin the
shape. If production shows members signed out at every click after the deploy: `npx wrangler
rollback` (runbook §10; a rollback across this PR is safe, nothing in the older check needs
0055), or a PR reverting `src/lib/auth/context.ts` and `src/lib/auth/claims.ts` alone. The
database half needs no rollback: revoking sessions on a role change is what the older check
assumed too. A smoke sign-in right after the deploy is the owner's check (README O-items).
