# F6: built-in section copy as shared data

- **Lane:** UI, Phase 0
- **Design:** README "Slice sequence", F6 [AV-23]; [ui.md](../ui.md) AV-23
- **PR:** #60 (branch `feat/f6-section-copy`)
- **Migrations:** none

## What was built

Every public section's built-in copy, the words it renders where its CMS content leaves a
field out, is data: one module per section type in `src/lib/sections/copy/<type>.ts`,
indexed by `SECTION_COPY` in `src/lib/sections/copy/index.ts` (30 modules, one per type,
beside the index and `text.ts`). The 30 section components that held copy import it instead
of their own `STR` tables, as do `ServicePage.astro` and `ContactForm.astro` for the words
departures 3 and 4 moved. Nothing else reads them yet: the page editor (E1, AV-25) is to
read the same values on the server, through `builtInContent(type, place)`, to prefill its
fields. No admin code changed, so the admin bundle did not move.

The public HTML is byte-identical. The proof is in three parts:

- **A byte snapshot taken before the move.** The first commit on the branch (`cd2bb08`) adds
  a `render` Vitest project (`vitest.render.config.ts`) that renders `.astro` components with
  Astro's container API, and `tests/render/sections.spec.ts`, which renders, in EN and AR,
  every page's default composition as its route composes it, every section type with all
  its content authored, and the variants, modes and route data the pages do not reach. Its
  snapshot was written by the components as they stood on `main`. Every commit after it
  leaves that snapshot unchanged. The bands that load their own data get fixtures
  (`tests/render/setup.ts`), so the copy around the data is in the output: the confidential
  client line, the LinkedIn label, the founding-year note, the empty team, and the
  explorer's previous and next labels are all in the snapshot. Review found fields no case
  authored (About's poster and clip, the hero's Stream UID and intro plate, the chosen
  Selected Work cards, the pinned Our Work project), so the branches behind them were never
  rendered. Four cases were added for them, as new snapshot keys written after the move
  (no earlier key changed), and a test now fails on any content-schema field that no case
  authors.
- **The design's per-type test.** `tests/render/sectionCopy.spec.ts` renders each type, in
  each of its looks and in both languages, with `content: {}` and with the look's built-in
  copy stored as its content. The two must be the same bytes. So must each storage unit
  (departure 9) stored alone at its built-in value. Each field, varied (other words, or an
  accent range or index one word over) and stored with the rest of its unit, must then
  change the output, so the comparison can never pass because a section ignores its
  content, and every built-in field must be one the spec can vary. Each declared
  `together` group must be needed somewhere. The spec was checked against mutations: a
  component rendering its own string instead of the copy, a `notVerbatim` field removed
  from the list, the `together` groups removed (46 cases fail), a component ignoring an
  authored accent, and a needless group declared on `contact` and `slogan`. It caught all
  of them.
- **A literal check, run once on the diff.** Every string literal removed from `src/` still
  exists, byte for byte, somewhere in the new `src/`. That is 458 literals, 199 of them
  Arabic. The only exceptions are the six template literals that became patterns:
  `Why ${brand}` became `Why %brand%`, `Since ${year}` became `Since {year}`, and
  `${i} of ${n}` became `{i} of {n}`, each in EN and AR.

`tests/lib/sectionCopy.spec.ts` holds the data to its own rules:

- one entry per rendered type;
- every look is valid content for its type, and names only fields the type has;
- every text field of every content schema has a built-in value, or a stated reason not to;
- every pair is written in both languages, with Arabic letters in the Arabic;
- no pair spells the studio's name;
- the design's Arabic-Indic digits are kept (`حوالي ٤٥ دقيقة`, `٢٨ خدمة`).

## Departures from the design, and why

1. **The copy is shaped like the content, not like the old `STR` tables.** AV-23 says
   "extract each component's STR/default copy". The tables were keyed by language
   (`{ en: { tag, heading }, ar: {…} }`). Each module now has the type's content shape:
   field by field, each value an `{ en, ar }` pair, an accent range or a list of them
   (`BuiltIn<Content, Field>` in `copy/text.ts`). That is the form the page editor fills
   and stores, so it can show a field's built-in text and store only what differs, with
   no mapping layer in between.
2. **Some types have more than one look.** The design assumes one set of defaults per type.
   Four types have several: the hero (the home copy, plus the contact, services and join
   presets), the discipline cards (the home layout and the `/services` layout), `social`
   (`paper` and `klein`), and `statistics` (`cards`, `band`, `reach`, `proof`, `services`).
   `builtInLook(type, { page, variant })` picks one, and `builtInContent` returns it. The
   hero presets' copy now lives in `copy/hero.ts`. `HERO_PRESETS` in
   `src/lib/sections/types.ts` keeps their layout and points at that copy, so the presets
   are still code-only route arguments, as §8 says.
3. **Text that no content field holds moved too.** This is accessible names, controls, and
   patterns around data, such as the carousel's buttons, "Since {year}", and the
   explorer's region name. Each module's `labels` holds them, so all of a section's words
   live in one module. The words a service page hands to "Say hello" (`v.helloH`,
   `v.helloP`) moved into `SERVICE_PAGE_COPY` (`helloLeadIn`, `helloLead`), the
   template's shared text, which E3 makes editable. `serviceHelloHeading` reads them from
   there.
4. **The contact form's words moved too, into `src/lib/forms/contactCopy.ts`.** ContactForm
   is not a section. Its words are what three of `contactInquiry`'s content fields fall
   back to (`note`, `successMessage`, `submitLabel`), so without the move the editor could
   not show those three fields' defaults. `CONTACT_INQUIRY_COPY` names them from
   `CONTACT_FORM_COPY`, without duplicating the strings. The form's two words that differ
   by layout became two keys each: the home form's button, and its Arabic placeholder,
   which says "builds" where `/contact` says "makes". E8 (forms config) makes this table
   editable, with these values as its defaults.
5. **aboutIntro's tag and heading are `notVerbatim`.** The design assumes that storing a
   built-in value as content renders the same thing. That holds for every field of every
   type but two. aboutIntro's built-in tag names the studio through `%brand%`, and its
   built-in heading bolds a `<b>` run. The type renders an authored tag and heading as
   plain text: it fills no `%brand%` and splits no `<b>`, unlike joinWhy, aboutStory and
   the hero's `altLink`. So a stored copy of either would read "Why %brand%" or show the
   tags. F6 keeps that public behaviour. `SECTION_COPY.aboutIntro.notVerbatim` names the
   two fields, and the render spec checks that each one really does render differently
   when stored. The choice for AV-25 is an owner question (below).
6. **Three text fields have no built-in value, by design.** Each is listed in the unit spec
   with its reason:
   - `statistics.rating` is a claim, so it shows only where authored (design-port S3-6);
   - `clientsMarquee.note` is the founding year from the public identity;
   - `workIntro.media` is an image, whose alt text belongs to the media library.
7. **`projectCatalog` has an empty module.** The type takes no content, and its words are
   the filter bar's `FILTER_STR`, which it shares with the in-page script. The module
   exists so that every type has one, and it says that it is empty.
8. **Patterns instead of template literals.** `%brand%` (`fillBrand`) and `{name}`
   (`fillTokens`) are filled by the component, with function replacements, so a brand is
   never read as a `$&` pattern. The Join bands' `withBrand` (`src/lib/sections/join.ts`)
   delegates to `fillBrand`, and its `BRAND_TOKEN` is `copy/text.ts`'s `BRAND`, so there is
   one token and one filler. On `main` it was a string `replaceAll`, so a brand holding
   `$&`, `$'`, `` $` `` or `$$` displayed wrong on `/join`. The same render test found the
   consent line's `{brand}` (`recruitmentConsent`, `packages/consent/recruitment.ts`) filled
   the same way; it now uses a function replacement too, with its wording and version
   unchanged. `tests/render/sectionCopy.spec.ts` renders the bands that name the studio
   under a brand made of replacement patterns. The Arabic founding year is still written
   in Arabic-Indic digits by the component (`arabicIndic`). The copy holds the pattern,
   never a converted number.

9. **Some fields are stored together, not one by one.** The design's test (empty content
   equals the copy module) holds for a whole look, but an editor that stores only what
   differs stores fields, and an accent range counts the words of its own heading. Every
   type whose accent is a range over a heading renders an authored heading with only an
   authored accent (none when none is stored), and seven (the hero, the discipline cards,
   hello, the three Join bands and the services proof line) ignore an authored accent
   stored without its heading. That
   public behaviour is kept: an authored heading never inherits a range that counts other
   words. Instead `SectionCopy.together` declares the groups (`heading` + `accent` on 16
   types, `line` + `lineAccent` on statistics, `quotesHeading` + `quotesAccent` on proof,
   `headline` + `accentFromEn` + `accentFromAr` on the hero), and the guarantee is stated
   as it holds: a whole look, or any one unit (a group, or another field alone) stored at
   its built-in value, renders the bytes of no content. E1 stores a group whole whenever
   one of its fields differs. (`contact`'s accent is a phrase and `slogan`'s an index read
   apart from its text; the spec shows neither needs a group.)

## Removed exports

All moved, none changed in wording:

- `DISCIPLINE_BAND_COPY` (`src/lib/services/cards.ts`);
- `EXPLORER_COPY` (`src/lib/services/explorer.ts`);
- `SERVICES_PROOF_COPY` (`src/lib/services/proof.ts`, deleted);
- `HELLO_COPY` and `SERVICE_HELLO_LEAD` (`src/lib/sections/hello.ts`);
- `JOIN_WHY_COPY`, `JOIN_STEPS_COPY` and `JOIN_APPLY_COPY` (`src/lib/sections/join.ts`).

Nothing outside the section components and their unit specs imported them.

## Left for later slices

- The page editor's use of the copy (prefill, "Reset to built-in", storing only what
  differs, each `together` group whole) is E1 (AV-25). `src/lib/admin/sectionUi.ts` still
  quotes four of these defaults in English help text (the cards' hint, the services
  statement, the explorer's button and joinWhy's tag). AV-25's prefilled fields replace
  that text.
- The visual capture diff that AV-23 lists under its tests is AV-34. The served-html and
  page e2e suites run in CI and need no change.

## Owner questions

- **aboutIntro, authored tag and heading.** Should an authored aboutIntro tag fill
  `%brand%`, and an authored heading bold a `<b>` run, as joinWhy, aboutStory and the hero's
  `altLink` already do? Yes would be a small public change, invisible for every page that
  has not authored those fields (the seeds store `{}`). After it, the editor can prefill
  both fields like any other. No would mean the editor shows them as built-in hints and
  stores nothing until they are changed, and an edited heading loses its bold run. F6
  ships the no-change default.
