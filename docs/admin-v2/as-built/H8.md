# H8: RLS on every telemetry partition, and SELECT only where staff only read

- **Lane:** hotfix (planned as the partition hardening "H7"; renumbered when the singleton fix
  took H7)
- **Design:** none (a Supabase linter finding). As planned: RLS + FORCE on every telemetry
  partition, the roll-forward doing the same for new ones and revoking the API roles, pgTAP
  asserting it
- **PR:** #51, merged as `65dd855` on 2026-10-08
- **Migrations:** 0037 (`0037_partition_rls_and_read_only_grants.sql`), applied to production
  before the merge

## As built

**Partitions (as planned).** `CREATE TABLE ... PARTITION OF` copies neither the RLS flags nor
the policies, so every monthly partition of `analytics_events` and `web_vitals` (0002's, and
each one `app.ensure_telemetry_partitions()` had made since) had RLS off. Nothing was exposed,
since 0011 revoked `anon` and `authenticated` on them, but the GRANT layer was the only one,
and the Supabase linter flagged every partition. 0037 enables and forces RLS on every current
child of both parents (found through `pg_inherits`, the default partitions included) and
revokes all from `public`, `anon` and `authenticated`; the roll-forward now does the same to
each partition it creates (its body and ACL kept, the change additive). There is no policy, so
a role without BYPASSRLS that names a partition reads nothing. Reads and writes through the
parents are unchanged: Postgres applies the parent's privileges and policies to rows reached
through it, and RLS does not govern dropping a partition.

**Read-only grants (beyond the plan).** 0011 §5d granted `authenticated` SELECT on the tables
staff only read, but never revoked Supabase's bootstrap grant of ALL, and production held it:
INSERT, UPDATE, DELETE and TRUNCATE. RLS was the only layer in front of the first three, and
on `profiles` its FOR ALL admin policy let an Admin token rewrite any column (`tenant_id` and
`locked_until` included) past the audited users endpoint; TRUNCATE is not subject to RLS at
all. The code was checked first (`src/`, `scripts/`, every SECURITY INVOKER function and
trigger): every write to these tables is the service role's or a SECURITY DEFINER function's,
except the users screen's PATCH, which updates `profiles.role`, `is_active` and `display_name`
through the staff session. So on all eight tables (`analytics_events`, `web_vitals`,
`rollup_daily_pageviews`, `search_queries`, `consent_log`, `notification_log`, `tenants`,
`profiles`):
- `anon` and PUBLIC hold nothing;
- `authenticated` holds SELECT, plus UPDATE on those three `profiles` columns;
- `service_role` holds SELECT, INSERT, UPDATE and DELETE, plus USAGE on the three bigserial
  sequences, stated rather than inherited (P-14).

The migration was renamed to cover both halves.

**`tenants_admin_write` dropped.** Nothing in the app writes `tenants`, and 0001's FOR ALL
policy let an Admin token delete its own tenant row, which every tenant-scoped table cascades
from. The GRANT layer already refused after 0037; with the policy gone, RLS refuses on its own.

**Production.** Checked read-only before (all eight tables held the staff write privileges)
and read back after applying: every partition RLS enabled and forced, no staff write privilege
on the eight tables, no write policy on `tenants`. A Worker rollback across #51 is safe
(launch runbook §10).

**Tests and docs.** pgTAP `telemetry_partitions.test.sql` and
`grants_read_only_tables.test.sql`. CLAUDE.md §3 Pillar 1 (grants are stated, never inherited)
and Pillar 4 (partitions), and `docs/retention.md`, record it.
