## What was built

**Capture (G1a, public).** `packages/schemas/analytics.ts` holds the closed click vocabulary
`CTA_IDS` (`whatsapp`, `email`, `skip_to_inquiry`, `start_project`, `language_ar`,
`language_en`, `discipline_card`, `project_card`, `contact_link`; no `phone`: the site renders
no `tel:` link), `INQUIRY_CTAS`, the service and contact path patterns, and
`AnalyticsEventSchema` as a strict discriminated union (`pageview` and `search` with no props,
`cta_click` with `{ cta }` from the vocabulary, `service_interest` with exactly one of
`{ discipline }` or `{ service }`, slugs `^[a-z0-9-]{1,64}$`; anything else is a 422).
PageView's script moved into `src/lib/client/analytics.ts` (an external module, never inline:
CSP): the page view as before, one delegated `click` listener for `[data-track]` (once per id
per page view, never inside a form) and a `bs:interest` listener the /services explorer
dispatches when the visitor opens a panel (a card, a tab, prev/next, a hash they navigate to)
or chooses a service, never for the panel a URL opened at load. Nothing is sent without
analytics consent (the cookie, then `hasConsent` again at the ingest); nothing new is stored
(the same per-tab `bs_sid`). The `data-track` attributes sit in `SiteHeader.astro` (the key
link, the menu's links to /contact through `trackHref`, the language link), `SiteFooter.astro`,
`sections/Hero.astro` (the `skipLink` pill), `service/ServiceFab.astro`,
`sections/ServiceExplorer.astro` (the start-a-project CTA), `sections/ContactChannels.astro`,
`sections/LeadBand.astro`, `sections/ServicesOverview.astro` (discipline cards),
`portfolio/ProjectCard.astro` and `sections/SelectedWork.astro`. **Public Tier A HTML changes
by those attributes only:** the F6 render snapshots (`sections.spec.ts.snap`,
`siteChrome.spec.ts.snap`) equal `main`'s with every `data-track="…"` removed (96 and 48
attributes; checked with a strip-and-compare script), and `served-html.e2e.ts` is a
banned-pattern scan with nothing to regenerate. `tests/lib/analyticsVocabulary.spec.ts` holds
`CTA_IDS` equal to the ids the components render (each one rendered), `INQUIRY_CTAS`, the path
patterns, the goal metrics and the time zones equal to 0071's literals, and no `data-track` on
a form control.

**The migration (`0071_stats_v2.sql`).**
- An index on `analytics_events (occurred_at)` on the partitioned parent (every partition, the
  default and future ones included; postcondition and pgTAP).
- **Raw telemetry is the service role's alone (D6):** `analytics_events_read` and
  `web_vitals_read` dropped, everything revoked from PUBLIC, anon and authenticated on both
  parents and every partition; the check is a function (`app.raw_telemetry_exposure()`, no API
  role executes it) that the postcondition and pgTAP share, so pgTAP can grant a privilege back
  in a rolled-back transaction and see the check fire. No deployed code reads either table as a
  person: the ingest writes with `serviceClient()` (`src/lib/data/telemetry.ts`), and
  `tests/lib/rollupOnly.spec.ts` holds every admin file to the rollups (re-checked after
  merging R5 and G2: still only the ingest names them). `grants_read_only_tables.test.sql`'s
  eight staff-read tables became six; `telemetry_partitions.test.sql` reads partitions as the
  service role.
- `rollup_daily_visits`, `rollup_daily_events`, `rollup_hourly_pageviews` (whole UTC hours, a
  CHECK) and `rollup_minute_activity` (whole UTC minutes, `top_paths` at most ten): derived
  rollups shaped like `rollup_daily_vitals` (U2's §8 departure: keyed by what they aggregate,
  no id or actor columns), RLS ENABLE + FORCE, one read policy each (the tenant predicate, then
  `app.role_analytics_read` on the token's role), staff SELECT, the service role the four
  writes, nothing else; postconditions under both regimes, MAINTAIN on 17.
- `app.rollup_visits(p_days)` (definer, empty search_path, 60 s): whole UTC days, every tenant,
  SET upserts that skip unchanged rows, window rows it no longer produces deleted, 400 days
  kept; per tenant, day and type the 100 busiest keys keep a row and every event counts in
  `'*'`. pg_cron `rollup-visits` at `4-59/15 * * * *` (offset from `rollup-pageviews`), and a
  90-day backfill at the push.
- `app.rollup_realtime()` (definer, empty search_path, 20 s): the last three complete minutes
  from the last eight minutes of raw rows through the new index, one statement (no temporary
  table: it runs 1,440 times a day), a minute with neither views nor anyone active writes no row
  and loses one it had, 48 hours kept. pg_cron `rollup-realtime` every minute; and
  `cron-history-purge` (`40 3 * * *`, seven days of `cron.job_run_details`) when the migration
  role may delete there, else a NOTICE (the runbook's).
- **Goals (G1c):** `app.role_analytics_goals` (Admin, SEO; its `HELPER_CAPABILITY` line in
  `tests/authz/sqlHelpers.spec.ts`), `public.analytics_goals` (name 1 to 80 plain characters,
  a metric from a closed list, `cta` only for a click goal, a target of 1 to 1,000,000,
  `version`; BEFORE triggers in name order: actor, `updated_at`, the version bump; the
  20-per-tenant limit is the one AFTER INSERT trigger, under a per-tenant advisory lock, 23514
  `analytics_goals_limit`), the JWT-layer policies
  (read on `analytics.read`, writes on `analytics.goals`) and a RESTRICTIVE live layer per
  command (`app.live_role()`), staff SELECT and DELETE with column INSERT (tenant and the four
  fields) and UPDATE (the four fields).
- Readers (INVOKER, empty search_path, authenticated alone, the empty shape for another tenant,
  22023 for a bound): `visit_summary`, `event_summary`, `busy_hours` (24 rows, local hours of a
  zone from 0035's allow-list), `realtime_summary`, `goal_progress` (this calendar month in UTC
  days; inquiries are non-spam leads this month, only for a role that works leads, else null).

## Rule 5: readers whose result grows

None: 0071 adds readers, changes none, and the deployed Worker never calls the new ones. Between
the push and the deploy the deployed Worker reads `pageview_summary`, `pageview_paths`,
`search_summary`, `vitals_summary` and `content_health` exactly as before, and its ingest writes
`analytics_events` as the service role, which keeps its grants. The one narrowing (staff lose
SELECT on raw telemetry) has no deployed staff reader (above). The dashboard's layout schema
gains a widget id (`realtime`); stored layouts are written only after the deploy, and the
deployed `readDashboardLayout` drops an id it does not know.

## Departures from the design, and why

- **One PR and one migration for G1a, G1b and G1c** (the owner's folded-PR decision); the
  number is assigned at merge.
- **No help-set restatement; the guide waits as a file** (H11, the catalog, replaces rule 1).
- **The goals card saves through its own four-field form, not `EditorForm` + `useEntitySave`**:
  a goal is saved at once with no autosave, draft or release (P-3), the C4b manual-lead pattern;
  recorded in deviations.md.
- **The goals config is not in `RESOURCES`** (no list screen, header search or editor page), as
  the brief allowed; its activity-log words are `EXACT` entries (kind `settings`).
- **A goal's PATCH sends the whole goal and its version** (`GoalUpdateSchema`), so the pairing
  rule (`cta` only for a click goal) is judged on what will be stored.
- **The Realtime tab is one island rendered on the server first**, its per-minute chart drawn by
  the island from `barsGeometry` (the same geometry as BarsV) without value labels over the 30
  bars (the table has every number), so an update changes text and attributes only.
- **The live dot pulses three times (under five seconds, WCAG 2.2.2) each time figures arrive**,
  not forever: the admin has no `body.motion-paused`, and admin.css's reduced-motion block stops
  it there.
- **BarsV gained `highlight` and `highlightSeries`** (the busiest hours), an optional addition
  to the shared chart; the funnel's lost part is a tint of `--ad-warn` mixed in stats.css (no
  new token: decoration, the words carry it).
- **`app.rollup_realtime` has no temporary table** (the brief left the shape open; the job runs
  every minute).

## What the self-review found and fixed

- **A cross-tenant oracle in the goals limit.** The brief's limit was a BEFORE INSERT trigger,
  which runs before RLS's WITH CHECK: another tenant's admin inserting a goal that names this
  tenant got 23514 when this tenant had 20 goals and 42501 when it had fewer. The limit is now
  an AFTER INSERT row trigger (it runs only once RLS accepted the row; the count then includes
  the new row, so the test is `> 20`), a postcondition holds it there, and
  `stats_goals.test.sql` gains the assertion (it fails on the BEFORE version: checked on the
  PGlite replay).
- **The minute rollup made a temporary table every minute** (1,440 catalog writes a day); it is
  one statement now, with the same results (`stats_realtime.test.sql` unchanged and green).
