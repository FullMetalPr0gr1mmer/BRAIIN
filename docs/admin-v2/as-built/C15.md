## Plan (written before building; kept current)

### Who

bulk capabilities), with the matrix invariant `crm.import ⇒ crm.contacts` (an import makes
contacts) and its one helper `app.role_crm_import` (`tests/authz/sqlHelpers.spec.ts`).
ROLE_CAPS, CLAUDE.md §5, architecture §3.4 and §9.3, the label and the Leads group of the roles
matrix, in small separate hunks (other slices touch the same files in parallel).

### The Free plan's 10 ms of CPU decides the shape

A row costs the Worker about 40 to 60 µs (parse, checks, an AES-GCM encrypt and an HMAC per
e-mail and per phone, `scripts/bench-lead-export.mjs`'s measures: about 9 µs a crypto call with
keys imported once). 5,000 rows in one request would be about 250 ms of CPU, which the Workers
Free plan stops at 10 ms (error 1102, an attempt with no outcome). So the import is a **batch
of pieces**:

1. **Open** (`step: 'open'`): the Admin confirms the lawful-basis statement; the browser sends
   the file's size and its number of rows (≤ 2 MB, ≤ 5,000, refused otherwise). The Worker
   rechecks the profile live, claims the import's own ledger key (`crm-import`, 5 an hour per
   person, 10 per tenant, fail-closed), writes the **attempt** audit row (fail-closed: no row,
   no import), and opens a batch row (`crm_import_batches`) through a service-role door that
   checks the actor live. Any open batch of the same Admin is stopped first, with its outcome.
2. **Rows** (`step: 'rows'`, up to 50 rows a request): the browser cuts the file at record
   boundaries and sends each piece as CSV text with the heading row. The **server parses each
   piece itself** (the same parser), maps the headings, checks every row, encrypts and indexes
   the e-mail and phone, and calls the door, which checks the batch is the actor's, open and
   younger than two hours, keeps the batch's running totals under 5,000 rows and the byte
   ceiling, dedupes and inserts. A lying browser can mislabel only its own report: every
   value is checked again on the server, the totals are the database's.
3. **Finish** (`step: 'finish'`): the door closes the batch; the Worker writes the **outcome**
   audit row with the counts only (rows, added, already contacts, repeated in the file, phone
   matches, not imported, the count per lawful basis).

### The file

- CSV, UTF-8 (a BOM is fine), the heading row first; `,`, `;` or tab as the separator (read
  from the heading row). At most 2 MB and 5,000 people; blank rows are skipped.
- Headings (English, or Arabic aliases, case and spacing ignored): `name` (required),
  `email`, `phone` (at least one per row: an import is deduped by them), `company`, `title`,
  `city`, `country` (two letters), `language` (`en`/`ar`), `stage` (lead, client, past,
  partner), `tags` (separated by `;` or `|`, at most 10), `lawful_basis` (required:
  `consent`, `contract`, `legitimate_interest`, `legal_obligation`). Other columns are named
  by number on the screen and left out (never sent, never stored). A heading twice, or no
  `name` or `lawful_basis` column, refuses the file.
- A row is refused (by its number only, with a reason in plain words, never its content)
  when its name is missing, a value is too long or has control characters, a text starts with
  `=`, `+` or `@` (a spreadsheet would run it as a formula on a later export), the e-mail or
  phone cannot be read, it has neither, the basis, stage, language or country is unknown, or
  it has more than 10 tags.
- **Dedupe by blind index:** a row whose e-mail is a contact's already, or (with no e-mail)
  whose phone is, is "already a contact" and changes nothing; one that repeats an earlier row
  of the same import is "repeated in the file" (with that row's number); one with a new e-mail
  whose phone another contact holds is added and listed as a "phone match" to check. The
  e-mail check runs under the link's own per-address advisory lock
  (`app.crm_email_holder`), so an import and an inquiry cannot both make a contact for one
  address. Importing the same file again adds nobody twice.
- An imported contact: `source = 'import'`, created by the Admin, its channels `source =
  'import'`, the first of each kind primary, stage `lead` unless given, language `en` unless
  given. Its retention clock starts at the import (`last_activity_at`), as a contact added by
  hand does; never an orphan (a person made it).
- **The lawful basis per row** is stored in `crm_contact_imports` (one row per imported
  contact: the batch, the file row number, the basis), deleted with the contact (retention,
  erasure, a merge's survivor). Staff holding `crm.contacts` read it (RLS + live check).

### SQL (0139)

- `app.role_crm_import(r)`.
- `crm_import_batches`: tenant, `created_by` (a composite key to profiles, SET NULL), the
  attestation version, the declared rows and bytes, the running rows and bytes, the counts,
  the count per basis (an object of known keys), status (open, done, stopped), stamps.
  RLS ENABLE + FORCE; SELECT for `crm.import` holders with the tenant predicate first and a
  RESTRICTIVE live check; no staff write; the service role reads and writes. No personal
  data (counts, the Admin's id).
- `crm_contact_imports`: tenant, contact (composite key, CASCADE, unique), batch (composite
  key), the row number, the basis. RLS ENABLE + FORCE; SELECT for `crm.contacts` holders,
  tenant first, live check; no staff write.
- Doors (SECURITY INVOKER, the service role only, each checking the actor live through the
  definer `app.crm_import_actor_ok`: active, unlocked, of the tenant, holding `crm.import` and
  `crm.contacts`): `public.crm_import_open`, `public.crm_import_rows`,
  `public.crm_import_finish`. Answers are counts and row numbers only.
- Postconditions for both grant regimes (P-14).

### Worker

  with limits, the heading map, the piece serialiser.
- `src/lib/crm/importRows.ts` (server): the row checks (codes only), the sealing with keys
  imported once a request (`blindIndexKey` in `blindIndex.ts`, `encryptPII` taking a
  `CryptoKey`), the door's answer mapped to row numbers.

- `POST /api/admin/crm/contacts/import` (`crm.import`): open, rows, finish as above; a body
  over its cap is refused before it is parsed; any refusal names a column number or a row
  number, never a value; nothing is logged with a value.
- `GET /api/admin/crm/contacts/import`: the last 10 batches (the screen's JSON twin).
- `GET /api/admin/crm/contacts/import/template`: the heading row as a CSV attachment through
  `src/lib/admin/csv.ts`'s `toCsv` (formula injection neutralised, the BOM), `no-store`,
  `nosniff`.
- `crm_import_batches` and `crm_contact_imports` in `FORBIDDEN_BACKUP_TABLES`; the audit
  actions `crm.import.attempt` and `crm.import.outcome` labelled.

## As built

- **Database (0139):** as planned. Six new functions: `app.role_crm_import`, the definer actor
  check `app.crm_import_actor_ok` (empty search_path, the service role's alone), the inlined
  `app.crm_import_counts`, and the three INVOKER doors `crm_import_open`, `crm_import_rows` and

  RLS ENABLE + FORCE, a read policy with the tenant predicate first and a RESTRICTIVE live
  policy each, SELECT only for staff, nothing for anon. The batch's CHECK holds its totals
  equal to the rows seen. Postconditions for both grant regimes (P-14).
- **Dedupe across pieces:** a repeat of an earlier row is found through `crm_contact_imports`
  (the batch and the row number), so a repeat in the 4,000th row of a file is named against
  its 12th even though they arrived in different pieces. A row that repeats a person who was
  already a contact before the import is "already a contact", not "repeated".
- **Worker:** the route of the plan (`index.ts`: open, rows, finish, and GET for the recent
  imports), the template (`template.ts`), `src/lib/crm/importCsv.ts` (pure, shared with the
  screen), `src/lib/crm/importRows.ts` (checks, sealing, the door's answer to row numbers),
  `src/lib/crm/importBatches.ts` (the recent imports, the counts by name), `src/lib/crm/importScreen.ts`
  (the screen's reading and pieces). `blindIndex.ts`, `hmac.ts` and `pii.ts` gained a

### Departures from the plan or the design

- **No Unicode folding of headings or values.** The plan folded "Unicode forms" (NFKC); that
  transforms digits, which P-12 forbids and `tests/lib/arabicDigits.spec.ts` refuses. Headings
  fold case, spaces, dashes, dots and underscores only; a heading typed in full-width Latin
  letters is not recognised (it is named by number and left out, as any unknown column).
- **Two byte ceilings.** The file's declared size is at most 2 MiB (`open`); the pieces' own
  bytes, counted by the server without each piece's repeated heading row, may total at most
  2.5 MiB, because the browser re-quotes the cells it sends and a quoted cell grows. A piece
  is at most 50 people and 256 KiB; a request body over 450,000 characters is refused before
  it is parsed.
- **The template is the heading row only**, with no sample person who could be imported by
  mistake.
- **A Zod failure answers "The import request was not understood."**, never Zod's own words,
  which can repeat a value.
- **`finish` is not rate-limited** (only `open` claims the ledger): it acts only on the
  Admin's own open batch and writes nothing personal.
