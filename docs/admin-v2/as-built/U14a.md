## What was built

**The database (0057).**
- `pages_tenant_id_id`, `UNIQUE (tenant_id, id)` on `pages`, for the two composite keys: a row
  names only a page of its own tenant, and its redirect only another page of that tenant,
  whoever writes it.
- `app.role_manages_visibility(r)`, the `maintenance.manage` helper (Admin, Developer),
  immutable and inlinable; `tests/authz/sqlHelpers.spec.ts` holds it to `ROLE_CAPS`.
- **`public.page_visibility`**: one row per CMS page or template ever set (no row is public,
  nothing seeded), `mode` public | hidden | link, `redirect_page_id` (hidden only; set to null
  when that page is deleted, which leaves the page hidden with a 404), `hide_from` / `show_on`
  (hidden only, in order), the templates `service` and `case_study` (public or hidden only),
  one row per page and per template. Triggers: the actor, `updated_at`, version, the guard
  (`app.tg_page_visibility_guard`, invoker: the homepage is never anything but public, 23514
  `page_visibility_home` with the admin's sentence, for every writer, the service role and the
  migration role included; and a row's page, template and tenant never change), the
  `content_versions` snapshot (`page_visibility`), and R4's release capture.
- `pages_route_slug_fixed`, `BEFORE UPDATE OF slug` on `pages` (`app.tg_pages_route_slug_fixed`,
  invoker): a page whose slug a public route renders (`PAGE_PATHS`) keeps it, no page takes one
  by rename, and a page with a visibility row keeps its slug, for every writer (23514; the pages
  resource shows it on the slug field). A setting is stored by page id but the edge enforces it
  by slug, and Content Creator may edit `pages.slug`: without the freeze, renaming a hidden page
  off its route would show the route again at the next snapshot, and swapping two slugs would
  move a setting to another page, a role without `maintenance.manage` changing who sees a page.
  Renaming one of these pages already broke its route, so nothing legitimate is lost.
- RLS ENABLE + FORCE: every CMS role reads (registry contract #1); Admin and Developer insert
  and update by the JWT role, and RESTRICTIVE by the live profile (`app.live_role()`), one
  policy each for INSERT, UPDATE and DELETE; no permissive DELETE policy and no DELETE grant;
  no anon access. Grants stated: authenticated SELECT, INSERT on the row's own columns, UPDATE
  on the mode and its extras; the service role SELECT and UPDATE; nothing for anon or PUBLIC.
- The release registry row (`page_visibility`, area settings, Admin and Developer, no delete
  roles, apply order 85).
- `app.help_article_set()` restated from 0055 (U12a's set) with one guide added, `page-visibility`
  (`maintenance.manage`, `/admin/visibility`), and seeded into every tenant.

**The edge.**
- `src/lib/visibility/routes.ts`: the seven CMS pages and the two templates by the route Astro
  matched (`/about`, `/ar/services/[slug]`...), never the path, so an encoded, doubled or
  dot-segment path gated by its route; `tests/lib/visibilityRoutes.spec.ts` holds the map to
  the files in `src/pages` (every public route gated or named as not gateable).
- `src/lib/http/visibility.ts`: KV `site:visibility`, a snapshot of what is not public by slug;
  read through a 60 s isolate memo over `SESSION.get(key, { cacheTtl: 60 })`, written through
  (the writing isolate's memo refreshed at once), failing open (a KV error keeps the last good
  snapshot and waits out the minute); `effectiveMode` (hidden only inside `[from, until)`),
  `decide` (pass, noindex, or hide: a 302 to a public or link-only page, else the 404; never a
  chain, never the page itself), `isListed`.
- `src/middleware.ts`: after the maintenance 503 and before anything renders, on every
  public request (not `/admin`, `/api`, `/healthz`, `/_image`), every method: hidden answers a
  302 (never 301, D2) to the localized target, or `next('/404' | '/ar/404')` (a rewrite: the
  404 page renders with its status and the middleware does not run again), each `private,
  no-store`, `X-Robots-Tag: noindex`, no `Cache-Tag`, through `secured()`; link only renders
  as usual (Tier A) with `X-Robots-Tag: noindex`; the snapshot rides `locals.visibility`.
- The readers (`src/lib/visibility/listing.ts`): the header and footer menus, `sitemap.xml`,
  `llms.txt` and `/api/search` list public pages only, and none of a hidden template's pages.
  With nothing hidden each returns its input as it came.

**The admin.**
- `GET`/`PUT /api/admin/page-visibility` (`maintenance.manage`): the list (every page of the map
  that has a `pages` row, then the templates with their published counts, and what the edge
  holds); the save (Zod, `packages/schemas/visibility.ts`; `liveRecheck`; the homepage refused
  422 with "The homepage cannot be hidden. Use maintenance mode instead."; a redirect only to
  another page of the list; insert at version 0, else versioned, 409 when someone saved first;
  audit `page_visibility.update` with the mode and the changed field names; the whole snapshot
  rebuilt into KV; `{ setting, kvSynced, purgeTags }`). `POST /api/admin/page-visibility/sync`
  ("Sync to edge", audit `page_visibility.sync`).
- `PATCH /api/admin/pages/visibility/[id]`, the legacy toggle, is an alias over the new table
  (`navVisible: true` public, `false` link only), so Developer's §5 row works (RLS refused it
  before: `pages_write` needs `app.can_write_content()`). The Pages list loses its "In nav"
  column and the "Show in navigation" checkbox.
- `/admin/visibility`, a tab of Settings › General: the list (Visible, Hidden, Link only, the
  window's days, "Template for N services"), "Who can see <page>?" in the kit's drawer (real
  radios in a fieldset with a legend; the hidden extras: where the old link sends visitors, the
  homepage first, and two optional Riyadh days; the template note; the homepage's other modes
  disabled with the refusal), a kit confirm ("This changes the live site within a minute."), a
  toast, the `kvSynced: false` note, and the edge's status line with "Sync to edge". Its own
  sheet, `public/styles/admin/visibility.css`; the page-visibility guide on its head.
- A daily cron job, `visibility` (`src/lib/cron/visibilitySnapshot.ts`): the launch tenant's
  rows as the service role, rebuilt into KV; budget 5, the sum 47 of the plan's 50.
- The release registry in TypeScript: `page_visibility` bound to `PAGE_VISIBILITY`
  (`src/lib/admin/pageVisibility.ts`), a full replace like entity SEO, its tags `nav:all` and
  its page's (through `tagParent`) or the template's pages'; `derivePatch` reads it; the derived
  publish matrix gains "Release — page visibility" (Admin, Developer; architecture.md §3.4) and
  `RELEASE_ANY_CAP` gains `maintenance.manage`.

**Proof that nothing public moved.** `tests/render/siteChrome.spec.ts` was committed first,
snapshotting the header and footer (EN and AR, both variants, three paths) as they stood on
main; every later render, with no snapshot, an empty one or one about pages neither menu links,
equals it. `tests/seo/visibilityDiscovery.spec.ts`'s snapshot of the sitemap and llms.txt was
written by main's versions of the two routes. `tests/lib/middlewareVisibility.spec.ts` renders
every gated route with no rows and with unrelated rows and holds status, headers and body
equal. The public client JS is unchanged (the gate is server code; the island is an `Admin*`
entry). The e2e `with nothing hidden, every gated route renders as seeded` checks the real build.

## Departures from the design, and why

1. **The release capture trigger and the service role's UPDATE.** The brief left capture and the
   guard to "R4/R5 later", but R4 (0051) has merged and its contract covers every registry
   table: one capture trigger each (`snapshot_coverage.test.sql` checks it for every row), and
   the service role able to read and lock every registry table FOR UPDATE (0051's
   postcondition). So 0057 creates `page_visibility_release_capture` and grants the service role
   SELECT and UPDATE, not SELECT alone.
2. **`id` in authenticated's INSERT grant.** A release's create names the id its draft
   pre-allocated (0051 inserts `id` as the publisher), so the column grant includes it.
3. **Three RESTRICTIVE live policies, one per command.** A policy names one command or ALL, and
   ALL would narrow SELECT too (Content Creator and SEO must read).
4. **`redirect_page_id is null or redirect_page_id <> page_id`**, not `is distinct from`: a
   template row has both null, which `is distinct from` refuses.
5. **The guard also fixes a row's target.** A row is about one page or template for good; the
   column grants already keep staff from moving it, and the guard keeps every other writer.
6. **A hidden template may also redirect** (the prototype offers the select for templates too):
   templates still take public or hidden only (D1).
7. **The TS registry entry is a new kind, `pageVisibility`,** bound to `PAGE_VISIBILITY`, not a
   resource config: a resource config would also be a generic CRUD route and editor. The
   release tests read it like entity SEO's (a full replace).
8. **`navVisible` stays a key of the pages resource** (only the list column and the checkbox
   go): it maps to `nav_visible`, which 0038's page row classifies as writable; dropping it from
   `fields` would drift the TS registry from the SQL one. Nothing sends it and nothing public
   reads the column; a contraction drops both.
9. **The alias's `version`** is the setting's own (0 while none), as on the screen's route, not
   the page's; it audits `page_visibility.update` (`via: 'nav_visible'`) and re-reads the person
   too. `page.visibility`'s label stays for the rows already written.
10. **`src/pages/search.astro` is unchanged**: it is a shell whose results come from
    `/api/search`, which filters them; `/api` is not gated by the middleware, so the endpoint
    reads the snapshot itself (the same memo).
11. **No `useEntitySave`.** The drawer is a radio group with a confirm, saved to a custom route
    that takes a target and returns `kvSynced`; it is not a field-kit editor of a resource or a
    singleton, the two targets the hook knows.
12. **The e2e is one file, `tests/admin/visibility.e2e.ts`,** not `tests/e2e/visibility.e2e.ts`:
    it needs the Admin's session the admin harness creates, and it hides real pages on the one
    preview every spec shares, so `playwright.config.ts` runs it as its own project after
    `chromium` and `admin`, and it puts every page back to public at the end.
13. **A menu item that leaves takes its children with it** (they sit under it); a child of a
    hidden template leaves on its own.
14. **The snapshot holds only what is not public**, with `builtAt` for the status line; the
    status line compares the edge's count with the table's.
15. **The cron resolves the launch tenant** (`resolveLaunchTenantId`) before reading: the key is
    the single tenant's, as `site:redirects` is. One more subrequest: budget 5, sum 47.
16. **The purge tags use the discovery files' route tags** (`route:sitemap`, `route:llms`), the
    ones those responses carry.
17. **With the service template hidden, llms.txt's Services section reads "(none published)"**
    (its existing empty state).
18. **The route-bound slugs are frozen** (`pages_route_slug_fixed`, a pre-merge review finding):
    the design keyed settings by page id and the edge by slug without saying what holds the two
    together; the freeze is what does, in the database, for every writer.

## Not done here (as the brief says)
- The password mode, its secret table, cookie, unlock route and the `page_sections` fence: U14b.
- Staging in releases (R3), the re-sync after apply and rollback and the purge (R7).
- Hiding one service or project (its own status), blog posts, legal pages and custom pages
  (E11); links to hidden pages inside content (Site health, later).
- The dashboard's "N pages are not public" (U1) and Site health's indexable count (U2) read this
  table later.
