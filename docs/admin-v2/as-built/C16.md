## Plan (written before building; kept current)

Status: built (2026-11-12); held. See "As built" below.

### Who

A new capability, **`crm.files`** ("CRM — contact files (add, download, remove)"), **Admin
only**: Developer none (owner default O-7, as every `crm.*`), Sales none (the brief's default:
C10b, built in parallel, gives Sales contacts and tasks; files are not in that grant unless
C10b's design says so, and its row here stays ❌). `crm.files ⇒ crm.contacts` (a file is about
a contact; matrix.spec). One SQL helper, `app.role_crm_files` (sqlHelpers.spec parity).

### SQL (0140)

- `public.crm_contact_files`: id, tenant_id, contact_id (composite key to the contact of its own
  tenant, ON DELETE CASCADE), `object_path` (`<tenant>/<contact>/<random uuid>.<ext>`, a shape
  CHECK and the tenant prefix; never the uploaded name), `name` (what staff see: 1 to 120, no
  control character, no slash), `content_type` (the five sniffed kinds), `bytes` (1 to 10 MiB),
  the extension held equal to the type, `created_at`, `created_by`. Unique object path.
  RLS ENABLE + FORCE; a read policy through `app.role_crm_files` (tenant predicate first) and a
  RESTRICTIVE live check for all commands (H16). Grants stated (P-14): staff SELECT every
  column but `object_path` (a column grant); no staff INSERT, UPDATE or DELETE (the service
  role's doors write); the service role SELECT, INSERT, DELETE (no UPDATE: a file row is
  immutable).
- Doors, SECURITY INVOKER, executable by the service role only, each checking the acting
  profile live in SQL (`app.crm_files_actor_ok`: active, unlocked, of the tenant, holding
  `crm.files` and `crm.contacts`): `public.crm_file_add(p_tenant, p_contact, p_file, p_actor)`
  (the contact must be the tenant's and not a merge tombstone; at most 20 files a contact,
  under a per-contact advisory lock, 23514 naming `crm_contact_files_cap`; the path must name
  this tenant and contact) and `public.crm_file_remove(p_tenant, p_contact, p_file, p_actor)`.
- A file added is the contact's activity (as a note is: a definer AFTER INSERT trigger calls
  `app.crm_touch`); removing one is not.
- `app.crm_contact_is_orphan` restated (C8's copy plus `-- C16` lines): an auto-contact with a
  file is not an orphan (a person added it, as a note or a channel a person added).
- `public.crm_file_orphans(p_older_than_minutes, p_limit)`: objects in the bucket, in the
  Worker's own shape, older than the grace, that no row names (service role only; `storage`
  resolved at run time, as 0029's `application_orphan_cvs`).
- The bucket `crm-files`: private, 10 MiB, the five types; a RESTRICTIVE belt on
  `storage.objects` for anon and authenticated (as 0029's). Postconditions for both grant
  regimes.
- No new timeline kinds: `crm_contact_events.kind` is a CHECK list that C11, C12 and C15 may
  restate in parallel; a file is in the audit log and its own card instead (departure 1).

### Worker

| Route | Capability | Order | Audit |
|---|---|---|---|
| GET `/api/admin/crm/contacts/[id]/files` | crm.files | the contact (RLS, 404), then its files as the caller (newest first, safe columns) | `crm.file.list` (queued) |
| POST `/api/admin/crm/contacts/[id]/files` | crm.files | length ≤ 10 MiB + form overhead (411/413) → live recheck → the contact (404) → the form (a file and its name) → the bytes sniffed (422 with plain words) → limit (`crm-file-upload`, 60 a day per person, 200 per tenant) → the object (service role, the sniffed type) → `crm_file_add` (refused: the object removed again) | `crm.file.upload` (queued, ids, kind and size; never the name) |
| GET `/api/admin/crm/contacts/[id]/files/[fileId]` | crm.files | live recheck → limit (`crm-file-download`, 60 an hour per person, 120 per tenant) → the row as the caller (404) → its path (service role) → audit **written** (fail-closed) → the object → `attachment`, `nosniff`, `no-store`, CSP `sandbox` | `crm.file.download` |
| DELETE `/api/admin/crm/contacts/[id]/files/[fileId]` | crm.files | live recheck → the row (404) → attempt audit **written** → the object first → `crm_file_remove` → outcome | `crm.file.delete.attempt` / `.outcome` |

- **Person erasure** (C6's `POST …/[id]/erase`, a small hunk): after the attempt audit and
  before `crm_erase_person`, the person's file objects are removed (the service role lists the
  contact's and its tombstones' paths), then their rows; an object that cannot be removed stops
  the erasure (nothing else erased; the outcome audit says `files`). The preview counts them
  (`files`) and the dialog says so.
- **Retention:** a contact deleted by `app.purge_crm` (pg_cron) takes its file rows by cascade;
  their objects are then orphans, which the sweep removes (below). Object first is kept
  wherever the Worker deletes (removal, erasure); the database-side purge cannot call the
  Storage API, so the sweep follows it.
- **The sweep:** `cron:crm-file-orphans` in the every-10-minutes schedule (the daily schedule's
  budget is exactly 50): one RPC, one removal, a log line only when it found something or
  failed. Budget 1 + 1 + 2.
- Strict Zod in `packages/schemas/crmFiles.ts`; the sniff in `src/lib/crm/fileSniff.ts` (PDF and
  .docx through the Join sniffer, PNG, JPEG and WebP by their bytes); storage and paths in
  `src/lib/crm/files.ts`.

### Departures from the plan or the design

- **No timeline kinds for files** (as planned): `crm_contact_events.kind` is a CHECK list that
  C11, C12 and C15 may restate in parallel. A file's add, download and removal are in the audit
  log and on the card instead; a file added still moves "last activity".
- **Upload and list audit rows are queued, not fail-closed.** The download and the removal
  write theirs first and refuse without it (the CV pattern). An upload stores personal data
  rather than releasing it, so it follows the note's way; the owner may ask for fail-closed.
- **A file stays with the contact it was added to.** C12 (merge duplicates, built in parallel)
  does not know this table: after a merge a tombstone's files are not on the survivor's card
  (the add door refuses a tombstone; the erasure does find them, through the tombstones). The
  C12 + C16 merge must move `crm_contact_files.contact_id` to the survivor in
  `crm_merge_contacts` (object paths keep the old contact's id: the path is a name, not a
  link). Recorded as owner question C16-Q2.
- **The removal deletes the object before the row** (the brief's order). If the database then
  refuses (a demotion between the live recheck and the door), the row stays without its object
  and a download of it is a 500 until an Admin removes it again; the outcome audit row says so.
