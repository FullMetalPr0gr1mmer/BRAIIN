# H10: a stale Admin token changes no profile, and an audit row names who wrote it

- **Lane:** hotfix (CRM / security lane), Wave 2's first merge
- **Design:** none as a slice. Found while planning U12 (users) and U13 (activity log); the
  fix is the database half of their briefs, built first so neither waits on it
- **PR:** number at review
- **Migrations:** 0050 (`0050_live_profiles_audit_actor.sql`), to be applied to production
  before the merge

## As built

**The defects.** RLS reads the role from the access token, which lives up to an hour.
- `profiles_admin_write` (0001, FOR ALL) admits any token whose claim says admin, and 0037
  grants `authenticated` UPDATE on `profiles.role`, `is_active` and `display_name`. A
  demoted, deactivated or locked Admin could therefore, until the token expired, write
  `profiles` at PostgREST directly: promote or reactivate itself (and the access-token hook,
  which stamps the role from the profile, would carry that into every later token), or
  change anyone else. Nothing audited it.
- `audit_insert` (0002) lets any staff token insert a row with whatever `actor_id`,
  `actor_role` and `created_at` it sends, and the chain trigger hashed those values: a
  forged, backdated row naming a colleague verified like any other.

**Profiles.** Three RESTRICTIVE policies, TO `authenticated`, one per write command
(`profiles_live_update`, `profiles_live_insert`, `profiles_live_delete`): the tenant predicate
first, then `app.role_manages_users((select app.live_role()))`. `app.live_role()` (0033) is the
profile's role read at query time, null unless the profile is active, unlocked, in the token's
tenant and agrees with the token. `app.role_manages_users` is the users.manage helper, held
equal to `ROLE_CAPS` by `tests/authz/sqlHelpers.spec.ts` (U12a was to add it; it lands here
and U12a reuses it). INSERT and DELETE have no staff grant; their policies are the second
layer. SELECT is untouched: the live read of colleagues' rows is U12a's.

What still works, checked: a live Admin on the users screen (its PATCH writes through the
Admin's session, so the live check applies to it, and `liveRecheck` refuses a stale Admin
before it gets there); renaming yourself (`update_my_profile`, a definer running as its owner,
outside these TO authenticated policies, with its own live check); the sign-in's lockout RPCs
(definers); the access-token hook (`supabase_auth_admin`, SELECT); the invite (service role).
The policies' `live_role()` reads `profiles` from inside a definer, under SELECT policies
only, so nothing recurses.

**The audit actor.** `app.tg_audit_actor()` (SECURITY INVOKER, empty search_path, no API role
executes it) and the trigger `audit_log_actor`, BEFORE INSERT FOR EACH ROW. When the writer
(`current_user`) is `authenticated` (or `anon`, which holds no INSERT anyway) it sets
`actor_id := auth.uid()` and `actor_role := app.current_role()`; for those and `service_role`
it sets `created_at := now()`. The service role, definers and operators keep the actor they
name: the password-reset rows (`src/lib/auth/recovery.ts`, service role) name the account,
`update_my_profile` names its caller itself, 0027's override trigger names the session user.
Every writer was checked: `writeAudit`/`writeAuditMany` (the session client, actor = the
session's user, role = the profile's), `writeAuthAudit` (service role), and the SQL inserts in
0027 and 0044. None sets `created_at`.
- **Bound, not refused (the brief's choice).** A correct caller already sends these values,
  so binding never fails one. A refusal (42501) would fail the fail-closed audited paths
  (reveal, exports, erase, notes) whenever the Worker's role and the token's differ, which
  happens in the minutes after a role change (the Worker compares the profile with the auth
  server's record, not the token: U12a); and a forger would leave no trace. Bound, the
  attempt is chained under the account that made it.
- **The token's role, not the profile's.** It is what RLS admitted, and the only role the
  database can attest for the statement; the profile's may be null (deactivated).
- **Keyed on `current_user`, not on JWT claims being present.** A definer still sees its
  caller's claims, and the service role's requests carry claims too; the writer's Postgres
  role is what tells a staff token's direct insert from trusted code.
- **Order.** BEFORE triggers on one event fire in name order, and `audit_log_actor` sorts
  before `audit_log_chain`, so the chain hashes the bound values. The chain trigger, its
  per-tenant lock, its id under the lock and its READ COMMITTED rule (0031) are not touched;
  the postconditions re-check 0031's source order and the two-trigger set. pgTAP recomputes
  each bound row's HMAC from the stored values and the Vault key: equal only if the binding
  ran first (a mutation renaming the trigger to sort after the chain fails it).

**Beyond the brief.**
- **`audit_log`'s grants, stated.** 0002 hard-revoked UPDATE and DELETE "so even the service
  role cannot tamper", and 0011 granted staff SELECT and INSERT, but neither withdrew the
  rest of Supabase's default ALL: TRUNCATE (which no policy and no row trigger sees, and which
  empties the chain in one statement), REFERENCES, TRIGGER and, on PostgreSQL 17, MAINTAIN.
  PostgREST cannot send a TRUNCATE, so a staff token could not use it, but the service-role
  key could, through any SQL path it reaches. Now revoked from every API role, then SELECT and
  INSERT granted to `authenticated` and `service_role` (the only privileges any code uses),
  and the id sequence's USAGE to the same two (never UPDATE, which is setval). The readback
  shows what production held before.
- **MAINTAIN on `profiles` withdrawn** from PUBLIC, anon and authenticated (PostgreSQL 17
  only; the word does not parse on 15). 0037 withdrew the default writes but not MAINTAIN,
  which 17 adds to the default ALL; it carries LOCK TABLE, enough to hold every sign-in up.
  Nothing in the app uses it. Found because the postcondition states every privilege, as
  P-14 asks; the readback shows what production held before.
- **The users PATCH refuses a write the database skipped** (`src/pages/api/admin/users/[id].ts`,
  `tests/lib/usersPatch.spec.ts`). RLS skips a row it will not let a session write rather
  than raising, so a refused update looked like a success: the route went on to stamp the new
  role into the person's claims with the service role (which `resolveAuthContext` then treats
  as a mismatch, locking the person out) and to audit a change that never happened. It now
  asks for the updated row back and answers 403 when none comes, before stamping or auditing.
  `liveRecheck` compares the profile with the session, not with the token, so this was
  reachable before H10 (a token whose role claim lagged) and H10's live check adds cases.

**Left open** (recorded in [deviations.md](../deviations.md), Residual risks): the Worker's
comparison against the token's claims, session revocation on a role change, the live read of
colleagues' profiles and the roles guide's sentence (U12a, 0055); the live read on
`audit_log` (U13, 0054); the remaining tables with no live check (a follow-up slice, or R14).
The roles guide (0046) still says a sign-in already handed out keeps its role for up to an
hour except on leads and applications; still true of the other tables, so it is left for
U12a's rewrite rather than restating `app.help_article_set()` here.
