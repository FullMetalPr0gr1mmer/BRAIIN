## Plan (written before the build)

Releases stay off in production until R14 (`app.release_tenants` is empty). Everything here is
inert while they are: no new markup, request or write on any admin screen, and every write path
sends exactly what it sends on `main`.

1. **The save follows the server.** A release-managed route already answers its row with a
   `draft` key (null or the pending change) when releases are on, and never when they are off.
   `useEntitySave` reads that key: present, the editor is in draft mode (it names the pending
   change on every save, `draftId` + `draftVersion`, as R3a asks); absent, it saves live, request
   for request as today. So R14's switch needs no client change, and releases off cannot reach
   draft mode. Draft mode: autosave on blur (focus leaving the form after a change), on a tab
   switch and on ⌘S elsewhere, after 800 ms idle where an editor asks for it (E1's page editor,
   which feeds the preview); a create stays an explicit Save; a value typed while a save is in
   flight is kept; the 409s R3a defines (`draft-conflict`, `draft-published`,
   `draft-discarded`, `scheduled`) each get their words and their way out; an `admin:pending`
   event tells the savebar a change was saved. In draft mode the per-item Schedule field is
   hidden and the status select is a "Visible on the site" switch (Archived too for a role that
   may archive).
2. **Badges.** A pending change is marked in the kernel lists (ResourceTable) and the
   collection lists (U7) beside the live status, and in every editor (EditorForm's draft line:
   "Unpublished changes", "New, not live yet", "Will be removed" with Undo removal, "Scheduled"
   read-only, "Changed on the live site" with the conflict panel). Rows carry `draft` only when
   releases are on.
3. **Conflicts** (R3's base rule): the editor's conflict panel (from the item's
   `draft.conflict`) and the dialog's rows (from the dry run's `conflict`) offer Keep my version
   and Use the live version (`POST /api/admin/drafts/[id]/resolve`, R3b) and Compare, a new
   read, `GET /api/admin/drafts/[id]/compare`: per conflicting column, live and yours as plain
   or bilingual text (R10's field formatter), under the person's RLS, for a role that reads the
   type.
4. **The savebar** (`AdminSavebar`, a new island in a new `admin-release` chunk group): rendered
   by AdminLayout only when the shell reads releases on (one `releases_enabled` read, CMS roles
   only, never Sales), so with releases off its markup and its JavaScript never reach a page.
   Counts by area, the waiting count, Discard (mine, or choose), Preview, Publish or Review.
5. **The publish dialog** (in the same island; also opened by an `admin:publish` event for E1
   and R13): grouped by area, every change I may publish ticked (at most 60, P-15), dependencies
   ticked from the dry run's `requires` and unticked with their dependants, waiting rows
   disabled with who can publish them, the dry run's status per row, the note, Preview
   selection (`?only=`), the results as R6 and R7 answer them; a discard mode for "Choose…".
6. **The pending summary** (R3b) gains each change's edit address and its fields in words.
7. **Draft audit** (P-5): at most one `draft_save` row per draft per person per ten-minute
   window, by the clock, not only after ten quiet minutes (autosave makes the second matter).
8. **Kit card.** `/admin/kit` gains a Publishing card (CMS roles only) drawing the savebar and
   the dialog over made-up changes, so the per-role sweep and an e2e exercise them in a browser
   while releases are off.

## What was built

### Releases off: what changes and what does not (the proof)

- **No markup, no script, no request.** AdminLayout draws `AdminSavebar` only when the shell
  read releases on (`shell.releases`, from `public.releases_enabled`, 0062: false for any tenant
  but the caller's; read for the four CMS roles only, never for Sales; a failed read is false).
  With releases off no admin page carries the island, its stylesheet rules match nothing, and
  nothing asks the release endpoints (`tests/admin/releases-ui.e2e.ts`, every role). The one
  cost is that read: one more subrequest, in the shell's parallel batch, on every CMS admin
  render.
- **Every write path sends what it sent.** The editors' mode is the server's answer (below); no
  answer carries `draft` with releases off, so every save is the live save request for request
  (`entitySave.spec` "follows the server", which pins the body's keys). The lists add a badge
  only for a row that carries `draft`, and say "removal" only when the list answer came through
  the release (`draftsInvalid`). `overlayDb.spec`, `releasePublish.spec`, `fields.e2e` and
  `singletonFirstSave.spec` are unchanged and green; `releaseOffWrites.spec` and
  `stagedKernel.spec` keep every case they had and gain the pre-merge review's: a save or a
  delete made in release mode, reaching the live path after a switch-off, is refused (below).
- **Bytes.** The pieces the lists and editors would draw ride where those already are: about
  1.0 KB gz more in `admin-ui` (every screen) and 2.7 KB in `admin-fields` (the editors), code
  that renders nothing with releases off. The savebar and the dialog are their own chunk,
  `admin-release` (14.1 KB gz with When and the review's fixes, as measured below), which no
  page loads with releases off but the kit's gallery.

### The save in release mode (`entitySave.ts`, `useEntitySave.ts`, `saveMode.ts`)

- **The mode follows the server.** `readDraft(row)`: no `draft` key is live mode (undefined),
  `draft: null` is release mode with nothing pending, a DraftMeta is the pending change (its
  id, version, op, fields, the scheduled release that claimed it, the columns live moved in,
  whether the live row is gone, whether its payload still reads). `saveModeFor` stays `live`:
  it is only the mode before the first answer. R14 switches releases on in the database and
  every editor follows; the hook no longer throws on `mode: 'draft'`.
- **Every save names its pending change** (`draftId` + `draftVersion` beside the live
  `version`; a pending create sends version 0), on the resource PATCH, the singleton PATCH and
  the entity-SEO PUT alike, as R3a and R3b read them.
- **Typed during a save, kept.** The machine keeps what the save sent (`sent`); when its answer
  lands in release mode, a field typed since stays as typed (the form stays dirty and saves
  again), everything else takes the server's row. Live mode re-seeds from the server as F5a
  built it.
- **The 409s and their way out.** `draft-conflict` (someone else saved the change): the
  conflict banner, "Reload their version"; with the server's words, a staged removal ("Undo
  the removal first") or a row gone under the change. `draft-published` / `draft-discarded`:
  the values stay, the form is on live again (its version, its stored values from the 409's
  `live` row), "This change was published while you were editing. Your edits are still here:
  save again to make them a new unpublished change." and the button reads Save again.
  `scheduled`: "This change is scheduled to go live, so it cannot be edited now. Unschedule it
  to change it."
- **Autosave (P-5).** `flush()` saves when the form holds an unsaved pending change
  (`autosaveDecision`, pure and tested): EditorForm calls it when focus leaves a control (after
  the change has landed in state) and on a tab switch, Ctrl/⌘+S saves as before, and an editor
  may ask for an idle timer (`autosave: { idleMs }`, E1's 800 ms). Never in live mode, never for
  a new record, a staged removal or a scheduled change; after a conflict or a change gone under
  the form it waits for the person (`held`); after a refused automatic save, for the next edit
  (`autoBlocked`). One save at a time: a trigger while one is on its way runs once it lands.
- After a save that came back with `draft`, `admin:pending` tells the savebar
  (`src/lib/admin/releaseEvents.ts`, with `admin:publish` for E1 and R13).
- `EntitySave`'s R12 members are optional, so a save built by hand (a test's, a screen's) is a
  live-mode save.

### The editors (`EditorForm`, `fields/DraftNotice.tsx`, `fields/VisibilityField.tsx`)

In release mode only (the save's `mode`):

- **The draft line** at the head of the form: the badge and its words ("Saved, not live yet: it
  goes live when it is published."; a new item; a removal; scheduled; a conflict with the
  fields in the editor's words), **Discard changes** (a confirm: "Your unpublished changes to
  this service will be thrown away. The live site doesn't change."; a new item's discard goes
  back to its list), **Undo removal** (no confirm: nothing is lost), and for a conflict **Keep
  my version**, **Use the live version** (R3b's resolve, per column; an edit not saved yet is
  saved first) and **Compare** (the new read: field, live now, yours, English and Arabic).
- A staged removal or a scheduled change is read only (the U8 read-only mode).
- The per-item Schedule field is gone and the status select is **Visible on the site** (Draft
  or Published) with **Archived** beside it (departure 6).
- "Saved as an unpublished change at 14:05"; "Live version N", or "Not live yet".

### The lists (`kit/PendingBadge.tsx`, ResourceTable, the collection screens)

- A row the release path read with a pending change wears its badge (Unpublished changes, New ·
  not live yet, Will be removed, Scheduled, Changed on the live site), under the name in a kernel
  list and after the item's badges in a collection list.
- A list read through the release (its answer carries `draftsInvalid`): Delete asks "Remove the
  service “…” from the site? The removal is saved as an unpublished change, and nothing leaves
  the site until it is published." and toasts the removal as saved; a staged reorder, copy or
  removal sends `admin:pending`.

### The savebar and the publish dialog (`screens/release/`, `islands/AdminSavebar.tsx`)

- **The bar** (`Savebar.tsx`, app.css 83-85): a fixed midnight pill at the bottom centre while
  anything unpublished the person may read is waiting. "You have 5 unpublished changes" and "1
  in Pages · 2 in Services · 2 in Our work · +3 waiting for someone who can publish", or "3
  unpublished changes waiting for someone who can publish them"; a reordered list counts once.
  Discard (a disclosure: "Discard my changes (k)", "Choose…"), Preview (the site with every
  pending change, a new tab) and Publish… (a role with something of its own to publish) or
  Review…. A region named "Unpublished changes"; the count is announced politely a second after
  it settles, by a status line that is in the page from the first render; the scroll port ends
  above the bar while it shows (WCAG 2.2 2.4.11); its slide-in is a transition the
  reduced-motion block drops. Discard my changes confirms (releases.md §7's words), throws away
  up to five rounds of 200, and says a failure in the bar (toasts are for success).
- **The dialog** (`PublishDialog.tsx`, the kit's Modal): "Publish to the website", "Everything
  ticked goes live together.", the changes by area (groups, not regions), each row its tick (or
  none, and "Needs an Admin", for a change another role publishes), its label in English and
  Arabic, its change badge (New, Changed, Published, Hidden, Shown, Archived, Removed,
  Reordered), "Service name, Tagline, +2 · Amal, 5 minutes ago", and what the check says:
  Checking…, Ready, a warning, an error with **Fix** (the change's editor), or a conflict with
  Keep my version, Use the live version and Compare. Every change the person may publish is
  ticked (owner default O-4), at most one release (60 changes, never splitting a row; the rest
  wait, said). The check runs on every selection (`POST /api/admin/releases/validate`, 350 ms
  after the last tick): a change the selection needs is ticked with it, "Included because
  “Sample Project” needs it"; a change the person unticked is never ticked back, and what needs
  it leaves with it, said once; a change that needs a new item a scheduled release holds says
  R11's words (`requires-scheduled`: publish it after that release, or unschedule it). Publish
  waits for a clean check; the note (at most 280); Preview selection (R9's `?only=`).
- **When** (a plain fieldset, its legend in the browser's own layout, two native radios in the
  segmented look): **Now** (the default) or **Schedule for** a day and a time, filled in with
  the first whole hour at least half an hour away, read on the studio's clock (U9's setting,
  Riyadh by default; the browser's zone plays no part: `scheduleInstant`), "Riyadh time" beside
  the time (its description). The button reads "Schedule 7 changes". A time under two minutes
  ahead or over 366 days is said under the time in the endpoint's own words before anything is
  sent ("Choose a time at least 2 minutes from now.", held equal to `SCHEDULE_COPY`), and the
  endpoint judges again on its own clock (its 422 on `scheduleAt` lands in the same place). A
  schedule is a success, so a toast: "Scheduled for 26 Oct 2026, 12:00 (Riyadh). These changes
  are locked until then." The bar then counts them as scheduled, and the dialog lists them
  locked ("Scheduled: locked until it goes live", no tick). A publish is a toast ("Published v15. The website now shows these
  changes.", or the purge's words: R7's `pending` and `failed`) unless the cache or the edge
  still owe it, when the dialog says so and stays. A 403 names the rows ("Your role can't publish
  this. Ask an Admin."), a 409 `pending-changed` reads the changes again and says so, a 422 or
  conflict lays the check on the rows, `releases-off` and `busy` say theirs: never a toast.
  Review (nothing of the person's own to publish) is the same list read only; Discard
  ("Choose…") ticks only what the role may throw away (the type's author capabilities) and
  confirms with the names of other people's changes.
- **The state** (`ReleaseUi.tsx`): the pending summary when the island loads, again after
  `admin:pending`, on focus and when the tab is shown, debounced; `admin:publish` opens the
  dialog (on an item's changes when it names one); a role with nothing of its own to publish
  gets Review.
- **The seam** (`api.ts`): one interface over the endpoints (`LIVE_RELEASE_API`: pending,
  validate, publish, schedule, discard, resolve, compare) and the kit's made-up one
  (`sampleApi.ts`, which schedules too: what it holds turns locked).
- **Ids**: every id in the dialog is its own (`useId`). With releases on, `/admin/kit` draws the
  layout's dialog and the kit card's, and the Modal keeps its body in the DOM while closed, so
  fixed ids (`pub-note`, `pub-area-pages`) would have been on the page twice.
- **The rules** (`model.ts`, pure): rows by area in the menu's order, one row per reordered list,
  the change badge from what the change stores, counts, the default selection, dependencies,
  every word.
- **Chunks.** `admin-release` (`astro.config.mjs`, priority 14, after admin-leads-lazy): the
  island and `screens/release/`, never admin-ui, never the field kit
  (`scripts/admin-bundle.mjs` check 8, `adminBundle.spec`). Each admin screen's eager graph
  counts the bar as part of the shell (the worst case: releases on).

### The server

- **The pending summary** gains four keys per change, all stored metadata or static per type:
  `status` and `visible` as stored (`payload->>status`, `payload->>visible`: the badge), `href`
  (where it is edited: a resource's own edit screen, the identity's General screen, the SEO
  screen, page visibility) and `fieldLabels` (its columns in the editor's words, from the UI
  configs through the registry's `fields`: `src/lib/release/words.ts`; `releaseWords.spec`
  holds every type's address to a page that exists and every allowlisted column to words).
- **`GET /api/admin/drafts/[id]/compare`** (`compareDraft`): the kernel admits any role that
  reads a release-managed type (the summary's gate, Sales 403), then the change's own type must
  be one the role reads (Developer reads no service: 403 naming the draft); the change and its
  live row are read under the person's RLS; per column live moved in since the change began
  (`conflicts`, R3's base rule), live now and the change's value through R10's `fieldChanges`
  (300 characters, a consent record "changed" only); a row gone is `removed`; a create or a
  removal is 422. Nothing written, nothing audited (a read).
- **A write made in release mode, after a switch-off** (pre-merge review,
  `src/lib/release/releasesOff.ts`): an editor's save in draft mode names its pending change or
  carries `staged: true`, and a list's or a drawer's DELETE read through the release adds
  `?staged=1`. The staged paths ignore the marker. With releases off, the live branch of the
  resource PATCH and DELETE, the singleton PATCH and the entity-SEO PUT refuses such a request
  (409 `releases-off`) before it reads or writes anything; no client sends the marker with
  releases off, so the live path is otherwise what it was.

### The kit's Publishing card (`/admin/kit`)

For a CMS role (never Sales): the same `ReleaseUi` in the page (`inline`) over ten made-up
changes (no person's data), who may publish each computed from `ROLE_CAPS` as the server does,
one of them conflicted, one needing another, one warned. The per-role sweep checks it at three
widths (axe, CSP, overflow, console); `releases-ui.e2e.ts` drives it.

## Departures from the design, each with its reason

1. **The mode follows the server, not `saveModeFor`** (F5a planned the function to flip at
   R14). The server already says which mode a record is in, per route; following it means a
   record is never saved the wrong way (with releases on, a live-mode form's second save is a
   409, R3a's open item), releases off cannot reach draft mode by construction, and R14 needs
   no client change. `saveModeFor` stays as the mode before the first answer.
2. **Autosave on blur, a tab switch and Ctrl/⌘+S; 800 ms idle only where asked** (README P-5,
   which wins over releases.md §7's "at least 30 s for long forms" and ui.md's "800 ms" for
   every editor). The page editor is E1's; the option is here. A create stays an explicit Save:
   nothing should be staged before the person says so.
3. **The savebar's first state is read when it loads** (ui.md §2.10: server-rendered). A
   server-rendered count needs the drafts read and up to ten archived reads (R3b) on every admin
   render, against P-15's 50 (the dashboard renders at 35); the bar is fixed, so appearing a
   moment later shifts nothing. Each CMS render pays the flag only.
4. **"Schedule for" is on the studio's clock, and the check does not carry the time.**
   releases.md §7 says "Riyadh time": U9 made the studio's zone a setting (Riyadh by default),
   and every admin date is on that clock, so the day and the time are read and named in it
   ("Riyadh time" while the setting is Riyadh). `validate` is sent without `scheduleAt`: the
   time changes nothing the check finds, and sending it would re-run the whole check (a
   check's subrequests) for every edit of the time; the dialog checks the bounds in the
   endpoint's words, and the publish request carries the time, where the endpoint checks it
   again. (As first written, before R11 was merged into this branch, this departure was "no
   When: the dialog publishes now".)
5. **No help guide, so no migration.** R12 adds no screen, and the bar and the dialog appear
   only once releases are on (R14): a guide about them now would be offered on every editor and
   be untrue there, and the `saving-and-publishing` guide's "What you save is what the site
   shows" is still true. R14 puts the publishing guide and revises that one, when both become
   true (owner question 3).
6. **Archived is offered to every role** (releases.md §7: "+ Archived for Admin"). The editors do
   not know the role (no page passes it; 56 edit pages would), and the select they replace
   offered Archived to every role with "archiving is Admin-only"; the switch says the same
   ("Off the site and kept. Only an Admin can archive."), and the server refuses it for any other
   role, staged or not (owner question 1).
7. **Compare is a new read.** The item read gives a conflict's columns only, and the dry run its
   live and base values: neither gives "yours", which releases.md §7 asks for.
8. **The pending summary grows four keys** (`status`, `visible`, `href`, `fieldLabels`): still
   stored metadata, no payload parsed; `PendingItemSchema` (strict) carries them.
9. **R3a's draft-audit rule is kept** (plan item 7 not built). R3a writes a `draft_save` row
   unless the same person amended the same change with the same op less than ten minutes before
   (P-5's "at most one per draft per user per 10 min", which holds). A clock window would also
   write one per window through a long session, but makes the route-level tests that save
   "moments ago" depend on the minute they run in; a long session is one row, and the publish
   is the record of what went live (`release.publish`). Owner question 2.
10. **Review is the dialog read only** (ui.md §2.10's separate review drawer): one list, one set
    of rows, whether the person may tick them or not.
11. **The kit's Publishing card** (not in the design): the only way to put the bar and the dialog
    in front of a browser, axe and the sweep before R14; it draws made-up changes and sends
    nothing.
12. **No bell items for releases** (ui.md AV-24): not in README's R12 row nor releases.md's R12;
    with R13's dashboard card or later.
13. **Discard ▾ is a disclosure** (a button with `aria-expanded` and a list of buttons), not an
    ARIA menu, and the dialog's areas are groups: no menu keyboard model to get half right, and
    no page landmark per area.
14. **No release-mode e2e of the editors, the lists or the real summary.** It needs releases on
    in CI, which is R14's (as R6's and R10's departures); the release mode is proven by unit and
    render tests (`entitySave.spec`, `editorForm.spec`, `pendingBadge.spec`, `releaseUi.spec`),
    the bar and the dialog in the browser on the kit card.

15. **A scheduled change says "Scheduled", not "Scheduled {date}"** (releases.md §7's per-item
    badge), in the lists, the editors and the dialog. An item read carries the claiming
    release's id, not its time (R3a's DraftMeta), so a date would cost every list read and
    every editor load one more read of `content_releases`; the time and "Unschedule" are R13's
    versions page (R11's move and cancel), and the editor says "Unschedule it to change it."
16. **"Publish now" on a scheduled release** (R11's open item) is R13's: it belongs to the
    versions page's scheduled releases, where "Change time" and "Unschedule" are.

## The R11 merge

What it changed here:

- the dialog's When (above), on R11's `scheduleAt`, `ScheduleResultSchema` and
  `RELEASE_SCHEDULE_MIN_MINUTES` / `RELEASE_SCHEDULE_MAX_DAYS`; `requires-scheduled` is shown in
