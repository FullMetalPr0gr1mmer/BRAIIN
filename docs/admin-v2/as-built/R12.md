## Plan (written before the build)

Releases stay off in production until R14 (`app.release_tenants` is empty). Everything here is
inert while they are: no new markup, request or write on any admin screen, and every write path
sends exactly what it sends on `main`.

1. **The save follows the server.** A release-managed route already answers its row with a
   `draft` key (null or the pending change) when releases are on, and never when they are off.
   `useEntitySave` reads that key: present, the editor is in draft mode (it names the pending
   change on every save, `draftId` + `draftVersion`, as R3a asks); absent, it saves live, request
   for request as today. So R14's switch needs no client change, and releases off cannot reach
   draft mode. Draft mode: autosave on blur (focus leaving the form after a change), on a tab
   switch and on ⌘S elsewhere, after 800 ms idle where an editor asks for it (E1's page editor,
   which feeds the preview); a create stays an explicit Save; a value typed while a save is in
   flight is kept; the 409s R3a defines (`draft-conflict`, `draft-published`,
   `draft-discarded`, `scheduled`) each get their words and their way out; an `admin:pending`
   event tells the savebar a change was saved. In draft mode the per-item Schedule field is
   hidden and the status select is a "Visible on the site" switch (Archived too for a role that
   may archive).
2. **Badges.** A pending change is marked in the kernel lists (ResourceTable) and the
   collection lists (U7) beside the live status, and in every editor (EditorForm's draft line:
   "Unpublished changes", "New, not live yet", "Will be removed" with Undo removal, "Scheduled"
   read-only, "Changed on the live site" with the conflict panel). Rows carry `draft` only when
   releases are on.
3. **Conflicts** (R3's base rule): the editor's conflict panel (from the item's
   `draft.conflict`) and the dialog's rows (from the dry run's `conflict`) offer Keep my version
   and Use the live version (`POST /api/admin/drafts/[id]/resolve`, R3b) and Compare, a new
   read, `GET /api/admin/drafts/[id]/compare`: per conflicting column, live and yours as plain
   or bilingual text (R10's field formatter), under the person's RLS, for a role that reads the
   type.
4. **The savebar** (`AdminSavebar`, a new island in a new `admin-release` chunk group): rendered
   by AdminLayout only when the shell reads releases on (one `releases_enabled` read, CMS roles
   only, never Sales), so with releases off its markup and its JavaScript never reach a page.
   Counts by area, the waiting count, Discard (mine, or choose), Preview, Publish or Review.
5. **The publish dialog** (in the same island; also opened by an `admin:publish` event for E1
   and R13): grouped by area, every change I may publish ticked (at most 60, P-15), dependencies
   ticked from the dry run's `requires` and unticked with their dependants, waiting rows
   disabled with who can publish them, the dry run's status per row, the note, Preview
   selection (`?only=`), the results as R6 and R7 answer them; a discard mode for "Choose…".
6. **The pending summary** (R3b) gains each change's edit address and its fields in words.
7. **Draft audit** (P-5): at most one `draft_save` row per draft per person per ten-minute
   window, by the clock, not only after ten quiet minutes (autosave makes the second matter).
8. **Kit card.** `/admin/kit` gains a Publishing card (CMS roles only) drawing the savebar and
   the dialog over made-up changes, so the per-role sweep and an e2e exercise them in a browser
   while releases are off.
