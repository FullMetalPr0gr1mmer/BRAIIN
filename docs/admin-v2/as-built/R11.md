## Plan (written before the build)

**Scope.** The server half of scheduling and the runbook's two switches; R12 draws the dialog's
"When: Now | Schedule" and R13 the scheduled and failed rows of the versions page.

1. **Schedule a release.** `POST /api/admin/releases` takes `scheduleAt` (an ISO time with its
   offset, at least 2 minutes ahead, at most 366 days): the same checks as a publish (R6:
   the drafts, every change's capabilities, the live re-read, the check over the state the
   selection leaves), then `apply_release` in `schedule` mode, which checks the person, the
   drafts and their bases as a publish does, runs the changes as a dry run (so the database's
   refusals and conflicts are known now), and only then stores the validated changes on a
   `scheduled` release and claims their drafts (read-only until the release goes live or is
   unscheduled), with a `release.schedule` audit row in the same transaction. One schedule per
   release; a rollback is published now, never scheduled. `validate` takes `scheduleAt` too.
2. **Move or cancel it.** `PATCH /api/admin/releases/[id]` (`{version, scheduleAt}`) and
   `DELETE /api/admin/releases/[id]?version=n`: version-checked, for a person who may publish
   every change it holds (P-2: an Admin always may), live re-read, and in the database
   `public.reschedule_release` / `public.unschedule_release` (service role only) check the
   person and their role against the registry again, under the per-tenant release lock, and
   audit (`release.reschedule`, `release.unschedule`). A cancelled release releases its claims.
3. **Fire it.** The minute cron (R7's schedule) first claims ONE due scheduled release
   (`public.claim_scheduled_releases`: SKIP LOCKED and a two-minute lease, so two runs never
   fire one release twice), re-checks every change's capabilities against the scheduler's
   LIVE role, then calls `apply_release` in `fire` mode with the scheduler as the publisher:
   the same function, the same apply path, the same live re-check, RLS bound as them. The
   apply re-reads the release under the lock and does nothing for a release that is no longer
   due and scheduled (a second run is a no-op). Then the release's after-effects as the system
   (R7's: snapshots, the purge, its record). A minute that fires a release spends itself on it;
   otherwise R7's purge retries run as before.
4. **Fail closed.** A scheduler no longer able to publish, a change the database refuses, a
   conflict with live: `public.fail_scheduled_release` marks the release `failed` with a code
   (never a message), releases its claims, a `cron:releases` error line; the dashboard's
   `release_failed` row (R5) and a new bell kind, `releases`, for the roles that publish one of
   its areas. A busy database leaves it scheduled for the next minute after the lease.
5. **The switches, `app.enable_releases(tenant, operator, fallback_scheduler)` and
   `app.disable_releases(tenant, operator, discard_pending default false)`.** Owner only (no
   API role holds EXECUTE, and each refuses a switched role or a role claim), audited
   (`releases.enable`, `releases.disable`), refused while a release is publishing (the
   per-tenant release lock, taken without waiting). Enable: the legacy scheduled rows that
   `app.publish_scheduled()` would have published become pending changes in `legacy_schedule`
   releases (live status from scheduled to draft), a baseline version, the flag. Disable:
   refused while pending changes or scheduled releases exist, unless the discard is named;
   with it, legacy schedules go back to their rows, other scheduled releases are cancelled and
   every pending change is thrown away; then the flag goes.
6. **Inert.** Releases stay off for every tenant until R14: scheduling and every new route
   answer 409 `releases-off` after the flag read, `apply_release` refuses `schedule` and `fire`
   for a tenant with releases off (55000), the minute cron's new claim finds nothing, and with
   the flag off every write path behaves as on `main` (proof below).

**Files.** `supabase/migrations/0107_release_schedule.sql`; `src/lib/release/schedule.ts` (the
schedule, move and cancel handlers), `src/lib/cron/releases.ts` (the fire step), `endpoints.ts`,
`apply.ts`, `afterEffects.ts` (the after-effects for a release no person published),
`versions.ts` (the release's `version`, for R13's move and cancel);
`src/pages/api/admin/releases/[id].ts` (PATCH, DELETE); `packages/schemas/release.ts`;
`src/lib/admin/notifications/releases.ts` and its kind; `src/lib/admin/auditLabels.ts`;
`docs/launch-runbook.md` (the two switches), CLAUDE.md (the Releases lane and §10).

**Tests.** pgTAP `release_schedule.test.sql` (schedule, fire, fail, move, cancel, claim, the
switches, `publish_scheduled` coordination; admin, content creator, SEO, developer, a sales
claim, anon, another tenant, inactive, locked and demoted schedulers); vitest
`releaseSchedule.spec.ts` (the routes over the PostgREST stand-in), `releaseCron.spec.ts` (the
fire step and the minute's budget), `releaseApplySql.spec.ts` and `releaseScheduleSql.spec.ts`
(the SQL's shape), `notifications.spec.ts` (the bell), authz cases for the new routes.

## What was built

- `POST /api/admin/releases` and `/validate` answer 409 `releases-off` after the flag read and

- `apply_release` refuses `schedule` and `fire` for a tenant whose releases are off (55000:

  can fire; its `publish` and `dry_run` paths are 0104's statement for statement but for a second
  read of the switch under the tenant's lock, which a tenant with releases off never reaches

  replay);
- the minute cron sends one more claim a minute (`claim_scheduled_releases`), which finds
  nothing, then R7's purge claim, which finds nothing; nothing is logged
  (`releaseFire.spec.ts`, "a minute with nothing due");
- every other write path is as on `main`: no kernel, staged, draft or singleton code changed;
  `releaseOffWrites.spec.ts`, `stagedKernel.spec.ts`, `releasePublish.spec.ts`,
  `releaseVersions.spec.ts` and `overlayDb.spec.ts` are unchanged and green, and
  `app.publish_scheduled()` is not restated (R5's skip of a tenant with releases on stands);
- what a person sees: the bell asks once more, for failed scheduled releases (there are none:
  one more subrequest on an admin render for the four CMS roles, Measured), and the bell

### The migration (`0107_release_schedule.sql`)

- **`content_releases.fire_lease_until`** (timestamptz, null) and a partial index on scheduled
  releases by their time. No grant changes: staff read it with the row, the service role writes
  it (0038's grants, restated as a postcondition, MAINTAIN under a version CASE).
- **`public.apply_release` restated** (0104's body; every passage that changed is marked R11):
  - `schedule` (`p_scheduled_for`, a minute to 366 days ahead; `p_kind` publish only): steps 0
    to 3 as a publish (the person live, the tenant theirs, the lock, the registry allowlist, the
    drafts unclaimed and as they saw them, the bases), steps 4 to 8 as a dry run (each change in
    its own block, as the person, undone by `BRDRY`), then, as the service role: a conflict is
    `BR409`, a refused change `BR422` (a publish's own codes and details), else the release is
    inserted `scheduled` with the validated changes as its `payload` (each change at the version
    its draft lands on when claimed, old + 1 by the draft lock, checked after the claim), its
    drafts claimed, and `release.schedule` audited naming the scheduler, in one transaction. It
    answers `{mode, release_id, scheduled_for, version, item_count}`.
  - `fire` (`p_release_id`, and no changes, note or kind of its own): the release is read for its
    changes, which then pass every check a publish's do; not scheduled or not due answers
    `{skipped}` (before the lock and again under it); `p_actor` must be its `scheduled_by`; the
    person live and of the release's tenant (else `BR403`); its drafts must be the ones it
    claimed; then exactly a publish: the scheduled row turns `applying`, a conflict refuses it,
    the changes apply fail-fast as the scheduler, `release.publish` is audited as them (detail
    `scheduled: true`), and the row is numbered and published.
  - every mode reads the switch again after the tenant's lock (55000), so a release that waited
    behind `app.disable_releases` finds the tenant as the switch left it.
- **`public.claim_scheduled_releases(limit 1..5)`**: due releases (`scheduled`, their time
  passed, no live lease), oldest first, `for update skip locked`, leased two minutes in the same
  statement; each answered with its scheduler as they are now (`role`, `tenant_id`, `live`:
  active and unlocked) and each change's `{entity_type, op, status}`, never a value.
- **`public.fail_scheduled_release(tenant, release, code, draft_ids)`**: under the lock, a
  release still scheduled and due becomes `failed` with `{code[, draft_ids]}` (the seven codes
  of `RELEASE_FAILURE_CODES`, never a message), its lease cleared and its drafts released. One
  that went live, failed or was cancelled meanwhile, or that a person moved to a later time
  since the claim (the move takes the same lock), is left as it is (`{failed: false}`), and the
  Worker reports it skipped in an info line.
- **`public.reschedule_release` and `public.unschedule_release`**: the person live (the tenant
  from their profile), releases on, the lock, the release of that tenant (P0002), scheduled
  (`BR409` `not-scheduled`) and at the version read (`BR409` `conflict` with the current one),
  every change among the person's role's author roles in the registry and, for a removal, an
  archive, or an edit that sets no status of its own to a row archived live (its status read
  under the lock: it keeps the row archived, hotfix H12's rule), its delete roles (`BR403`
  `forbidden`); a move sets the time and `scheduled_by` to the mover, a cancel sets `cancelled` and releases the drafts; each audited (`release.reschedule`,
  `release.unschedule`) naming the person, in the same transaction.
- **`app.enable_releases` and `app.disable_releases`**: below.
- **Postconditions**: the column and the index; `content_releases`' privileges per API role;
  every function INVOKER with `search_path ''` and `lock_timeout 5s` (the apply keeping its
  `statement_timeout`); EXECUTE (the apply and the four, the service role only; the two
  switches, no API role, PUBLIC included); the apply reads as R11 restated it (four modes, a

### The switches, and the rules they keep (R14 runs them)

Owner only: EXECUTE is no API role's, and each refuses a switched role or a role claim (42501),
so a definer an API request reached cannot call them either. The operator (and, to switch on,
the fallback scheduler) is an active, unlocked Admin of the site (22023). Each takes the tenant's
release lock without waiting and is refused while a release is publishing (55P03). Each audits
itself naming the operator (`releases.enable`, `releases.disable`, counts only).

- **On.** Refused when on already, or when pending changes or scheduled releases remain from an
  earlier time (55000; there can be none: drafts are written only while releases are on, and
  switching off leaves none). The legacy schedule is converted: every row
  `app.publish_scheduled()` would have published by itself (its eight tables, held equal by
  `releaseScheduleSql.spec.ts`, and its predicate: `scheduled` with a time) is locked, moved to
  draft (as the owner: no guard and no capture while off; its history row is written), and
  becomes a pending change `{status: published}` claimed by a `legacy_schedule` release at that
  time (a time passed fires at the next minute), grouped by time and scheduler, at most 60
  changes a release. A release goes live as the row's last editor while that person may still
  publish it (live, of the site, among its author roles), else as the fallback scheduler. What
  the legacy path never published by itself is counted (`left_scheduled`) and left as it is: a
  row of those tables scheduled with no time, and the scheduled rows of the registry's other
  status tables (team members, statistics, certifications). Release mode cannot set `scheduled`
  on a row, but a pending change can still move such a row to published or draft. Then the
  baseline (version N, 1 the first time, "Releases switched on", `not_needed`), the flag, the
  audit row.
- **Off.** Refused when off already. A SHARE ROW EXCLUSIVE lock on `content_drafts` makes every
  draft write in flight land first and every later one wait (then meet the switch off). With a
  change pending or a release scheduled it is refused (55000, with the counts) unless the
  discard is named (`p_discard_pending => true`). With it: the flag goes first (nothing after it
  is captured); a `legacy_schedule` release's rows go back to their own schedule (status
  `scheduled` at the release's time, where the row is still the draft enable made it, so
  `app.publish_scheduled()` publishes them as before; one that cannot be put back is counted,
  `not_restored`); every scheduled release is cancelled; every pending change is thrown away.
  Versions, history and the ledger stay; switching on again writes a new baseline.
- **`app.publish_scheduled()` and scheduled releases never both act.** It acts only for a tenant
  with releases off (R5's skip); a scheduled release exists and fires only for a tenant with
  them on (`apply_release` refuses both modes otherwise); and each switch moves the flag and the
  rows in one transaction, the rows locked, so a legacy row is either published by
  `app.publish_scheduled()` before the switch or converted by it, never both. pgTAP section 6: a
  due row of a tenant with releases off is published, one of a tenant with them on is not;
  section 7: a converted row goes live only as its release, and a row the switch put back is
  published by `app.publish_scheduled()` again.

### The Worker

- **Scheduling** (`src/lib/release/endpoints.ts`, `apply.ts`): `PublishRequestSchema` takes
  `scheduleAt` (`ScheduleAtSchema`: ISO 8601 with its offset; a local time names no zone and is
  refused). After the flag: a rollback with a time is 422 on `kind`; a time under
  `RELEASE_SCHEDULE_MIN_MINUTES` (2) or over `RELEASE_SCHEDULE_MAX_DAYS` (366) is 422 on
  `scheduleAt`; then every step of a publish (R6) and `schedule()`, whose answer is
  `ScheduleResultSchema` (`{release: {id, scheduledFor, version}, items, warnings}`) and whose
  refusals are a publish's. Validate checks the time and runs the dry run as before.
- **A dependency a scheduled release holds** (R6's departure 9): a link to a pending new item
  claimed by a scheduled release is `requires-scheduled` ("This needs X, which goes live with a
  scheduled release. Publish this after it does, or unschedule that release first."), never a
  `requires` the dialog would try to tick.
- **Moving and cancelling** (`src/lib/release/schedule.ts`; `PATCH` and `DELETE
  /api/admin/releases/[id]`, kernel `content.publish` with `RELEASE_ANY_CAP`): after the flag,
  the release and its claimed drafts read as the person (the drafts by stored metadata:
  `entity_type`, `entity_id`, `op`, `payload->>status`); not found 404; not scheduled 409
  `not-scheduled`; a stale version 409 `conflict` with the current one; a change the person
  cannot publish 403 (the capability missing, and `waitingFor`: the roles that could move all of
  it), judged as a publish judges it: an edit that sets no status of its own is read against the
  live row's status (`liveStatuses`: the key and the status, under the person's RLS and in their
  tenant, one `release_read_rows` request, nothing when no change needs it), so one that keeps a
  row archived live archived needs `content.archiveDelete` (hotfix H12: a Content Creator can
  neither move an Admin's release holding it, which would make it theirs to fail, nor cancel
  it); a move's time 422;
  `liveRecheck`; the RPC, its refusals in the same words (never the database's message), 503
  `busy` with `Retry-After` on a lock wait.
- **The fire** (`src/lib/cron/releases.ts`): above, and the module's comment gives the order.
  `fireCheck` is the Worker's layer: the scheduler live, of the release's tenant, a publisher,
  and `canPublish` for every change from its stored status (departure 5). `failureOf`
  (`apply.ts`) maps the apply's refusals to failure codes, and a lock wait, a deadlock, a
  serialization failure or no answer to "busy" (left scheduled; the lease ends; tried again).
  A release that goes live more than `RELEASE_OVERDUE_MINUTES` (5, the dashboard's
  `release_overdue` mark) late logs its line as a warning with `lateMinutes` (§4.6:
  `cron:releases` logs fire failures and overdue releases); no subrequest is added.
- **After a fire** (`afterEffects.ts`): `afterFire` runs a publish's after-effects as the
  system: the snapshots, the purge (`source: release`), its record; the slugs its images do not
  carry are read with the service client scoped to the release's tenant, one read per table
  (`systemSlugs`), and no `release.purge` audit row is written (the cron is no person, R7's
  rule). `afterPublish` is the same steps with the publisher's slugs and audit row, unchanged in
  behaviour (`releaseAfterEffects.spec.ts` and `releasePublish.spec.ts` green as they were).
- **The bell** (`src/lib/admin/notifications/releases.ts`, kind `releases`, its words in U11's
  `kinds.ts`): the tenant's failed releases in the bell's window, one read, for the roles that
  publish one of a release's areas (`publishableAreas`: Admin every area, Content Creator the
  content areas, SEO `seo`, Developer `settings` and `appearance`; Sales none, and never asked):
  "The release scheduled for {date}, {time} could not go live", its reason by code
  (`src/lib/release/failureCopy.ts`, client-safe, for R13 too) and "Its changes are waiting to
  be published again."; new from when it failed; no link until R13's versions page.
- **Versions** (`versions.ts`): each listed release carries its own `version`, which a move or a
  cancel names (R13's "Change time" and "Unschedule").
- **Activity log** (`auditLabels.ts`): "Scheduled a release", "Changed the time of a scheduled
  release", "Unscheduled a release" (publishing), "Switched on publishing in releases" and
  "Switched off publishing in releases" (settings).

## Departures from the design, each with its reason

1. **The fire claim is a lease column**, `content_releases.fire_lease_until` (two minutes),
   with SKIP LOCKED, R7's pattern; the design says only that "a second run finds the release no
   longer scheduled". The apply's own re-read under the tenant's lock is what makes a double
   publish impossible; the claim keeps two overlapping runs from both paying for one release, and
   a run that dies holds it only until its lease ends.
2. **A schedule is dry-run in the database before it is stored** (the design runs the Worker's
   steps 1 to 5, then stores). A schedule the database would refuse (a content creator's archive,
   a slug taken, a conflict) is refused when it is made, not at its time.
3. **A rollback is never scheduled** (422): a restore's changes go live as one version, and a
   delay between restoring and publishing leaves room for edits the rollback check refuses
   anyway.
4. **The fire does not re-run the Worker's check over the state the release leaves** (R6's
   `checkSelection`). There is no person's token at fire time to read as (`release_read_rows` is
   CMS staff's; the service role would read past RLS), and its reads would pass the minute's
   budget. What binds at fire: the payload as validated when scheduled, frozen with its drafts
   claimed (no path changes either); the scheduler live with every capability (`fireCheck`); and
   the database as them (RLS, the RESTRICTIVE gates, CHECKs, foreign keys, uniqueness, the
   guards, the conflict check against each change's base). What does not: the Worker's cross-row
   rules against what changed elsewhere since (a redirect added since that makes a chain with one
   the release holds; a discipline unpublished since, which is only a warning). Owner question 1.
5. **The fire's capability check reads each change's stored status, not live** (R6's publish
   reads live for hotfix H12's "keeps an archived row archived" rule). An edit of a row archived
   after it was scheduled is refused at fire by the archive gates, which bind as the scheduler
   (pgTAP section 4: an archive refused for a content creator), so the database decides it.
6. **A moved release goes live as the person who moved it** (`scheduled_by`): they may publish
   all of it (the move's own rule), and a release goes live as one person.
7. **A failure writes no audit row** (§4.6 lists `release.fail` among the kernel's audits). No
   person acts at fire: the failure is the release's (`status`, `failure`), a `cron:releases`
   error, the dashboard's `release_failed` row and the bell. A fire that goes live is audited as
   `release.publish` by the apply, naming its scheduler.
8. **One thing a minute**: a fire, or R7's purge retries (Measured).
9. **Switching on converts only `app.publish_scheduled()`'s rows, and picks the scheduler**: the
   design converts every release-managed row with status `scheduled`, grouped by
   `scheduled_for`, under `coalesce(updated_by, fallback)`. A scheduled team member, statistic
   or certification, and a row of the legacy tables scheduled with no time, was never published
   by the legacy path, so converting it would publish something that would not otherwise have
   gone live (a timeless row has no time to group by either); and a last editor who has left or
   lost the role would make the release fail at its time, so they are passed over for the
   fallback.
10. **Switching off throws pending work away only when the discard is named, and puts legacy
    schedules back** (edge case 21 keeps drafts, read-only, with a banner, unless `force`). The
    task names the discard; drafts nobody can publish while releases are off would surface at a
    later switch-on, which enable now refuses. A legacy schedule was the site's own before
    releases, so it returns to its row rather than being lost.
11. **A new issue code**, `requires-scheduled` (R6 departure 9's wording).
12. **No help guide and no e2e.** R11 adds no screen: the dialog's "When" (R12) and the versions
    page's scheduled and failed rows (R13) carry their guides; `releases-schedule.e2e.ts` needs
    the e2e workflow in release mode, which is R14's (as for R6, R7 and R10). The your-account
    guide (U11, revision 3) lists the bell's kinds; it gains the releases kind when R14 switches
    releases on (Open), since nothing can appear under it before then.

### Second review (the build resumed after a session limit)

The work was judged again against the design and the task before the gates were re-run. Kept:
the migration, the routes, the fire, the bell and the documents, after a full re-read and a
fresh PGlite replay of every suite on the merged tree. Fixed, each with tests that fail without
the fix (the source change reverted alone, from a saved patch):

- **Switching on published rows the legacy path never would.** `enable_releases` converted a
  row scheduled with no time at `coalesce(scheduled_for, now())`, so it went live at the next
  minute, and switching off then put it back with that time, so `app.publish_scheduled()`
  published it too. Nothing in the schema or the admin's schemas requires a time on a scheduled
  row. It now converts exactly `publish_scheduled()`'s rows and counts the timeless ones in
  `left_scheduled` (pgTAP rows 79 to 95 and a postcondition; `releaseScheduleSql.spec.ts`).
- **A failure could undo a person's move.** `fail_scheduled_release` failed any release still
  scheduled, so a release moved to a later time between the cron's claim and its failure was
  failed and its drafts released. It now leaves a release that is no longer due, as the fire
