# R12b: a create or a move made in release mode is refused once releases are off

- **Lane:** Releases (a follow-up to R12)
- **Design:** R12's pre-merge review ("a screen left open across the switch-off wrote live"),
  its as-built (Pre-merge review; Open: U5 + U6's own lists), E1's as-built and security review
  (the page editor's moves), and the owner's rule: releases off means main, so a screen loaded
  in release mode must never write live after a switch-off
- **PR:** at review (branch `fix/r12b-releases-off-posts`, on R12's head `609772b7`; R12 is
  #112 and merges first)
- **Migration:** none
- **Builds on:** R12 (`src/lib/release/releasesOff.ts`, `STAGED_DELETE`, `STAGED_KEY`)

## The problem

R12 marks every release-mode save (`staged: true`, or the pending change it names) and a list's
or drawer's DELETE (`?staged=1`). With releases off, the live branch of the resource PATCH and
DELETE, the singleton PATCH and the entity-SEO PUT refuses a marked request (409
`releases-off`) before it reads or writes anything. The POSTs were not covered:

- **a create**: a collection drawer's Add, the Services and Projects screens' modals and
  drawers, a case study added in a service's editor, the SEO screen's new redirect, and a
  Duplicate (a collection's, the service editor's). In draft mode the service editor copies
  `save.saved`, the pending change, so after a switch-off that throws the change away the copy
  would have put thrown-away words on a live row;
- **a move** (the reorder POST): R12 left a list's move unmarked as "main's own action, main's
  own wording". The owner's rule overrules that, and E1's security review shows it is not only
  words. A screen in release mode numbers a move against the **staged** order (the list it
  shows) and sends only the rows that moved. Written live, the rows it leaves out keep their
  live numbers, so the public order becomes one nobody saw.

U5 + U6's lists (the Services overview, a discipline's page, Projects) did not know their mode
at all (R12's Open), so their eye (a PATCH) and the editors' and the discipline drawer's Delete
were unmarked too.

## What was built

### The server (`src/lib/admin/resource.ts`, `src/lib/release/releasesOff.ts`)

The live branch of `collectionRoutes(...).POST` (create) and `reorderRoute` (every
`/api/admin/<slug>/reorder`, one factory) of a release-managed resource now calls R12's
`refuseStagedQuery(ctx.url, entity)` before anything else, as the DELETE does: a request whose
address carries `staged`, `draftId` or `draftVersion` is 409 `releases-off` with R12's detail,
and nothing is read, written or audited. The staged branches ignore the address, as before.

The marker rides in the address, not the body. Both routes' bodies are parsed by the route's
own schema in the kernel before the handler runs (`config.createSchema`, the reorder schema),
so a body key never reaches the handler (it is stripped, or refused by a strict schema, and
then also with releases **on**). The address changes nothing for main's callers, which send
none.

A resource outside the release (media, the Style-Finder) has no registry entry and never
refuses the marker.

### The client

**The helpers** (`src/lib/admin/releaseEvents.ts`, R12's file, a few bytes with no imports):

- `STAGED_QUERY` (`?staged=1`; R12's `STAGED_DELETE` is now its alias);
- `stagedUrl(url, staged)`: the address with the marker when the screen is in release mode,
  else exactly as it was;
- `stagedBody(body, staged)`: a PATCH body with `staged: true` (R12's `STAGED_KEY`), for a
  list's eye; here so a list does not import the field kit's `entitySave.ts`;
- `readsThroughRelease(answer)`: a list answer came through the release (it carries
  `draftsInvalid`, which `stagedList` always answers, and only with releases on).

**A screen's mode is its own, never a row's** (E1's security review): a list route's row with
nothing pending carries no `draft` key at all (`overlay.ts` shapes the live row as it is), so a
row-based test would leave most writes of a release-mode screen unmarked. Every list decides
from its answer (`setStaged(readsThroughRelease(data))`, read again on every load), every
editor from its own answer (`save.mode`, R12).

**Creates through `useEntitySave`**: `SaveTarget` (resource) gains `staged`; a create
(`id === null`) from a screen in release mode posts to `/api/admin/<slug>?staged=1`. Only the
create: a saved record's mode is its own answer's. A refused create holds (R12's
`releases-off` state, its words and Reload), and its **Reload reloads the page**: there is no
record to read (R12's Reload of an existing record reads it live; for a new one it would have
read the list as a row), and the screen reads its list again, live. The form starts over, as
an editor's Reload takes the live row over what it held. Only in that state: every other
Reload is R12's, unchanged.

**The sites** (each with the screen's own mode):

| Screen | Write | Marker |
|---|---|---|
| ResourceTable (every kernel list) | move | `stagedUrl(…/reorder)`; its New calls `onCreate(staged)` |
| SEO, Redirects tab | new redirect (drawer) | target `staged` from the table's `onCreate` |
| Collection screens (U7) | move, Duplicate (create + renumber) | `stagedUrl` |
| Collection drawer | Add; Delete (R12, now through `stagedUrl`, the same request) | target `staged`; `save.mode` |
| Services overview (U5) | the disciplines' move; the eye | `stagedUrl`; `stagedBody` |
| Discipline drawer | Add; Delete | target `staged`; `save.mode` |
| A discipline's page | the services' move; the eye | `stagedUrl`; `stagedBody` |
| Add service modal | create | target `staged` |
| Projects (U6) | move | `stagedUrl` |
| Add project modal | create | target `staged` |
| Tags drawer | Add sector | target `staged` (its own sectors read) |
| A service's case study | Add a case study | target `staged` (its own case read) |
| Service editor | Duplicate; Delete | `save.mode`; `editorDelete` `staged` |
| Project editor | Delete | `editorDelete` `staged` |

On the Services screens a `releases-off` 409 on the eye now says its own words ("It was not
changed. Publishing was switched off. Reload to edit the live site."), not "Someone else
changed this…", which every other 409 still says. Every refusal of a list's write re-reads the
list (as each did already), which is then live, so the next action is main's.

### Releases off: what does not change

No list answer carries `draftsInvalid` and no editor answer `draft` with releases off, so no
client adds a marker: every request is main's, byte for byte (`stagedUrl(url, false)` is `url`,
`stagedBody(body, false)` is `body`, `buildSaveRequest` without `staged` is the old create). The
routes' live paths are unchanged for an unmarked request: `stagedKernel.spec`'s releases-off
block (create, reorder, delete, persist and hooks) and `releaseOffWrites.spec` (every config's
`toRow`, the singleton and entity-SEO writes, snapshot) are untouched and green. The markup,
the chunks and every request of a screen with releases off are what they were.

## Not covered, and why

- **The create pages** (`/admin/<slug>/new`: ResourceForm, the service and project editors'
  create). They have had no answer from the server, so they know no mode (R12: an editor's mode
  is only ever the server's answer, and an editor never reads the shell's flag), and they draw
  main's form (the status select, the Schedule field). Giving them a mode would take an extra
  read on every create page (R12 forbids a new request with releases off) or the shell's flag
  passed to each create page (owner question 1). Inert until R14.
- **Page visibility** (`/api/admin/page-visibility`, `/api/admin/pages/visibility/[id]`): no
  route stages it yet, so its writes are live in either mode; nothing to refuse.
- **The intake switch** (`/api/admin/site-profile/intake`): immediate by design (R3b), releases
  on or off.
- **E1's page editor** is on its own branch, stacked on R12: its Add section and its section
  moves must carry the marker too (`stagedUrl`, or the target's `staged`), with the page's mode
  from its own answer (owner question 2 / E1's open item). `releaseModeWrites.spec` fails on an
  unmarked write once E1 merges over this, so the gap cannot land silently.

## Proof

Each test was seen red with its fix reversed in the source (`git diff > p; git apply -R p`),
never by stashing.

- **`tests/lib/stagedKernel.spec.ts`** (the routes, over the in-memory PostgREST): a create
  carrying `?staged=1` or a `draftId` is 409 `releases-off` with only the flag read, no row, no
  audit; **E1's case**: a list read with releases on (a pending move put the third service
  first), then releases switched off and every change thrown away, then a move of the two rows
  it moved, numbered on the staged order, marked from the list answer: 409, the live order
  `10, 20, 30` untouched, nothing but the flag read; an unmarked create and move (a list read
  live, `readsThroughRelease` false) are main's; with releases on the marker is ignored (a
  staged create, a staged move); a Style-Finder move ignores the marker.
- **`tests/lib/entitySave.spec.ts`**: a create from a `staged` target posts to `?staged=1`
  with the same body and no `staged` key; `false` or absent is main's address; an existing
  record ignores the flag; the refused create holds, and its Reload reloads the page (the
  hook's wiring read from its source, as R12 reads its settle subscription).
- **`tests/lib/editorDelete.spec.ts`**: an editor's Delete in draft mode carries `?staged=1`.
- **`tests/lib/releaseModeWrites.spec.ts`** (new): the helpers; each list takes its mode from
  its answer; the editors from `save.mode`; each create site carries its screen's mode; every
  resource editor is a create site or named with its reason; and **a scan of every
  `adminFetch` write in `src/components/admin` and `src/lib/admin`** (its arguments parsed, not
  guessed): a POST or DELETE to a release-managed route (the registry's resource slugs, or a
  screen's own `${def|ui|req.slug}`) carries the marker in its address, a PATCH in its body;
  every move goes through `stagedUrl`.
- **Authz** (`tests/authz/cases/releases.ts`, `caseManifest.ts`): two twins, `services create
  made in release mode (releases off)` and `services reorder made in release mode (releases
  off)`: the gate is the flag-off row's (Admin, Content Creator), checked before the refusal;
  every other role 403. The other cases are unchanged.
