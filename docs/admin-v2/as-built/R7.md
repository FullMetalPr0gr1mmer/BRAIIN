## Plan (written before the build)

- **Scope.**
  1. The purge seam, `src/lib/http/purge.ts`: Cache-Tag purges through the zone API, at most
     30 tags a call (more collapse to `tenant:default`), at most 30,000 tags in 24 hours
     (CLAUDE.md §2) counted in the database, retried with jitter, an isolate breaker, never
     throwing, and "Not set up" (`skipped`, nothing sent, nothing read) while
     `CF_ZONE_ID`/`CF_CACHE_PURGE_TOKEN` are unset (O-3). Media alt, tags and folder saves
     purge `media:all` through it.
  2. A release's tags, `src/lib/release/tags.ts`: the union of every item's before and after
     tags (old and new slugs), a section's page and an SEO row's target resolved, the sitemap
     and llms.txt on a URL change.
  3. `SECTION_READS` (`src/lib/sections/reads.ts`): every composed page stamps its route tags
     plus the tags of the sections it renders; `media:all` on About, Our Work, All projects and
     the case study (both languages); `tenant:default` on the sitemap and llms.txt;
     `tierATags` keeps the always, route and locale tags, and a test fails any route above 30.
  4. After a publish, never fatal: the redirect map and the page-visibility snapshot rebuilt AS
     THE SYSTEM (the service client, the release's tenant) when the release changes redirects,
     page visibility, or renames or removes a page (R6's question 2); the purge; the outcome
     recorded on the release; `release.purge` audited in its own words when a purge was sent.
  5. The minute cron (`* * * * *`, `src/lib/cron/releases.ts`): failed purges retried with
     backoff (up to 10 attempts), and a published release whose after-effects never ran (the
     Worker stopped after the commit) gets them, each release claimed once in the database
     so two runs never act on it twice.
  6. The CI check: Workers Cache (`wrangler.jsonc` `cache`) or Astro's cache provider cannot
     be switched on without a matching purge backend (`tests/lib/cacheLayer.spec.ts`).
  7. O-16: the validate of a release touching every registry type measured on the merged tree,
     and brought under the Free plan's 50 with one batched read RPC under the caller's RLS.
- **Migration.** A purge ledger (`cache_purge_log`) and its budget function, the cron's claim
  of due purges, the batched read for O-16; P-14 grants and postconditions; no capability, no
  registry row, no screen.
- **Tests.** `purge.spec`, `releaseTags.spec`, `sectionReads.spec`, `releaseCron.spec`,

- the rules' legacy queries are unchanged call for call (`tests/lib/overlayDb.spec.ts`,

- the minute cron sends one claim a minute that finds nothing, and logs nothing;
- Tier A HTML is unchanged: Contact and Join load their data in the route now, with the same

### The purge seam (`src/lib/http/purge.ts`)

`purgeTags(tenant, tags, {source})` never throws and answers `{status, tags, requests, reason?}`:

- **Not set up** (`CF_ZONE_ID` not 32 hex characters, or no `CF_CACHE_PURGE_TOKEN`): `skipped`,
  nothing read or sent. Both are optional `astro:env` entries (the zone public, the token a
  secret; `scripts/push-secrets.mjs` pushes it when `.env` names it).
- **The tag set** (`purgeTagSet`): lower case, each once; more than 30, or a tag the API cannot
  take (`^[a-z_]+:[a-z0-9_:-]+$`, the rule `record_release_purge` holds), is `tenant:default`
  alone; none is `not_needed`.
- **The day's budget**: before each request the tags are taken from 30,000 a day in the
  database (`public.cache_purge_take`, 0103), so the count holds across isolates; over budget
  or unreadable, nothing is sent (`failed`, `budget` or `budget-unread`).
- **The request**: `POST https://api.cloudflare.com/client/v4/zones/{zone}/purge_cache {tags}`
  through `outboundJson` (G2): 1.2 s timeout, one retry after 200 to 600 ms of jitter on a
  network error or a 5xx, never on a 4xx (a 429 is `failed`, `rate-limited`, and the cron
  retries it). `success: false` in the body is `refused`. A reason code only, never the token
  or the body.
- **The breaker**: three failures in a row in the isolate stop requests for a minute (`failed`,
  `breaker`, nothing read or sent); a success closes it.
- `purgeAfterSave(tenant, tags, 'media' | 'visibility')`: the same, plus one warning
  (`purge:<source>`) when it failed. `PURGE_BACKENDS = ['zone']`.
- **A media save purges only when a public page would change** (`mediaChangeIsPublic`; the
  pre-merge review): a column of `PUBLIC_MEDIA_COLUMNS` (alt, the file's key, kind, provider,
  dimensions, the Stream id) whose value moved. Tags, folder and the display name are the
  library's own: each purge spends the Free plan's 5 a minute and the day's budget, and a
  refused one after an immediate save is not retried, so a burst of tag edits must not cost
  a later alt fix its purge. The kernel PATCH compares its own read of the row before the write
  (`afterWrite` now receives it as `before`) with the row it wrote; the meta route sends no
  purge for tags or folder alone, and with a zone set up reads the alt before its write (one
  read, only then: with no zone the save reads and sends what it did). Not knowing the row
  before purges. A replace always purges (the file moved).

### The cache model and its layers (`tests/lib/cacheLayer.spec.ts`)

The zone purge serves the Tier A cache the design names (releases.md §5.3, R43/KAN-20): the
zone's cache as the Worker itself reads and fills it through the Cache API on the custom
domain. Cloudflare runs a Worker before the zone's cache and never caches a response the
Worker builds by itself, so there is no "zone cache in front of the Worker"; the lookup is the
Worker's own and, when it is built (O-3, KAN-20), sits in `src/middleware.ts` after the
maintenance check and the page-visibility check (CLAUDE.md §3's "pre-cache" checks,
`src/lib/http/maintenance.ts`). Maintenance (on, off, its allowlist) and a hidden page or its
window then hold for cached pages with no purge. The spec refuses a Cache API lookup anywhere
else, or in the middleware before either check, and proves it is not vacuous (the pre-merge
review found R7's first notes describing a cache in front of the Worker, which would have
skipped both checks).

Workers Cache (`wrangler.jsonc` `cache`) and Astro's route cache (`cache`, `routeRules`,
`cacheCloudflare()`, `memoryCache()` in `astro.config.mjs`) would hold Tier A responses where
the zone purge does not reach, for a year, and answer before the middleware (maintenance and
page visibility included). The spec fails a config that switches either on while
`PURGE_BACKENDS` lacks its backend, and proves it is not vacuous.

### What a page stamps (`src/lib/sections/reads.ts`, `src/lib/http/routeTags.ts`)

- `SECTION_READS`: what each section type reads, in the registry's vocabulary (`clients:all`,
  `team:all`, `certifications:all`, `faq:all`, `media:all`...). `sectionTags(sections)` unions
  what the visible sections read.
- Every composed route (Home, About, Services, Our Work, All projects, Contact, Join, both
  locales) stamps its own list plus `sectionTags` of what it renders; the lists live in one
  table, `TIER_A_ROUTES`. New: `media:all` on About, Our Work, All projects and the case study
  (the README's 8 routes), `team:all` on the blog index and posts (a post shows its author).
- **`media:all` on every Tier A response** (`ALWAYS_TAGS`, `src/lib/http/cacheTags.ts`; the
  pre-merge review): every head renders a URL built from a media row, the default share image
  (`seo_defaults.default_og_media` through `src/lib/seo/head.ts`), so a media replace or alt
  edit, whose purge is `media:all` only, must reach Join, the blog, search and the legal pages
  too, which read no media in their sections. `sectionReads.spec` holds every route of
  `TIER_A_ROUTES` to it in both locales; the 8 routes' own lists keep the tag (harmless twice).
- Contact and Join load their data in the route (`src/lib/sections/contactPage.ts`,
  `joinPage.ts`), so the route holds the sections before it sets its headers; the components
  render what they are handed.
- The sitemap and llms.txt also stamp `tenant:default` (`SITEMAP_CACHE_TAG`, `LLMS_CACHE_TAG`).
- `tierATags` past 30 keeps the always, route and locale tags and drops entities from the end.
  A purge naming a dropped entity would miss that response (only a collapsed purge,
  `tenant:default`, or a kept tag reaches it), so `sectionReads.spec` holds every route within
  30 with every section a page could hold, and nothing is dropped in practice.

### A release's tags (`src/lib/release/tags.ts`)

The union over the apply's items (every row it changed, cascades and the case-study link sets
included) of the registry's `entityTags` for the row before AND after (a rename purges both
URLs), plus a section's or a visibility row's page and an SEO row's target, resolved from the
release's own images first and otherwise in ONE read as the publisher (`publisherSlugs`,
`release_read_rows`); `route:sitemap` and `route:llms` for any change of a page, service,
discipline, case study, post, page visibility or search settings; `tenant:default` for anything
it cannot resolve (a failed read, a row gone, an unknown type). A redirect alone purges nothing
(`not_needed`): its rule lives in the KV map. `tests/lib/releaseTags.spec.ts` holds every tag
every registry type can emit, for a create, an edit and a removal, to one a route stamps, and
every CMS page slug to its route's `page:<slug>`.

### After a publish (`src/lib/release/afterEffects.ts`)

Each step on its own, never fatal:

1. **The edge snapshots, rebuilt as the system** (the service client, the release's tenant; a
   documented system-actor exception like the daily cron's re-syncs, reading only that tenant's
   rules and returning nothing to anyone): the redirect map when the release changed a redirect
   (`syncRedirectsOfTenant`), the page-visibility snapshot when it changed page visibility or
   renamed or removed a page (`rebuildVisibilitySnapshot`). The snapshot names pages by slug,
   so a hidden page renamed by a Content Creator would otherwise be public under its new name
   until the daily re-sync (R6's question 2). A release found committed after no answer: both,
   and `tenant:default`.
2. **The purge** of the release's tags (`source: 'release'`).
3. **The record** (`record_release_purge`, 0051): its status, the tags sent, and for a failure
   the cron's next try (about a minute, jittered). A record that cannot be written is logged;
   the release then stays `pending` and the cron treats it as an orphan.
4. **`release.purge`**, audited as the publisher when a request was sent (counts, status and a
   reason code, never a tag's value), in its own words in the activity log ("Refreshed the
   cached pages of version 15", `src/lib/admin/auditLabels.ts`).

### The minute cron (`src/lib/cron/releases.ts`; `wrangler.jsonc` `* * * * *`)

One job, `releases`, on its own schedule (its own invocation, its own 50 subrequests):
`public.claim_release_purges(5)` (0103) takes the due releases of ONE tenant, the one waiting
longest, with SKIP LOCKED, and pushes them five minutes ahead in the same statement: a failed
purge whose next try has come (fewer than 10 attempts), and an orphan (a published release
still `pending` with no attempt two minutes after it went live: the Worker stopped between the
commit and its after-effects). Never a baseline, a release not live, or one done. Then an
orphan's snapshots are rebuilt as the system; ONE purge goes for every claimed release (their
tags together, more than 30 is `tenant:default`; an orphan is `tenant:default`), so a minute
stays within the Free plan's 5 purge requests; each release is recorded with backoff (1, 2,
4... minutes, at most 60, jittered; after the tenth failure none, an error line, and the
dashboard's `purge_failed` row from 0066); one line a run (`cron:releases`). Nothing claimed,
no line. Its worst case is 31 subrequests (`tests/lib/releaseCron.spec.ts`).

### O-16: one read for a publish's check (`public.release_read_rows`, `listMany`)

R6's check read the live rows and every link one PostgREST request per table: a release
touching all 22 registry types cost 42 requests before its rules ran, about 51 for a clean
publish, one past the Free plan's 50. `release_read_rows(tenant, reads)` answers up to 40 reads
of up to 500 ids each in ONE request, as the caller (SECURITY INVOKER: RLS, the RESTRICTIVE
gates and the column grants bind as for a PostgREST read): CMS staff of their own tenant only
(a Sales token, a token with no role, anon and the service role are refused), registry tables
and `media_assets` only, columns the table has (each `%I`-quoted after the catalog confirmed
it), keyed by `id`, or by `tenant_id` only for a table the registry keys by its tenant (the
two singletons, `site_profile` and `seo_defaults`: never a whole table), the ids bound as
`uuid[]`, at most 2,000 over all the reads of a call (each id names one row at most, so a call
answers 2,000 rows at most, however its reads repeat), each read's rows ordered by its key.
`OverlayDb.listMany` sends the reads it can serve exactly that way (an `in` on the key, a
tenant key only for `RELEASE_SINGLETON_TABLES`, plain column names, no order, limit or other
filter; a request closed before it would pass 40 reads or 2,000 ids) and every other read as
before;
`layeredDb` plans its reads and sends them together, `memoDb` remembers each. `readLive` and
`primeLinks` read through it, and so do a release's slug reads.

## Departures from the design, each with its reason

1. **The listing tags are `route:sitemap` and `route:llms`**, not §5.1's `seo:sitemap` and
   `seo:llms`: those are the tags the two routes already stamp, and two names for one thing
   would drift. Both routes also stamp `tenant:default` (§5.2).
2. **Any change of a listed type purges the sitemap and llms.txt**, not only a URL change
   (§5.1): the sitemap's `<lastmod>` is the row's `updated_at`, which every applied edit moves
   (truthful dates, Pillar 3), and llms.txt names titles and descriptions.
3. **One retry within the request (1.2 s each), not three within 2.5 s** (§5.3): each try is a
   subrequest on a publish already near the plan's 50 before this slice, and the outbound
   helper's rule (G2) is one retry on a network error or a 5xx; a 429 is retried by the minute
   cron, never inside the request.
4. **The day's 30,000 is a database ledger** (`cache_purge_log`, `cache_purge_take`): an
   isolate's counter would not hold across isolates. It holds no person's data (a tenant, a
   count, a source and a time, kept 48 hours); RLS FORCEd with no policy, the service role
   alone holds it. It departs from §8's row shape as `content_release_items` does (an
   append-only record the system writes: no `updated_at`, actor or version columns).
5. **The minute cron fires no scheduled release.** `apply_release` refuses `schedule` and
   `fire` until R11 (0051), so nothing can be scheduled yet. The cron is R7's retry seam: failed
   purges, and the after-effects of a release whose Worker stopped after the commit (which R6
   left to the daily re-sync), each release claimed once in the database. R11 adds its fire step
   to the same schedule, with a claim of the same pattern.
6. **The snapshots are always rebuilt as the system after a release**, never with the
   publisher's client (R6 used the publisher's): a rename or removal of a page now rebuilds the
   visibility snapshot too (R6's question 2, the owner's default), whoever published it.
7. **Page-visibility, page-password and "show in menu" saves purge** their page's tags; §5.3
   names only media. The three routes already answered `purgeTags` for R7 to wire: the page
   itself is refused by the middleware's check before any cache lookup, but every cached page's
   menus, and the sitemap and llms.txt, list pages from the snapshot, so they must be purged
   when a page leaves or joins them. A failed purge after an immediate save is a warning, not
   retried: no release row holds it (owner question 2). The purge goes right after the
   snapshot's write, inside its own propagation bound (about three minutes): see Open, the
   cache model.
8. **O-16 by one read, not a cap on types per release**: the read keeps a release of every type
   at 26 subrequests, so no refusal is needed. It is a new RPC in an exposed schema that gives
   staff nothing a PostgREST read of the same table does not (invoker, its own tenant, registry
   tables only).
9. **`release.purge` only when a request was sent**, as the publisher, from the publish
   request; the cron (no person) writes `system_logs` only. The activity log's prefix rule
   (`release.` is a publish) gains an exact entry, and `auditLabels.spec`'s disjointness test
   now forbids an action under another KIND's prefix (an exact entry under its own kind's prefix
   is the point).
10. **The blog's routes stamp `team:all`**: found by the closure work (a post shows its author's
    name, and a team member's change purges `team:all`); the README named only the 8 media
    routes.
11. **No help guide**: R7 adds no screen. **No e2e**: release-mode e2e is R14's; the public
    `Cache-Tag` assertions in `tests/e2e` use `toContain` and still hold.
12. **No nav-href warning** ("a menu link to an unpublished page", releases.md §4.2 step 5),
    which R6 (departure 6) handed to "R7's route map". R7's tag work maps rows to the tags their
    routes stamp, never a menu link's path back to a row, so the warning is not built here. It
    moves to **R12** (the publish dialog shows the warnings): a link's href read through the
    preview's route map (`src/lib/preview/routes.ts`, R9) to the page, service, case study or
    post it names, warned when the release leaves that row unpublished. Recorded in Open.
