## Plan (written before the build)

  The legacy routes go: `GET /api/admin/leads` (the old list; the POST that adds a lead by hand
  stays) and the `?pii=1` alias of `GET /api/admin/leads/[id]` (the CRM's audited

  gone (C4b); the PATCH's refusals of `status` and `internalNotes` (422s naming the field) stay,
  since they write nothing.
- **Both schemas.** Every query the code makes must work on today's production schema (the
  columns present, the legacy sync and the notes mirror still running) and on C14b's (the
  columns gone), because C14b is applied while this code is live. A query that names none of
  the five columns does both.
- **Files.** `src/lib/admin/leadFields.ts` (the safe, gated and sensitive lists without the
  legacy columns), `src/lib/crm/reveal.ts` (no legacy field set), `src/pages/api/admin/leads/
  index.ts` (POST only), `[id].ts` (no `?pii=1`), `[id]/reveal.ts` and `LeadContactCard.tsx`
  (no `timeline_band`), `export.ts` and `packages/schemas/crm.ts` (no status column or filter,
  no band column; note bodies still never exported, the count from the thread), `src/lib/crm/
  exportRead.ts`, `src/pages/api/hooks/notify-lead.ts` (the timeline from the encrypted field
  only), `src/lib/crm/indexBackfill.ts` (the cron reads no band), `src/lib/crm/settings.ts` and

- **Tests.** A static gate, `tests/lib/leadsContract.spec.ts`: no code under `src/`,

## What was built

- **The removed routes.** `GET /api/admin/leads` (the legacy panel's list) is gone: the file
  keeps only the POST that adds a lead by hand, and a GET finds no handler (Astro answers 404;
  signed out, the middleware's 401 comes first). `GET /api/admin/leads/[id]` reads no query
  parameter any more, so `?pii=1` answers the same safe row as a plain GET: it decrypts
  nothing, spends no reveal slot and writes a plain `lead.view` row, never `lead.view_pii`.
  The CRM's `POST /api/admin/leads/[id]/reveal` is the one reveal (`revealLead` has one
  caller, asking for the score's reasons only). The legacy panel island had already gone in
  C4b; the PATCH's two refusals stay (`status` and `internalNotes`, each a 422 naming the
  field): they write nothing and tell a stale tab what to do.
- **No legacy column in any query.** `src/lib/admin/leadFields.ts`: `SAFE_LEAD_COLUMNS` loses
  `status`; `GATED_LEAD_COLUMNS` and `SENSITIVE_LEAD_COLUMNS` lose `timeline_band`,
  `internal_notes` and `ip_inet`. `LEGACY_LEAD_COLUMNS` names the four once, for
  `stripSensitive` (a row from today's schema never carries one into a response) and the
  tests, never for a query. `src/lib/crm/reveal.ts` drops the legacy field set, and
  `PLAIN_GATED_FIELDS` keeps `score_signals` only. The reveal answers `timeline` alone (the
  visitor's words, or a legacy band's label, which the daily cron stored there encrypted,
  0035), and `LeadContactCard` shows it or "Not given".
- **The export** (`src/pages/api/admin/leads/export.ts`, `src/lib/crm/exportRead.ts`,
  `packages/schemas/crm.ts`): no `status` column or filter and no `timeline_band` column. The
  PII rules are unchanged: contact details only for `export.csv` holders through the
  lockdown, decrypted under one imported key, never the score's reasons. The notes: the file
  carries each lead's note COUNT from the thread (`public.crm_lead_note_counts`, service
  role), never a note's words, as crm.md §9 decided ("Drops note bodies"); the words leave
  only through the thread's own audited door. A link that still carries `?status=` (one saved
  from the legacy panel) is refused with a 422 naming the field and saying "Choose a stage
  instead", before a slot, an audit row or a lead is touched, rather than exporting more than
  it asked for. `scripts/bench-lead-export.mjs` measures the new row shape.
- **notify-lead** reads the lead without `timeline_band` and hands a PII recipient the
  decrypted timeline only; its field gating (`receivesLeadPiiUnasked`) and the stored field
  names are unchanged.
- **The daily index cron** (`src/lib/crm/indexBackfill.ts`) reads no band and sends no
  `p_timeline_text_enc`: `crm_index_lead`'s default (null) leaves the timeline as it is, and a
  call that does not name the parameter keeps working whatever C14b does with it.
- **CRM settings** (`src/lib/crm/settings.ts`, the screen's types) no longer read or answer
  `crm_settings.timezone`: the studio's one zone is `site_settings.timezone` since U9 (0102,
  `src/lib/admin/studioTimeZone.ts`). (C9a's follow-up and the prompt say `site_profile`; U9
  put it in `site_settings`, its recorded departure.)
- **The unused legacy schemas** (`LeadStatusSchema`, `LeadUpdateSchema`,
  `LeadListQuerySchema`, `ExportQuerySchema` in `packages/schemas/admin.ts`) are gone.
- **The admin e2e.** `/admin/leads`'s locked-screen twin was the removed GET; it is now
  `GET /api/admin/crm/stages` (the board's twin already), and `adminRoutes.spec` holds that
  every twin serves a GET that refuses each role the screen refuses.
- **Dashboard counts, the preview dataset, database types.** Nothing to change: the counts
  read "initial stage and not spam" since C4a/C4b, the preview dataset
  (`src/lib/preview/dataset.ts`) reads no CRM table, and the repo has no generated database
  types file. The static gate below keeps it so.

## Both schemas, and how it is proven

C14b will be applied to production while this code is live, so every query here must work on
today's schema (the four columns present, the legacy sync and the notes mirror still running
inside `app.tg_lead_pipeline` and `app.tg_lead_timeline`) and on C14b's (the columns gone). A
query that names none of them does both: PostgREST answers a dropped column with 42703, and a
column that is there but unnamed is simply not returned.

- **The static gate**, `tests/lib/leadsContract.spec.ts`, reads `src/`, `packages/`,
  `scripts/` and `supabase/functions/` with the TypeScript parser (comments are not code):
  `timeline_band` and `ip_inet` are named only by `LEGACY_LEAD_COLUMNS`; `internal_notes` only
  there and in job-application code (`job_applications` keeps its own, 0029); no lead query
  names any of the four (a `.from('leads'|'leads_safe')` chain, the variable it is kept in and
  the calls made on it later, the crud helpers called with `'leads'`, an embedded `leads(...)`
  read from another table), following every name such a query uses to what it holds (a
  constant, an import, a function's result, a parameter's call sites, a name destructured from
  a row, so createLead's fallback insert is covered); no `crm_settings` query names
  `timezone`; the list route exports no GET; no endpoint case drives a removed route; no
  string asks a lead route for `?pii=1`. The reader is tested on the ways a query can be
  written, and on values, member reads and other tables it must leave alone.
- **Behaviour on both schemas.** Stand-ins that answer a dropped column with 42703, as
  PostgREST would, drive notify-lead (`tests/api/notifyLead.spec.ts`), the index cron
  (`crmIndexBackfill.spec`), the detail GET, `?pii=1` and the PATCH (`leadsAdmin.spec`, every
  test on both schemas), the reveal (`leadDetailApi.spec`) and the export (`leadExport.spec`).
- **Endpoint cases.** `tests/authz/cases/leads.ts` loses "leads list" (the removed GET);
  `endpointCoverage` holds completeness. The per-role cases of the reveal and the notes thread
  are unchanged: Admin, Developer and Sales allowed; Content Creator, SEO, anon and
  `other_tenant` refused. `leadDetailApi.spec` adds that Admin, Developer and Sales get the
  same audited reveal with no legacy field.

## Departures from the design, and why

1. **The plaintext band is not moved any more** (crm.md §4.5, "timeline_band is encrypted").
   The cron moved a legacy band into the encrypted timeline since 0035; a query naming the
   band cannot run on C14b's schema, so C14a stops. Every lead the cron has indexed since
   0035 had its band moved (and the band cleared by `crm_index_lead`); a band left after that
   is one the cron could not read (a value outside the four, or a batch the key decrypted none
   of). C14b therefore starts with a read-back and refuses to drop the column while any lead
   holds a band and no timeline (Notes for C14b, step 1), so nothing is dropped silently.
   Owner question 1.
2. **The export refuses a legacy `?status=` link (422) rather than ignoring it.** Ignoring it
   would export every stage for a link that asked for one; the PATCH already refuses the same
   key with the same words.
3. **`?pii=1` answers the safe view, not an error.** The parameter is simply not read, so a
   stale tab gets what a plain GET gets and nothing is spent or decrypted. A 400 would have
   needed the route to read the very parameter it no longer honours.
4. **`LEGACY_LEAD_COLUMNS` stays in `leadFields.ts`** for `stripSensitive` while today's
   schema holds the columns, and for the tests; C14b (or a later slice) can delete it.
5. **crm.md names the drop migration "0041"** (its number when the design was written) and
   lists only `status`, `internal_notes` and `ip_inet`. Numbers are assigned at merge now, and
   the prompt and C9a/U9 add `timeline_band` and `crm_settings.timezone`; C14b's plan below
   covers all five. `consent_marketing` is not renamed (crm.md's "may"): a rename is its own
   expand and contract, a third PR, and nothing needs it.
6. **No help guide changes.** No leads, CRM settings or Sales guide describes the legacy list,
   the alias, the status filter or the band, and this PR carries no migration to put one, so
   no `sort_order` is taken.

## Notes for C14b (the migration, its own PR, after this one has deployed)

Order (launch runbook §5a): this PR merges and deploys; at least one release passes with no
legacy writer (crm.md CRM-14: an old Worker version in the field must never meet a dropped
column); then C14b alone is applied to production and merged. C14b changes no Worker code,
only the tests and docs listed below.

**Read-back before writing it** (production, one SELECT, each count expected 0 unless said):

```sql
select
  (select count(*) from public.leads
    where timeline_band is not null and timeline_text_enc is null)        as bands_not_moved,
  (select count(*) from public.leads where timeline_band is not null)     as bands_left,
  (select count(*) from public.leads where ip_inet is not null)           as addresses,
  (select count(*) from public.leads l
    where nullif(btrim(l.internal_notes), '') is not null
      and not exists (select 1 from public.lead_notes n
                       where n.tenant_id = l.tenant_id and n.lead_id = l.id
                         and n.source = 'legacy'
                         and n.body = left(l.internal_notes, 5000)))      as notes_not_mirrored,
  (select count(*) from public.leads where length(internal_notes) > 5000) as notes_truncated,
  (select count(*) from public.leads where stage_id is null)              as leads_without_stage,
  (select count(*) from public.crm_settings c
     left join public.site_settings s using (tenant_id)
    where s.tenant_id is null)                                            as zones_without_row;
```

`bands_left` may be above 0 only for leads that also hold a timeline (the band is then a
copy). `bands_not_moved`, `notes_not_mirrored`, `notes_truncated` or `zones_without_row`
above 0 stops C14b until the owner decides (owner question 1).
