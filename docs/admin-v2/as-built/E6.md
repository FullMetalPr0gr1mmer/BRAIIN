## Plan (written before the build)

Releases stay off in production until R14. With releases off every save is live; with them on
the singleton kernel and the resource kernel stage it (R3b, R12b). There is no second write
path: the footer's basics are the identity singleton's existing PATCH
(`/api/admin/site-profile`, `settings.general`), the columns are the navigation API's existing
routes (`/api/admin/navigation`, `nav.edit`). No new API route, no new capability, no new
table.

### Storage

- **The basics** already exist (U9, 0102): `site_profile.footer_copyright` (bilingual
  template, only `{year}`, `{brand}`, `{place}` braced), `footer_style` (light, dark),
  `footer_show_email` (default true), `footer_show_social` (default false). They stage with
  the identity (the registry's `site_profile` row lists them since 0102) and keep its history
  (R14-prep). E6 adds no column there.
- **The columns** are navigation heading rows (AV-29): `navigation.is_heading boolean not null
  default false`, and `href` becomes nullable, held by one CHECK
  (`navigation_heading_shape`): a heading has no link, is in the footer, is top level and is
  never the key link; every other row keeps a link (so every existing row is valid as it is).
  A column's links are the footer links whose parent is the heading (the existing `parent_id`).
- **At most four columns** per tenant: a BEFORE trigger (`navigation_footer_columns`, INVOKER,
  after the release guard by name) takes a transaction advisory lock per tenant, counts the
  tenant's other heading rows under the writer's RLS and refuses a fifth with 23514 naming
  `navigation_footer_columns_max` (the kernel maps it to a 422). Counting hidden headings too:
  a column hidden today is one shown tomorrow.
- **The release registry**'s `nav_item` row restated with `is_heading` appended (0038's row
  otherwise word for word), so a release stages and publishes a heading like any other column;
  the TypeScript registry derives the same list from the resource's fields.
- No grant changes: anon's table-level SELECT on `navigation` (0011) reads the new column as
  every other; staff write it under the table's RLS (`navigation_write`, Admin and Content
  Creator).
- **The help guide** `footer` (H11's put, revision 0, place 44, caps `settings.general` and
  `nav.edit`, screen `/admin/appearance/footer`).

### The public footer (Tier A, zero hydration)

- `getFooterNavigation()` (`src/lib/data/navigation.ts`) reads the footer's visible rows with
  `is_heading` through the content seam and never throws; the header's `getNavigation` is
  unchanged.
- `SiteFooter.astro`:
  - the copyright line from the template (`src/lib/appearance/footer.ts`, pure): `{year}`
    (Arabic-Indic in Arabic, as today), `{brand}` (site_profile, §1), `{place}`; no template is
    today's line exactly;
  - the mailbox only while "show the email" is on (default on);
  - the visible social accounts as small icon links while "show social icons" is on (default
    off);
  - the columns, at most four, each a `<nav>` named by its heading with its links; footer links
    outside any column stay in today's flat list; no heading means today's list exactly;
  - `data-style="dark"` on the `<footer>` for the dark style; `global.css` maps it to the dark
    variant (contrast-audit entries for its pairs);
  - the legal links hard-wired as today (PDPL), whatever is saved.
- Byte-identical with no new settings and no heading: `tests/render/siteChrome.spec.ts`'s
  snapshot unchanged, EN and AR. CSP unchanged (no inline style, no script, no new origin).

### The admin screen: `/admin/appearance/footer`

- Appearance › Footer in the sidebar for `settings.general` or `nav.edit` holders (Admin,
  Developer, Content Creator); each card for its own capability:
  - **Basics** (`settings.general`, Admin and Developer): the copyright template (bilingual,
    blank is the built-in line, the three placeholders explained), the style (Light, Dark),
    show the email, show social icons (the accounts are in General), saved through the
    identity singleton with useEntitySave and EditorForm (explicit Save, 409, release mode,
    History of the site identity as on General); beside it a sketch of the footer drawn from
    the form (classes and `data-*`, no `style=`).
  - **Columns** (`nav.edit`, Admin and Content Creator): the footer's columns in order with
    their links; Add a column (bilingual title; refused past four), Move up and Move down, the
    eye, and a column picker on every footer link (which column it sits in, or none), each one
    versioned write of the navigation API, marked in release mode (R12b); Edit and removal on
    the Menus screen, whose form gains "Column heading" (no link needed).
  - **Legal links**: Privacy, Terms and Cookies shown locked: "Always shown: required by the
    Saudi data law (PDPL)".
- The help guide, the page guide entry, the sidebar link and the stylesheet (rule 4).
