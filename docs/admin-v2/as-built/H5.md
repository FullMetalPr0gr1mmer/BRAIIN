# H5: the audit chain is serialized

- **Lane:** hotfix, found by F0's signed-in sweep
- **Design:** none (a live defect, found after the program's hotfix table was written)
- **PR:** #36, merged as `c0a56e6` on 2026-10-07
- **Migrations:** 0031 (`0031_audit_chain_serialize.sql`), applied to production before the merge

## As built

**Why.** The signed-in admin sweep (F0) signs four roles in at once, and the Activity log then
reported "Chain break detected at entry 2". `app.tg_audit_chain()` linked each row to the
latest one with a plain SELECT, so two transactions inserting at the same moment both chained
off the same predecessor and the chain forked. Because the bigserial id was taken by its
DEFAULT before the trigger ran, a row could also sit below the row it followed. Any two audited
actions at once could reach it, and the hourly anchor verifier would have paged on a false
tamper alarm.

**What shipped.**
- The trigger takes a per-tenant, transaction-scoped advisory lock, then takes the row's id
  under it (`nextval`), then reads the predecessor. Same payload, same HMAC, same Vault key.
- It refuses an insert outside READ COMMITTED (0A000) before taking the lock: under REPEATABLE
  READ or SERIALIZABLE the read after the lock would reuse the statement's snapshot, so the
  chain could still fork silently. Every path today runs at READ COMMITTED. (Added in review.)
- The postconditions and pgTAP (`audit_chain.test.sql`) pin the per-tenant lock key and the
  order: isolation check, lock, id, predecessor read.
- The migration's header explains how to recognise a fork made before 0031 (two rows naming
  the same `prev_hash`, each a valid HMAC) without editing the append-only log: a `prev_hash`
  that names no existing row is the only unexplained break.
- CLAUDE.md §3 records the property: one writer per tenant chain.
- The PR also carried a lockfile-only patch for four advisories (sharp, source-map-js,
  compression, proxy-addr) that had turned every branch's supply-chain gate red.
