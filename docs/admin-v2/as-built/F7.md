# F7: sign-in v2, keep me signed in, forgot and reset password

- **Lane:** UI (Wave 1)
- **Design:** README "Slice sequence", F7 [AV-06]; [ui.md](../ui.md) "Login, forgot and reset
  (AV-06)" and "AV-06: Sign-in v2, keep me signed in, forgot and reset password"
- **PR:** #61 (branch `feat/f7-sign-in-v2`)
- **Migrations:** none

## What was built

- **Three screens, zero JavaScript.** `/admin/login` (Welcome back, Email, Password, "Keep me
  signed in", "Forgot password?"), `/admin/forgot` and `/admin/reset` are plain HTML forms in
  their own shell, `src/layouts/AuthLayout.astro`: the prototype's split layout (the rider
  still under a midnight gradient, the quote with the host from `PUBLIC_SITE_URL`, the logo with
  the brand from `site_profile` as its alt). `login.astro` lost its `<script>` and its
  grandfathered entry in `tests/lib/adminConventions.spec.ts`; the shell carries no script
  either, and the test says so.
- **The sign-in page's script, before and after** (`npm run size`, gzip, KB = 1,000 B): F4a had
  already taken it from 168.4 KB (admin-ui) to **2.2 KB** (the login script and `admin-client`);
  with AdminLayout's own script the page loaded 2.9 KB. Now **0 B** on all three screens. The
  gate (`scripts/admin-bundle.mjs`) weighs every sign-in screen and their shell against the
  10 KB budget and reports the 0. On its base the admin bundle sum went 225.37 → 224.93 KB;
  merged with F8 it is 228.11 KB (of 300), each screen's eager graph 107.7 KB.
- **Endpoints.** `POST /api/admin/auth/login` (extended), `/forgot` and `/reset` (new). A form
  post gets a 303 (back to its page with an outcome code, or on to `next`); a JSON post gets
  JSON. `src/lib/auth/body.ts` reads both; `src/lib/auth/messages.ts` holds the fixed copy a
  page renders for a code, so nothing typed and nothing written into a link is echoed. The
  middleware's pre-auth paths are these three pages and three endpoints (two before).
- **Keep me signed in** (owner item O-14: on by default). `LoginSchema.remember` (default
  true; a form sends the box only when ticked). Ticked: the session cookie carries Max-Age 7
  days and is written again at each token refresh, so the browser drops it **7 days after the
  last refresh**. Unticked: session cookies, which end **when the browser closes** (one that
  restores its session on restart keeps them). The choice is a third `__Host-` cookie,
  `__Host-braiin-session-only`, because a browser never sends a cookie's attributes back and
  a refresh must know which kind to write. It is written only once a sign-in has succeeded:
  until then the choice lives for the request (`chooseSessionPersistence`, then
  `commitSessionPersistence`), so a failed attempt, say a wrong password typed into a login
  page left open in another tab, never changes the lifetime of a session already open in the
  browser (F7 review; before, it did).
- **What the 7 days bound, and what they do not** (F7 review). They are the cookie's lifetime.
  The refresh token inside it is Supabase Auth's, valid until a sign-out or a reset revokes
  it, or Auth's own session limits (an inactivity timeout, a time-box) end it; neither limit
  is set on the local stack, and on a hosted project they are a dashboard setting on a paid
  plan (launch runbook §2c, folded into owner item O-24). So a cookie value copied off a
  machine keeps working past the 7 days. CLAUDE.md §3 now says exactly that, where it said
  sessions last "at most 7 days from their last use"; `tests/lib/session.spec.ts` holds the
  sentence to the cookie's number and the residual.
- **Forgot.** One answer for every address: status, body, page, and time (the call to Supabase
  runs after the response, `waitUntil`). Limits per IP (5 an hour), per e-mail as an HMAC (3)
  and per tenant (50), on EXC-004's Postgres counter with new scopes, failing closed. One audit
  row per accepted request (`auth.password_reset_requested`), service role, no actor.
- **Reset.** The page carries the e-mail's `token_hash` to the endpoint, which in one request
  verifies it, sets the password, signs the account out everywhere (`signOut({ scope:
  'global' })`), clears this browser's session cookies, and audits `auth.password_reset`
  against the account. Per-IP limit (10 an hour), failing closed. What the person is told
  depends on whether the link is still good: a short, long or mismatched password, our limit,
  and a verify the auth server throttles (429) or cannot answer (5xx, the network) keep it, and
  the form comes back; an invalid link, a password the auth server refuses (`refused`) and a
  set that breaks after the verify (`interrupted`) spend it, and the page offers a new one.
  The last two log the account's id (from the verify) and the auth server's status and code
  to `system_logs` (`auth.reset`), never the token or the password.
- **Tests.** `tests/authz/login.spec.ts` (form answers, `next`, remember, the six pre-auth
  paths), `tests/authz/recovery.spec.ts` (forgot and reset end to end over stubs),
  `tests/lib/session.spec.ts` (Set-Cookie headers from Astro's own cookie jar),
  `tests/lib/authScreens.spec.ts`, `tests/schemas/auth.spec.ts`; e2e
  `tests/e2e/admin-sign-in.e2e.ts` (no session) and `tests/admin/signin.e2e.ts` (its own
  account: remember on and off, `next`, a full reset that signs a second device out, a spent
  link), CSP and axe on all three screens. The F0 harness still signs in through the form.
- **The screens' server markup, rendered in vitest** (F7 review). The CI preview is built
  with `AUTH_EMAIL_READY` off, so no browser suite ever saw the forgot screen people get once
  e-mail is set up. `tests/render/authPages.spec.ts` renders the three pages, whole and with
  their real shell, through F6's render project (`vitest.render.config.ts`: Astro's own Vite
  config and container API), in both states: set up, a plain form posting to the endpoint
  with the CSRF field, no script, no `style=`, each `?status=` code's fixed copy under its
  role (`alert` or `status`) and nothing for an unknown one; not set up, no form and the
  notice; plus the codes the middleware sends a form back with, the reset page's link from
  its URL or its cookie, and its Referer policy. Before F6 merged, this branch compiled
  `.astro` files for the unit project with a plugin of its own over Astro's compiler, a
  dependency of `astro` and not of ours; the final review asked for it to load lazily, and
  F6's project made it unnecessary, so it is gone. The e2e forgot test now runs without
  JavaScript and empties the forgot limiter's windows on the local stack before it posts, so
  it holds once O-2 turns e-mail on for the CI build too (step 5 of runbook §2b puts
  `AUTH_EMAIL_READY` in `wrangler.jsonc`, whose `vars` the CI build reads).

## Departures from the design, and why

1. **Zero-JS forms, not an island.** CLAUDE.md §8 allowed either. A page reached without a
   session that loads no code has nothing to attack and nothing to download, and "the no-JS
   form" was something the design meant to keep. It did not work before: the endpoint read
   JSON only, so a post without JavaScript got a 400. Now it is the only path a browser takes.
2. **Their own layout.** AdminLayout's one script (sign-out, menus, the sidebar popover) would
   load on the sign-in screens for nothing, and the split layout shares nothing with the
   shell. AdminLayout keeps its `bare` mode (no page asks for it now; it is what a page gets
   with no session), so this slice changes only a comment there.
3. **A form post's failure is a 303 with a code, not a 401 or 423 status.** Post, redirect,
   get, as `/api/apply` already does; the address never goes into the URL. JSON callers keep
   the generic 401 and the lockout 423 exactly as before.
4. **The token is verified at submit, not when the page opens.** Mail scanners fetch links: a
   GET that spent the token would leave the person with a dead link, and holding the verified
   session between the GET and the POST would need it in a cookie, which would open the admin
   to whoever has the link before any password is set. So the page only checks the token's
   shape; the endpoint verifies it, sets the password and signs everything out in one request,
   on a client made for that request.
5. **The link carries `token_hash`, which needs the recovery template changed** (runbook §2b,
   the design's "PKCE vs hash" risk). Supabase's default link puts a session in the URL
   fragment, which no server reads; such a link shows "not valid" and offers a new one.
6. **A new password follows the account screen's rule** (F8, `packages/schemas/adminPrefs.ts`:
   at least 10 characters, at most 72 bytes, the most bcrypt reads; the auth server's own
   minimum is 10 too, owner item O-24), not a rule of its own: the design named none, and two
   floors for one account (a change and a reset) would be a policy nobody chose. This branch
   first had 12 to 128 characters (OWASP ASVS 4.0.3 V2.1.1); F8 merged first with 10, and
   72 bytes is also a correctness bound here, since the auth server refuses a longer password
   only after the link is spent. `newPasswordProblem` (`packages/schemas/admin.ts`) checks
   both before the token is spent, so a short, long or mismatched password keeps the link; a
   test holds it equal to F8's schema. Sign-in keeps its 8 to 256, which must still accept the
   passwords accounts hold. If Supabase then refuses the password (its own policy, or the same
   password as before), the token is already spent: the recovery session is signed out and the
   page asks for a new link, plainly.
7. **"Not set up" is a switch, `AUTH_EMAIL_READY`** (astro:env server var, default false),
   not a detection: nothing the Worker can reach says whether Supabase has SMTP. While it is
   off the forgot screen shows "Not set up" and no form, and the endpoint counts, sends and
   audits nothing: a JSON request gets `503 not-set-up`, a form post a 303 back to
   `/admin/forgot`, which shows the notice. The reset side works either
   way: its token can only come from a real e-mail (or, in e2e, GoTrue's admin API).
8. **The rate limits' numbers and failure mode** were not in the design: 5/h per IP, 3/h per
   e-mail, 50/h per tenant for forgot, 10/h per IP for reset, all failing closed (the counter
   shares Supabase's database, so when it is down a reset could not complete anyway). The
   tenant cap bounds what a crowd of addresses can make the endpoint do: each accepted
   request is a GoTrue call, maybe an e-mail, and a hash-chained audit row. It counts only a
   request the per-IP and per-e-mail windows let through (`checkForgotLimits`, F7 review):
   counted with them, a request one address's own limit had refused still spent the shared
   cap, so one machine sending 50 requests an hour closed "Forgot password?" for every staff
   member. What remains, by design: many addresses (each IPv6 /64 is one) can still spend the
   tenant's 50, which is the cap's job; and anyone who knows a staff address can spend its
   per-e-mail window with 3 requests, holding back that person's reset e-mails for the hour,
   never their sign-in. `tests/authz/recovery.spec.ts` holds both orders.
9. **The forgot audit row names no one.** The answer must not depend on whether an account
   exists, so the row has no actor and an empty detail, and holds no address and no IP (an
   anonymous visitor's address kept forever in an append-only log would be personal data with
   no purpose). The reset row is the account's, written by the service role too: the recovery
   session is never trusted with a write. Sign-in's own audit row gains `remember`.
10. **Two cookie defects, found and fixed.** The session cookie carried @supabase/ssr's
    Max-Age of 400 days, not the 7 the code said: the library passes its own default on every
    write and `setAll` forwarded it (`src/lib/auth/session.ts` now decides every lifetime).
    And `clearSessionCookies` deleted the `__Host-` cookies without `Secure`, a deletion a
    browser refuses, so sign-out left the (revoked) cookie in place; deletions now carry the
    prefix's attributes.
11. **No length hint under "Keep me signed in"**, as in the prototype; the lengths are in
    CLAUDE.md §3 and the UI lane.
12. **The art panel** is lazy and hidden below 900px, so a phone never downloads it; its widths
    and the logo's (the sidebar's 104 and 264, drawn at 140 CSS px) are on the `/_image`
    allow-list. The quote's second line is the sidebar's text token, not white at 70% (an AA
    pair, `scripts/contrast-audit.mjs`), and the gate gained `primary` on `bg`, the links on
    the light panel.

13. **The runbook section is §2b.** F8 merged first and took §2a (O-24, the current-password
    rule); F7's e-mail steps follow it, and its check now includes completing one reset after
    §2a's settings are on (a reset sends no current password: see Owner items). The F7 review
    corrected it: the switch (`wrangler.jsonc`) reaches only production, so the staging check
    runs a local build; and it gained the link's lifetime, a Supabase setting the copy's "one
    hour" depends on (pinned locally as `otp_expiry = 3600` in `supabase/config.toml`, held to
    the copy by `tests/lib/authScreens.spec.ts`). Session limits are §2c.

14. **A sign-in form the CSRF check refuses goes back to its page** (F7 review). Before F7 the
    login used `fetch()` and showed the middleware's JSON 403 as its own message; as zero-JS
    forms, the browser showed `{"ok":false,"error":"csrf"}` itself, with no way back. A person
    meets it in ordinary use: `__Host-csrf` is a session cookie, so a sign-in tab a browser
    restores after a restart carries a token that matches nothing. Now a urlencoded post to
    one of the three endpoints that fails the token check gets a 303 to its page with
    `expired-form` ("This page was open too long. Please try again."), and the page's GET
    mints a new token (`src/lib/auth/expiredForm.ts`, called by the middleware). The handler
    never runs. Only what the page already had goes back: `next` (held to /admin) in the URL,
    and the reset link's token (shape-checked) in the reset page's cookie (departure 17), so
    the reset form comes back with its link intact. A JSON post, a post carrying the token header, any other path, and a mismatched
    Origin keep the JSON 403 (a cross-site form post never reaches the middleware: Astro's
    `checkOrigin` answers it first).

15. **A finished reset does not lift a sign-in lockout; the notice says so** (F7 review). The
    usual way to a reset is a few wrong passwords, then "Forgot password?", and the lockout
    (5 failures in 15 minutes, 0009's `login_is_locked`, plus `profiles.locked_until`) still
    stands when the reset is done, so the new password could be answered "Too many attempts".
    Clearing it needs a definer RPC over `login_attempts` and `profiles`, so a migration,
    which F7 does not take. The `reset=done` notice now ends "If sign-in was locked after too
    many attempts, it opens again within 15 minutes." (`RESET_DONE`, from
    `LOCKOUT_DURATION_MINUTES`). Keeping the lock is not a hole: whoever completed the reset
    holds the mailbox, and the lock ends on its own within the 15 minutes. Whether to clear
    it on reset is an owner decision (below).

16. **`next` is judged as the browser resolves it** (final review). `safeNext` used to test
    the string: `/admin/../services`, `/admin/%2e%2e/x` and `/admin/..//evil.example` start
    with `/admin/` but resolve outside it (the last to `//evil.example`, which an authored
    redirect, consulted after a 404, could send on to another site), and a raw `/admin/日`
    in the Location header threw and made a successful sign-in a 500. It now resolves the
    value against a placeholder origin and keeps the resolved path, query and fragment when
    the path is `/admin` or under it: dot segments resolved, everything outside ASCII
    percent-encoded, backslashes and control characters still refused.
    `tests/lib/authScreens.spec.ts` sweeps Latin-1 and beyond and holds every answer to a
    valid header value under /admin; `tests/authz/login.spec.ts` drives the endpoint. The
    second review found the path Astro routes can differ from the browser's: Astro decodes a
    path up to ten times and resolves the dots it then finds, so `/admin/%252e%252e/old-page`
    reached the middleware as `/old-page` (a 404 the authored redirects answer). `safeNext`
    then decoded the path the same way and held that result to /admin as well; the third
    review found it imitated Astro in the wrong order. It resolved the dots before it
    collapsed doubled slashes, and Astro 7.3.5 collapses first (`fetch-state.js`: decode,
    collapse, the URL setter, collapse), so in `/admin//%252e%252e/old-page` the empty segment
    took the `..` here, while in Astro it popped /admin and the middleware read `/old-page`
    again. So `safeNext` no longer imitates: it decodes as Astro decodes (up to ten decodings
    that change the path), and refuses any path a later step of Astro's could move: a dot
    segment, a doubled slash, a backslash (the setter reads it as a slash), a control character
    (the setter drops a tab or a newline), or a `%` left once decoded, as well as one that
    cannot be decoded or needs more than ten decodings. A `next` of `/admin//leads` now goes to
    `/admin`. `tests/lib/authScreens.spec.ts` runs the review's inputs, and a corpus of about
    6,300 dot, slash, backslash and control-character paths at every depth of encoding,
    through Astro's own installed helpers (`validateAndDecodePathname`, the slash collapse,
    `setPathname`, `createNormalizedUrl`): every value kept routes under /admin for the router,
    the middleware and a rewrite (the `safeNext` before it kept 537 of those paths that Astro
    routes outside /admin). The ten-decoding limit has its own test: a path that takes ten
    decodings is kept and one that takes eleven, each of them succeeding, is refused by the
    limit (the earlier case failed at its second decoding, so the limit was never reached:
    raising it to 1,000 broke no test; now raising it or lowering it to 9 does).

17. **The reset link's token is kept out of request URLs where the code can** (final review).
    `wrangler.jsonc` turns observability on, so Workers Logs record every request URL, and
    the link carries its token in the query string: the e-mail click, a mail scanner's
    prefetch, and, until now, every 303 back to the page for a failure that keeps the link
    (`?token_hash=…&type=recovery&error=…`), one more logged URL each. Now that 303 goes to
    `/admin/reset?error=<code>` and the token rides in `__Secure-braiin-reset`
    (`src/lib/auth/resetToken.ts`): HttpOnly, SameSite Strict, Path=/admin/reset so no other
    request carries it (a `__Host-` cookie would need Path=/), 15 minutes long. The page reads the link's own token first, else the cookie's, and drops the cookie in the same response that puts the token in its form (second review: until then a kept link was offered to the next person on the browser for 15 minutes); a reload of `?error=…` then says to open the link again; every answer that spends the link, or sets
    the password, drops it. The expired-form 303 does the same. The page also sets
    `<meta name="referrer" content="strict-origin">` (an `AuthLayout` prop), so its form post
    and links send the origin alone as Referer, not the URL with the token; not
    `no-referrer`, which makes a browser send `Origin: null` on the post, which Astro's
    `checkOrigin` refuses. What stays logged (the click and the prefetch) is a residual risk
    in [deviations.md](../deviations.md), folded into owner item O-2.

18. **A pre-auth body is bounded before anything reads it** (final review). Anyone can post
    to the six pre-auth paths, and a body there was read up to three times with no bound
    (the middleware's CSRF clone, a refused form's clone, the handler). The middleware now
    refuses one over 16 KB first (`src/lib/auth/bodyLimit.ts`): by its declared
    Content-Length without reading anything, or, with none declared (chunked), by reading a
    copy up to the limit and no further. A sign-in form goes back to its page with
    `too-large` ("That form was too large to send. Please try again."), nothing of it read,
    so not even `next` goes back; a script gets a JSON 413. Nor the reset link: since the
    page drops its cookie in the response that puts the link in its form (departure 17), a
    too-large reset post comes back to a page with no link, which until the third review
    said only "To try again, open the link in your email once more, or ask for a new one."
    (true, the endpoint never ran, but silent on why; a comment and a render test still
    described a kept link). It now says "That form was too large to send." first
    (`RESET_TOO_LARGE`), and `tests/render/authPages.spec.ts` follows the middleware's own
    303s for a too-large and a stale-token reset post to the page each lands on. 16 KB rather
    than the 8 the review suggested: the largest form the schemas accept is about 9.3 KB (a
    2,048-character `next` of characters form-encoding triples, a 256-character password of
    3-byte characters, a 254-character e-mail, all at their worst once form-encoded), and a
    cap must never refuse a form a person can send; `tests/lib/bodyLimit.spec.ts` builds that form. `safeNext` now also
    refuses a `next` whose encoded form passes 2,048 characters, which is what bounds it.
    The second review found the same read on every other private path, older than F7: the
    session gate came after the CSRF check, which clones any urlencoded body without a token
    header, so a signed-out POST of any size to `/api/admin/leads` (Origin set to the Host is
    enough) was buffered twice before its 401, enough to exhaust the isolate's 128 MB and
    every request on it. Now a signed-out non-safe request to a path that needs a session is
    answered first (401 for the API, the sign-in redirect for a page), before any read; the
    pre-auth list is read without a trailing slash (`trailingSlash: 'ignore'` routes
    `/api/admin/auth/login/` to the endpoint, which skipped the cap); and signed in, the one
    body the middleware reads itself, a urlencoded form's clone for its token, is held to
    1 MB (`PRIVATE_FORM_BODY_LIMIT`). Not a blanket cap on every private body: the upload
    takes a raw file of up to 20 MB and checks its own Content-Length, and a handler's JSON
    is the handler's; both are reached only with a session and the token header.
    `tests/authz/login.spec.ts` drives it with an endless body that counts its reads: none
    before a 401. The third review found the 1 MB bound and the token reader asking different
    questions of the token header: the bound stood aside when `x-csrf-token` was there at all,
    while the reader looked in the body unless the header held a token, so an empty header
    skipped the bound and still had the whole form read. The bound, the reader and the sign-in
    forms' refusal now ask one question, `csrfHeaderToken` (`src/lib/http/csrf.ts`: a
    non-empty header), and the reader reads only what `tokenInBody`, the bound's own test,
    names. An 8 MB form with an empty header is now a 413 at the limit (it was a 403 after
    nine reads), and a sign-in form with one goes back to its page like any form.

## Owner items

- **O-2:** SMTP, the Site URL and redirect, the recovery template and the link's one-hour
  lifetime (Email OTP Expiration = 3600 s, which the forgot copy promises) on staging and then
  production, then `AUTH_EMAIL_READY` (runbook §2b). Until then "Forgot password?" says "Not
  set up". `AUTH_EMAIL_READY` is read when the Worker is built (`astro:env` inlines a public
  server variable, and `wrangler.jsonc`'s `vars` win over the build environment), so it takes
  effect with the production deploy that carries it, and turns the CI preview's forgot screen
  on too. There is no staging Worker, so staging is checked from a local build against
  `braiin-staging` with the switch in the build environment (runbook §2b, "Check it on
  staging"), before the `wrangler.jsonc` PR. Before that PR, also decide the reset-link
  logging residual ([deviations.md](../deviations.md), departure 17): accept it, turn
  Workers Logs' invocation logs off or sample them, or move the token into the link's
  fragment (a later slice).
- **O-24 meets O-2:** with "require the current password" on, whether the auth server still
  lets a recovery session set a password without it is not something the local stack can show
  (the CLI has no key for that setting). The runbook's §2b check completes one reset on staging
  after §2a's settings; if it is refused, `system_logs` (`auth.reset`) names the code, and the
  page tells the person plainly that the link is spent.
- **WAF:** rate-limit `/api/admin/auth/forgot` and `/api/admin/auth/reset` per IP when the zone
  exists (runbook §7).
- **Decision: clear the lockout on a finished reset?** Today the reset leaves it and the
  notice explains (departure 15). Clearing it would be a service-role-only definer RPC
  (forget the address's failures in the window and clear `profiles.locked_until`), called by
  the reset endpoint after the password is set: a migration number and pgTAP, in a later
  slice.
