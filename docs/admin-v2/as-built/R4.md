## What was built

Nothing calls it yet: R6 adds the publish and validate endpoints. It is inert by a database
fact, not a code convention: the apply answers 55000 for every tenant with no row in
`app.release_tenants`, which stays empty until R14.

- **`public.apply_release(p_actor, p_role, p_mode, p_items, p_note, p_kind,
  p_restores_release_id, p_release_id, p_scheduled_for)`**, SECURITY INVOKER, EXECUTE for the
  service role only, `search_path ''`, `lock_timeout 5s` (every lock wait, the advisory
  lock's included, ends in 55P03 after 5 s). Its SET clause also names `statement_timeout
  20s`, which bounds nothing inside a call (the timer is armed when a top-level statement
  starts; a function's SET clause does not re-arm it): it stays only for PostgREST's hoisting
  (see Open, R6), and no postcondition or test treats it as a cap. The full
  signature now (D6); modes `publish` and `dry_run`; `schedule` and `fire` answer 22023 until
  R11.
  1. Refuses any `current_user` but `service_role`, `postgres` included (D4, verification
     Q1f(2)); checks the call's shape: 1 to 60 changes (`RELEASE_MAX_ITEMS`, P-15), each
     exactly `{draft_id, draft_version, entity_type, entity_id, op, patch, base[, children]}`,
     each draft once, a note of at most 280 characters with no control character.
  2. The person publishing, live: active, unlocked, holding the role named (a demoted
     person's stale token names the old one) and a CMS role, else `BR403`. The tenant is the
     profile's (D1's flag is then asked for it: 55000 when off).
  3. `pg_advisory_xact_lock` per tenant: one release at a time.
  4. Each change against the registry (as the service role): a type it manages, patch keys
     within its writable columns (22023 naming the column: loud drift), never an immediate
     column, never a per-change schedule, a singleton keyed by its tenant and never removed,
     link sets only for a case study that stays. Then the drafts, locked in id order: each in
     the actor's tenant, unclaimed, at the version, type, id and operation the item names
     and, for an update, holding the same base as the item for every column it changes, else
     `BR409` `pending-changed` listing them. The draft's own `base` (not the request's) must
     cover every column an update changes (`BR422` `base-missing`), and is what the conflict
     check reads (review 5).
  5. The release row (`applying`, in the profile's tenant, named explicitly: Q1f(1)).
  6. The conflict check, before any write: each live row an update or removal touches,
     locked in registry order then id order; each changed column is compared with the base
     through `jsonb_populate_record` as the column's own type (`12.50` is `12.5`), whatever
     the row's version says (review 7: `app.tg_bump_version` keeps a version a writer sends
     when it differs from the stored one, so a version equal to the draft's base version
     proves nothing; `base_version` is no longer read by the apply). A missing row is a
     conflict `removed`. Publish: `BR409` `conflict` naming the draft and the columns; dry
     run: the same with the live and base values (for R12's "Compare"), and the change is
     skipped.
  7. The statements, built once from the registry (identifiers through `%I`, the column
     lists made of `%I`-quoted names only, values in `$1` read by `jsonb_populate_record`,
     the tenant in `$2`, the key in `$3`). `published_at` joins a change that publishes a row
     whose live value is null (a create published, a first publish), and never otherwise.
  8. The release token (`pg_current_xact_id()`) and the publisher's identity: claims
     `{sub, role: authenticated, app_metadata: {role, tenant_id}}`, `request.jwt.claim.sub`
     and `request.jwt.claim.role`, then `SET LOCAL ROLE authenticated`.
  9. The changes, as the publisher: creates and updates by apply order ascending (within one
     order, a change that sets a unique flag to true after the others, so a cleared flag
     lands first), then the self-references held back from them, then removals by apply
     order descending. Each statement names its row's draft to the capture trigger
     (`app.release_item`). A statement RLS filters (0 rows) raises 42501. A custom theme
     switched on switches the others off first. A case study's link sets go through
     `app.apply_portfolio_children`, their images before and after kept for a synthetic
     `portfolio_children` item.
  10. The `release.publish` audit row, as the publisher (`audit_insert` binds, D3): the
      number, the kind, the restored version, the count and `{type, id, op}` per change;
      never a value.
  11. Back to the service role; the claims, `claim.sub`, `claim.role` put back; the token,
      the release id and the item setting cleared (D7). Then the synthetic items, the drafts
      consumed, the release numbered (max + 1 under the lock) and live, with its publisher,
      count and areas.
  12. Returns `{release_id, number, items}`: the release's items in id order, then each
      team-member change as `{entity_type, entity_id, op, draft_id}` (no images, D2).
  Publish runs the changes in one exception block (fail fast): the first refusal becomes
  `BR422` `refused` with the draft, SQLSTATE, constraint, column and message, and nothing is
  kept. A dry run runs each change in its own block, collects `{draftId, sqlstate,
  constraint, column, message}` per refusal, and ends the whole block with `BRDRY`, which
  undoes everything (the release row, the token and the identity included) and uses no
  number; it answers `{mode, ok, item_count, conflicts, errors}`.
- **`app.tg_release_capture()`**, SECURITY DEFINER, `search_path ''`, owned by the snapshot
  owner (who bypasses RLS), executable by no API role. An AFTER INSERT, UPDATE and DELETE row
  trigger, `<table>_release_capture`, on the 19 registry tables but `team_members`, created by
  a loop over `app.release_entities`, with the table's generated columns (read from the
  catalog) left out of its images. It returns at once unless `app.release_token_valid()`;
  inside a release it appends `{before, after, op, draft_id, actor_id}`, the draft only for
  the row the apply named (a cascade, a set-null or a theme switched off gets none). An
  UPDATE that changes only the version and the stamp writes nothing.
- **`app.apply_portfolio_children(p_tenant, p_portfolio, p_service_ids, p_media)`**, INVOKER,
  `search_path ''`, EXECUTE for authenticated only: `save_portfolio`'s child section, moved.
  **`public.save_portfolio`** is re-created around it: same signature, settings, allow-list,
  parent logic and ACL (authenticated only); `rls_portfolio_children.test.sql`'s 27 rows pass
  unchanged.
- **`public.record_release_purge(p_tenant, p_release, p_status, p_tags, p_next_at,

  most 100, `<kind>:<value>` in lower case, each kept once) and merged side effects. P0002

- **`app.releases_enabled(uuid)`**: EXECUTE for the service role (was no API role).
- **Grants** (P-14, both regimes): each function revoked from PUBLIC, anon, authenticated and
  the service role, then granted exactly. No table, column or sequence is created.
- **Postconditions** (each says what it checks): both RPCs INVOKER with their settings and

## Departures from the design, and why

- **The conflict check runs as the service role, before the impersonation** (the brief's
  step 6 runs after it). `SELECT ... FOR UPDATE` under RLS also needs the UPDATE policy, so
  an SEO publisher's change to a service would have read as "removed on the live site" (a
  409) instead of the refusal it is (a 422 from RLS). Read past RLS, whether the row exists is
  a fact; whether this person may change it is still decided by their own policies, at the
  write. The rows are locked in registry order then id order, as designed.
- **The second pass runs after creates and updates, before removals** (the design: "after
  every item"). A self-reference moved off a row the same release removes (a link moved from
  a menu group that goes) would otherwise be deleted by the cascade before it moved.
  Removals come last because `services.discipline_id` is `ON DELETE RESTRICT`: a release that
  moves services to another discipline and removes the old one must move them first.
  Known limit, reported by the dry run: a removed row's unique flag (the navigation key)
  cannot be handed to another row in the same release, since the removal lands after the
  flag is set; publish the move, then the removal (R12's dialog can split it).
- **A removal that finds its row already removed by this release is done** (review 1).
  Removals of one type run by id, not by depth, and `navigation.parent_id` is `ON DELETE
  CASCADE`: removing a parent link before its child (by id) cascades the child away, and the
  child's own removal then matches no row. A removal that matches no row is a refusal
  (42501) unless this release has already captured that row's removal; then it is done,
  and captured once (pgTAP: two parent and child pairs, parent id first and child id first,
  in a dry run and a publish).
- **Publish uses two nested exception blocks, not one**: the outer block a dry run needs to
  undo itself (`BRDRY`) is shared by both modes, and a publish runs all its changes in one
  inner block. Still fail fast, with two subtransactions, not one per change.
- **A dry run's second pass is one block**, not one per change, so the subtransactions stay
  at most 62 (60 changes, the second pass, the outer block), inside the 64 a backend caches
  (verification claim 7). A refusal in it is reported for its draft and ends that pass.
- **The base is required up front for every column an update changes** (`BR422`
  `base-missing`), from the locked draft's own `base` column; the item's `base` must equal it
  for those columns (else `pending-changed`), so a request cannot hide a conflict by sending
  a base of its own (review 5).
- **Busy is not refused** (review 6): 55P03, 40P01 and 40001 leave both exception blocks
  unchanged, in a publish and a dry run, where any other error in a change becomes `BR422`.
- **`request.jwt.claim.role` is set and put back too**, beside the claims and
  `claim.sub`: `auth.role()` reads it first. No policy uses it today.
- **Restoring is explicit and on both paths**: the outer block's error handler and the
  success path each switch back to the service role and put the saved claims back (a
  subtransaction's settings would already be undone on error; the explicit restore makes the
  rule visible and pinned by the static spec).
- **More input refusals (22023)**: a removal carrying a patch, an update that changes
  nothing, a singleton removal, link sets on a removal, a rollback with no version to restore
  or a publish naming one, a restored version that is not a live release of the tenant.
- **`app.apply_portfolio_children` adds two lines** to the moved section: the tenant named
  must be the caller's (42501), and a project and a tenant are required (22023).
  `save_portfolio` always passes its own tenant, so its behaviour is unchanged. EXECUTE is
  authenticated only (§5.2 of the brief; its grants file list said "authenticated,
  service_role", which §5.2 itself corrects).
- **A children-only change does not touch the project row** (no version bump), where
  `save_portfolio` with an empty patch rewrites the row. The synthetic item carries the
  change; R6 can always send a patch if the parent's dates should move. It still proves the
  publisher may write the project (review 3): the project row is locked `FOR UPDATE` as the
  publisher first (the UPDATE policy binds; no row is 42501, a `BR422`), since RLS would
  otherwise filter the link-set deletes silently for SEO or Developer and the change would be
  consumed with nothing done. Link sets that name no set (`{}`, or both null) are refused
  (22023), in SQL and in `ApplyChildrenSchema`.
- **A removal whose row moved since the draft began is not a conflict** (a removal changes no
  column); a removal of a row already gone is (`removed`).
- **The release row's `created_by` is the publisher**, passed explicitly (the service role's
  claims carry no `sub`). The audit detail adds `restores` (an id, null for a publish).
- **`record_release_purge` also refuses any `current_user` but the service role**, keeps the
  stored tags when none are given, stores each tag once, and treats a release that is not
  live as not found.
- **One postcondition the design did not list**: the service role holds SELECT and UPDATE on
  every registry table, which the conflict check's `FOR UPDATE` needs.
- **The catalog check excludes extension-owned functions** (pgTAP's own, `pg_trgm`'s), so it
  holds in CI and on production alike.
- **No `migrations.md` row** was touched: `main` has no Wave 2 reservation rows yet, and the
  row moves to "Applied" with the production push (owner).

## Open

- **Staging rehearsal (R14):** the role switch needs PostgREST's `authenticator` to be a
  member of `authenticated` and `service_role` (the Supabase default). pgTAP switches roles
  from `postgres`, so it cannot prove `authenticator`'s memberships; the SECURITY DEFINER
  fallback stays documented, not built (releases.md §4.4).
- **R5:** the guard, and the capture of child-table cascades (`portfolio_services`,
  `portfolio_media` when a service or a project is removed) and of out-of-band writes. Until
  then a removal published before R5 cannot be fully restored; releases stay off until R14.
- **R6: the time cap is the caller's.** The function cannot bound its own run (above).
  PostgREST v12 hoists a function's `statement_timeout` into the transaction it opens
  (verification Q1e): confirm that on staging, or set a `statement_timeout` PostgREST applies
  for the service role, and keep the Worker's own request timeout and cancel either way.
- **R6:** build `p_items` with `ApplyRequestSchema`, map `BR403`/`BR409`/`BR422`/`55000`/
  `22023`, and map the three "busy" SQLSTATEs the apply passes through unchanged (review 6:
  55P03 a lock waited past 5 s, the per-tenant advisory lock included; 40P01 a deadlock;
  40001 a serialization failure) to a retryable answer, never to "refused", and run its per-change `assertCap` (the second layer, D8). `PUBLISHER_ROLES`
  equals the SQL's list; ROLE_CAPS stays the only source of who may publish what.
- **R6: links into another tenant (review 9).** `save_portfolio` checks that a case study's
  `sector_id`, `client_id`, `poster_media_id` and `next_portfolio_id` name rows of the
  caller's tenant (a bare foreign key would accept another tenant's row); the apply writes
  those columns through the registry with no such check (only the link sets, through
  `app.apply_portfolio_children`, are fenced). The same holds for every registry column that
  names another row (a service's `discipline_id` or `poster_media_id`, a case's
  `service_id`/`portfolio_id`, a testimonial's `client_id`...). R6's validation must hold
  each to the tenant (the overlay's `assertLinkInTenant`, releases.md §3) before it calls the
  apply; a database-side fence (composite keys, or a check in the apply) is a candidate for
  R5.
- **R10:** restore refuses team members ("History isn't kept for team members yet", D2) and
  reads the earliest `before` per entity (the second pass and theme switches add items).
- **Owner item O-12** decides whether `team_members` is ever captured.
