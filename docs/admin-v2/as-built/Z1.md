### 1. Admin visual baselines: pixel baselines made where CI runs, never a required gate

What the repository does today: E9 and E12 recorded visual regression as computed-style
assertions, contrast measured in the page, axe, and the design capture's pictures (an
artifact), never a pixel diff; nothing calls `toHaveScreenshot`. The reason holds here: CI is
Linux and every builder's machine is Windows, so a baseline made locally never matches the
runner's fonts and anti-aliasing, and a committed picture is only ever right when the runner
made it.

So the baselines are made by CI and committed by hand:

- `tests/visual/admin.visual.ts`: one `toHaveScreenshot` per capture route (the admin capture's
  set, `captureRoutes`: Admin on every screen its sidebar, tabs and inner links reach, the other
  four roles on their dashboard, for their sidebars) at 1440 x 900 and 390 x 844, full page,
  reduced motion, animations off, the caret hidden, fonts ready. Masked: every `<time>`, the
  relative and absolute dates the admin prints ("5 min ago", "3 Nov", "14:05", a year), the
  sidebar's counts, the KPI figures and their changes and sparklines, the dashboard's "ago"
  lines and the pages list's "edited" lines, the charts, and the editors' preview frame. Its name
  ends in `.ts`, not `.e2e.ts`, so no project of the required job ever collects it (the root
  `testMatch` is `**/*.e2e.ts`); the design named `admin.visual.e2e.ts`.
- `playwright.config.ts`: with `ADMIN_VISUAL` set (`update` or `compare`) one more project,
  `admin-visual`, after `admin-samples` and before any spec that writes, its baselines under
  `tests/visual/admin-baselines/<platform>/`. Unset (the required job), the projects are main's,
  field for field (`tests/ci/releasesRehearsal.spec.ts` keeps holding that).
- `.github/workflows/admin-visual.yml`: by hand only (`workflow_dispatch`, input `mode`), never on
  a push or a PR, never a required check, never a need of the deploy, read-only, actions pinned
  to the e2e job's commits, the e2e job's stack step for step up to the preview. `update` makes
  every baseline (`--update-snapshots=all`), then runs once more comparing against what it just
  made (AV-34's "stable across two runs"), and uploads the baselines as the artifact
  `admin-visual-baselines`; `compare` compares against the committed baselines
  (`--update-snapshots=none`) and uploads the report and the diffs when one differs.
  `tests/ci/adminVisual.spec.ts` holds all of that.
- The operator's steps are below ("Making the baselines"). Until the pictures are committed the
  spec runs nowhere but in that workflow; joining the required job is a later decision (a pixel
  gate makes every admin look change need a hand run first), recorded as a follow-up.

### 2. The per-role axe matrix with dialogs open

The F0 sweep already opens every screen each role's sidebar offers (plus its create and edit
screens) and runs axe on it. Z1 does not repeat that: it opens the dialogs.

- `tests/admin/dialogs.ts`: the registry. Each case names its screen (a sweep route, so the
  matrix follows the sidebar), who sees its trigger (from `ROLE_CAPS`), the steps that open it
  (the accessible names, traced against the markup and the specs that already press them), the
  dialog's name, its source files, and its widths. A case runs for every role whose sweep has
  the screen and who sees the trigger. The shell's dialogs (the palette, help, the bell, the
  account, and the phone menu's popover) run on the dashboard for every role at 1440 and 390.
- `tests/admin/dialogs.e2e.ts`: per role and case, open the screen, open the dialog, wait for
  exactly one open `<dialog>` (or the popover), check it has an accessible name (the case's,
  when it names one), run axe WCAG 2.2 A/AA (zero violations), close it with Escape and check
  that it closed and that focus went back to a shown element, never `<body>`.
- Dialogs opened only after a write, only with a row a spec makes, only with releases on, or
  only where opening them would take the shared preview down (maintenance) are named in
  `DIALOGS_COVERED_ELSEWHERE` with the spec that opens them with axe and the reason. Where such
  a spec opened the dialog without axe (the goal delete, the two SEO confirms, the maintenance
  confirm), that spec gains the axe check.
- `tests/lib/adminDialogs.spec.ts` (vitest): every admin source file that renders a dialog
  (`<Drawer`, `<Modal`, `<ChromeDrawer`, `<dialog`, `createElement('dialog')`, comments
  stripped) is named by a matrix case or a covered-elsewhere entry, or is one of the primitives;
  each case's screen is a sweep route of at least one role that sees it; ids are unique; each
  covered-elsewhere spec exists, names its dialog and runs axe.
- **Fix:** the shared confirm dialog (`src/lib/admin/confirm.ts`) had no accessible name (axe's
  `aria-dialog-name` is a best-practice rule, outside the WCAG tags, so nothing caught it; WCAG
  4.1.2 and ARIA require a dialog's name). It is now named by its message
  (`aria-labelledby`); `tests/lib/confirmDialog.spec.ts` guards it.

## Making the baselines (the operator's steps)

1. On GitHub: Actions, "Admin visual baselines", Run workflow, branch `main` (or the branch to
   baseline), mode `update`.
2. When it is green, download the artifact `admin-visual-baselines` (a zip of
   `tests/visual/admin-baselines/linux/`).
3. Locally, on a branch from that commit: unzip it into `tests/visual/admin-baselines/linux/`
   (the zip holds the PNG files at its root), look through the pictures (they are the admin as
   the seeded CI database shows it, with the masked regions pink), and commit them in a PR.
4. After that merge, run the workflow again with mode `compare`: green means the committed
   baselines match. A red run uploads `admin-visual-report` (the expected, actual and diff
   pictures); a change that was meant is re-baselined by steps 1 to 3.

## As built

### Departures from the design, and why

1. **The pixel baselines are not committed by this slice.** They can only be made where they are
   compared (the Linux runner), so the slice ships the spec, the project and the hand-run
   workflow, and the operator commits the first set (above). AV-34's "stable across two runs" is
   the `update` mode's second, comparing run.
2. **The spec is `tests/visual/admin.visual.ts`**, not the design's `admin.visual.e2e.ts`: the root
   `testMatch` is `**/*.e2e.ts`, so with that name the public `chromium` project would collect it
   (it lives under `tests/visual`), and every PR would run or at least skip it. Under `.ts` only
   the `admin-visual` project reaches it.
3. **The baseline set is the capture's** (`captureRoutes`): Admin on every screen the sweep
   opens (111 routes), the other four roles on their dashboard for their sidebars; at 1440 and
   390 that is 230 pictures. Every role on every screen would be about 600 pictures (tens of
   megabytes in the repository) for screens whose content the sweep and the dialog matrix
   already check per role.
4. **Masked**, beyond the design's "time and count regions": the KPI figures and their changes,
   the charts (their axes are dates), the realtime figure, and the page editor's and template
   editors' preview frame (the public page with its own motion). Masks are CSS, plus the admin's
   own date words and times found by text (`relTime.ts`'s "5 min ago", "3 Nov", "14:05").
5. **The axe matrix is `tests/admin/dialogs.e2e.ts`**, not `tests/a11y/axe.e2e.ts`: it needs the
   staff sessions, which only the `admin` project has (the F0 capture's reason). It opens dialogs
   only; the screens themselves are the sweep's.
6. **Dialogs the matrix leaves to their own specs** (`DIALOGS_COVERED_ELSEWHERE`, each with its
   reason): the job-application drawer, the integration drawer (already every role that sees it),
   the invite drawer and its cancel, the edit-user drawer and its confirms, Require 2FA, erasing
   a lead, maintenance on, a visibility mode's confirm, the upload dialog, Clear logs, a goal's
   delete, the site-wide noindex, the publish dialog and Change time (releases on), and the kit's
   samples (made-up data, the same for every role). Four of those specs opened their dialog
   without axe; they now run it with the dialog open: `stats-v2.e2e.ts` (New goal, Edit goal,
   the delete), `seo.e2e.ts` (the page's and the site's noindex confirms), `maintenance.e2e.ts`
   (the turn-on confirm), `kit.e2e.ts` (the arrange drawer).
7. **Known limit:** the maintenance and page-visibility confirms are opened as Admin only.
   Developer holds the same switches and sees the same components, but opening them in the
   shared `admin` project could take the preview down for every spec beside it, so they stay in
   their own projects, which run as Admin.
8. **A dialog's name is checked, and the shared confirm had none.** `confirmDialog`'s
   `<dialog>` is now `aria-labelledby` its message. axe's `aria-dialog-name` rule is a
   best-practice one, outside the WCAG tags every admin axe run uses, which is why no check had
   caught it.
9. **The row an edit screen opens is found in one place**, `tests/admin/openRoute.ts` (moved out
   of the sweep verbatim): the sweep, the capture's CSRF read, the dialog matrix and the visual
   baselines use it, and `adminRoutes.spec` holds all four to it.
10. **No `docs/admin-v2.md`**: AV-34 names it, but the program's decisions live in this folder's
    README since the program was approved; the closure is written there and in
    [deviations.md](../deviations.md).
