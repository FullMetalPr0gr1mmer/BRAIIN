## Plan (written before the build)

**Scope.** The server half of versions; R13 builds the screens (the Backups and versions page,
the history drawer) on it.

1. **History numbers.** `content_versions.seq`: a snapshot's place in its entity's history (1,
   2, 3 …), unique per `(tenant, entity_type, entity_id)` and in commit order, given by a
   BEFORE INSERT trigger on `content_versions` itself (so every path that writes history,
   the snapshot triggers, a migration or a test, is numbered the same way and none can supply
   or skip it), under a per-entity advisory lock, with a unique index as the backstop. Existing
   rows are numbered by `created_at, version, id`. `version` keeps the row's own version.
2. **The state at a version.** `public.release_as_of(p_tenant, p_number, p_limit, p_page)`:
   SECURITY INVOKER (staff read the ledger under RLS), one subrequest. For every entity the
   ledger touched after version N (release items and system items), the `before` of its
   earliest such item (its state at vN, null when it did not exist then) and whether it exists
   now (its latest item is not a removal); `portfolio_children` items give a case study's link
   sets. `p_page` limits it to one page and its sections.
3. **Endpoints** (each a case in `tests/authz/cases/releases.ts`):
   - `GET /api/admin/releases`: the versions, newest first, scheduled and failed on top.
   - `GET /api/admin/releases/[id]`: one version's changes, filtered by what the caller reads,
     with field-level before and after for plain and bilingual fields ("changed" for the rest).
   - `POST /api/admin/releases/[id]/restore` (`{scope?: {pageId}}`): stages the state at vN as
     pending changes through `write_drafts` (the person's own RLS) and marks them as a restore
     (`origin_kind`, `origin_release_id`, the service role: the draft lock lets no staff token
     write them). Refused, with the list, when an entity already has a pending change, when the
     caller cannot publish every change (P-2), when a link names a row that is gone and that
     the restore does not bring back (a deleted picture, a team member), when a stored image
     no longer reads as a change the editor could make, or above 60 changes (one release).
   - `GET /api/admin/history`: an entity's numbered snapshots (with the release that made each),
     its pending change, whether it is live or was removed (and in which version);
     `scope=page` lists the versions that touched a page or its sections.
   - `POST /api/admin/history/restore`: one snapshot staged as a pending change.
   - `POST /api/admin/releases` with `kind: 'rollback'`: publishes restore changes of one
     version as a rollback naming it (`restores_release_id`, default note "Restored vN").
4. **Row images back to changes.** `src/lib/release/rowPayload.ts`: a stored row (a ledger image
   or a snapshot) to the payload its editor would have sent, checked by a round trip through
   the entity's own schema and `toRow` (the publish path, A3-13), so a restore never stages
   anything the version did not hold.
5. **Preview of a version** (`/admin/preview/…?v=N`): R8's dataset in an as-of mode (the
   changes from vN to now, laid over live instead of the pending changes), R9's ribbon saying
   which version it shows.
6. **Inert.** Releases are off for every tenant: no release exists, so the list is empty and
   every version, restore and preview of one answers that it does not exist or 409
   `releases-off`; with the flag off every write path behaves as on `main` (the one database
   change on that path is the history number, proven in pgTAP).

**Files.** `supabase/migrations/0104_release_versions.sql`; `src/lib/release/{versions,
rowPayload, revert, restore, history}.ts`; routes under `src/pages/api/admin/releases/` and
`src/pages/api/admin/history/`; `src/lib/release/endpoints.ts` and `apply.ts` (the rollback
kind); `src/lib/preview/{dataset,routes,ribbon,report}.ts` and `src/lib/http/preview.ts`
(`?v=`); `packages/schemas/release.ts` (the shapes); `src/lib/admin/auditLabels.ts` (the
restore words).

**Tests.** pgTAP `release_versions.test.sql` (the numbering on every path, the backfill, the
lock and the index, `release_as_of` over admin, content creator, SEO, developer, a sales
claim, anon and another tenant, releases off unchanged); vitest `releaseRowPayload.spec.ts`
(every registry type round-trips), `releaseRevert.spec.ts` (as-of chains: create, update,
delete, cascades, link sets, system items, page scope), `releaseVersions.spec.ts` (the
endpoints over the PostgREST stand-in), `previewAsOf.spec.ts`; authz cases per route,
including a cross-area restore refused for a Content Creator.
