## Plan (written before the build)

**Scope.** The server half of versions; R13 builds the screens (the Backups and versions page,
the history drawer) on it.

1. **History numbers.** `content_versions.seq`: a snapshot's place in its entity's history (1,
   2, 3 …), unique per `(tenant, entity_type, entity_id)` and in commit order, given by a
   BEFORE INSERT trigger on `content_versions` itself (so every path that writes history,
   the snapshot triggers, a migration or a test, is numbered the same way and none can supply
   or skip it), under a per-entity advisory lock, with a unique index as the backstop. Existing
   rows are numbered by `created_at, version, id`. `version` keeps the row's own version.
2. **The state at a version.** `public.release_as_of(p_tenant, p_number, p_limit, p_page)`:
   SECURITY INVOKER (staff read the ledger under RLS), one subrequest. For every entity the
   ledger touched after version N (release items and system items), the `before` of its
   earliest such item (its state at vN, null when it did not exist then) and whether it exists
   now (its latest item is not a removal); `portfolio_children` items give a case study's link
   sets. `p_page` limits it to one page and its sections.
3. **Endpoints** (each a case in `tests/authz/cases/releases.ts`):
   - `GET /api/admin/releases`: the versions, newest first, scheduled and failed on top.
   - `GET /api/admin/releases/[id]`: one version's changes, filtered by what the caller reads,
     with field-level before and after for plain and bilingual fields ("changed" for the rest).
   - `POST /api/admin/releases/[id]/restore` (`{scope?: {pageId}}`): stages the state at vN as
     pending changes through `write_drafts` (the person's own RLS) and marks them as a restore
     (`origin_kind`, `origin_release_id`, the service role: the draft lock lets no staff token
     write them). Refused, with the list, when an entity already has a pending change, when the
     caller cannot publish every change (P-2), when a link names a row that is gone and that
     the restore does not bring back (a deleted picture, a team member), when a stored image
     no longer reads as a change the editor could make, or above 60 changes (one release).
   - `GET /api/admin/history`: an entity's numbered snapshots (with the release that made each),
     its pending change, whether it is live or was removed (and in which version);
     `scope=page` lists the versions that touched a page or its sections.
   - `POST /api/admin/history/restore`: one snapshot staged as a pending change.
   - `POST /api/admin/releases` with `kind: 'rollback'`: publishes restore changes of one
     version as a rollback naming it (`restores_release_id`, default note "Restored vN").
4. **Row images back to changes.** `src/lib/release/rowPayload.ts`: a stored row (a ledger image
   or a snapshot) to the payload its editor would have sent, checked by a round trip through
   the entity's own schema and `toRow` (the publish path, A3-13), so a restore never stages
   anything the version did not hold.
5. **Preview of a version** (`/admin/preview/…?v=N`): R8's dataset in an as-of mode (the
   changes from vN to now, laid over live instead of the pending changes), R9's ribbon saying
   which version it shows.
6. **Inert.** Releases are off for every tenant: no release exists, so the list is empty and
   every version, restore and preview of one answers that it does not exist or 409
   `releases-off`; with the flag off every write path behaves as on `main` (the one database
   change on that path is the history number, proven in pgTAP).

**Files.** `supabase/migrations/0104_release_versions.sql`; `src/lib/release/{versions,
rowPayload, revert, restore, history}.ts`; routes under `src/pages/api/admin/releases/` and
`src/pages/api/admin/history/`; `src/lib/release/endpoints.ts` and `apply.ts` (the rollback
kind); `src/lib/preview/{dataset,routes,ribbon,report}.ts` and `src/lib/http/preview.ts`
(`?v=`); `packages/schemas/release.ts` (the shapes); `src/lib/admin/auditLabels.ts` (the
restore words).

**Tests.** pgTAP `release_versions.test.sql` (the numbering on every path, the backfill, the
lock and the index, `release_as_of` over admin, content creator, SEO, developer, a sales
claim, anon and another tenant, releases off unchanged); vitest `releaseRowPayload.spec.ts`
(every registry type round-trips), `releaseRevert.spec.ts` (as-of chains: create, update,
delete, cascades, link sets, system items, page scope), `releaseVersions.spec.ts` (the
endpoints over the PostgREST stand-in), `previewAsOf.spec.ts`; authz cases per route,
including a cross-area restore refused for a Content Creator.

## What was built

Releases stay off for every tenant (`app.release_tenants` is empty until R14), and no version
exists while they are: the versions list is empty (`enabled: false`), every version is "not
found", a restore answers 409 `releases-off` after the flag read and reads nothing else, and a
preview of a version is a 404. Every existing write path is as on `main`: the one change on it
is the history number the database gives a snapshot (pgTAP section 3: a Content Creator's save
lands as before, its history row only gains `seq`), and the draft lock's one change binds only
callers no staff token is (below). `releaseOffWrites.spec.ts`, `stagedKernel.spec.ts`,
`overlayDb.spec.ts` and `releasePublish.spec.ts` are unchanged and green (one test of the last
renamed: a rollback is now refused on its kind because no restore staged its change, not
because restores did not exist).

### The migration (`0104_release_versions.sql`)

- **`content_versions.seq`** (int NOT NULL, CHECK ≥ 1, UNIQUE `(tenant_id, entity_type,
  entity_id, seq)`), given by `app.tg_content_version_seq` (BEFORE INSERT OR UPDATE, the only
  trigger on the table, SECURITY DEFINER owned by the snapshot functions' owner, `search_path
  ''`, callable by no API role): an insert takes a transaction-scoped advisory lock on its
  entity and numbers itself max + 1, whatever number it sent; an update keeps the number. The
  existing history is numbered per entity by `(created_at, version, id)` before the trigger
  exists; a postcondition checks every entity runs 1..n. `version` keeps the row's own version
  (`app.tg_bump_version` keeps a version a writer sends back, so two snapshots can share one:
  that is what `seq` is for).
- **`public.release_as_of(p_tenant, p_number, p_limit default 200, p_page default null)`**:
  STABLE SECURITY INVOKER, `search_path ''`, EXECUTE for `authenticated` alone (anon, PUBLIC
  and the service role nothing). It answers `{release, cutoff, total, entities[]}`: the version
  (published, the tenant's, else P0002), the last ledger item of any version up to N, and per
  entity changed after it, in the order first changed, its earliest before-image, whether it
  exists now and, for a page section, its page. Items of releases not published are never
  counted; team members never answered. Another tenant named is 42501, a bad number or a limit
  outside 1..2000 is 22023. The ledger's staff-only RLS decides who reads anything, so a Sales
  claim, another tenant and anon read no version.
- **`app.tg_draft_lock` restated** with one change (not in the design, departure 6): an UPDATE
  by a caller the lock does not bind (the service role, or no role claim) that names no user
  keeps the draft's `updated_by` (`coalesce(auth.uid(), old.updated_by)`) instead of clearing
  it. A bound caller (every staff token, a definer called with a staff claim) is stamped with
  `auth.uid()` exactly as before, and the provenance stays the unbound caller's alone. The
  postconditions restate 0062's lock checks and add this one.
- Postconditions: the column, CHECK and index; the 1..n numbering; the one trigger and its
  function (definer, owner, search path, no API role); `content_versions`' privileges as 0032
  left them (authenticated SELECT only of the seven; PUBLIC and anon nothing) and its staff-only
  read policy; the reader's shape and EXECUTE; neither new function calls `set_config` or
  switches role (R4's and R5's catalogs); the ledger's read policies still CMS staff only; the
  draft lock; releases still off.

### The reads (`src/lib/release/versions.ts`, `history.ts`)

- `GET /api/admin/releases` (kernel: `PENDING_ANY_CAP` at full, view or meta, so every CMS role
  and never Sales): published versions newest first, 50 a page (`?before=N`), the live one
  marked, a rollback naming the version it restored, scheduled and failed releases on top of
  the first page, people named through F8's `staff_directory` (a person it does not list is
  named null). The frozen payload of a scheduled release and a failure's message are never
  selected (the failure's code is).
- `GET /api/admin/releases/[id]`: one version's ledger items (at most 1,000), each listed only
  when the person reads its area (the others counted in `hidden`), with its area, label, whether
  it was a cascade or side write (no pending change of its own), and its fields: bookkeeping
  columns dropped, a plain value or a bilingual pair shown before and after (300 characters at
  most), anything else ("changed"), a quote's consent record "changed" only, a case study's link
  sets as `service_ids` / `media` changed.
- `GET /api/admin/history?entityType&entityId[&scope=page][&before=n]`: the person must read the
  entity's area (403 otherwise, so Developer never reads a service's history). Its numbered
  snapshots newest first (`seq`, the row's `version`, when, who, the version that made it, null
  for a save made while releases were off), live now or removed (and the version that removed
  it, from the ledger's delete item), its pending change (fields, author, whether it is
  scheduled or a restore) and whether the person may restore it (publishes that type, releases
  on). A snapshot's content is never listed. `scope=page` lists every version that changed the
  page or a section whose image before or after names it.

### Restoring (`src/lib/release/asOf.ts`, `revert.ts`, `restore.ts`, `rowPayload.ts`)

- **The state at a version** (`asOf.ts`): `readAsOf` (one call), `asOfTargets` (one target per
  entity, a case study's link sets beside its row, team members and unknown types dropped) and
  `asOfChanges` (what a preview lays over live: an edit carries the whole image, a removal since
  comes back as a create, a creation since goes).
- **A row back to its change** (`rowPayload.ts`): each entity's key map inverted (clips from
  their `preview_*` columns, page visibility's target and Riyadh days, a case study's link sets
  from the ledger's image), then the round trip: the payload is parsed and mapped as a publish
  would (`derivePatch`), and every allowlisted column the image holds must come back with its
  value (derived columns, restore-only columns and immediate ones aside), or the item is
  refused (`unrestorable`), never staged as something the version did not hold.
- **The plan** (`planRestore`): live read under the person's RLS (one read per table, the
  allowlist selected), the case studies' link sets, the pending changes. Per entity: only the
  columns that differ from live (an update; the link sets only when they differ), a row removed
  since back with its own id and link sets (a create), a row created since removed (a delete),
  except what no release removes (the identity, SEO defaults, an entity's search settings: left
  and listed as `kept`), and a page-visibility setting made since put back to public (a release
  never removes a setting). Refused whole, every item named: a pending change on one (409
  `pending-changes`), a change the person cannot publish (403 `forbidden`, with who could: the
  release publish matrix, P-2, including H12's rule that an edit leaving an archived row
  archived is an Admin's), then (422 `not-restorable`) an image that no longer reads, a link to
  a row that is gone and that the restore does not bring back (a deleted picture, a team member,
  a removed discipline), or an address (a slug, a redirect's source) that another item holds
  now and that the restore leaves as it is (edge case 5). More than 200 entities changed since
  (one draft write) or more than 60 changes (one release) is 422 `too-many` with the count. An
  item in an area the person does not read is named by its type and id only (no label).
- **Staging** (`restore.ts`): releases on (else 409); the version published and the tenant's
  (else 404 or 422); the plan; `liveRecheck`; one `write_drafts` call under the person's RLS (the
  drafts' policies, the live check and the draft lock bind as for any save); then the mark by
  the service role on exactly those new drafts at version 1 with no provenance yet
  (`origin_kind: 'restore'`, `origin_release_id`: the version, or null for one snapshot, whose
  publish is a plain publish). A mark that does not land (a co-author moved the draft, a dropped
  call) leaves ordinary pending changes, logged, `marked: false`. The answer names each staged
  change at the version it holds. Audit: `versions.restore` (the version's number, the scope,
  the page, the count, the types, the kept count) or `<type>.history_restore` (the snapshot's
  `seq`, the version that made it, the op): ids, counts and types, never a value.
- **One snapshot** (`POST /api/admin/history/restore`): the person must read its area first
  (403, whatever the flag), then the same plan over one target, the snapshot's row as its
  image. A snapshot keeps the row only: a case study's link sets stay as they are. Team
  members keep no history (422, "History isn't kept for team members yet").
- **The rollback** (`endpoints.ts`, `apply.ts`): `kind: 'rollback'` was refused by R6; now every
  selected change must carry one published version's restore mark (else 422 on `kind`), and
  `apply_release` gets `p_kind: 'rollback'`, `p_restores_release_id` and, with no note given,
  "Restored vN". The validate route sends the same to the dry run. Everything else is R6's
  publish, unchanged, H12's live read included.

### The preview of a version (`src/lib/preview/*`, `src/lib/http/preview.ts`, the bridge)

`/admin/preview/<path>?v=N` (N 1 to 999,999,999, once, never with `only`: 400 otherwise):
after the door, the handler reads the state at N with the person's own client (`release_as_of`,
at most 500 entities); no such version is a 404 that renders nothing; a ledger it cannot read is
a plain 503, logged with the route only. `createPreviewSource({asOf})` then lays the changes
back to N over live in place of the drafts read (no `content_drafts` read at all), each kept
only in an area the person reads (the others counted), through the same overlay, mirror and
report; more changes since than were read marks the render untrusted (`truncated`). The ribbon
names the version ("Preview of version N, as it was published. It's shown with today's design
and pictures."), says what it cannot show as it was, and its twin link, a redirect the page
answers and every link clicked in the page (the bridge) keep `v`.

## Departures from the design, and why

1. **A new column, `seq`, not a renumbered `version`.** `version` is the optimistic-lock value a
   row carried, which editors, the apply's base and `app.tg_bump_version` all read; numbering the
   history in its own column changes nothing that reads `version`.
2. **The state at a version in SQL** (`public.release_as_of`), not computed in `revert.ts` from
   the item chains: one subrequest whatever the ledger holds (P-15), read under the ledger's own
   RLS. `revert.ts` plans the restore over its answer; the preview reuses the same answer.
3. **No `POST /api/admin/releases/[id]/purge`.** A purge retry is R7's purge seam, which has not
   merged; there is nothing to retry until it does (the purge is a logged no-op, O-3).
4. **No staff-directory migration.** F8's `public.staff_directory(p_tenant)` exists (and C10a's
   0097 kept it for CMS staff).
5. **No e2e** (`releases-rollback.e2e.ts`): it needs the e2e workflow to switch releases on after
   seeding, which is R14's (as R6's departure 7). The SQL is pgTAP's, the Worker the stand-in's.
6. **The draft lock restated** (not in the design). Without it the restore's mark, made by the
   service role whose key names no user, cleared every restored change's author, which "Discard
   my changes", the savebar and the history's pending row read. The change binds only unbound
   callers that name no user; R11's claims (the same service role) gain the same. One
   consequence, handled in the Worker: a restored change now names the restorer, as if they had
   just saved it, so P-5's coalescing (one `draft_save` row per person per ten minutes) would
   have skipped their first edit of it, and the restore's own row (`versions.restore`) names the
   version, not the entity. `shouldAudit` (`src/lib/release/drafts.ts`) treats a restore's
   change still as the restore left it (`origin_kind` restore at version 2, the write and the
   mark) as not yet audited, so that first edit writes `<type>.draft_save` and the next one
   coalesces as before (`stagedKernel.spec.ts`).
7. **A taken address is refused at restore time** (the design: "reported" by validation). The
   dry run would refuse the publish with a unique violation anyway; saying so before anything
   is staged keeps a restore that cannot publish from leaving pending changes behind. A holder
   the same restore renames or removes is left to the dry run (edge case 6's ordering).
8. **A restore is at most one release** (60 changes, 200 entities read). A rollback published in
   parts would leave the site between two versions; "Restore a more recent version first" is the
   answer instead (owner question 2).
9. **Items of an unread area are named by type alone** in a refusal (the design lists them):
   their titles are not the person's to read in the admin.
10. **No help guide.** R10 adds no screen; R13 writes the versions guide with its page and
    drawer. The preview's guide (`previewing-changes`, R9) is unchanged: a version's preview is
    reached from R13's screens.
11. **History never lists a snapshot's content**, and a snapshot made while releases were off
    names no version, so R13's history "Preview" opens the version that made a snapshot
    (`?v=N`), and only for one made by a release.

## Found, not changed

- **`authenticated` holds MAINTAIN on `content_versions`** (PostgreSQL 17): 0032 revoked every
  other write privilege by name and MAINTAIN is Supabase's default; no API path can use it
  (PostgREST runs no VACUUM, ANALYZE, REINDEX or LOCK). 0104 grants and revokes nothing on the
  table, and the read-back records it. Revoking it is a privilege removal (critique 13: a gate,
  not a grep) for a later slice, or R15's contract.
- **The numbering's lock and a very large transaction.** Each snapshot takes one
  transaction-scoped advisory lock on its entity (kept from the first build: the entity's own
  row lock already serializes two writers of one entity, so the advisory lock guards only a
  direct insert, and the unique index is the backstop). A single transaction that snapshots
  more distinct entities than the shared lock table holds (`max_locks_per_transaction` times
  the connections, a few thousand on a small instance) would fail with "out of shared memory";
  a release is at most 60 changes and a seed a few hundred rows. A future bulk data migration
  over thousands of content rows should run in batches, or the lock can be dropped (the row
  lock and the index suffice).
- **Commit order and ledger order.** Items are ordered by their `bigserial` id, assigned at
  insert, and releases are serialised by the apply's per-tenant lock; an out-of-band write in a
  transaction that began before version N committed and ended after it could carry an id below
  N's last item and so not be undone by "Restore vN". The window is one transaction's length and
  needs a staff write racing a publish while releases are on.

## Self-review

Read once for security and authorization, once for correctness and the standard. Fixed: the
per-item restore read the flag before the area, so Developer got 409 rather than 403 for a
service's history while releases were off (the area now comes first, `history restore
(releases off)` row); a refusal listed the titles of items in areas the person does not read
(now type only); a page's history used `or` and `not` filters the readers' stand-ins (and
`.or()`'s quoting) would not carry (three plain reads instead); the preview threw on a ledger it
could not read (a plain 503 now, logged); the restore's publish reference lacked the live status
H12 added (an archived row's edit is an Admin's). Checked: every read is scoped to the caller's
tenant (the authz suite's other-tenant sweep covers the new routes); the service client is used
for the mark (ids the person's own write returned, at version 1, no provenance yet), the live
re-read and nothing else; no database message or stored value reaches an answer or an audit
row; a restore never writes a live table (the stand-in records none).

## Deploying

Expand, so the push comes first (rule 5), then the merge. Nothing deployed reads
`content_versions` (no parser to check, rule 5) and `release_as_of` is new. Run
`readback_r10.sql` (scratchpad) after the push: the column, its numbering, the trigger, the
reader, the restated lock, `content_versions`' privileges as 0032 left them (MAINTAIN recorded),
releases still off. The backfill numbers production's existing history in one UPDATE under a
5 s lock timeout.
