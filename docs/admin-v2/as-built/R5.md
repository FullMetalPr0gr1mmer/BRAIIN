## What was built

Releases stay off for every tenant (`app.release_tenants` is empty until R14), and every new
branch asks `app.releases_enabled(tenant)` first, so with releases off every write path behaves
exactly as on `main`: the guard returns the row at its step 4, the capture returns at once, the
link triggers keep nothing, `publish_scheduled` publishes every tenant's due rows, and the only
visible changes are `media_usage`'s new `pending` column and the dashboard's reads (below). The
existing pgTAP suites (all of them, run on the PGlite replay) pass with the guard in place; the
two that switch a tenant on were adjusted, never by removing the guard (Proof).

### The guard

- **`app.tg_release_guard()`**, SECURITY DEFINER, `search_path ''`, owned by the snapshot owner
  (who bypasses RLS), executable by no API role. One BEFORE INSERT/UPDATE/DELETE row trigger,
  `<table>__release_guard`, on every registry table (21: the 20 of 0038 and U14a's
  `page_visibility`, `team_members` included) and on `portfolio_services` and
  `portfolio_media`, created by a loop over `app.release_entities`. The double underscore sorts
  before every other trigger name on its table (`<table>_actor`, `_guard`, `_password`,
  `_placeholder_guard`, `_sample_lock`, `_updated_at`, `_version`, `_links_stash`), so it fires
  first: its 42501 is what staff see, and no other BEFORE trigger's work runs before it.
- For a tenant with releases on (the row's tenant; either image of an UPDATE), it refuses any
  write (42501, "Live content changes only through a release.", hint "Save it as a pending
  change, then publish it.", detail `{table, op}`) except, in this order:
  1. inside this transaction's release (`app.release_token_valid()`): the apply's writes and
     every cascade they cause;
  2. no switched role and no staff claim (`current_setting('role')` is `none` and the claims
     carry no `app_metadata.role`): migrations, seeds, the runbook, pg_cron, GoTrue;
  3. the service role with no staff claim (out of band; captured as a system item);
  4. releases off for the row's tenant;
  5. an UPDATE that changes only the registry's immediate columns (`exempt_columns`, read at
     run time: `site_profile.accepting_applications`, U14b's `page_visibility.password_version`)
     plus the stamps (`updated_at`, `updated_by`, `version`) and generated columns. A save that
     changes nothing but stamps is refused: it is still a write outside a release.
  Every allow path returns OLD for a DELETE and NEW otherwise.
- **No `pg_trigger_depth` exemption** (verification claim 8): a trigger reached by a staff
  request is refused like the request (pgTAP, a test-only table whose trigger updates a
  service). The role setting is what PostgREST's `SET LOCAL ROLE` set and a SECURITY DEFINER
  call does not change, so a staff request that reaches a registry table through any definer
  is still seen (pgTAP: `authenticated` with no claims, through a definer, refused).
- **TRUNCATE** revoked from PUBLIC, anon, authenticated and the service role on the same 23
  tables (the same loop). On the replay (Supabase's default privileges) the service role held
  it on 22 of them and `authenticated` on 15 before 0066; production is read back before the
  push (`readback_0066_before.sql`).
- **`app.publish_scheduled()`** restated with `search_path ''` and every name qualified; its
  UPDATE gains `and not app.releases_enabled(tenant_id)`. A legacy `scheduled` row of a tenant
  with releases on never goes live outside a release (R11's `enable_releases` converts them).

### Complete capture

- **System items.** `content_release_items.release_id` is nullable; a CHECK
  (`content_release_items_system_shape`: `release_id is not null or draft_id is null`), a
  partial index `(tenant_id, created_at) where release_id is null`, and a second owner-scoped
  insert policy, `content_release_items_insert_system` (tenant first, no release, no draft, no
  token, releases on), beside 0038's. No API role gains anything.
- **`app.tg_release_capture()`** re-created (same arguments, same 20 triggers): outside a
  release, a write to a registry table of a tenant with releases on is a system item (no
  release, no draft, `actor_id` = `auth.uid()`, usually null). Skipped as before: an UPDATE
  that changes only the version and the stamp; out of band also an UPDATE of immediate columns
  only (the intake switch). Inside a release, unchanged.
- **Link sets.** `app.portfolio_link_sets(tenant, project)` is exactly 0051's image expression
  (`{service_ids, media}`), shared by the capture and compared with R4's synthetic item in
  pgTAP. Two triggers per link table: `<table>_links_stash` (BEFORE ROW, I/U/D) keeps the case
  study's sets in `app.release_link_pending` the first time a statement (with its cascades)
  touches it, and `<table>_links_capture` (AFTER STATEMENT, I/U/D) writes one
  `portfolio_children` item per case study kept (op update, `before` = the kept sets, `after` =
  the sets now; nothing when equal) and empties the table. Inside a release the item carries the
  release (and the draft when `app.release_item` names the project); out of band it is a system
  item. The apply's own link-set step (`app.release_item` names the project and the project
  still exists) is skipped: R4's synthetic item stands alone (D4). A project removal or a
  service removal is a cascade and is captured.
- **`app.release_link_pending`**: `(xact xid8, tenant_id, portfolio_id, before, release_id,
  draft_id, created_at)`, primary key `(xact, portfolio_id)`, RLS forced, no policy, no
  privilege for any API role; empty between statements.

  `false`; a ninth lists each draft (not a removal; claimed or not) whose payload holds the id as
  a string anywhere, in any spelling `uuid_in` reads (case, braces, hyphens), labelled by the
  draft's English label, else its payload slug, else "pending change" (120 characters at most).
  The base is never read (it holds live values). EXECUTE: authenticated only (restated).
- **`public.dashboard_attention` v4**: 0028's text unchanged, plus `release_scheduled_today`
  (the Riyadh day, not yet 5 minutes late), `release_overdue` (more than 5 minutes late),
  `release_failed` and `purge_failed` (within 7 days), `draft_stale` (unclaimed, untouched for

- **The dashboard** (`src/lib/admin/dashboard/loaders.ts`): `KIND_LABEL` gains the five kinds
  ("Release going live today", "Release late to go live", "Release that could not go live",
  "Website cache not refreshed after a release", "Pending changes untouched for 30 days"),
  `TYPE_LABEL.release = 'Release'`; a release row's title is its note, else "Version N", else "A
  scheduled release", with no link (R13 adds `/admin/backups`); a stale change links through its
  registry type and never gets the "On the … page" line. **The 500-row cap:** the list's read
  now excludes `draft_stale`, and a second read takes the five oldest stale changes with an
  exact count, so pending changes (which can be many once releases are on) never crowd the

- **Media routes**: `GET /api/admin/media/[id]/usage` passes `pending` through; `DELETE
  /api/admin/media/[id]` names a pending reference as such ("a pending change to page section

- **Shapes** (`packages/schemas/release.ts`): `LedgerItemRowSchema` (any ledger row: a system

## Rule 5: the deployed parsers read v4 safely

The migration is applied before the PR merges, so between the push and the deploy the old Worker
reads `media_usage`'s four columns. Its two parsers are
`src/pages/api/admin/media/[id]/usage.ts`'s `UsageRowSchema` and `src/pages/api/admin/media/[id].ts`'s
`UsageSchema`, both `z.object({ entity_type, entity_id, label })` with no `.strict()`: Zod drops
the unknown `pending` key, and the routes map only the three named fields. During that window the
old Worker also counts pending references in the hard-delete gate (a refusal it words as a live
reference), which is the intended behaviour, not a regression; no pending change can exist while
releases are off anyway. `tests/lib/mediaUploadApi.spec.ts` proves the new parsers ignore an
unknown column and read a row without `pending` as live. `dashboard_attention` gains rows, not
columns; the old dashboard labels an unknown kind by its key, and no such row exists before
R3/R7/R11.

## Write paths the armed guard will refuse (for R3b, R12 and R14)

With releases on, each of these is refused (42501) unless it stages first: the kernel's live
writes (`src/lib/admin/crud.ts` insert, update, delete; `resource.ts` reorder; `save_portfolio`
through `resources/portfolio.ts`) are staged by R3a; the singletons (`src/lib/admin/singleton.ts`:
site profile, SEO defaults) and `src/pages/api/admin/entity-seo.ts` are R3b's; the themes'
`afterWrite` switch-off (`resources/themes.ts`) never runs when staged; U14a's page visibility
(`src/lib/admin/pageVisibility.ts`, `/api/admin/page-visibility`, the `/api/admin/pages/visibility/[id]`
alias) and U14b's `set_page_password` (it writes `mode` and `note`, staged columns) stay live
writes today: R14's static write-path test must stage them or name them immediate. R3b's intake
switch (`accepting_applications` alone) passes step 5.

## Departures from the design, and why

1. **Link sets are captured through a kept "before", not by reversing a transition table**
   (brief §5.4, D5). The brief's statement triggers rebuilt each case study's `before` from the
   sets after the statement with that statement's transition rows reversed. PostgreSQL runs a
   foreign key's cascades as part of the parent statement and fires every child table's
   statement triggers after all of them (verified on the replay: a project removal empties both
   `portfolio_services` and `portfolio_media` before either trigger fires; RI queries run with
   `fire_triggers = false`, so 15 and 17 behave alike). Reversal would give a project removal two
   items, each missing the other table's half, and an "earliest before" without the media (C6).
   D5's fallback (BEFORE DELETE triggers on `portfolio` and `services`) is exact for one removal
   but not for a statement removing two services of one project. The kept-before design is exact
   on every path: a BEFORE ROW trigger keeps the sets the first time a statement touches a case
   study (in `app.release_link_pending`, keyed by the transaction), and the first link-table
   statement trigger to fire writes one item with the sets kept and the sets now. It needs no
   transition table, so two triggers per table, not three. A project removal is one item holding
   both sets; one statement removing two services of one project is one item holding both
   (release_capture.test.sql C6 to C10).
2. **A new table**, `app.release_link_pending`, for that kept state (no tenant-visible data: an
   image of link sets, deleted at the end of every statement). It has `tenant_id` (with its
   foreign key) and `created_at`, no `id`, `version` or actor columns: like `app.release_tenants`
   it is internal state no API role reaches (RLS forced, no policy, no privilege).
3. **`team_members` stays in the guard** (w3 corrections, R5: the choice between excluding it
   and a recorded R14 blocker). Excluding it would leave team-member edits live while R3a stages
   them and the apply applies them. It is guarded and captures nothing, recorded as an R14
   blocker under O-12 in [deviations.md](../deviations.md); `snapshot_coverage.test.sql` names
   the exemption.
4. **Stale drafts are read apart on the dashboard** (w3 corrections: the 500-row cap). One more
   subrequest (25 and 35, within P-15's 50) for a true count and a cap that content kinds own.
5. **`app.publish_scheduled()` moves to `search_path ''`** with qualified names (P-14 for a
   definer restated); its body is otherwise 0028's.
6. **`page_visibility.password_version`** is an immediate column since U14b (0061), so step 5
   covers it with no code of its own; `page_passwords` (U14b) is not a registry table and gets no
   guard: it is reachable only through its definers, and TRUNCATE on it was already held by no
   API role.
7. **Postcondition 1 also covers `publish_scheduled` and the two link triggers**, and a 4b block
   holds the scratch table closed; postcondition 5 restates the items' sequence and append-only
   privileges. The help set is not restated (no screen).
8. **Postcondition 10 gains a role-switch row** (found in the self-review): the guard trusts the
   role setting as well as the claims, so in any schema the only function that switches role
   (`SET LOCAL`/`SESSION ROLE`, `SET ROLE` to a name, `set_config('role', …)` or a `SET role`
   clause) must be `apply_release`. An UPDATE's `set role = …` is a column (0010's
   `bootstrap_admin` writes `profiles.role`) and is not counted, so a function running the
   generic `SET role = '…'` form through `execute` would slip past this regex; none exists.
   pgTAP and the read-back carry the same check.
9. **MAINTAIN asked inside a CASE** in the postconditions (found in the self-review):
   PostgreSQL does not promise AND short-circuits, and the privilege functions refuse the word
   before 17, so an AND would have failed the migration in CI (PostgreSQL 15).
   `tests/lib/releaseGuardSql.spec.ts` holds it.

## Deploying

Expand, so the push comes first (rule 5), then the merge. Before the push, run
`readback_0066_before.sql` (scratchpad) read-only on production: the service role's and staff's
TRUNCATE on the 23 tables (recorded, not judged), the 21 registry rows with `page_visibility`'s
`password_version`, no `tg_release_guard` yet, the link tables' triggers, releases off. After it,
`readback_0066.sql`, then a staff save on production (releases off: the guard returns at step
4). The launch runbook §10 records that R5 does not move the Worker rollback line.
