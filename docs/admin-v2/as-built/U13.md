## What was built

**The database (0054).**
- `app.role_views_audit(r)`, the `audit.view` helper (Admin, Developer), immutable and inlinable,
  executable by staff and the service role; `tests/authz/sqlHelpers.spec.ts` holds it to
  `ROLE_CAPS`.
- `audit_read` (0002, the JWT layer) restated with the helper by `ALTER POLICY` (same command,
  kind and roles; no moment without the policy), and **`audit_log_live_read`**, RESTRICTIVE FOR
  SELECT TO authenticated: the tenant predicate first, then
  `app.role_views_audit((select app.live_role()))`. A demoted, deactivated or locked Admin or
  Developer token, and a token whose claim disagrees with the profile, reads no entry at
  PostgREST: the stale-token gap H10 left open for the log is closed. SELECT only: a plain
  insert reads no row back (no RETURNING), so a stale token's audit insert still lands, bound
  to the stale account by 0050's `audit_log_actor`; and the chain trigger reads its
  predecessor as its owner (a definer), outside these policies, so no writer can fork the
  chain by reading less.
- Two indexes for the filters: `audit_log_tenant_actor_idx (tenant_id, actor_id, id desc)` and
  `audit_log_tenant_created_idx (tenant_id, created_at desc)`, plain `CREATE INDEX IF NOT
  EXISTS` under the 5 s lock timeout (the table is small; production's row count goes in the
  PR from the read-back).
- **`public.audit_people(p_tenant, p_ids)`**, the people directory's audit door (P-7: one
  directory, documented doors). A log names the people who acted, and some have left:
  `app.staff_directory()` lists active members only, so the log would lose exactly the former
  members' names. This door answers id, display name, role and `is_active` for the profiles of
  the tenant among the ids asked (at most 100; 22023 above), active or not, never an e-mail,
  and only for a caller whose LIVE role views the log, naming the token's own tenant. SECURITY
  DEFINER (a staff token reads no other profile), empty search_path, EXECUTE for authenticated
  alone (not the service role: the door is for a signed-in reader).
- `app.help_article_set()` restated from 0046's text and seeded into every tenant again: only
  the `site-health-and-logs` guide changed (see Departures).
- Postconditions: the helper's answers, volatility and ACL; `app.live_role()` a definer staff
  alone call; RLS ENABLE + FORCE; the exact policy set on `audit_log` (name, command, kind,
  roles) and each side of each policy (the tenant predicate first, the role test, no side a
  command does not have); the trigger set exactly H10's `audit_log_actor` then
  `audit_log_chain`, both BEFORE INSERT FOR EACH ROW, enabled, matched by function oid, and
  neither function callable by an API role; `audit_log`'s privileges for PUBLIC, anon,
  authenticated and the service role, table-wide (MAINTAIN on 17 only) and per column, as 0050
  stated them; the two indexes' definitions; `audit_people`'s kind, result type, search_path,
  ACL and that its body never reads an e-mail; the help set holds the new guide, no API role
  executes it, every tenant holds it.

**The Worker.**
- `packages/schemas/audit.ts`: the filters, one schema for the page, the JSON route and the
  export: `kind` (edits, publishing, leads, users, settings), `actor` (uuid), `from`/`to`
  (calendar days 2000 to 2100, inclusive, swapped when picked the wrong way round), the exact
  `entityType`/`entityId` a later history link (R10) may carry, and `page` (1 to 10,000). A
  blank form field is no filter. Strict: an unknown key is refused (no free text, D1).
- `src/lib/admin/auditLabels.ts`: the registry. Per action: its kind, the verb ("Revealed the
  contact details of"), the noun ("a lead"; a resource's from its editor's `singular`), and
  whether the item may be titled. The kernel's `${entity}.create|update|delete|reorder` for every
  `RESOURCES` entity, the five settings rows' `.update`, every other action by its exact key,
  and `release.*` by its prefix ("Published version 15", from the `number` R4's
  `release.publish` writes). `describe(row)` returns structured parts; `kindFilter(kind)` the
  chip's PostgREST `or` expression from the same entries. An unknown action reads "Did <its
  words>" (kind `other`, under All only), and one that is not a plain key "Did something the
  log cannot describe". Changed fields: the names in `detail.fields`, through the editor's
  labels (else the column in words), plain keys only, at most 12 ("and N more"); never a value.
- `src/lib/admin/auditTitles.ts`: titles from an allowlist (entity type → table, column), one
  read per type on the page (at most 8 types, 25 ids, uuids only), through the viewer's client,
  so RLS decides; a lead, a note, an application, a profile, a contact (later), an export or a
  sign-in is never titled (`DENIED_TITLE_TYPES`), and the table read is never built from the
  row's words (a staff token can write a row of its own).
- `src/lib/admin/activity.ts`: `loadActivity` for the page and the JSON route (the page of 25
  with its exact count; the chain check over the newest 100 entries, read UNFILTERED, because
  neighbours on a filtered page are not neighbours in the chain; names through `audit_people`;
  titles), `applyFilters` (the tenant first; a Riyadh day is 21:00 UTC the day before to 21:00
  UTC on the day), `verifyChain` (exported for its test), the page's lenient URL reading.
- `src/pages/admin/audit.astro`: server-rendered, no island of its own (the shell's chrome
  only). PageHead "Activity log", "Who changed what, and when. Kept permanently and
  tamper-evident.", Export (a plain link carrying the filters) for `export.csv` holders, the
  Guide; a GET form (Person: "Everyone" then the directory, plus the filtered person when they
  have left; From; To; Apply; Clear filters); the kind chips (`LinkChips`, a named `<nav>`,
  `aria-current`); the chain note ("The latest N entries link up: none has been removed or
  moved." or "Entry N does not link to the one before it. Tell whoever runs the site.", an
  alert); `ServerTable` (Who, What, Details, When) with its range and pager; the empty states
  ("Nothing logged yet", "No activity matches these filters"). A role without `audit.view` gets
  a 403 with "Your role does not allow that." and nothing read.
- `GET /api/admin/audit`: the JSON twin, rewritten on `loadActivity` (the old `limit`,
  `offset` and `action` parameters are gone; nothing else called them).
- `GET /api/admin/audit/export`: the export lockdown in the lead export's order: `export.csv`
  (the route) and `audit.view` (in the handler); `liveRecheck`; `claimPrivilegedOp(auth,
  'export-activity')` (`EXPORT_LIMITS`, its own op); the attempt row `export.activity.attempt`
  naming the filters used (names only), fatal (503); a keyset read by id, newest first, through
  the caller's client, asking one past `ACTIVITY_EXPORT_CAP` (1,000); names through
  `audit_people` in chunks of 100; records through `describe` without titles (D5); `toCsv`; the
  outcome row with the count and `truncated` (a failed one on an error after the attempt); a
  `system_logs` warning at the cap; `private, no-store`, `attachment;
  filename="activity-<Riyadh day>[-first-<n>].csv"`, `x-export-rows`, `x-export-truncated`.
  Columns: `when_utc`, `when_riyadh`, `who` (a switched-off member marked "(former member)"),
  `role`, `kind`, `what`, `item_type`, `item_id`, `changed_fields`. Never a `detail` value, a
  hash or a title.
- The kit: `ServerTable` gains two typed cells, `person` (an avatar toned by the person's id, the
  name, a sub-line, the name a link when given) and `tagged` (a plain badge before a sentence of

## Departures from the brief, and why

- **No actor binding here.** H10 (0050) built it, with `audit_log`'s stated grants; 0054 only
  re-checks both (the trigger set by oid, the privileges).
- **A status move, not every status.** The brief had the kernel's PATCH record `status` whenever
  the patch sets one. The editors send the status with every save, so a typo fixed on a
  published page would have read "Published". The PATCH records `status` and `previousStatus`
  only when the status changed, against the stored row the kernel already reads for every
  resource with a status (each has a publish rule; `auditLabels.spec` holds that). The settings
  rows have no status; a create already recorded its status. Old rows have none and read as
  updates: the help guide says so.
- **Refusals a person can act on come back to the page.** Export is a plain link, and a JSON
  body is no answer for a person. A navigation (`Sec-Fetch-Mode: navigate`) refused by the hourly
  limit or by an attempt row that cannot be written gets a 303 to `/admin/audit?<filters>&export=
  limit|unavailable`, where a note explains; a script gets the 429 or the 503. A refusal of
  authority (the capability, the live recheck) stays the JSON 403 every admin API answers.
- **The export cap was measured, and the code changed to keep it.** `scripts/bench-activity-
  export.mjs` (new, in the style of the lead export's) bundles the real `toActivityRecords` and
  `toCsv` into workerd: 23 µs a row, nearly all of it `formatDateTime` (three
  `Intl.DateTimeFormat.formatToParts` a call). The file's Riyadh time is now
  `riyadhDateTime`, from the fixed +03:00 offset, held equal to `formatDateTime` by a test:
  5 to 6 µs a row, so 1,000 rows take about 6 ms of the Free plan's 10, the lead export's
  margin. D4's 1,000 stands; it could not rise on the Free plan. After review, the file reads only the detail keys its words
  need (`EXPORT_COLUMNS`: status, previous status, target, menu visibility, number, version,
  fields), never the whole jsonb, so a large detail (a release's item list) costs nothing.
- **Who an entry names when nobody can be named.** No actor (a reset asked for by a visitor, an
  operator's row): "No account". A profile that no longer exists: "A former member" with the
  role the row recorded. A names read that fails: "Someone", and the page still renders. The role
  shown is the one the row was written under (the token's, bound by 0050), not today's.
- **Titles.** The brief's allowlist, as given; a section has no name column, so it reads as its
  type ("Hero section"); the Style-Finder's questions and styles are not titled.
- **The locked-screen render mode is U2's field, built here first.** `LOCKED_SCREENS` gains
  `render?: 'island' | 'server'` (default island) exactly as U2's brief defines it, with
  `/admin/audit` the first server screen and `refusals.e2e.ts` asserting the page's own 403 and
  refusal. Whichever of U2 and U13 merges second keeps one copy of the field and adds its own
  screens' lines.
- **`ReadOnlyPanel` keeps `variant?: 'logs'`,** so `/admin/logs` (U2 rewrites that page) needs
  no edit here.
- **`helpCentre.spec`'s member screens** now count only the sweep's extras that need no
  capability: the filtered activity log (an extra for `audit.view` holders) would otherwise have
  made `/admin/audit` look reachable by every role. Its "never who" test became the opposite,
  held to the page and the guide.
- **The guide.** Only `site-health-and-logs` changed: the activity log's item now says the
  database writes who and when, that entries name the person (former members included) and the
  changed fields' names, never their content, and that the log is kept for good; a new item
  covers the filters (Publishing finds publishes recorded since the filters arrived), the export
  (three an hour, recorded, items by type and id) and the chain line; the tip says "who", not
  "which role". `personal-data` still says the log lists a reveal "with its time and that
  account's role": still true, so left alone (U16's rule: change only what the slice changes).
- **Not done:** free-text search (D1); a sixth "Hiring" chip (D6: application entries are kind
  `other`, under All); titles in the file (D5). The count is `exact`: past about 100,000 rows,
  `planned` would do.
- **Docs not touched:** [crm.md](../crm.md) CRM-10 still quotes the old §5 label for the Sales
  column; C10 writes that row when it adds the column.
