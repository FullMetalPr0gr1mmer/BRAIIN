## What was built

- **`/admin`, server-rendered and complete without JS.** The greeting in `ADMIN_TIME_ZONE`
  (Asia/Riyadh: Good morning before 12, afternoon before 17, else evening; the display name's
  first word, else the e-mail's local part), the sub-line "Here is how <host> is doing.", the
  head actions (Customize from the island, View site in a new tab with
  `rel="noopener noreferrer"`, Edit homepage for `pages.write`), the banners (maintenance on,
  with Turn off for `maintenance.manage`; design samples live, for the roles that read the
  attention list), and the board: a full-width top row and two columns
  (`src/components/admin/ui/dashboard/Board.astro`), each widget a `<section class="wg">` named
  by its heading (`WidgetFrame.astro`), its edit controls server-rendered `hidden` and each named
  for its widget ("Move Site health down").
- **The widget registry** (`src/lib/admin/dashboard/widgets.ts`): eleven widgets (`kpis`,
  `quick`, `views`, `leads`, `attention`, `health`, `activity`, `applications`, `pages`,
  `disciplines`, `notes`), each with the capabilities that show it, `widgetsFor(role)` from
  `ROLE_CAPS`, and a code default per role. `resolveLayout` (`layout.ts`) takes the person's
  layout if it has any column, else the role's preset, else the code default, then drops the
  ids the role may not see or this build does not know and puts the allowed ids it does not
  mention under `hidden`. Only the widgets on the board are loaded (`loaders.ts`), each through
  the caller's RLS-bound client, the shared reads (page views, the lead summary, the attention
  list) once per render: Content Creator and SEO never query leads or applications, not even for
  a count (`tests/lib/dashboardWidgets.spec.ts`, with a spy client). A widget whose read fails
  shows its own error and writes `system_logs`; the page still renders.
- **The widgets.** `kpis`: page views over 7 days with the change on the previous 7 and the
  Arabic share (from U2's `loadPageviewSummary` over 30 days), then "New leads waiting" (the
  initial stage, `lead_summary`) for `leads.manage`, else "Pages live" and "Services live" (two
  head counts). `views`: EN and AR per day over 30 days, and for `leads.manage` a separate
  "Leads, 30 days" bar chart (non-spam leads' `created_at`, at most 1,000, counted per Riyadh day
  in the Worker; never scaled onto the views chart). `leads`: the six newest through
  `leads_list` (name, interest label, stage, "3 h ago"; never budget or contact). `attention`:
  `dashboard_attention` minus its UTC `scheduled_today`, plus "Going live today" from the Riyadh
  day (`goingLiveToday`, exported from `notifications/scheduled.ts`, the bell's two reads; D9).
  `health`: U2's `loadHealthSummary` (the page links `health.css`). `activity`: the five newest
  `audit_log` rows in U13's words (`src/lib/admin/auditLabels.ts`) and names. `applications`: the
  new ones' count, Admin only. `pages`: the top paths over 7 days. `disciplines`: non-spam leads'
  discipline over 90 days (at most 1,000, counted in the Worker). `notes`: the team note.
- **Customize** (`src/components/admin/islands/AdminDashboard.tsx`, code in
  `screens/dashboard/`): the F4b Sortable core bound to the server's columns (`customize.ts`),
  so a widget moves by pointer, by keyboard (Space lifts, arrows move within and across columns,
  Space drops, Escape cancels) and by its Move buttons, one click each, said in a live region;
  Hide; the bar's Add widget (a drawer, Left or Right; it saves, then reloads), Reset (a
  confirm; back to the role's layout, the person's quick actions kept, D8), Admin's "Save as the
  default for a role" (a modal: pick a role, save this layout and the library actions, or reset
  that role to the standard layout), Done. Each move or hide is saved as it happens under the
  preferences' version; a 409 says the dashboard changed in another tab and offers Reload.
- **Quick actions.** One library (`src/lib/admin/quickActions.ts`, shared with the palette):
  each action has a stable id and a capability, the screens that exist today only (edit
  homepage, add service, add project, write a post, new page, add a testimonial, upload, edit the
  menu, edit SEO, add a redirect, open leads, website stats, site health, invite, maintenance, job
  applications, view site); `QUICK_DEFAULTS` per role. The drawer (`QuickActionsDrawer.tsx`):
  the person's list on the kit Sortable, the library chips the role may use, "Add your own"
  (label at most 40 characters with no control or format characters, a link `/admin/…` or
  `https://…` with a dotted host and no credentials, an icon from `QUICK_ICONS`, at most 8 own,
  12 in all), explicit Save and Reset to default. An outside link opens in a new tab with
  `rel="noopener noreferrer"`.
- **Preferences.** `AdminPrefsPutSchema` is `{version, notifications?, dashboard?,
  quickActions?}`, strict, at least one (the account drawer's `notifications` alone still
  works); `saveMyPrefs` generalises F8's save (insert or update under the version, 23505 a 409);
  `PUT /api/admin/me/preferences` refuses (422) a widget or a library action the role may not
  use, and an id this build does not know. The dashboard reads the layout columns
  (`readMyDashboardPrefs`) on `/admin` only; the shell's per-render read stays the bell's.
- **Role presets** (`public.admin_role_defaults`, one row per tenant and role): an Admin writes
  them (`app.role_manages_users` on the live role, H10's helper), every staff member reads their
  own role's row, an Admin every row, behind a RESTRICTIVE live check; the database's CHECK
  (`app.quick_library_only`) refuses any quick action but `{"id": "<library id>"}`, so a preset
  can never carry a link (D3). The trigger `admin_role_defaults_guard` moves the version only on
  a change of content, stamps, and refuses a change of tenant or role. Routes:
  `GET /api/admin/dashboard/defaults`, `PUT` and `DELETE /api/admin/dashboard/defaults/[role]`
  (`users.manage`; the ids refused for **that** role; audited `dashboard.defaults.update` and
  `dashboard.defaults.reset` with the role and the fields changed).
- **Team notes** (`public.team_notes`, one per tenant): read by every `analytics.read` holder
  with a live check; no staff write grant: `public.save_team_notes(p_tenant, p_body,
  p_version)` is the one door (SECURITY DEFINER, `search_path = ''`): the live role, the tenant,
  a raw body over 4,000 characters refused before anything scans it, trailing whitespace
  trimmed (rtrim, linear), at most 2,000 characters, the contact rule, the version (0 = no
  row yet; 40001 on a stale one), the upsert and the audit row (`dashboard.notes.update`, the
  length only) in one transaction. The rule (D5): no C0/C1 control character but tab and line
  feed, no format character (Cf), nothing shaped like an e-mail address, no run of 8 or more
  digits (Western, Arabic-Indic, Extended Arabic-Indic) with up to two spaces, dots, hyphens or
  brackets between (so 055.123.4567 and (055) 123-4567 are refused; slashes are not
  separators, so a date written 14/10/2026 passes, and so does 055 / 123 / 4567);
  `packages/schemas/dashboard.ts` states it for the Worker and `tests/lib/teamNotes.spec.ts`
  holds the two to one table of inputs. `app.expire_team_notes()` blanks a note 180 days after
  its last edit (version + 1, audited `dashboard.notes.expire` with no actor), daily at 03:25 UTC
  by pg_cron (`team-notes-retention`), not the Worker's cron (D6). The widget edits in place
  through the field kit's SingletonForm (`src/lib/admin/ui/teamNotes.ts`, loaded on Edit notes),
  `GET` and `PATCH /api/admin/dashboard/notes` (`analytics.read`; 409, 422 with the rule's
  sentence on the field).
- **The JSON twin** `GET /api/admin/dashboard`: the resolved layout and each shown widget's data
  from the same loaders.
- **The guide** `your-dashboard` (`/admin`, every role, EN and AR); `finding-your-way` no longer
  names `/admin`. The help set is 0057's (U14a: rebased from 0055's when U12b and U14a merged
  first) plus those two changes and nothing else: 15 guides, seeded into every tenant.
- **Tests:** `dashboardWidgets` (the widget set per role from `ROLE_CAPS`, no lead or
  application read for Content Creator and SEO, a role with no caps, failures isolated, the
  subrequest budget), `dashboardLayout` (schemas refuse duplicates and unknown ids on write,
  `readDashboardLayout` drops them on read, `resolveLayout`'s order, presets held to their
  role), `quickActions` (the href rule against `javascript:`, `JaVaScRiPt:`, `data:`, `//host`,
  `/\host`, `http:`, credentials, `..`; the limits; the library per role; every library href
  resolves to a page), `teamNotes` (Zod and SQL on one table, both Arabic digit sets),
  `greeting`, the `adminBundle` chunk plan, `tests/astro/dashboard.spec.ts` (each partial on
  fixtures: no `style=`, chart tables equal their data, edit controls `hidden`), six new authz
  cases (`tests/authz/cases/dashboard.ts`, `account.ts`), pgTAP over the four live roles, anon,
  other_tenant, three stale Admin tokens (demoted, deactivated, locked) and the service role, and
  `tests/admin/dashboard.e2e.ts` (CI only: per role at 320, 390 and 1280px, keyboard Customize,
  the drawers, the notes' 409 and refusal, a preset a fresh SEO session sees, axe with each
  drawer and modal open).

## Departures from the brief, and why

- **Migration 0060, not 0053.** U13's 0054 merged first, and once 0054 is on `main` a 0053
  sorts below main's highest, which `scripts/check-migrations.mjs` refuses (rule 1). 0060 is the
  lowest number above `main` that no other slice holds; `migrations.md` releases 0053.
- **No `app.role_users_manage`.** H10 (0050) already defined `app.role_manages_users` for
  `users.manage`; a second helper for the same capability would break the one-helper rule. The
  postconditions check that it answers Admin only.
- **`app.team_note_problem(text)` beside `app.team_note_ok`.** The definer raises a stable
  message per rule (`team_notes_chars`, `team_notes_contact`), so the reason needs a function of
  its own; `team_note_ok` is `team_note_problem(p) is null`.
- **The CHECK helpers are executable by their writers.** The brief has `app.team_note_ok` and
  `app.quick_library_only` executable by no API role, but PostgreSQL checks EXECUTE on a
  function in a CHECK as the writing role at execution time. So `team_note_ok`/`_problem` are
  the service role's (the one role besides the definer's owner that writes `team_notes`), and
  `quick_library_only` is `authenticated`'s and the service role's (an Admin's token writes
  presets). Each is immutable, takes only its argument and reads nothing.
- **The RESTRICTIVE live check reads `(select app.live_role()) is not null`**, not `is not
  distinct from app.current_role()`: `app.live_role()` (0033) is already null unless the live
  profile's role equals the token's, so the two say the same, and this is how F8's preferences
  write it.
- **Write policies are three** (`_insert`, `_update`, `_delete`): PostgreSQL gives one policy
  one command or ALL, and ALL would also open SELECT to the write test.
- **Team notes save by `PATCH`, not `PUT`,** and the editor is the field kit's `SingletonForm`
  with a `team-notes` config, not a bespoke `TeamNotesEditor`: F5a's `useEntitySave` saves a
  singleton by PATCH and already has the 409 "Reload their version", the 422 on the field, the
  explicit Save and the version line. The hint and counter are the field's `help` and
  `maxLength`.
- **`describeAudit` is U13's registry.** U13 merged first with `src/lib/admin/auditLabels.ts`
  (risk 3); the dashboard's activity widget uses it, and U1 adds its four actions there
  (`dashboard.notes.update`, `.expire`, `dashboard.defaults.update`, `.reset`), so no
  `activity/describe.ts`.
- **The KPI's 7-day change comes from the 30-day read.** One `loadPageviewSummary` over 30 days
  feeds `kpis` and `views`; the 7 days and the 7 before are cut from it (`previous: false` on
  the loader, a small U2 edit), one read fewer.
- **The notes widget is hidden by default** for every role (the prototype's `DASH_DEFAULT`
  hides it too); Add widget brings it.
- **The dashboard's editing code is its own chunk** (beyond the brief). Claimed by admin-ui's
  path rule it rode on every admin screen (116.9 KB each, about 10 KB more); now
  `ADMIN_DASHBOARD_SCREEN` keeps the island's eager file in its entry and `admin-dashboard`
  (`astro.config.mjs`) holds what loads on first use. The reset confirm became `ResetModal.tsx`
  so the eager file holds no Modal.
- **Without JS no editing** (D10): the board renders, the notes read as text, and Customize,
  the quick-actions editor and the notes editor are absent.
- **Not built** (out of scope): Realtime and "Right now", "Won this quarter" and `pipeline`,
  `publish` and "Last published vN", the hidden-pages banner, the GA line, activity filters.
