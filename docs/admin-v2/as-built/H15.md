## Plan (written before the build)

The four problems share one cause: a value a staff token can write is read by code that
recurses (zod's recursive node schema, the renderer, `JSON.stringify`) or that trusts the shape
it was given. Each fix bounds or checks the value once, iteratively, before anything recursive
reads it, and keeps what is rendered today byte for byte.

1. **Article bodies (PRE-1): the blog, service and project bodies.** `LocalizedDocSchema` (the
   three write schemas, create and update) and `renderTiptapToHtml` run zod's recursive
   `TiptapNodeSchema`, unbounded: about 1,250 levels (42 KB) throws a RangeError, a 500 on save,
   and a body stored around the API makes the service page a 500 on every request and empties
   the case-study index. The fix:
   - one iterative walk for an article body (`articleDocProblem` beside E10's
     `sectionDocProblem`, sharing its helpers): it accepts exactly what `TiptapDocSchema`
     accepts (an article keeps every node and mark the renderer has ever taken: images, h1 to
     h6, unknown types) within bounds sized from long real articles (measured below), and it
     never recurses or stringifies;
   - `LocalizedDocSchema` built on that walk, with the same output as before (unknown keys
     dropped, as zod dropped them), so no write runs zod's recursion;
   - `TiptapNodeSchema`'s object hoisted (built once, not once a node), for the callers that
     still parse with it;
   - `renderTiptapToHtml` and `tiptapToPlainText`: the walk, then the renderer on the JSON as
     stored (no zod parse), inside a try, so an invalid body renders '' as the comment promises
     and nothing in them can throw;
   - `renderBody` catches inside; the service page maps its row inside a guard (no `.then`
     outside the loader's try); `parseCaseStudies` maps each row inside its own guard, so one bad
     row is a 404 and leaves the index whole; the index stops rendering bodies it never shows.
   - Output byte for byte: a snapshot corpus of article renders committed BEFORE the change, a
     differential check that the walk accepts exactly what `TiptapDocSchema` accepts and that
     rendering the stored JSON equals rendering zod's parse of it, the seeds' `body_html` equal
     to the renderer (unchanged spec).
2. **The blog's stored `body_html` (PRE-2).** The post page renders its body from `body` with
   the allowlist renderer (`renderBody`, as projects and services do). A post with no `body`
   (the seed's, which hold only the cache) is read back from its `body_html` into a Tiptap
   document by a strict reader of exactly the markup the renderer writes, then rendered by the
   renderer, so no stored HTML is ever emitted; anything the renderer would not have written
   renders nothing. `body_html` stays a derived cache that no public page emits; CLAUDE.md §8's
   sentence says so.
3. **The 64 KB refine.** `SectionWriteSchema`'s `JSON.stringify(v).length <= 65_536` overflows
   past about 4,782 levels: an iterative depth check runs first and refuses with an issue. The
   same for the release draft payload's byte check (`DraftPayloadSchema`, `jsonBytes`).
4. **The older section types' nested objects.** Section content is stored as sent, and the
   older types nest non-strict objects (`Text`, `AccentSchema`, `VideoClipSchema`,
   `MediaRefSchema`, and some types are not strict at the top), so a hidden `mediaId` rides in
   and 0024's and 0102's `$.**.mediaId` makes that asset anon-readable. On WRITE only:
   `sectionContentIssues` refuses any key the type's schema does not name, at any level (the
   raw content against the schema's parsed output, one rule for every type, the new ones
   included). The read stays tolerant (the loader's parse drops unknown keys, as today). The
   page editor's typed form stops carrying a stored key its type does not have, so a typed save
   of such a row drops the key instead of being refused. `h15_prod_check.sql` (scratchpad, READ
   ONLY, counts only) counts the production rows a strict write would refuse, by section type,
   and the article bodies past the new bounds; the session lead runs it before merge.
5. **Tests** that fail without each fix: a probe-style spec per crash class (a deep body, a
   deep `type`, deep attributes, many marks, a deep section payload, a deep draft payload) that
   asserts an issue or '', never a throw; render specs for the service page, the case study and
   its index, and the blog page; the CPU of a long real article.
6. **No migration**, P-12 copy for every new refusal, the README index line, CLAUDE.md §8 where
   the standard changes (the derived cache, the section write rule).

## What was built

The plan held. Every item is built as planned, with the departures below.

### 1. Article bodies (PRE-1)

- **One walk, `readArticleDoc`** (`packages/schemas/tiptap.ts`, beside E10's
  `sectionDocProblem`, sharing its helpers: `isObject`, the node and mark key lists, the plain
  refusals, `TOO_DEEP`, `SETTINGS`, `SECTION_BODY_MISSING`). It reads the raw JSON once, with a
  stack, and never recurses or stringifies anything it was given. It accepts exactly what
  `TiptapDocSchema` accepts (a node's `type` a string of at most 40, `text` a string, `attrs`
  and a mark's `attrs` a record, `marks` an array of `{type, attrs}`, `content` an array of
  nodes; unknown keys ignored), so an article keeps every node and mark the renderer has ever
  taken, images, h1 to h6 and unknown types included. Within bounds sized from the long real
  articles measured above: `ARTICLE_DOC_MAX_NODES` 5,000 (some 23,000 words),
  `ARTICLE_DOC_MAX_DEPTH` 32 (fifteen lists inside lists), `ARTICLE_DOC_MAX_MARKS` 16 on one
  run of words, `ARTICLE_DOC_MAX_FORMATTING` 20,000 marks and attribute values together, and an
  attribute value at most `ARTICLE_ATTR_MAX_DEPTH` 8 deep. Each budget is checked before the
  list it counts is read (E10's CR8). With `copy` it answers zod's own output for the body (the
  shape's keys in the shape's order, a record's keys but `__proto__`, values as they were), so a
  save stores exactly what it stored before; `articleDocProblem` is the check alone.
- **The write.** `LocalizedDocSchema` (the blog, service and project write schemas, create and
  update) is `{ en, ar? }`, each read by the walk through a `z.unknown().transform`: no zod
  recursion on any write. A missing English body says so ("Write the English text.").
- **The render.** `renderTiptapToHtml` and `tiptapToPlainText` (`src/lib/content/tiptap.ts`):
  the walk's check, then the allowlist renderer on the JSON as stored (the renderer reads only
  `type`, `text`, `attrs`, `marks` and `content`, exactly as it read zod's parse of it), inside a
  try, so an invalid body renders '' as the comment always promised. The plain-text walk is
  iterative. `renderSectionDocToHtml` got the same try.
- **`TiptapNodeSchema`'s object is built once** (`content: z.array(z.lazy(() => node))`): no
  public write or render runs it any more, and it stays the stored shape's statement the walk is
  held to.
- **The loaders.** `renderBody` catches inside (no body, never a failed page). One helper,
  `mapRows` (`src/lib/data/parse.ts`), maps validated rows each inside its own guard and logs a
  row it drops (its slug and the error's name). The service page maps its row through it (no
  `.then` outside the loader's try), and so does `parseCaseStudies`, the page's and the index's
  one row path: one bad row is a 404 and is missing from the index, never an empty index.
  (Since the code review, CR8: the renderer's guard is the one guard of a body's render, and
  `mapRows` stays in `parseCaseStudies` only, the list; a refused stored body is logged, CR1.)
  `getCaseStudyIndex` maps without the body (`{ body: false }`): the sitemap and llms.txt never
  show it, and it rendered every project's body on each miss; since `renderBody` cannot throw,
  which rows survive does not depend on it.

### 2. The blog's stored `body_html` (PRE-2)

- `getPostBySlug` selects the body's Tiptap source too (`POST_DETAIL_COLUMNS`,
  `PostDetailRowSchema`, `body` read as it is) and answers a `PostDetail`: the row without
  `body` or `body_html`, plus `bodyHtml`, which `BlogDetail.astro` emits. The page never
  receives the stored cache.
- `postBodyHtml` (`src/lib/data/blog.ts`): a post with a source renders from it through
  `renderBody` (the projects' and services' rule; a value that is not a document is no body). A
  post with none (`body` null: the seed's two posts hold only the cache) has each language of
  its cache read back by `docFromRenderedHtml` (`src/lib/content/renderedHtml.ts`) and rendered
  from that.
- `docFromRenderedHtml` is not a sanitiser. It reads one language, the markup
  `renderTiptapToHtml` writes (its tags, its attribute forms and order, its five entities, a link
  or image address `keptHref` keeps exactly as written, tags closed in order, a formatting tag
  around one run of words), builds the document that markup was rendered from, and refuses the
  whole value at the first thing outside it. Iterative and bounded. Nothing it reads is emitted:
  the renderer renders the document it built. Every render of every article corpus reads back
  into a document that renders to the same bytes, so the seed's posts serve their cache's bytes.
  Since the review (SEC-1) it is bounded like the walk it feeds: a cache longer than
  `RENDERED_HTML_MAX_LENGTH` (128 K characters a language) is refused before it is read, and the
  reading stops at the first node past `ARTICLE_DOC_MAX_NODES`; `postBodyHtml` reads back inside
  its own try (COR-5).
- The list query (`getPublishedPosts`) and `PostRowSchema` are unchanged: a post whose cache the
  schema refuses is still a 404 and missing from the list, as before. (Changed by the code
  review: the list selects no body, and the page reads the cache as data, so such a post renders
  from its source and is listed, CR4; the page renders only the language served, CR2; a source
  the walk refuses falls back to its cache, CR5.)

### 3. The 64 KB refine

- `jsonDepthWithin` (`packages/schemas/jsonDepth.ts`, zod-free): whether a JSON value nests at
  most N levels, iteratively, reading what `JSON.stringify` reads.
- `SectionPayloadSchema` (`packages/schemas/admin.ts`) checks the depth first
  (`SECTION_CONTENT_MAX_DEPTH` 64; the deepest a section writes, a Text block's body at its 8
  levels, is about 22) and stringifies only a value within it. Past it, for every section type:
  "This section has too many levels inside each other. Remove some and save again." on
  `content`, and `checkSectionContent` does not read the content further.
- `jsonBytes` (`packages/schemas/release.ts`, the release draft payload's and label's byte check)
  answers infinity for a value deeper than `JSON_MEASURE_MAX_DEPTH` 128 (an article at its own
  bound inside a draft is under 80), so `DraftPayloadSchema` refuses it as `too-large` and the
  draft writer says "This change is too large to save". `DraftLabelSchema` needed nothing more
  (strict, two strings). No other `JSON.stringify` size check on user JSON exists in
  `packages/schemas` or `src` (searched).

### 4. The older section types' nested objects

- `sectionContentIssues` (the write's per-type check, used by `SectionWriteSchema`,
  `SectionUpdateSchema` and `sectionResource.assertWritable`, so by the staged save and the
  publish check too) compares the raw content with the type's schema's parsed output,
  iteratively, and refuses the first key the parse dropped, anywhere: "This section does not use
  this setting. Remove it and save again." on its path (`content.heading.mediaId`). One rule for
  every type, the new ones included; the E10 blocks, strict already, are refused first by zod.
- The read is unchanged: `toSection` parses with the same schemas, so a row stored with such a
  key renders as it did (an older type's object drops it; a strict UI v2 object refused it
  already).
- The page editor (`sectionStateFromObject`, `src/lib/admin/formPayload.ts`) carries a stored key
  its fields do not edit only when the type has it (`SECTION_ADVANCED_ONLY`, today `hero.intro`):
  a stored key the type does not have is dropped by a typed save, so such a row is never
  unsaveable for an editor. Every nested value is rebuilt from its fields too: the review (COR-1)
  found a pair of languages (a bilingual, prose or rich-text value) was sent back whole, so a key
  hidden inside one (`heading.mediaId`) rode back and the strict write refused an untouched typed
  save; a pair now keeps only its `en` and `ar` (`languagePair`, `src/lib/admin/formPayload.ts`).

## Departures from the plan, and why

1. **The article walk is its own walk, not E10's section walk widened.** The section walk holds
   a body to StarterKit's content model and the editor's attributes; stored articles hold what
   the renderer has always taken (images, h1, unknown nodes), and holding them to it would stop
   them rendering. The two share the helpers and the refusal words.
2. **The write does not run zod's node schema at all**, hoisted or not: the walk answers zod's
   output itself (held equal by a differential spec), at a quarter of the hoisted parse's cost
   at the cap. `TiptapDocSchema` stays exported, and hoisted.
3. **The index renders no body.** Not asked for; found while making it per-row safe: every
   project's body was rendered on each sitemap and llms.txt miss to fill a field neither uses.
4. **A post with no source is read back, not dropped.** Rendering only from `body` would have
   emptied the seed's two posts (published in local, CI and staging by `seed.sql`) and, in
   production, the two published posts, which hold only the cache too (the production check's
   Q3, below; `seeds/production.sql` inserts the seed's posts as drafts, so they were published
   there since). The read-back is what keeps production's only published posts rendering.
5. **Strict on write is "refuse what the schema drops", not a strict copy of every schema.** One
   rule reads the type's own schema, so a type added later is strict on write with nothing to
   remember, and the read path keeps its schemas untouched.
6. **The page editor drops a stored key its type does not have** (it used to carry it): with the
   strict write, carrying it would make the row unsaveable for anyone but an Admin in Advanced
   (JSON). The page never read the key.
7. **E10's deep-type spec moved one line**: a section body nested 3,500 deep is now refused at
   `content` by the depth check, before the body is read (it was refused at `content.body.en`).
8. **Not changed:** the 64 KB message ("section payload exceeds 64 KB") keeps its words (it is
   not new); zod's own message for a key a strict UI v2 object refuses.
9. **A draft staged before the deploy, or a save from an admin tab opened before it, is held to
   the strict write too** (code review CR3, recorded, not changed): releases are off in
   production, so no staged draft exists, and an old tab's save gets the plain refusal, which a
   reload fixes (the editor it loads drops the key).

## The production check

`h15_prod_check.sql` (the build's scratchpad; generated by `h15/gen_prod_check.mjs` from the
branch's own schemas, through `tests/fixtures/sectionShapes.ts`) is one READ ONLY transaction,
rolled back, of three SELECTs that answer counts only: no row contents, no key names, no PII.

- **Q1** counts, by section type, the `page_sections` rows (and the staged section drafts and
  the section history) whose content holds a key the strict write refuses, and how many of those
  hold it at the top. Such a row still renders as before and a typed save fixes it; only an
  Advanced (JSON) or API save of the same JSON is refused. Expected: 0.
- **Q2** gives, for the blog, service and project bodies (and their drafts and history), the
  largest node count, depth, marks on one word and formatting, and how many are past H15's
  bounds. A body past a bound would render nothing after H15. Expected: 0.
- **Q3** counts, by status, the posts that hold only the cache, and of those the ones whose
  cache holds a tag or attribute the renderer never writes (no body after H15). Expected: 0.

Run in PGlite over every migration and `seed.sql` (scratchpad `h15/try_prod_check.mjs`) with
crafted rows added: the seed's sections count 0; the crafted hidden `mediaId` in an About
heading, a stray key at the hero's top and a key inside an Our Work clip each count once (in
`page_sections` and in their history rows); a valid Text block body is not read into; a body
40 deep counts over the depth bound (the count stops one level past it) and one with 17 marks
over the marks bound; the seed's two posts count as cache-only, and the crafted foreign tag and
attribute once each.

**The answers on production** (the session lead, 2026-11-01, `h15_prod_check.sql`, three
SELECTs in one read-only transaction):

- **Q1:** 54 groups (`page_sections` and `content_versions`), 0 rows with a refused key in every
  one, 0 of an unknown type, 0 not an object.
- **Q2:** the services' bodies and their history (production has no blog or project body in the
  Tiptap columns): at most 2 nodes and 2 levels, 0 past any bound.
- **Q3:** 2 published posts, both holding only the cache (`body` null, `body_html` set); 0 with a
  foreign tag, 0 with a foreign attribute.

**v2, after the review (SEC-3).** Q3 was weaker than the reader it stands in for: it counted only
a tag the renderer never writes and an `on*`, `style`, `class` or `id` attribute, while the reader
also refuses any entity but the five, a raw `'` or `"` in text, `<br>` without ` />`, a `target`
