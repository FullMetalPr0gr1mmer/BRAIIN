## What was built

**The database (0061).** Four rules shaped it, and each is a postcondition as well as a
sentence:

1. *The password is never stored in the clear.* `public.page_passwords` holds one bcrypt
   hash per page (`extensions.crypt` / `gen_salt('bf', 10)`) and nothing else about it: RLS
   ENABLE + FORCE, **no policy at all**, and **not one privilege for any API role**, table
   wide or per column, under either Supabase grant regime. The only code that touches it is
   this file's SECURITY DEFINER functions, which run as its owner.
2. *It is never read back.* Nothing returns the hash and no function turns a page into a
   password. `public.set_page_password(tenant, page, password, note)` (EXECUTE
   `authenticated`) checks the caller against the **live** profile
   (`app.role_manages_visibility(app.live_role())`, as 0057's RESTRICTIVE policies do),
   refuses the homepage and a password outside 8 to 72 bytes, then writes the secret, the
   mode, the message and `password_version + 1` **and its audit row** in one transaction:
   a page is never in password mode without a password, and a change whose audit row cannot
   be chained does not happen. The row (`page_visibility.password_set`) names the page, the
   new version and whether a message was set — never the password, never the message.
3. *Checking it is server-side only.* `public.page_password_check` is EXECUTE `service_role`
   alone. It answers the page's current `password_version` on a match and null on anything
   else, always running `crypt()` exactly once — against the row's hash, or, when there is
   no secret, against a fixed dummy of the same cost, so "no such page" costs what "wrong
   password" costs.
4. *The page's words are fenced in the database, not only at the edge.*
   `page_sections_password_fence`, RESTRICTIVE FOR SELECT TO anon and authenticated, over
   `app.is_staff() or not app.page_is_password_locked(page_id)` (the lock is a STABLE
   definer, EXECUTE anon and authenticated), so `/rest/v1/page_sections?page_id=eq.<id>`
   with the public anon key returns `[]` for a locked page. Staff pass it: the editor keeps
   writing the page. Any other signed-in token is fenced as anon is: `page_sections_read` is
   TO public and 0011's fence lets a non-staff token read what anon reads, so a fifth role
   (the planned Sales role, which `app.is_staff()` leaves out by design, P-6) would otherwise
   read a locked page's words. pgTAP holds a staff token reading and a non-staff one not. A request that HAS typed the password reads through
   `public.page_sections_unlocked(tenant, page)` (service role only), which returns exactly
   the rows and columns anon would have read without the fence — a visible section of a
   published page: `type, content, visible, sort_order`. pgTAP holds the two equal on a page
   that is then switched back to public. The fence also takes the page's own images from
   anon, because `media_assets_public_read` (0045) asks `page_sections` under anon's RLS: a
   still only the locked page names is gone for anon. So the images an unlocked request
   renders come through `public.page_media_unlocked(tenant, page, ids)` (service role only,
   SECURITY DEFINER, empty search path): the ids a visible section of that published page
   names by `mediaId`, of a provider the public may render, in `PUBLIC_MEDIA_COLUMNS` and
   nothing more. pgTAP holds that it answers nothing for a hidden section's id, an id no
   section names, a draft page or another tenant's id, and that anon and staff tokens cannot
   call it.

Also: `page_visibility.mode` widened to `public | hidden | link | password` (templates still
public or hidden only, the homepage still only public — 0057's guard refuses the rest);
`note jsonb` ({en, ar}, either side absent, each a non-blank line of at most 140 characters
with no `<`, `>` and no control character, in `app.help_text_ok`'s style) and
`password_version int`; `app.tg_page_password_sync`, a BEFORE INSERT OR UPDATE trigger that
refuses password mode without a secret **for every writer** and, on leaving it, deletes the
secret, clears the message and moves the version; the registry row restated with `note`
staged and `password_version` exempt; the help set restated from 0060's (U1's, the
latest on `main`; its page-visibility guide is 0057's unchanged) with the page-visibility
guide's password section.

**The edge.**
- `src/lib/visibility/access.ts`: the unlock cookie.
  `__Host-braiin-pa-<page id, hex, no dashes>`, `HttpOnly; Secure; SameSite=Lax; Path=/;
  Max-Age=43200`, its value `base64url("v1|<page>|<pv>|<expiry>")` and an HMAC-SHA256 of
  that text under `labelledKeyMaterial(LEAD_PII_ENC_KEY, 'page-access/v1')` — no new secret,
  the `src/lib/applications/keys.ts` precedent. The page is in the name *and* in the
  signature, so a cookie verifies for no other page; the version is too, so a password
  change ends every cookie within the snapshot's minute. The comparison is constant-time.
- `src/lib/visibility/scope.ts`: an `AsyncLocalStorage` scope naming the one page this
  request unlocked, and its tenant. Its own module, away from the content seam R8 extends.
- `src/lib/visibility/gate.ts`: the password box. Zero client JavaScript on a public route
  (a plain `<form method="post">`), one nonced `<style>` as `maintenanceResponse` does it,
  every authored string escaped, `lang`/`dir` per locale, 403 with `private, no-store` and
  `X-Robots-Tag: noindex`.
- `src/middleware.ts`: after the maintenance 503 and before anything renders, a password
  page answers the gate for **every** method unless the cookie verifies; with it, the render
  runs inside the scope and the answer leaves `private, no-store`, noindex, with no
  `Cache-Tag`.
- `src/pages/api/page-access.ts`: the unlock. Same-origin, a 2 KB body (`bodyWithinLimit`:
  a declared length that is not a number is refused, and a chunked body is read from a copy
  only up to the cap), the page matched
  against the snapshot, `next` matched against that page's own path (no open redirect), then
  the EXC-004 counter — `page-access:ip` 10 per 15 minutes (IPv6 by its /64) and
  `page-access:page` 60 an hour — **failing closed**, then `page_password_check` as the
  service role. Success sets the cookie and 303s to the page; failure 303s to `?pa=wrong`.
  No audit row (the caller is anonymous, and a row per guess is a log of guessing); one
  `system_logs` warning, naming the rule (`page-access:page`), its limit and window, on the
  attempt that first passes the per-page ceiling in its window, and nothing for any later
  refusal or any per-address one, as `/api/contact` and `/api/apply` log nothing on a limit.
- `src/lib/data/pageSections.ts` and `src/lib/data/sectionMedia.ts`: the two service-role
  reads behind the content seam (the sections, and the images they name), made only inside
  the scope and only for the page the scope names, each pinned with its reason in
  `tests/lib/contentSource.spec.ts`. So an unlocked page renders what a public one would,
  its images included.
- The snapshot entry for a password page carries the page's id, its `password_version` and
  the message, and never a hash; the snapshot carries the tenant it was built from.

**The admin.** The drawer's fourth option, "Behind a password": a password field that is
never pre-filled (nothing can read one back), a Show/Hide button, the bilingual message, and
Apply disabled until the password is 8 to 72 bytes. It saves through its own door,
`POST /api/admin/page-visibility/password` (`maintenance.manage`, `liveRecheck`, then the
RPC, then the KV sync), because the list's PUT takes the three modes that need no secret.
The list shows a Password badge.

## Departures from the design, and why

1. **The cookie is signed over the page and its version, not over the tenant too.** The
   brief's payload was `tenant|pageId|pv|exp`. The tenant would have had to come from the
   KV snapshot on both sides, and a cookie minted by one isolate would then be refused by
   another whose snapshot was a minute older in the one deploy window where the tenant was
   added — a lock-out for no gain. Page ids are uuids, globally unique, and the tenant is
   still enforced where it decides anything: `page_password_check` and
   `page_sections_unlocked` are both called with the tenant the snapshot names, and the RLS
   fence is tenant-scoped. The snapshot carries the tenant for exactly those two calls.
2. **`VisibilityEntry` carries the page's id, not only its slug.** The gate needs an id to
   name and sign the cookie, and the unlocked read needs one. Ids are not secrets (they are
   in admin URLs), and holding one unlocks nothing: the signature key is the Worker's.
3. **A password entry that cannot be read becomes a 404, not a public page.** A snapshot
   whose entry has no id or no version cannot be unlocked, so publishing the page would be
   the wrong way to fail. The next save or the daily re-sync writes it again.
4. **Changing the message means setting the password again.** `set_page_password` takes the
   password every time, as the brief defines it. A "keep the current password" branch would
   be a second path into the one function that writes a secret, for a convenience; the
   drawer says so ("Setting it again is the only way to change the message too").
5. **`note` is a `restoreOnly` column of the TypeScript registry.** The SQL row stages it,
   but no payload key of `PageVisibilityWriteSchema` writes it (the password door's schema
   does), which is the same shape `page_section.style` already has.
   `tests/lib/resourceFields.spec.ts` gained one more exception for `password_version`: the
   first immediate column that the DATABASE writes, rather than a legacy PATCH.
6. **No permissive `page_visibility` change was needed for the mode.** Staff already hold
   the column UPDATE on `mode`; the new trigger is what stops anyone naming `password`
   without a secret, which is why the refusal is 23514 and not 42501.
7. **The gate page has colour literals**, like `maintenanceResponse`: it is answered before
   anything renders, so it links no stylesheet and reads no theme. `scripts/contrast-audit
   .mjs` covers the admin's tokens, not this page; its pairs are checked by hand (white on
   near-black, and the error line) and by axe in the e2e, EN and AR.
8. **`page_passwords` carries no `id` and no `created_by`**, against CLAUDE.md §8 ("every
   table: `id`, `tenant_id`, timestamps, `created_by`/`updated_by`"). The brief's column list
   is `tenant_id, page_id, password_hash, created_at, updated_at, updated_by`. The page IS
   the row's identity: one secret per page, keyed `(tenant_id, page_id)` on the page's own
   composite key, so a surrogate `id` would be a second key nothing reads, and no API role
   can name a row of this table anyway (no privilege at all). A row is rewritten in place
   rather than created anew, so `created_by` would record whoever set the first password,
   which the audit chain already records, with every later one.
9. **No cron job was added.** The daily run already spends 49 of the Free plan's 50
   subrequests (`tests/lib/dailyJobs.spec.ts`), and the password mode needs none: the
   secret goes with the mode, in the same statement.
10. **The e2e lives in `tests/admin/visibility.e2e.ts`**, beside U14a's, for the reason
    U14a gave: it needs the Admin's session and it changes real pages on the one preview,
    so it runs as its own Playwright project after everything else and puts every page back.

## What this does not claim

- **Link only is still unlisted, not private** (D5). Only the password mode closes a page.
- **The fence covers `page_sections`.** A password page's `pages` row (its slug and title)
  and its `entity_seo` row stay anon-readable, as they are for every page: the gate hides
  the page's *content*, not the fact that the page exists. Anything confidential belongs in
  the page's sections, which is where the fence is.
- **Rate limiting is one ring** (EXC-004's note): the Postgres counter. The WAF ring arrives
  with the zone (KAN-20).
- **The per-page ceiling can lock real visitors out.** It is counted before the password is
  checked, on every attempt, so 60 wrong attempts in an hour from a few addresses (six, at
  ten each) refuse everyone that page for up to an hour, the right password included. That
  is the price of failing closed with one ring: per address alone, a botnet could guess
  without end. The zone's WAF (KAN-20) is the real answer. Until then the window is counted by
  page, not by password, so setting a new one does not reopen it: the warning in Site health
  says it happened, and the page reopens when the hour ends.
- A page behind a password is **not cacheable**, and neither is its gate; once a cache sits
  in front of the Worker (L9/R7), `visibilityPurgeTags` already names what a change touches.

## Not done here
- Staging visibility in releases (R3), the re-sync after apply and rollback and the purge
  (R7). The registry row is in place, with `note` staged and `password_version` exempt.
- A password on a template (decision D1), on a single service or project, on a blog post or
  on a custom page (E11).
- Any way to recover a forgotten password: there is none by design. An Admin or Developer
  sets a new one.
