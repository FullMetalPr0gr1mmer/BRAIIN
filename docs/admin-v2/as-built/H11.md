# H11: the help-guide catalog, one row per guide instead of one restated set

- **Lane:** hotfix (UI lane, U16's help centre), Wave 3
- **Design:** none as a slice. The Wave 3 corrections' rule 1 ("the help set is serial") and the
  plan's critique 2: thirteen Wave 3 PRs restated `app.help_article_set()`, and a slice built on
  an older set silently reverted a sibling's guide unless it was re-based before every push
- **PR:** the `feat/h11-help-catalog` branch (its number is given at review)
- **Migration:** built as 0069 (`0069_help_catalog.sql`); its number is assigned at merge with
  `scripts/renumber-migration.mjs`. Expand only: push, then merge. It restates no guide, so it is
  right after any restatement that lands first (G2's 0067 and C4c's 0068 were replayed before it)

## What was built

**The catalog (0069).** `app.help_guide_catalog`: one row per guide with the nine fields the
set carries (`slug` the key, `sort_order` unique, `minutes`, `tags`, `screens`, `caps`, `title`,
`title_ar`, `body`), plus `revision`, `created_at` and `updated_at`. Its CHECKs are
`help_articles`' word for word (`app.help_text_ok`, `app.help_keys_ok`, `app.help_body_ok`, the
slug shape, the minutes range; pgTAP compares the two tables' constraint definitions), plus
`revision >= 1`. RLS enabled and forced, no policy, everything revoked from PUBLIC, anon,
authenticated and service_role and nothing granted: the migration role (postgres, BYPASSRLS) and
the definer seed read it, nobody else. It is filled with `insert … select … from
jsonb_to_recordset(app.help_article_set())`, the set as the database holds it at the push, so
0069 holds no guide text and needs no re-base whichever restatement lands before it.

**The set (unchanged for every caller).** `app.help_article_set()` keeps its name, signature,
grants (none for an API role) and output: `jsonb_agg(jsonb_build_object(the nine keys) order by
sort_order, slug)` over the catalog. It is STABLE instead of IMMUTABLE because it reads a table;
nothing indexed or generated depends on it. `app.seed_help_articles()`, the `tenants_help_defaults`
trigger, `public.help_search` and every pgTAP file that reads the set work unchanged.

**Proof that nothing moved.** Before the function is replaced, the migration stores
`md5(set::text)` and its length in a session setting (not a temp table, which a
statement-per-transaction runner would drop at once); after, the postconditions compare them and
refuse the push on any difference, then clear the setting. jsonb orders an object's keys itself,
so the rendered text is the literal's byte for byte (replayed on PGlite after 0065, after
0066 + 0067 and after 0068; a mutated rendering, ordered by slug or with `minutes` as `3.0`, fails
the push). Every tenant is then re-seeded (a no-op where it matches) and must hold every catalog
guide field for field.

**One guide at a time.** `app.put_help_guide(p_guide jsonb, p_revision int)` and
`app.drop_help_guide(p_slug text, p_revision int)`: invokers with an empty search path, for
migrations only (no API role executes either). A put takes exactly the nine keys, each of its
JSON type (text, whole numbers, lists of text, an object for the body; 22023 otherwise, before
anything is written; a number in a list is refused, never cast), then the catalog's CHECKs
(23514) and the unique place (23505). It upserts that one row and re-seeds that one slug into
every tenant with `help_articles`' own upsert (inserted, or updated only where it differs, so the
guard moves the version once); no other guide is read or written. A drop deletes the catalog
row and every tenant's copy; a slug the catalog lacks is P0002.

**The revision (the sibling-overwrite guard).** Every guide starts at revision 1; a put that
changes it moves it by one, one that changes nothing leaves it. Put and drop name the revision
the migration was written against (0 for a new guide), and any other is refused with 55000 and a
hint, before anything is written. This is what `hs_rebase.py` refused (two slices editing one
guide): the second to land names a revision the guide has left and fails, in CI first
(`tests/fixtures/helpSet.ts` computes every revision from the files and its error names the
number to use) and at the push as a backstop.

**The tests' reader.** `tests/fixtures/helpSet.ts`: the set is the last `$help$` restatement
before the migration that creates the catalog, then every top-level
`select app.put_help_guide($guide$ {...} $guide$::jsonb, N);` and
`select app.drop_help_guide('slug', N);` after it, in file order and in the order written,
sorted by `sort_order`. `helpSetViolations()` names every migration after the catalog that
restates `app.help_article_set()` (it would replace the catalog's reader with a literal and lose
every put since), holds a `$help$` literal, writes the catalog other than through put and drop,
or calls them in any other shape (inside a DO block, through `perform`, indented, without a
revision). `tests/lib/helpCentre.spec.ts` reads `SET` through it; every assertion it made stays
(the per-file restatement tests read the historical files, which never change), and it gains the
catalog's own: made once from the last restatement, no violations, unedited guides byte for byte
the base's, put's keys equal `HelpArticleSeedSchema`'s, the reader's order, refusals and the
revision guard on synthetic migrations, and no text holding `$guide$`.

**pgTAP.** `supabase/tests/help_catalog.test.sql`, `plan(83)`: RLS forced with no policy, the
CHECKs equal to `help_articles`', no API-role privilege on the table or the three functions;
the set as the catalog rendered (nine keys, by place, field for field, at least the fifteen
guides); a put unchanged changes nothing (the set's md5, every tenant's version and stamp, the
revision); a change reaches every tenant with the version and the revision moved once and
nothing else moved; a new guide reaches every tenant and a tenant made after it; the refusals
(22023 shapes, 23514 rules, 23505 place, 55000 stale, never-cast numbers) leave nothing behind; a
drop retires one guide everywhere and the set's md5 is again the one before the put; and admin,
content_creator, seo, developer, another tenant's admin, anon and the service role are each
refused (42501) reading the catalog and calling put or drop. `dashboard_layer.test.sql` and
`help_leads_v2.test.sql` count the guides as a floor (`>= 15`), so a slice that adds a guide
edits neither (plans unchanged: 73 and 10).

## How a slice changes a guide now (replaces corrections rule 1 and `hs_rebase.py`)

1. Write only your guide: `select app.put_help_guide($guide$ {the nine keys} $guide$::jsonb, N);`
   at the start of a line, outside any DO block, N the guide's revision on `main` (0 for a new
   guide; `helpSet(readMigrations()).revisions` says which, and the spec's failure message names
   it). Retire one with `select app.drop_help_guide('slug', N);`. Never restate the set.
2. Take a free `sort_order` (10, 15, 20, 30, 35, 40, 50, 60, 70, 80, 90, 100, 105, 110 and 120
   are taken; 45, 65, 75, 95 and 125 are free) and say which.
3. Postconditions and pgTAP check your guide only; count guides as a floor, never exactly.
4. If a sibling's put of the same guide lands first, CI fails with the revision to use: merge
   `main`, rewrite your guide on its current text, name the new revision. Guides you did not
   touch need nothing. Pre-push gate: no put or drop of your guide on `main` newer than the
   revision you name (the push refuses it anyway, 55000).
5. `PAGE_GUIDES`, `tests/admin/routes.ts`' `EXTRA_LINKS` and the nav registry still move with a
   new screen's guide (corrections rule 4): the catalog changes how the text ships, not where
   the screen is.

**G2 (0067) and C4c (0068)** are in flight with full restatements and merge before this. Nothing
in 0069 needs re-basing onto them: it copies whatever set the database holds when it runs. What
does change when they land first: `tests/lib/helpCentre.spec.ts` reads its base from the last
restatement before the catalog (theirs, automatically); their own pgTAP pins (`health_probes`,
`help_leads_board`: "15 guides") should become floors the next time either file is touched, and
0069 must keep sorting after both (`scripts/renumber-migration.mjs` at merge). A restating slice
that would land AFTER 0069 must be converted to a put of its own guide first: CI refuses its
restatement.

## Departures from the brief, and why

- **`put_help_guide(jsonb, int)` and `drop_help_guide(text, int)`, not `(jsonb)` and `(text)`.**
  The revision argument keeps the one protection the restated set had (`hs_rebase.py` refused
  two slices editing one guide); without it the later of two puts of one slug silently wins.
- **The catalog is filled from `app.help_article_set()` at the push, not from a literal of
  0065's set.** The brief asked for a seed "from the set as main holds it when you merge"
  (re-based with `hs_rebase.py` if 0067/0068 land first). Reading the live set makes the
  migration right after any restatement with no re-base, and the md5 postcondition proves the
  rendering identical to whatever it replaced. The TypeScript reader follows the same rule (the
  last restatement before the catalog is the seed).
- **The byte-for-byte "before and after" check is the migration's postcondition, not pgTAP.**
  pgTAP runs after every migration and never sees the literal; the migration is the only place
  both texts exist. pgTAP proves the rendering's shape and that put and drop restore the md5.
- **No tenant column, no actor columns.** Stated in CLAUDE.md §8 U16 as an exception to the
  every-table rules, on `app.release_entities`' precedent (0038): global configuration written
  only by migrations, the same for every tenant; each tenant's copy is `help_articles`.
- **Two pgTAP counts became floors** (`dashboard_layer`, `help_leads_v2`), so adding a guide is
  one file. Every other assertion in them is unchanged.
