## Plan (written before the build)

Releases are off in production until R14. With them off a theme save is live (the legacy save
path), with them on it is a pending change in the release registry like every other staged area,
published by `theme.edit` holders (Admin, Developer; P-2).

**What the site wears.** Only the colours that already follow a token: primary (`--bs-klein`),
hover (`--bs-cobalt`) and accent (`--bs-sky`, which `--bs-accent` reads), plus what is derived
from them (`--bs-sky-soft`, the two glows and two shadows). The dark ground, the light section
and the paper stay fixed in v1 (see Departures). The admin wears the same three through
admin.css (`--ad-primary: var(--bs-klein, …)`, `--ad-primary-hover`, `--ad-accent`).

1. **`packages/theme/`** (pure, shared by the editor, the Worker, the CI audit):
   - `palette.ts`: the prototype's `opsPalette` HSL rules (Simple mode: one colour makes hover and
     accent), hex/HSL helpers.
   - `pairs.json`: every contrast pair a theme colour takes part in, public and admin, with
     colours written as a theme role, a fixed hex, or "A at alpha over B" (the translucent text
     the audit precomposites). Mirrors `scripts/contrast-audit.mjs` (a unit test holds every audit
     pair that uses a theme-following token present here, and the default theme's composites
     equal to the audit's precomposited values) and admin.css's fixed tokens.
   - `gate.ts`: evaluates the pairs for a palette; a failure names the pair in words ("White
     text on Hover is 3.2:1, needs 4.5:1") with a suggestion (the nearest lightness of the colour
     that makes every pair it is in pass: "Use #0B6EB0 instead"); `settle()` moves GENERATED
     colours to their nearest passing lightness (deviations.md: the gate may adjust generated
     colours), never a colour the person typed.
2. **Schemas** (`packages/schemas/theme.ts`): `ThemeSettingsSchema` (`v: 1`, `mode` simple |
   advanced, `colors` {primary, hover, accent} as `#RRGGBB`, `motion` {marquee normal | slower |
   slowest, reveal boolean}), strict; `ThemeTokensSchema` tightened to the closed enum of keys,
   each with its own value pattern (no `;` `{` `}` `<` `>` `\` can pass any of them).
3. **Compile** (`src/lib/theme/compile.ts`): settings → tokens (only what differs from the
   brand defaults), the gate refusing a palette that fails (422 naming the pair). The resource
   (`themes`) takes `{name, settings, isActive}`, compiles `tokens` in `toRow`, so a staged
   change, its publish (R6 re-validates through the same schema) and a live save all compile
   and gate the same way.
4. **Migration 0118** (`custom_themes`): `settings jsonb` (null on legacy rows); one theme row
   with settings per tenant (partial unique index); a CHECK that a row with settings holds
   tokens of the closed key set, each value of its key's pattern, and colours that pass the
   gate's pairs (the same pairs, in SQL, held equal to pairs.json by a test); anon reads the
   active v1 row only (`is_active and settings is not null`, the tenant fence first) through a
   column grant on `id, tokens, version`; the registry row restated with `settings`; postconditions
   proving the snapshot, capture and guard triggers stay on the table; the help guide `theme`
   (new) and `roles-and-access` (no longer says saved themes do not change the site).
5. **Delivery**: `GET /styles/theme.css?v=<version>` (`src/pages/styles/theme.css.ts`): only
   `:root{--name:value;…}` from the parsed tokens (no other CSS can be emitted), `text/css`,
   `public, max-age=31536000, immutable` when `v` is the live version, short and revalidated
   otherwise, `Cache-Tag: site:chrome`. BaseLayout and AdminLayout link it only when the active
   theme differs from the brand defaults, so a site with no theme row, or one reset to the
   defaults, renders byte for byte as before. `site:chrome` joins the ALWAYS tags; the
   registry's `custom_theme` purges it.
6. **Preview**: the releases preview (R8) reads `custom_themes` through its anon mirror, and
   draws the pending theme as a nonced `<style>` of the same custom properties (a preview is a
   Tier C, nonce-CSP admin response; Tier A never carries it). The editor previews the admin
   itself through the CSSOM while the palette passes, and a sample of the site's blocks.
7. **Motion (reduce only)**: marquee speed (normal, slower, slowest) and reveal on scroll (on,
   off), as two custom properties `global.css` reads with today's values as fallbacks, so an
   unthemed page renders as before. Nothing can add motion. "Reduced motion is respected
   automatically", Archivo/Almarai only, no smooth scrolling or parallax: read-only facts.
8. **Editor** `/admin/appearance/theme` (`AdminTheme`, theme.edit): Simple (one colour, 8
   swatches, the generated palette with each chip's contrast) and Advanced (primary, hover,
   accent, "Generate the rest from Primary"); the gate's errors inline with "Use … instead";
   motion; read-only facts; "Reset to brand defaults" behind a danger confirm; saves through
   `useEntitySave` (live Save now, the draft path when releases are on, R12b markers). The nav's
   Theme link moves there; `/admin/themes/**` answers with a 302.
9. **Checks**: the contrast audit gains THEME_PAIRS (pairs.json at the default theme); the
   per-route budgets (no public JS change; one stylesheet of well under 1 KB when themed); CLS
   and LCP reasoning recorded below (lhci cannot run locally: it needs the server).

## As built

**The theme package** (`packages/theme/`, the `@theme/*` alias in tsconfig and vitest; pure, one
copy for the editor, the Worker, the CI audit and the database's generated rules):

- `colour.ts`: hex channels, WCAG 2.2 luminance and contrast (the audit's maths:
  `tests/lib/themeGate.spec.ts` holds them equal to `src/lib/admin/contrast.ts`), `mix()` in whole
  channels rounded half up (as `app.theme_mix` computes it, so the two agree to the last digit),
  HSL both ways.
- `palette.ts`: the three roles, the brand defaults (from `pairs.json`), the prototype's eight
  swatches and its `opsPalette` HSL rule (`generatePalette`).
- `pairs.json`: 45 pairs, 30 on the site and 15 in the admin, each colour a hex, a role or
  `[top, alpha, under]`, each pair with its threshold and its place in words. The resume added
  one: a hovered link in a hovered table row (`primary-hover` on `surface-2`), a pair the hover
  colour takes part in now that it is a theme colour, added to the audit too.
- `gate.ts`: `failuresFor` (a failure names the pair in words: "White text on Hover is 2.5:1,
  needs 4.5:1 (white text on a hovered button)."; the ratio floored, never rounded up to a pass),
  `suggestFor` (the nearest lightness of the colour's hue whose own pairs pass), `settle` (moves
  GENERATED colours only), `simplePalette`, and `suggestMain` (Simple mode's main colour; it now
  passes over a lightness whose Primary-only pairs fail without settling it, the same answers as
  the full search, about 1 s down to under 70 ms for a swatch), and `skySoftFor`, the light accent
  tint derived from the accent (global.css's own at the brand colours).
- `compile.ts`: `compileTheme` (settings to tokens: none for the brand's own colours and motion;
  the eight colour tokens otherwise, the glows and shadows global.css's own recoloured; the motion
  tokens only when motion is reduced), `hasTokens`, `themeCss` (one `:root` rule of the closed set
  in a fixed order, each value re-checked against its key's shape, '' for anything else) and
  `DEFAULT_THEME_SETTINGS`.
- `sql.ts`: generates the migration's three blocks (the pairs, the token shapes, the defaults).

**Schemas.** `packages/schemas/theme.ts`: `ThemeSettingsSchema` (strict at every level, `v: 1`,
`mode`, three `#RRGGBB` colours stored upper case, motion `marquee` normal | slower | slowest and
`reveal`), the gate as a refinement whose issues sit on the colour a pair names first; and, since
the resume, `ThemeWriteSchema` / `ThemeUpdateSchema` (out of `admin.ts`: see Sizes).
`packages/schemas/themeTokens.ts`: the closed set of eleven keys, one pattern each, none able to
hold `;` `{` `}` `<` `>`, a backslash, a quote or a newline.

**Migration 0118** (placeholder): `app.theme_luminance`, `theme_mix`, `theme_contrast`,
`theme_palette_ok` (the 45 pairs, generated) and `theme_row_ok` (the settings' closed shape, the
tokens' closed set and shapes, the motion tokens exactly what the motion says, the colour tokens
absent at the brand colours and all eight otherwise, the three named ones equal to the settings,
every pair passing): invoker, immutable, empty search path, executable by `authenticated` and
`service_role` (a CHECK runs as the writer), never anon; `custom_themes.settings jsonb` (null on a
legacy row, which the CHECK leaves alone and nothing serves); `custom_themes_theme_v1` CHECK;
`custom_themes_one_theme_v1` (one v1 theme per tenant); `custom_themes_public_read` (anon, the
tenant fence first, active and v1) with a column grant on `tokens, version` only; the registry's
`custom_theme` row with `settings`; the `theme` guide (new, place 97) and roles-and-access
(revision 4, the Developer line); postconditions for all of it, including the policy set, every
anon privilege, TRUNCATE for nobody and the three release triggers.

**The save.** The `themes` resource takes `{name, settings, isActive}` and compiles `tokens` in

## Departures

1. **v1 themes primary, hover and accent; the dark ground, the light sections and white stay
   fixed** (ui.md's Advanced lists dark, light and paper too). Those three are the ground of
   nearly every text pair of the site (the audit's whole public list, and translucent grounds
   written as literal colours that follow no token), so theming them needs a gate over every pair
   of global.css. v1 themes the three colours that already follow a token, whose pairs are the 45
   here. Recorded in deviations.md; owner question 3.
2. **Motion: Normal, Slower, Much slower, and the reveal on or off** (ui.md: "slower, normal,
   faster"). README "Appearance" and verification §6.1 allow settings that only reduce motion, so
   there is no "faster"; the reveal switch is the verification table's "reveal" toggle. Both are
   tokens global.css reads with today's values as fallbacks.
3. **The preview is a drawn sample of the site and the admin itself, not the REL iframe with a
   `tokens` op** (ui.md "Preview"). The prototype's own screen draws a sample (`opsThemePreview`);
   E2's column is built around a page's sections and a 1280 px frame scaled into a wide column;
   a framed page costs a Worker render per open (P-15). With releases on, the pending theme is
   drawn on any page by R9's preview (the screen links it in draft mode); with them off a save is
   live. The bridge's `tokens` op is ready for it (the closed set, only the tokens a message
   carries). Owner question 2.
4. **A stylesheet, not a nonced inline `<style>`** (verification's review suggested evaluating
   one). An inline style in a Tier A page would carry a per-request nonce inside a page the edge
   caches (a cached nonce), and the stylesheet measured as costing nothing over HTTP/2 (Sizes).
   A preview, which is a Tier C response, does use the nonced style.
5. **The stylesheet at any other version answers the current theme for a minute** (ui.md names
   only the immutable answer): a page cached with an older link before its purge lands still draws
   today's colours, and nothing stale is kept.
6. **A live save purges nothing.** With releases off (production until R14) a theme save is live,
   and no zone cache exists yet (O-3), as for an identity save; a theme's publish purges
   `site:chrome`, the tag every Tier A page and the stylesheet carry.
7. **The CHECK recomputes the contrast, not the glows and shadows.** It holds the three colour
   tokens equal to the settings, the derived tint by its pairs, and every other token by its
   shape. A staff token writing PostgREST directly could store a glow of another colour (never a
   text colour, never outside its shape); the Worker always writes the compiled ones.
8. **The Klein bands' accent glow is not scored**, as the audit does not score it: the bands are
   scored as solid Primary. A much lighter accent brightens that corner (`--bs-glow-sky` at 45% at
   its centre). Owner question 4.
9. **The prototype's eight swatches as they are**: six of them make a Simple palette that fails
   (a Hover too light for white text); the screen offers the darker main colour that passes.
   Owner question 1.
10. **The theme's write schemas live in `packages/schemas/theme.ts`, not `admin.ts`**: the
    browser's shared admin chunk carries `admin.ts` whole (`updatable()` is not a schema chain
    `scripts/zod-pure.mjs` may drop), and they carry the gate.
11. **The admin reads the theme on every screen** (AdminLayout), one anon read beside the shell's
    own, started before them and awaited with them.
12. **A legacy theme's version cannot be restored** (Backups & versions): its tokens have no field
    since E4, so a restore names it unrestorable (`columns: ['tokens']`) rather than writing a
    theme the editor cannot show. No legacy theme was ever served.
