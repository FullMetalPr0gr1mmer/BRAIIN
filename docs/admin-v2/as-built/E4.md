## Plan (written before the build)

Releases are off in production until R14. With them off a theme save is live (the legacy save
path), with them on it is a pending change in the release registry like every other staged area,
published by `theme.edit` holders (Admin, Developer; P-2).

**What the site wears.** Only the colours that already follow a token: primary (`--bs-klein`),
hover (`--bs-cobalt`) and accent (`--bs-sky`, which `--bs-accent` reads), plus what is derived
from them (`--bs-sky-soft`, the two glows and two shadows). The dark ground, the light section
and the paper stay fixed in v1 (see Departures). The admin wears the same three through
admin.css (`--ad-primary: var(--bs-klein, …)`, `--ad-primary-hover`, `--ad-accent`).

1. **`packages/theme/`** (pure, shared by the editor, the Worker, the CI audit):
   - `palette.ts`: the prototype's `opsPalette` HSL rules (Simple mode: one colour makes hover and
     accent), hex/HSL helpers.
   - `pairs.json`: every contrast pair a theme colour takes part in, public and admin, with
     colours written as a theme role, a fixed hex, or "A at alpha over B" (the translucent text
     the audit precomposites). Mirrors `scripts/contrast-audit.mjs` (a unit test holds every audit
     pair that uses a theme-following token present here, and the default theme's composites
     equal to the audit's precomposited values) and admin.css's fixed tokens.
   - `gate.ts`: evaluates the pairs for a palette; a failure names the pair in words ("White
     text on Hover is 3.2:1, needs 4.5:1") with a suggestion (the nearest lightness of the colour
     that makes every pair it is in pass: "Use #0B6EB0 instead"); `settle()` moves GENERATED
     colours to their nearest passing lightness (deviations.md: the gate may adjust generated
     colours), never a colour the person typed.
2. **Schemas** (`packages/schemas/theme.ts`): `ThemeSettingsSchema` (`v: 1`, `mode` simple |
   advanced, `colors` {primary, hover, accent} as `#RRGGBB`, `motion` {marquee normal | slower |
   slowest, reveal boolean}), strict; `ThemeTokensSchema` tightened to the closed enum of keys,
   each with its own value pattern (no `;` `{` `}` `<` `>` `\` can pass any of them).
3. **Compile** (`src/lib/theme/compile.ts`): settings → tokens (only what differs from the
   brand defaults), the gate refusing a palette that fails (422 naming the pair). The resource
   (`themes`) takes `{name, settings, isActive}`, compiles `tokens` in `toRow`, so a staged
   change, its publish (R6 re-validates through the same schema) and a live save all compile
   and gate the same way.
4. **Migration 0118** (`custom_themes`): `settings jsonb` (null on legacy rows); one theme row
   with settings per tenant (partial unique index); a CHECK that a row with settings holds
   tokens of the closed key set, each value of its key's pattern, and colours that pass the
   gate's pairs (the same pairs, in SQL, held equal to pairs.json by a test); anon reads the
   active v1 row only (`is_active and settings is not null`, the tenant fence first) through a
   column grant on `id, tokens, version`; the registry row restated with `settings`; postconditions
   proving the snapshot, capture and guard triggers stay on the table; the help guide `theme`
   (new) and `roles-and-access` (no longer says saved themes do not change the site).
5. **Delivery**: `GET /styles/theme.css?v=<version>` (`src/pages/styles/theme.css.ts`): only
   `:root{--name:value;…}` from the parsed tokens (no other CSS can be emitted), `text/css`,
   `public, max-age=31536000, immutable` when `v` is the live version, short and revalidated
   otherwise, `Cache-Tag: site:chrome`. BaseLayout and AdminLayout link it only when the active
   theme differs from the brand defaults, so a site with no theme row, or one reset to the
   defaults, renders byte for byte as before. `site:chrome` joins the ALWAYS tags; the
   registry's `custom_theme` purges it.
6. **Preview**: the releases preview (R8) reads `custom_themes` through its anon mirror, and
   draws the pending theme as a nonced `<style>` of the same custom properties (a preview is a
   Tier C, nonce-CSP admin response; Tier A never carries it). The editor previews the admin
   itself through the CSSOM while the palette passes, and a sample of the site's blocks.
7. **Motion (reduce only)**: marquee speed (normal, slower, slowest) and reveal on scroll (on,
   off), as two custom properties `global.css` reads with today's values as fallbacks, so an
   unthemed page renders as before. Nothing can add motion. "Reduced motion is respected
   automatically", Archivo/Almarai only, no smooth scrolling or parallax: read-only facts.
8. **Editor** `/admin/appearance/theme` (`AdminTheme`, theme.edit): Simple (one colour, 8
   swatches, the generated palette with each chip's contrast) and Advanced (primary, hover,
   accent, "Generate the rest from Primary"); the gate's errors inline with "Use … instead";
   motion; read-only facts; "Reset to brand defaults" behind a danger confirm; saves through
   `useEntitySave` (live Save now, the draft path when releases are on, R12b markers). The nav's
   Theme link moves there; `/admin/themes/**` answers with a 302.
9. **Checks**: the contrast audit gains THEME_PAIRS (pairs.json at the default theme); the
   per-route budgets (no public JS change; one stylesheet of well under 1 KB when themed); CLS
   and LCP reasoning recorded below (lhci cannot run locally: it needs the server).
