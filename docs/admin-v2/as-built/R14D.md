## Plan (written before the build)

Releases stay OFF in production and in the required e2e job; `playwright.config.ts` keeps its
projects. Every test change holds in both modes or branches on `releasesOn()`, and with releases
off each converted spec asserts what it asserted on main. e2e runs only in CI, so every changed
step is traced against the markup in both modes.

### 1. general.e2e "a second tab's save is a 409" in release mode

The rehearsal (`rehearsal5.log`) never saw "Someone else saved changes while you were editing."
Investigation (systematic-debugging) before any change:

- **Evidence.** The second tab saves `foundedYear: 2019`. The seed's `founded_year` is 2019
  (`supabase/seed-data/00-tenant.json`). With releases off the legacy update writes the row
  whatever the value and moves its version, so the first tab's save (at the old version) is a 409.
  With releases on the staged singleton kernel (`stagedSingletonUpdate`) drops a save equal to
  live and stages nothing (`stagedSingleton.spec.ts` "a save equal to live stages nothing", R14a
  G7): there is no pending change, so the first tab's save is the first change, not a conflict.
- **Hypothesis.** The test's "other save" is a no-op in release mode; with a real change the
  first tab's blind save meets the second tab's pending change (`draft-conflict`, no `detail`),
  which `useEntitySave` maps to the same banner.
- **Decision.** Not a product bug: with releases on, a save that changes nothing makes nothing
  to conflict with, which is right. The test is fixed: the second tab changes the founded year
  to a value that differs from live (in both modes), asserts (releases on) that its save left a
  pending change, and the banner's words come from one constant the form renders
  (`CONFLICT_WORDS`). The restore puts the founded year back too. A unit test drives the exact
  sequence through the real route (a staged edit, then a blind save over it: 409
  `draft-conflict` with no `detail`, the pending change untouched), and one holds the form's
  banner to the constant.

### 2. The admin visual baselines: the activity log's growing list

The first `update` run on main made 220 baselines, and its second run failed on the two activity
log screens at both widths: the page grew from 1015 to 1271 px because every sign-in, save and
view in between adds a row. The fix keeps every other screen as it is and gives those two a
data-independent frame: `tests/visual/adminVisualSteady.ts` gains `FRAMED` (the screens whose
list grows with any write, and the regions that list lives in: the table card and the chain
note), and before the picture the spec fixes each region's block size through the CSSOM (no
`style=` attribute; CSP allows the CSSOM) with its overflow clipped, and masks it. The picture
is then the same size and the same pixels whatever the log holds. `tests/ci/adminVisual.spec.ts`
holds that the frame names exactly the activity log's capture routes, that the regions are the
markup's classes, and that the spec frames before it takes the picture. Z1.md records it.

`test.skip(releasesOn(), RELEASES_OFF_ONLY)` goes, each test runs in both modes with R14a's
