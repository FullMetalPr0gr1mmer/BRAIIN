## Plan (written before the build)

**Scope.** AV-20 whole: Integrations typed, the Forms overview, the bell's settings.

**Migration.**
1. `app.role_manages_integrations(r)` (Admin, SEO: `settings.integrations`), held equal to
   `ROLE_CAPS` by `tests/authz/sqlHelpers.spec.ts`.
2. Typed, CHECKed columns on `site_integrations` holding public identifiers only:
   `ga4_measurement_id`, `search_console_token`, `calendly_url`. No captcha column (O-19: the
   provider is not chosen). No backfill from the legacy jsonb (a NOTICE counts the rows that
   hold any, never a value); the jsonb stays granted for the deployed Worker until U15 drops it.
3. Policies: read and write narrowed to Admin + SEO (`TO authenticated`, the helper on the
   token's role), a RESTRICTIVE live check (`app.live_role()`), and an anon read of the
   launch tenant's row; the tenant predicate first everywhere.
4. Grants stated (P-14): staff by column (no DELETE), the service role S/I/U/D, anon SELECT
   on `tenant_id` and `search_console_token` only.
5. Guides through H11's catalog: `integrations` (new, place 62), `forms-and-spam` (new,
   place 85), `your-account` (revision 2: the settings screen and one line).
6. Postconditions under both grant regimes.

**Server.** `packages/schemas/integrations.ts` (patterns shared with the CHECKs); the
integrations route on the typed columns; a public loader for the token; SeoHead's
`google-site-verification` meta on `/` and `/ar/` only; the preview mirror learns the table;
`GET/PATCH /api/admin/me/notification-settings` (booleans per kind the role can see, over
`admin_user_prefs.notifications.muted`).

**Screens.** `/admin/integrations` (server frame + `AdminIntegrations`: tiles, a drawer per
setting on the field kit, the captcha tile read-only "Not set up"); `/admin/forms` (zero JS,
derived from the schemas and the EXC-004 limits); `/admin/settings/notifications`
(`AdminNotificationSettings`); the account's link and the bell page's head action; the nav.

**Tests.** pgTAP `integrations.test.sql`; `rls_admin_cms` loses its integrations rows;
`preview_dataset` literals; unit (schemas, SQL parity, the loader, the head render, the
settings mapping, the forms facts, help claims, sidebars, cases); e2e (integrations as SEO,
the settings screen per role, the forms screen in the sweep and the refusals).

The plan was built as written, with the changes under Departures. The first build was cut off
by a session limit after the migration, the pgTAP, the screens and the render snapshot; the
resume added the Search Console tag (only its snapshot, written before it, was there), the
preview mirror, the help wiring, every unit and e2e spec, and these notes.

## What was built

**The database (0105).** `app.role_manages_integrations(r)` (`language sql immutable`, not a
definer, EXECUTE for `authenticated` and `service_role`), mapped to `settings.integrations` in
`tests/authz/sqlHelpers.spec.ts`. Three typed columns with CHECKs:
`site_integrations_ga4_shape` (`^G-[A-Z0-9]{4,15}$`), `site_integrations_gsc_shape`
(`^[A-Za-z0-9_-]{10,100}$`), `site_integrations_calendly_shape` (`https://calendly.com/` and
one to three path segments, no query or fragment, at most 200 characters). Five policies, the
tenant predicate first in each: `site_integrations_read`, `_insert` and `_update` TO
authenticated on the token's role; `site_integrations_live` RESTRICTIVE FOR ALL on
`(select app.live_role())`; `site_integrations_public_read` TO anon, the tenant alone. Grants
revoked from PUBLIC, anon, authenticated and service_role, then: staff SELECT on every value
column, the key, `version` and `updated_at` (not `updated_by`), INSERT on the key and the
values, UPDATE on the values (never DELETE, the key, the version or the stamps); the service
role SELECT, INSERT, UPDATE, DELETE; anon SELECT on `tenant_id` and `search_console_token`. A
NOTICE counts the rows holding legacy JSON (a count, never a value). The postconditions check
all of it under both grant regimes (MAINTAIN under a version CASE), the CHECKs by name and by
evaluating their patterns, that the table is not in `app.release_entities` and releases are
off, and that every tenant holds the three guides as the catalog has them. Replayed on PGlite
(PostgreSQL 17.5): every migration, then `integrations` 45/45, `preview_dataset` 23/23,
`rls_admin_cms` 25/25, `rls_sales_role` 66/66, `help_catalog` 85/85, `help_centre` 64/64 (the
replay cannot run `grants_app_schema`'s section 8, the deploy-guard role, for every slice; its
U11 assertion passed). The read-back matched on every column but the server version.

**The guides (H11's catalog).** `integrations` (new, revision 0, place **62**, after
seo-and-redirects at 60), `forms-and-spam` (new, revision 0, place **85**, between
personal-data at 80 and job-applications at 90), `your-account` (revision **2**, as U17's 0072
left it; one line added to the bell section and `/admin/settings/notifications` added to its
screens). Each literal is `docs/admin-v2/guides/<slug>.json` byte for byte
(`tests/lib/helpU11.spec.ts`, which also holds each claim to the code: the limits, the CV size,
the required fields from the overview's derivation, the controls the screen draws).
`PAGE_GUIDES` gains both guides and the bell settings screen (its own entry: it is deeper than
U9's `/admin/settings`, and the longest match wins). `helpCentre.spec.ts`: SEO's list gains
`integrations`, Developer's `forms-and-spam`, and U17's screens claim now reads the set as U17
left it.

**The API.** `PATCH /api/admin/integrations` takes `IntegrationsSchema`
(`packages/schemas/integrations.ts`, re-exported from `admin.ts`): any of `ga4MeasurementId`
(trimmed, upper-cased), `searchConsoleToken` (a whole pasted `<meta
name="google-site-verification" content="…">` tag, in either attribute order and either quote,
is read for its content) and `calendlyUrl` (also parsed with `URL`: https, exactly
`calendly.com`, no port, credentials, query or fragment), a blank or null clearing one, and
`version`; strict, so the legacy jsonb keys and anything else are a 422. GET and PATCH read
and write the typed columns only (`src/lib/admin/integrations/load.ts`); the queued audit
`site_integrations.update` names the columns saved. `GET/PATCH
/api/admin/me/notification-settings` (`analytics.read`, every member): one boolean per kind the
role's bell shows (`src/lib/admin/notificationSettings.ts`, pure), over F8's
`admin_user_prefs.notifications.muted`; a kind the role's bell never shows is a 422, a mute of
a hidden kind is kept, a stale version is a 409; not audited (as `preferences.ts`).

**The public head.** `src/lib/data/siteVerification.ts` reads `search_console_token` through
`contentClient()` (never throws; a refused read, no row, or a value the pattern refuses is no
tag, the failures reported). `SeoHead` starts the read only on an indexable home page
(`logicalPath === '/'`, no `noindex`), beside the identity read, and emits one
`<meta name="google-site-verification">` after the robots meta. With no code set the head is
byte for byte what it was: `tests/render/seoHeadVerification.spec.ts` was written, and its
snapshot stored, before SeoHead changed; `seoHeadVerificationSet.spec.ts` proves the tag is the
only addition, on `/` and `/ar` only, that no other route asks for it, and that a value stays
inside its quoted attribute.

**The preview (R8) learns the table.** `site_integrations` is a preview table (relations,
`TABLE_KEYS` by tenant), column-granted (`ANON_COLUMNS`: the key and the code), its anon
policy mirrored (`MIRRORED_POLICIES`, the md5 of `(tenant_id = app.effective_tenant_id())`, as
`site_profile_read`'s), its rule the tenant fence alone; `preview_dataset.test.sql` pins the
literals and adds the anon read and the empty reads of a Content Creator, a Developer, Sales
and another tenant; the loader joins `previewLoaders.spec`'s cases and the seam's pinned
loaders (`contentSource.spec`).

**The screens.** `/admin/integrations`: the page decides `settings.integrations` (a 403 and
`Refused.astro` otherwise, nothing read), reads the row once as the person, and hands the
values to `AdminIntegrations`: four tiles (`src/lib/admin/integrations/tiles.ts`; the
prototype's `.ops-int`, `public/styles/admin/integrations.css`) with a badge, the saved value
and Set up or Edit; each opens a kit `Drawer` holding `EditorForm` over `useEntitySave` (the
singleton, that one field), with Remove (a confirm, then null) once saved; the tiles reread the
row when the drawer closes. The captcha tile is read-only "Not set up" and links to the Forms
overview for `settings.general` holders. `/admin/forms` (`settings.general`, no island of its
own): LinkTabs Inquiry form | Join form, the fields with Required or Optional
(`src/lib/admin/forms/overview.ts` derives "Required" from what the schema refuses when a
control is left as it starts; the inquiry tab lists every field of the three variants the site
renders, the home page's, Contact's and the services pages', and marks a field asked only in
some places, such as the phone, which only the services pages ask), the protections (the hidden field, the limits and fail modes
from `CONTACT_LIMITS`/`APPLY_LIMITS`, "Captcha: Not set up", Join's consent version), where the
words are edited (Pages, for `pages.write` holders) and whether applications are open (the
switch is Admin's, in General). `/admin/settings/notifications`: `AdminNotificationSettings`,
one switch per kind (`src/lib/admin/notifications/kinds.ts` names them; the server hands the
role's switches over), saved by `useEntitySave`. The account drawer gets a Notifications row
with "Choose what the bell tells you"; `/admin/notifications` a head action "Notification
settings". Nav: Settings gains Forms (`settings.general`, icon `form`) and Notifications
(`analytics.read`, icon `bell`), between SEO and Integrations. Both islands join the
`admin-fields` chunk group by name (`astro.config.mjs`).

**Tests.** The pgTAP above. Unit: `tests/schemas/integrations.spec.ts`,
`tests/lib/integrationsSql.spec.ts` (each Zod pattern equals its CHECK's, read from the newest
migration that adds it), `integrationTiles.spec.ts`, `siteVerification.spec.ts`,
`notificationSettings.spec.ts` (the switches per role, the merge, the route's 200, 409 and
422), `formsOverview.spec.ts` (the facts held to the forms, the schemas, the limits and the
consent version), `helpU11.spec.ts`, and the edits to `sqlHelpers`, `adminRoutes` (`SIDEBAR`,
the server-rendered locked screens), `adminStyles`, `contentSource`, `previewLoaders`,
`previewMirror`, `previewSelect`, `previewVisibility` and `helpCentre`. Authz cases: the
integrations write sends a typed field; `account: my notification settings read/save` for
every role. E2E: `tests/admin/integrations.e2e.ts` (the tiles and a drawer as Admin and SEO at
320, 390 and 1280 px with axe and overflow; as SEO a pasted tag saved as its code, `/` and

in `src/`, `scripts/`, `supabase/functions/` and `supabase/migrations/`. Readers: the
integrations route (`src/pages/api/admin/integrations.ts`, `singletonRoutes`), the screen's

not G2's health report or probes, not the backups (`BACKUP_TABLES` does not list it), not the

all still granted, and a real session's token carries the `sub` the live check needs: between
the push and the deploy nothing it does is refused. No reader's result shape grows (rule 5):
the deployed route selects its columns by name.

## Departures from the design, and why

- **"Saved", not "Set up", for GA4 and Calendly.** ui.md has two statuses. A GA4 id the site
  does not load yet (U15) and a booking link no page shows are saved, not set up; calling them
  "Set up" would be the fake "Connected" the design removes (its own risk: "GA4 is stored but
  never injected (honest copy)"). Search Console, which the home pages use at once, is "Set up".
- **The captcha tile is read-only, with no column.** ui.md and AV-20 name a "reCAPTCHA (site
  key)" field. The provider is not chosen (O-19, Turnstile recommended), so a reCAPTCHA field
  would be speculative; E8 adds the provider's site key (its secret never in a staff-readable
  row) with the switch. §5's row keeps the label "reCAPTCHA" (renaming it is snapshot churn
  across four documents).
- **The verification tag is on the home pages only**, not on every page SeoHead renders: Google
  reads the HTML tag method on the home page, and no other route pays the read (P-15).
- **Content Creator and Developer get a 403 and the refusal**, not a read-only view ("Read-only
  for anyone without settings.integrations"): §5 gives them ❌, and default deny.
- **The bell's settings are their own flat route** (`/api/admin/me/notification-settings`, a
  singleton shape `useEntitySave` saves), not a variant of U1's `PUT /api/admin/me/preferences`.
  The switches are the bell's kinds today (leads, applications, scheduled, maintenance, and G2's
  health); ui.md's "Changes waiting" and "Published" become switches as soon as the releases
  register those kinds in `NOTIFICATION_KINDS` (`kinds.ts` must name them; a test says so).
- **The Notifications link shows for every member, Sales included** (`analytics.read`). ui.md
  says "any staff (personal)"; Sales has a bell (new inquiries, maintenance), so its sidebar
  gains a Settings group with that one link. C10a's "Sales's sidebar: Dashboard, Leads, Website
  stats" predates it; the account drawer reaches the page either way (an owner question).
- **The Forms screen's refusal probe asks General's read** (`/api/admin/settings`, the same
  capability) instead of making `LockedScreen.api` optional: the page has no JSON twin, and the
  probe still proves the server refuses each role without the capability.
- **`src/lib/admin/ui/integrations.ts` stays**, rewritten to the three typed fields: the tiles
  take their field from it, and the activity log names a saved column by its label
  (`auditLabels.ts`, `ui: 'integrations'`). The JSON boxes are gone.
- **The legacy jsonb columns stay, granted and unread** by this slice's code: the deployed
  Worker reads and writes them until this slice's deploy. U15 drops them, after that deploy.
- **A Content Creator's or Developer's preview of the home page carries no verification tag**:
  the dataset reads through the person's own client, and they may not read the row (§5). The tag
  is in `<head>`, which the parity e2e does not compare; Admin's and SEO's previews carry it.
- **No `site_integrations_staff_columns` block** (the Sales boundary names one for a new public
  relation where authenticated holds more columns than anon): Sales reads no row, by the token
  check and the live check both, so a non-staff block would add nothing.
  `rls_sales_role.test.sql`'s catalog walk covers the table (its fixture row in the Sales
  tenant is there since C10a) and passed on the replay.

## Notes for later slices

- **R7 (purge):** a save on `site_integrations` changes the home pages' head; the purge owes
  them `site:identity` (ui.md §5), which `/` and `/ar` already carry (`ALWAYS`). No purge call
  here: nothing caches Tier A and there is no seam to call yet.
- **R8 and R9:** `site_integrations` is a preview table now (above); it is not in the release
  registry, so it has no drafts and the overlay passes it through as live.
- **U15:** loading GA4 needs CSP sources and the consent hook; this slice made no CSP change.
  U15 also gives the Worker its way to read `ga4_measurement_id` on public pages, and drops the
  legacy jsonb after this slice's deploy.
- **E8:** the captcha's provider, site key and switch; the forms config (labels, required,
  order) replaces the read-only overview.
