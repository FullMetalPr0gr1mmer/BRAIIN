## What was built

- **The guides, in the database.** `public.help_articles`, one row per guide and tenant: a title
  in each language (`title`, `title_ar`: §8, a scalar → `_ar`), the body locale-keyed in one
  JSONB (`{"en": [...], "ar": [...]}`), the reading time, tag keys, the admin screens the guide
  belongs to (`screens`) and the capabilities whose holders it is for (`caps`, none meaning every
  member). A stored `search_text` (both titles, the tags and every text of both bodies, folded
  with `app.normalize_ar_q` and lower-cased), `version`, the stamps and the actor columns. RLS
  ENABLE + FORCE; one policy, staff read their own tenant's guides (`tenant_id =
  app.effective_tenant_id() and app.is_staff()`). Grants stated for both regimes (P-14):
  authenticated SELECT only, the service role SELECT, INSERT, UPDATE, DELETE (0037's statement for
  the tables staff only read), nothing to PUBLIC or anon; no column grant; no sequence (uuid key).
  The postconditions check all of it both ways, MAINTAIN on PostgreSQL 17 only.
- **Typed blocks, never HTML.** A block is `{t: "p" | "h" | "tip", x: text}` or
  `{t: "ol", x: [text, ...]}`, the prototype's four kinds. `app.help_body_ok` holds the shape in a
  CHECK (exactly `en` and `ar`, 1 to 40 blocks each, exactly `{t, x}` per block, known kinds only,
  the sizes; 64 KB in all), `app.help_text_ok` refuses `<`, `>` and every C0/C1 control character
  in any text, titles included, and `app.help_keys_ok` holds the tag, screen and capability lists
  (one dimension, bounded, patterned, no repeats). The same rules are `packages/schemas/help.ts`,
  which the Worker reads every row with (a row it refuses is left out and logged to
  `system_logs`, never shown half-read); `tests/lib/helpCentre.spec.ts` holds the two to the same
  patterns and limits. Every text renders as a React or Astro text node.
- **Who writes: the migrations.** CLAUDE.md §5 assigns help no capability and the design defers
  editing (TDD phase 7, "editing can wait; reading should not"), so no staff role writes a guide in
  either layer: no write policy and no write grant. The guides are `app.help_article_set()`, one
  JSON array in the migration (written for the features that are built); `app.seed_help_articles`
  upserts it into a tenant (inserted, or brought back to the set's text where it differs; a guide
  the set does not hold is left alone), run for every tenant by 0046 and for each new tenant by
  the `tenants_help_defaults` trigger (as 0034 seeds the lead pipeline). A later slice that changes
  a screen a guide describes replaces the set in its own migration and seeds again; one that
  retires a guide deletes it by slug. A BEFORE trigger (`help_articles_guard`) owns the version
  (it moves only when the guide changes), the stamps and the actor, and refuses a change of id,
  tenant or slug.
- **The guides themselves (12).** The prototype's fifteen are rewritten for what exists; nine of
  them described later-phase screens (DNS, sending and receiving e-mail, WhatsApp and its
  templates, segments, campaigns, automations, the inbox) and are not carried, and "roles"
  contradicted §5 (per-person exceptions). The set: finding your way around; your account,
  password and bell; roles; saving, publishing and scheduling; the media library and alt text;
  SEO defaults and redirects; working with leads; personal data and the PDPL; job applications;
  maintenance mode; website stats; site health, errors and the activity log. Each in English and
  Arabic, block for block; the admin's own labels (Save changes, Reveal contact details…) stay in
  English inside the Arabic text, because the admin is in English. No brand is spelled (§1), no em
  or en dash (P-12), and every number in them is the code's (the reveal's 60 an hour, the export's
  3, the 10-character password, the 24-month and 30-day defaults, the 90-day raw telemetry, the
  hour an issued sign-in lasts). The roles guide says what a role change or a switched-off
  account does and no more (CLAUDE.md §2, session invalidation): the admin turns the person away
  at their next click, a new role reaches every save once their sign-in renews, and a sign-in
  already handed out can reach the database directly, outside the admin, with its old role for
  up to an hour, except leads and job applications, which check the account on every read
  (the stale-token gap; the spec holds the guide to it).
- **Which guides a role is shown.** Decided on the server from `ROLE_CAPS`
  (`mayRead`, `src/lib/admin/help/access.ts`): a role sees a guide when it holds any of its capabilities at
  full, view or meta (the menu's rule), every role when it names none; a capability this build does
  not know counts for nobody (fail closed). Admin sees all twelve, Content Creator six, SEO six,
  Developer nine (pinned role by role in the spec). The spec also holds the rule the verification
  asked for, "nobody is sent to a screen they cannot open": every role that may read a guide
  reaches one of its screens.
- **Search.** `public.help_search(p_tenant, p_q)`, SECURITY INVOKER (RLS decides the rows), a
  500 ms statement timeout: "contains" over `search_text`, the query folded by the same function
  (`app.normalize_ar_q`, as §8's contains searches: ta marbuta, alef forms, tashkeel; no article
  stripping, which only the FTS index needs), `%`, `_` and `\` escaped, a title match first. It
  answers up to 100 guides, the list's own cap (`MAX_GUIDES`): the Worker filters them by role and
  only then keeps the first 20 (`MAX_RESULTS`), so guides for other roles ranked above a role's
  own never crowd them out; the spec holds the set under the cap, so the list's read and the
  search's both see every guide. Over 64 characters or a control character is a 22023; under
  two characters finds nothing; a tenant other than the token's gets nothing (the Worker names
  it, as for `crm_people`). The Worker cleans a query as the header search does before sending
  it, counting and cutting by code points (as PostgreSQL's `char_length` counts the 64) and
  dropping half a surrogate pair, so a cut never leaves text no JSON or URL encoder can send.
- **The routes.** `GET /api/admin/help?screen=` (every guide the role may read, and the slugs of
  the ones for that screen), `GET /api/admin/help/search?q=` and `GET
  /api/admin/help/article?slug=` (one guide in both languages; a 404 when there is none by that
  slug OR the role may not read it, the same answer). All `analytics.read`, the capability every
  member holds (as the bell and the palette). Cases in `tests/authz/cases/help.ts`.
- **The "?" drawer.** The topbar's "?" (`info` icon, named "Help centre", before the bell as in the
  prototype) is a link to `/admin/help?screen=<this page>`; with JS, `AdminChrome` opens it as a
  drawer on F8's `ChromeDrawer` (a modal `<dialog>`): "Short guides, written for people, not
  developers", a search box (focused on open), the live status line, then "On this screen" (the
  guides whose screens hold this page, `/admin/services` covering `/admin/services/<id>`) and "All
  guides". A row is a link (a new tab works); a plain click opens the guide in place: "All guides",
  the reading-time and tag badges, the text, a tip as a tinted box, "Related" (up to three guides
  sharing a tag, from the role's own list). "اقرأ بالعربية" switches the guide to its Arabic text,
  marked `lang="ar" dir="rtl"`, in Almarai; "Read in English" switches back. "All guides"
  shows the lists, clearing a search the guide was opened from (the prototype's `showList('')`).
  Focus goes to the guide's heading when it opens and back to its row on "All guides"; Escape
  closes and focus returns to the "?". The list is asked for the first time the drawer opens
  (never on a timer, P-15); a search waits 250 ms after typing and a newer one cancels an older
  one. A guide's fetch is cancelled by the next guide, "All guides", typing a search and opening
  the drawer again, and an answer that lands anyway is applied only while it is the latest and
  the drawer is open, so a slow guide never replaces a newer view or takes focus.
- **The page head's "Guide".** The prototype's `ROUTE_GUIDE` button: on a screen that has a
  guide, "Guide" (named "Guide to this screen") is the first of the page head's actions, a link
  to `/admin/help?guide=<slug>`; with JS it opens the drawer on that guide, heading focused, the
  lists loading behind it for "All guides". Which guide a screen offers is a code map,
  `PAGE_GUIDES` in `src/lib/admin/help/pageGuides.ts` (a screen covers the pages below it), so the
  shell decides it with no read (the link carries this screen, `&screen=`, as every help link
  does); the layout shows it only to a role that may read the guide (SEO opens Pages, Services,
  Projects and Posts without the content guide, which is for the roles that write content). `tests/lib/helpCentre.spec.ts` holds the map to the set the last migration
  seeds: every slug is a guide of the set with the set's capabilities, every screen is one its
  guide names and appears once, and every screen a guide names has a page guide (the help page
  aside). `useOpenOn` (F8) now hands the trigger to the drawer's `open`, which reads the guide
  from its `data-help-guide`.
- **The no-JS page.** `/admin/help` renders every view on the server with the same components:
  `?screen=` (this screen's guides first), `?q=` (a GET search form), `?guide=<slug>` and
  `&lang=ar`. The screen rides along on every link the page builds (rows, related guides, the
  language switch, the search form; `guideHref(slug, screen)`), so "All guides" always lists
  that screen's guides first; the drawer's rows carry it too, for a new tab. Every member (403
  otherwise), a 404 for a guide that is not there or not the role's.
  In the per-role sweep's extras, all four views. Page-only frames in
  `public/styles/admin/help.css`; the drawer's content in `admin.css` (it renders on every page).
- **Tests.** pgTAP over admin, content_creator, seo, developer, anon, another tenant's admin and a
  token whose role is not staff: reads, refused writes (matched by the grant layer's message, so
  a regained grant that RLS would refuse with another fails them), the search's folding and
  escaping and bounds (105 matching guides answer 100), the CHECKs and the guard for the service role, the seed (new tenant, again, an edited
  guide brought back), both grant regimes run locally on PGlite (PostgreSQL 16 and 18, once and
  twice). `tests/lib/helpCentre.spec.ts` (the set against the schema, ROLE_CAPS, the pages and the
  copy rules; the page guides against the set and per role; who is shown what; the loaders and
  routes; the query cut by code points; the role filter before the cut to 20; the links carrying
  the screen; the roles guide's one-hour limit; the standard's account of the fold).
  `tests/admin/help.e2e.ts` (the drawer, axe with it open in English and Arabic and on a guide,
  focus, search by role, "All guides" from a search, a guide answering late after a search was
  typed and after the drawer was closed and reopened, the page head's "Guide" with and without
  JS and its absence for SEO on Pages, the 404, the links without JS keeping the screen through
  the language switch and back to "All guides").

## Departures from the design, and why

- **Migration 0046, not 0042.** The ledger reserved 0042; F8 (0044) and U3 (0045) merge first, so
  0042 is released and U16 takes the next free number above them. C13's 0043 is then below
  `main`'s highest as well: the ledger releases it and reserves 0047 for C13, as the Wave 1 plan
  does (U3's PR rewrites the same rows); the next free number is 0048.
- **No staff role edits help (decision).** The TDD asks for "articles as content in the database
  so the client can edit them", and the verification proposed Admin write. §5 has no help row and
  the design puts editing in TDD phase 7, so editing would need a new capability, a §5 amendment
  (with `ROLE_CAPS`, architecture §3.4 and §9.3) and an editor screen, none of which this slice
  was asked to build. The articles are in the database, as the TDD asks; staff read them, and the
  migrations write them. Owner question under "Open".
- **The capability filter is the Worker's, not RLS.** RLS lets every staff member of the tenant
  read every guide, and the Worker shows each role only the guides for its capabilities. A guide
  describes the admin, holds no data, and is published in the migration (the repository is
  public), so filtering it in SQL would hide nothing; it would also need a copy of `ROLE_CAPS` in
  SQL to keep in step (there is one helper per capability for the ones RLS needs, not a matrix).
  The header search draws the same line (`src/lib/admin/globalSearch.ts`).
- **The page head's "Guide" comes from a code map, not a `guide?` prop per page.** ui.md §0 has
  AdminLayout reserve a `guide?` prop; the layout instead looks the screen up in `PAGE_GUIDES`,
  one list beside the guides' own code, so no page passes anything and a new screen under a
  mapped one inherits its guide. The map is a copy of what the set says (which guide, its
  capabilities), because reading the database for it would cost a read on every admin render
  (P-15); the spec fails CI when a migration retires or retargets a guide the map names. The
  prototype's map is not carried: every entry but `/settings/users` (roles) and `/leads` (lead
  scoring, a later-phase guide) points at a later-phase screen; here every screen with a guide has
  one.
- **Not built, because nothing behind them exists:** the drawer's footer ("Get connected", a
  later phase under A1; "Ask us", which the prototype stubs with "In the live version this opens a
  chat") and the prototype's empty-search line "Ask us and we will write one" (now "No guide
  matches that. Try other words.").
- **Arabic on request.** The admin is in English (ui.md §0, "Arabic admin" is later), so lists and
  titles are English; every guide also opens in Arabic, which the prototype did not have. Search
  covers both languages. The tag badges stay their English keys in both.
- **The slug is `text` with a lower-case CHECK, not `citext`.** §8 makes slugs citext so a
  case-insensitive pair cannot exist; a slug that can only be lower case gets the same uniqueness
  from `(tenant_id, slug)`.
- **The seed re-applies the set's text.** A guide edited by an operator through the service role
  goes back to the set's text the next time the set is seeded (a later migration). Nothing but the
  migrations is meant to write a guide until an editor exists; that editor's slice decides how a
  re-seed treats an edited guide.

## Review fixes (2026-10-14)

Seven low-severity findings from the Wave 1 review, each fixed with a test that fails without
it (0046 is applied nowhere yet, so it was changed in place; the pgTAP plan stays 62, run on
PGlite on PostgreSQL 16 and 18 under both grant regimes, the migration applied twice, and each
tightened row checked against the mutation it guards):

- **u16-security-2**: a query cut by UTF-16 units kept half a surrogate pair, which the database
  refuses as JSON (an error row and a 500) and `encodeURIComponent` refuses to encode. Cut by code
  points, lone halves dropped.
- **u16-security-3**: the roles guide promised that a role change or a switched-off account
  "signs them out at once". It now says what is true, in both languages (above).
- **u16-correctness-1**: a slow guide could replace the search typed while it loaded, or open over
  the lists after the drawer was closed and reopened, and take focus. Cancelled and checked.
- **u16-correctness-2**: the staff insert refusals matched only 42501, which RLS also raises, and
  the "at most 20" row could not fail with twelve guides. Matched by message; 105 guides.
- **u16-correctness-3**: the search's LIMIT ran before the role filter. Moved after it (above).
- **u16-correctness-4**: "All guides" went back to a search's results. It shows the lists now, as
  the prototype's did, and clears the box (the prototype left the typed words above an unfiltered
  list).
- **u16-correctness-5**: without JS the page lost its screen at the first row, and the language
  switch rebuilt the URL without it. Every link keeps it now, the page head's "Guide" too.
- **u16-correctness-6**: CLAUDE.md's bullet said the search folds "as the Arabic FTS rule above
  folds", which also strips the article; it folds with `app.normalize_ar_q` only, as the CRM's
  contains search does. ChromeDrawer's header now names the help drawer.

Left open:

- **The read cap is a bound, not a filter in SQL.** The list and the search read at most 100
  guides and filter them by role in the Worker (the design keeps the capability filter out of
  SQL). The set holds twelve and the spec fails a migration that grows it past the cap; only
  guides an operator adds by hand with the service role, past 100, could crowd a role's own out.
- **The stale-token gap itself** is not U16's to close: ending the person's sessions on a role
  change or deactivation (GoTrue's sign-out for that user) and live checks on the remaining
  tables are the separate fix the guide now describes the absence of.
- **The header search cuts its query the same way** (`cleanQuery` in
  `src/lib/admin/globalSearch.ts`, by UTF-16 units): pre-existing and outside this slice. Its
  query reaches PostgREST as a URL parameter, where a lone half becomes U+FFFD rather than an
  error, so it fails softer; the same fix applies.

## Open

- **Who edits the guides.** Nobody in the admin yet (see Departures). Editing them in the admin
  needs an owner decision: a new capability (Admin only, as the verification proposed, or Admin
  and Content Creator), its §5 row with `ROLE_CAPS`, architecture §3.4 and §9.3, a write policy
  and grant on `help_articles`, and an editor screen. Until then a slice that changes a screen a
  guide describes replaces the set in its own migration.
