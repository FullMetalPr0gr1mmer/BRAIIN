# H6: history rows are written by the snapshot trigger only

- **Lane:** hotfix; it pulls part of the release track's R1 forward
- **Design:** [releases.md](../releases.md) R1 ("Revoke INSERT on content_versions from
  authenticated") and the README's mapping finding "staff can forge `content_versions` rows"
- **PR:** #42, merged as `a6defba` on 2026-10-07
- **Migrations:** 0032 (`0032_content_versions_insert.sql`), applied to production before the
  merge

## Departures from the design, and why

- **Shipped ahead of R1, as a hotfix.** `authenticated` held INSERT on `content_versions`
  (0011) and two permissive insert policies admitted any staff JWT, so any Admin, Content
  Creator, SEO or Developer could post an invented history row (any entity, any version, any
  `created_by`) straight to the API. Nothing reads history yet; R10's "Restore vN" will stage
  it as content.
- **More than R1 planned.** R1 revokes INSERT and keeps 0009's staff insert policy. 0032
  revokes INSERT, UPDATE, DELETE and the rest from `public`, `anon` and `authenticated` (staff
  keep SELECT), and replaces the two insert policies with one for the role that owns
  `app.tg_snapshot_version()`, the only legitimate writer. Review found that RLS still admitted
  a forged staff insert, because those policies applied to PUBLIC and only the GRANT refused
  it. Postconditions check that no write policy reaches `public`, `anon` or `authenticated`
  and that the trigger function is still SECURITY DEFINER.
- **Left to R1:** `content_versions_read` moving to `app.is_cms_staff()`, `release_id`, and
  the wider snapshot coverage.
- **Version numbers.** A snapshot records the row's `version`, which `app.tg_bump_version`
  keeps when a writer sends a different value; unique, ordered numbering is R10's (CLAUDE.md
  §8, Versioning).
- **Tests.** `content_versions_writes.test.sql`: every API principal (another tenant and anon
  included) is refused a direct insert, DELETE is refused for all four staff roles, a staff
  edit still records its snapshot attributed to the real editor (`auth.uid()`), and an
  RLS-only proof (the GRANT restored inside the transaction, the insert still refused by
  policy). Its history-count helper is created as the setup role, because `authenticated`
  cannot create objects in `public`.
