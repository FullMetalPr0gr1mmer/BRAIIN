## Plan (written before the build)

### What is captured, and when

Nothing at all unless the visitor said yes to analytics in the consent banner, checked on the
server through the one gate, `hasConsent(request, 'analytics')` (packages/consent/gate.ts),
and mirrored in the browser (the stored first touch is written and read only with that yes).

With that yes, a lead stores, beside itself:

| Column | What | From |
|---|---|---|
| `landing_path` | the page the inquiry was sent from: path only, no query, no fragment | the server, from the POST's same-origin `Referer`; never from the client |
| `referrer_host` | the other site that sent the visitor at the start of the browsing session: host name only, cross-site only | the browser's first touch (sessionStorage), checked again on the server |
| `utm_source` / `utm_medium` / `utm_campaign` | the campaign tags of that first page: bounded lower-case slugs | the browser's first touch, checked again on the server |
| `device_class` | mobile, tablet or desktop | the server, from `Sec-CH-UA-Mobile` or the User-Agent at the send; the User-Agent itself is never stored |
| `country` | ISO 3166 two-letter code | the server, `request.cf.country` (Cloudflare's network location); never the IP, never a city |
| `channel` | organic, social, paid, referral, direct, email (existing column) | the server classifies it from the above; without consent it stays `unknown` |

`service_page` (a score signal since 0035, not set by anything until now) is added when the
recorded `landing_path` is a service page (`/services/<slug>`, `/ar/services/<slug>`), so it too
depends on the consent. The CRM settings screen offers its points from this slice.

**Never stored:** IP address, the full User-Agent, any full URL or query string, a city, the
analytics session id (`bs_sid`), or anything that links a lead to its page views (G1 D4).

### Departures from the design, and why

- **`landing_path` is consent-gated too.** crm.md §7.3 captured it with every submission as
  "the form's own context". This slice's brief says that with no consent nothing is captured,
  and that is the narrower reading, so the lawyer can widen it (register question) rather than
  narrow it after the fact. A consequence: `service_page` scores only with consent.
- **One set of columns, the session's first touch.** The design has one set; the source,
  medium, campaign and referrer are the first consented page of the browsing session (a tab),
  and the landing path is the page the form was sent from (the last touch). No second set.
- **The attribution never costs a lead.** The input is `.catch(undefined)` (a malformed
  attribution object is dropped, never a 422), each value is cleaned on its own (a bad one is
  dropped, the rest kept), and if `crm_ingest_lead` refuses a lead that carried attribution
  (an older database without 0132, or a CHECK), the Worker sends it again once without the
  attribution and logs a warning with the code only. The plain-insert fallback leaves the
  attribution out.
- **The consent banner's words and `CONSENT_VERSION` are not changed here.** Changing the
  banner's copy moves the bottom-pinned bar's box (the R3-0 font work) and the trimmed font
  subsets, and `CONSENT_VERSION` is the GA4 switch-on's bump (ga4Switch.spec). Whether a yes
  given before the notice changed covers attribution, and whether the banner must name it,
  are register questions with the proposed wording ready (docs/legal file below).
- **The notices' "Last updated" dates are not moved.** The date is the day the lawyer approves
  the text, set at the merge with C5's part.
- **`leads_safe` is not re-created** (nothing reads it since C14b; the columns reach lead
  workers through the column grant and the detail GET).

### Database (0132, expand only)

- `leads` gains the six columns, nullable, each with a named CHECK (path `^/[^?#\s]{0,199}$`,
  host name shape ≤ 253, slugs `^[a-z0-9][a-z0-9._+-]{0,63}$`, device in three values, country
  `^[A-Z]{2}$`; no `@` and no run of 7+ digits in the path or a slug, so an e-mail address or a
  phone number cannot be stored there).
- Lead workers read them: a column SELECT grant to `authenticated` (RLS and the live check
  decide the rows, as for every lead column). No UPDATE or INSERT grant; `anon` nothing.
- `public.crm_ingest_lead` restated (0091's body) with the six keys on its allow-list and in
  its insert. Still SECURITY INVOKER, service role only.
- Postconditions: the columns, the grants exactly, the function's rights.

### Worker

- `src/lib/crm/attribution.ts`: the pure server side (landing path from the Referer, the
  cleaners, device, country, channel classification, `service_page`), and
  `leadAttribution(request, input)`, which returns nothing without `hasConsent`.
- `packages/schemas/lead.ts`: `attribution`, a strict bounded object, optional, `.catch`.
- `src/pages/api/contact.ts` passes the request's attribution to `createLead`, which adds the
  columns and the signal, with the retry and the fallback above.
- `src/lib/client/attribution.ts`: the first touch in sessionStorage (`bs_ft`), written by the
  analytics emitter only with consent, removed when consent is withdrawn; the contact form reads
  it at the send, only with consent.

### Admin

- The lead detail GET reads the six columns too; the lead page shows a "How they found us"
  card (channel, page, the site that sent them, campaign, device, country), or says nothing was
  recorded and why. Any role that reads leads (`leads.manage`) sees it; nothing here is in the
  §3 gated list.
- The source badge says "Web form · Search" (etc.) once a channel is known; the Source filter
  offers the web form's channels.
- CRM settings offers `service_page`'s points.

### Legal (HELD)

- `src/lib/legal/attribution.ts`: the privacy notice's new section (`#inquiry-attribution`) and
  the cookie policy's session-storage line, EN and AR, added to content.ts in their own hunks.
- `docs/legal/privacy-notice-c13-attribution.md`: the same text for sign-off, in its own clearly
  marked section, separate from C5's file.
- `docs/legal/review-register.md`: the questions (lawful basis and re-consent, the landing path
  without consent, country from the network location, retention and withdrawal, the banner
  wording), never a claim of compliance.

### Tests

- vitest: consent off → no attribution and channel unknown; consent on → values stored and
  bounded; the landing path ignores client input, strips the query and refuses another origin;
  classification; createLead's allow-list, retry and fallback; the form payload; the client
  first touch; the notice text present in both languages and equal to the docs/legal file.
- pgTAP `crm_lead_attribution.test.sql`: CHECKs, ingest stores the columns, grants, roles.
- e2e `lead-attribution.e2e.ts`: no `bs_ft` before consent, written after Accept, removed after
  Reject. (As first built the Reject case only checked that nothing was ever written; the
  review added the removal after a yes, and after a yes to an older notice.)

### The merge, when O-11 is answered

1. The lawyer's answers go in the register; any change of wording goes in
   `src/lib/legal/attribution.ts` and the sign-off file together (the spec fails otherwise).
   Once no C13 HIGH row is `open`, `tests/lib/legalAttribution.spec.ts` fails until
   `ATTRIBUTION_NOTICE_HELD` (src/lib/legal/attribution.ts) is set to `false`.
2. With it `false` the same spec fails until the notices' "Last updated" dates move past
   2026-10-04: they move to the approval day with C5's part (legal.spec ties them to the
   recruitment notice version: a re-date appends a version there, J-17).
3. Consent version (L-C13-2): attribution counts only a yes given under the current
   `CONSENT_VERSION` and at least `ATTRIBUTION_CONSENT_VERSION` (packages/consent/version.ts,
   both 1 today). If the lawyer asks that earlier choices be asked again, raise both to the new
   version in the merge (with the banner wording and the consent-banner layout tests,
   `consent-banner.e2e.ts`, `fontFallbacks.spec.ts`; the GA4 switch plans the same bump, so the
   two can be one re-prompt). If a withdrawal control is a precondition (L-C13-3), it ships
   first.
4. **C5 and C13 both restate `public.crm_ingest_lead` from 0091's body** (C5's 0131 adds the
   contact link at arrival, this slice's 0132 the attribution keys). Whichever applies last
   would silently drop the other's change. The PR that merges second restates the function from
   the other's merged body, so the last definition has both; `tests/lib/leadAttributionSql.spec.ts`
   fails if the last definition lacks an attribution key, or lacks `perform
   app.crm_link_lead_core(` once any migration defines that function (checked here against
   C5's 0131 at either number, see the review fixes). C5's as-built should name the same step;
   that file is C5's, so it is an item for C5's merge rather than an edit here.
5. Renumber 0132 at the merge train, apply it to production, run the read-back
   (scratchpad `readback_c13.sql`, its `'0132'` lookup moved with the number), then merge.
   The code reads the new columns (the detail GET, the backfill), so the deploy guard's order

6. On staging before the production merge: send a consented inquiry and check the lead stores a

   geolocation is on); neither was observed on a deployed Worker in this build.

## Review fixes (2026-11-10)

Each finding was checked against the code first. Each fix has a test that failed on the tree
before the fix (red/green on a `git archive` copy of the branch head under the scratchpad's
`c13_mut/`, the new tests copied in: 17 vitest failures and 4 pgTAP failures before, all green
after).

- **C13-S1 and C13-COR-1 (medium, fixed; one finding seen twice).** Attribution read only the
  analytics boolean, never the cookie's version, so raising `CONSENT_VERSION` would not have
  stopped it. Now `packages/consent/version.ts` (zod-free, so the browser can import it) holds
  `CONSENT_VERSION` and `ATTRIBUTION_CONSENT_VERSION`, and `attributionVersionOk(v)` requires
  `v === CONSENT_VERSION` and `v >= ATTRIBUTION_CONSENT_VERSION`. The server asks
  `hasAttributionConsent(req)` (gate.ts: `hasConsent` plus that version check), the browser asks
  `attributionConsent()` (analytics.ts) before writing, keeping or sending `bs_ft`, and an
  outdated yes removes `bs_ft` on the next page. First-party page views still count a yes
  under any version (unchanged; not in scope). Tests: leadAttribution.spec "the consent must be
  given under the current notice" (server and browser, older and newer versions) and the e2e
  "a withdrawn yes, or a yes to an older notice, removes the first touch". The minimum is 1
  today; the lawyer's answer to L-C13-2 sets it (merge step 3).
- **C13-S2 (medium, fixed here for C13's side).** Confirmed: C5's 0131 and this 0132 each
  restate `crm_ingest_lead` from 0091. New `tests/lib/leadAttributionSql.spec.ts` checks the
  last definition in the migrations: the seven attribution keys on the allow-list and in the
  insert, and the call to `app.crm_link_lead_core` once any migration defines it. Shown red with
  C5's 0131 copied in at 0131 (0132 last: the link is missing) and at 0133 (C5 last: the
  attribution keys are missing). Named in merge step 4 and in CLAUDE.md §8. C5's as-built is not
  edited from this branch.
- **C13-S3 (low, fixed).** Confirmed with the probe's inputs. The Worker and the CHECKs now
  refuse an IP address as the referrer host (a numeric last label; the integer and hex
  spellings normalise to dotted form first), a percent-escape anywhere in the path (every page
  path on the site is ASCII; `%40` is an `@`), and seven digits split by single separators in
  a path or a tag (`[0-9]([^0-9A-Za-z]?[0-9]){6}`, `050-123-4567`). The patterns are exported
  from `src/lib/crm/attribution.ts`, and leadAttributionSql.spec holds the CHECK text to them.
  A tag such as `q4-2026-11` (seven digits with separators) is now dropped: the stricter reading
  costs a campaign name, never a lead. pgTAP: four new shape cases. The "cannot hold an
  address" wording is softened below and in the sign-off file ("written plainly in a link").
- **C13-S4 (low, fixed in the text; the question is the lawyer's).** The notice now says "We
  store no identifier that links your inquiry to your visits to our pages" instead of promising
  that nothing links them. New register row L-C13-8 (MEDIUM) asks whether matching the landing
  path and the inquiry time against the raw page views needs saying or preventing. Coarsening
  the inquiry time staff see was not done (it would change the leads screens for every lead;
  the register question decides).
- **C13-S5 and C13-COR-6 (low, fixed; one finding seen twice).** The postconditions now require
  the service role's SELECT and INSERT on each attribution column, and pgTAP has the same check.
  A mutation that revokes the service role's SELECT on `leads` makes 0132 refuse to apply.
- **C13-S6 (low, fixed).** The pgTAP row section adds a live Sales token (reads the attribution),
  and deactivated and locked developer tokens (0 rows). The suite is 48 tests.
- **C13-S7 and C13-COR-2 (low, fixed; one finding seen twice).** The first touch is the first
  page seen WITH consent, by design: keeping tags from before the yes would store them before
  consent. When that page was reached from inside the site, `firstTouchOf` stores
  `{ lateConsent: true }` (the arrival was not seen), the schema takes it, and
  `classifyChannel` returns `unknown` instead of `direct` (tags, if any, still classify). The
  notice (EN and AR), the cookie policy line and the sign-off file now say "the first page you
  viewed in that visit after allowing analytics cookies". Tests in leadAttribution.spec and
  legalAttribution.spec.
- **C13-COR-3 (low, fixed).** The retention sentence now says `bs_ft` stays in the tab's session
  storage until the tab closes and a copy is kept with an inquiry (an inquiry does not remove
  it, so a second inquiry from the tab carries it too). The withdrawal sentence stays as drafted
  for the lawyer under L-C13-3, which now points at it.
- **C13-COR-4 (low, fixed).** `ATTRIBUTION_NOTICE_HELD` in src/lib/legal/attribution.ts, held by
  legalAttribution.spec to the register (true exactly while a C13 HIGH row is open); once false,
  the spec requires the notices' date past 2026-10-04. Shown red both ways by mutation (rows
  answered while held; released with the old date).
- **C13-COR-5 (low, fixed in code, verification left for staging).** Adapter 14 does document
  `Astro.request.cf`, but Astro rebuilds the request with `new Request(url, request)` on its
  forwarded-host path, and outside workerd that drops `cf`. `countryOf` now falls back to
  Cloudflare's `CF-IPCountry` header, which survives a rebuild (test). Whether workerd keeps
  `cf` across the rebuild and whether the zone sends the header are not verifiable here: merge
  step 6.
- **C13-COR-7 (low, fixed).** New e2e (EN and AR): accept, then a cookie that says no with
  `consent-updated` removes `bs_ft`; a yes again keeps it; a yes under an older version, then a
  navigation, shows the banner again, removes `bs_ft`, and the inquiry carries no attribution.
  Runs in CI only; traced against the banner's script and the form's send.

## Self-review

- Security: no new API role can write anything (no grant); the consent is the server's own read
  of the cookie, at the current notice's version; the landing path cannot be supplied by the
  body; every value is bounded twice (Worker cleaners, database CHECKs, the same patterns) and
  refuses an `@`, an encoded `@`, an IP-address host and seven digits in a row or split by
  single separators, so an address or a phone number written plainly in a link is not stored
  (a determined spelling, such as digits spelled out, is not caught); the admin prints the
  values as text, never as links; logs carry codes only.
- Residual, accepted: a visitor can forge their own consent cookie, first touch or (where the
  edge does not set it) `CF-IPCountry` header; that only affects what is recorded about their
  own inquiry, within the shapes above.
- Legal: nothing here is called compliant; the open questions are in the register, three of
  them HIGH, and the PR stays held.
