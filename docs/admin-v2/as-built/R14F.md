# R14f: the last release-mode rehearsal failures, and one bound

- **Lane:** Releases (R14 prep)
- **Branch:** `fix/r14f-rehearsal` from main `2a14b028` (R14d and R14e merged)
- **Migration:** none

The hand-run Releases rehearsal on R14d (5ac35c43) got through the admin project and into the serial
chain, with two failures in specs R14d converted to both modes. The Admin visual baselines `update`
run on the same branch failed its "stable across two runs" compare on one screen. Each cause was
found in the code and the CI logs; each fix has a test that was run red without it and green with it.

## 1. A reorder holds SORT_ORDER_MAX in both modes (product, both modes)

**Seen:** `tests/admin/reorder.e2e.ts:125`, as Content Creator, answered 422 to the move with
releases on (200 with them off).

**Cause:** the spec's rows sat at 99,910 to 99,930. The reorder route took any integer
(`z.number().int()`), so with releases off the move wrote it live; with releases on the move is
staged, and a staged change goes through the entity's schema, whose `SortOrderSchema` holds
-10,000 to 10,000, so the same move was refused. The reorder route was the one write of a sort
order without that bound.

**Fix:**
- `reorderRoute` (`src/lib/admin/resource.ts`) bounds `sortOrder` by `SORT_ORDER_MAX` in both modes,
  so no move stores a number a release could not carry.
- The spec's rows are 9,910 to 9,930.
- Production (read-only, 2026-11-08): no row of any reorderable table (portfolio, services,
  disciplines, faq_items, navigation, page_sections, sectors, clients, certifications) is above
  10,000, and every screen already clamps its numbers, so the bound refuses nothing anyone sends
  today.

**Guard:** `tests/authz/reorder.spec.ts` "a sort order past SORT_ORDER_MAX: 422 in both modes,
nothing written or staged" (and the two ends are a move like any other). Red with the route's
bound taken out, green with it.

## 2. The redirect's delete confirm, by its mode's label (test)

**Seen:** `tests/admin/seo.e2e.ts:340`, as SEO, waited 30 s for a dialog button named "Delete".

**Cause:** with releases on, the list's Delete stages a removal (here it throws away a pending
create), and ResourceTable's confirm says so with the button "Remove" (`confirmLabel: staged ?
'Remove' : 'Delete'`). The product was right.

**Fix:** the spec presses `releasesOn() ? 'Remove' : 'Delete'` (exact), with a comment naming
ResourceTable's `confirmLabel`. RedirectsTab's header comment, which still said releases do not
stage redirects, now says they do (the registry's `redirect` entry; the edge map is rebuilt on
publish).

**For R14c's copy:** the redirect field help ("Takes effect at the edge within a minute of
saving") and the seo-and-redirects guide's same sentence are true with releases off only; with
releases on a rule takes effect when it is published. `tests/lib/helpCentre.spec.ts` holds the two
equal, and the guide lives in the database, so the change is a guide put (a migration) in R14c's
copy pass.

## 3. Relative times masked in the visual baselines (test)

**Seen:** `admin-admin-d-admin_notifications` differed by 9,337 px between the update run's two
passes.

**Cause:** the Notifications page prints the bell's relative time from
`src/lib/admin/notifications/ago.ts` (Intl: "4 minutes ago", "in 3 hours", "last week"). The
masks' `WHEN` pattern knew only relTime.ts's short forms ("5 min ago"), so the label was pictured,
and it moved on between the passes.

**Fix:** `WHEN` moves to the pure `tests/visual/adminVisualSteady.ts` (exported, the spec imports
it) and covers Intl's long forms, past and future, and "last/next week|month|year". It does not
match ordinary words ("Check now", "Last name").

**Guard:** `tests/ci/adminVisual.spec.ts` "relative times in the baselines": every label
`agoLabel()` prints for 24 offsets, past and future, alone and after an item's detail, is masked;
the short forms still are; ordinary words are not; the spec masks with this one pattern. Red with
the old pattern, green with the new.
