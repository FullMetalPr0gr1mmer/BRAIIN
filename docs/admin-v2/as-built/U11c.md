## Plan (written before the build)

**Scope.** Close U11's residual: until now an Admin or SEO token could write anything into
`site_integrations`' four legacy jsonb columns (`ga4`, `search_console`, `calendly`,
`recaptcha`) through PostgREST and read it back. Nothing else changes: no screen, no route, no
guide.

**Revoke or drop.** At 0105's push the NOTICE counted 0 production rows holding legacy JSON,
so the columns hold nothing worth keeping and DROP COLUMN is the clean contract: no residual
grant to reason about, nothing a later grant could reopen. The migration still counts again
at its own push and refuses (raises, so nothing is dropped) if any row holds JSON by then, so
a value written in the window between 0105 and this push is never destroyed unread.

**Migration.**
1. `set local lock_timeout = '5s'`.
2. The precondition: no row holds legacy JSON (else the push stops, with what to do).
3. `alter table public.site_integrations drop column ga4, drop column search_console, drop
   column calendly, drop column recaptcha` (RESTRICT: a dependent object fails the push).
4. Grants restated (P-14): revoke all from PUBLIC, anon, authenticated, service_role, then
   U11's grants on the columns that remain.
5. Postconditions under both grant regimes: the four columns gone and the table's columns
   exactly the seven that remain; RLS ENABLE + FORCE; the exact policy set, tenant first; the
   table and column privileges of every API role, what must and must not hold (TRUNCATE,
   REFERENCES, TRIGGER; MAINTAIN under a version CASE); the three CHECKs; no function in
   `public` or `app` names the table; still out of the release registry.

**Proof the deployed Worker keeps working** (between the push and the deploy). A new unit
spec, `tests/lib/integrationsContract.spec.ts`: the table's columns replayed from every
migration, then every reader's columns held inside them: the admin load and the route
(`INTEGRATION_COLUMNS`, `INTEGRATION_DEFAULTS`, the route's `toRow`), the public loader
(`SEARCH_CONSOLE_COLUMN`), the preview dataset's projection, the editor's fields,
export-backup's table list, the seeds; a source scan that no file naming the table names a
legacy column; no SQL function or view reads the table.

**Tests.** pgTAP `integrations.test.sql` (the legacy write now 42703, the columns and the
staff column grants exact; `plan(n)` recounted), `grants_app_schema.test.sql` (its anon
assertion named `recaptcha`, which no longer exists; one assertion added); the unit spec
above; `integrationsSql.spec.ts`'s residual test turned into "closed, and said so".

**Docs.** CLAUDE.md's U11 bullet, U11.md's residual and owner item, the deviations register's
Integrations line, the launch runbook's rollback floor (§10: a contraction moves it), the
README's index line, this note. No help guide: none describes the old boxes.

The plan was built as written, with the changes under Departures.

## What was built

**The migration (`0110_integrations_contract.sql`).** In one transaction: `lock_timeout` 5 s;
`lock table public.site_integrations in access exclusive mode` (the mode the drop takes
anyway, taken first so no write lands between the count and the drop), as the first
statement of the counting DO block, which sets the 5 s bound again with `set_config` (review:
the Supabase CLI applies a file as one extended-protocol pipeline with no BEGIN, which
PostgreSQL does not count as a transaction block, so a top-level LOCK TABLE raises 25P01 and
neither `supabase start` nor `db push` could apply it; in plpgsql the lock is not top level
and holds to the end of the batch; `integrationsContract.spec.ts` pins it there and refuses a
top-level LOCK TABLE in any migration); the precondition, that DO block, which counts the rows holding anything but `'{}'` in any of the four boxes (a count,
never a value) and raises `U11c: N site_integrations row(s) hold legacy integration JSON, so
nothing is dropped`, with a hint saying what to do; a second precondition, the grant guard,
which compares every column privilege of anon and authenticated with 0105's, whole, and
refuses (nothing dropped) if a migration since 0105 changed them, because the restatement
below would undo that change in silence; `alter table … drop column ga4, drop
column search_console, drop column calendly, drop column recaptcha` (RESTRICT); the grants
restated from nothing, exactly 0105's on the columns that remain. The postconditions: the
table's live columns are exactly `calendly_url, ga4_measurement_id, search_console_token,
tenant_id, updated_at, updated_by, version`; RLS ENABLE + FORCE; 0105's five policies by name,
command, kind and role, each leading with the tenant predicate, the live one still on
`app.live_role()`; no table privilege for PUBLIC, anon or authenticated, the service role
exactly SELECT, INSERT, UPDATE, DELETE, and nobody TRUNCATE, REFERENCES, TRIGGER, nor
MAINTAIN on 17+ (under a `server_version_num` CASE, so CI's 15 reads it too); every column
privilege compared whole (anon SELECT `search_console_token, tenant_id` and nothing else;
staff SELECT the three values, the key, `version` and `updated_at`; INSERT the key and the
values; UPDATE the values; no REFERENCES; PUBLIC none); the three CHECKs still there and
validated; no function in `public` or `app` whose body names the table and no view that
depends on it; the table still out of `app.release_entities`. Nothing else moves: the helper,
the policies, the CHECKs and the triggers are 0105's, and no help guide describes the old
boxes.

**Replayed in PGlite** (PostgreSQL 17.5, every migration then the seed): 0110 applies after
0105 (whose NOTICE counted 0 legacy rows); with a row planted before it holding a key in
`recaptcha` or `calendly`, or JSON `null` in `ga4`, the push is refused and nothing is
dropped; with only `'{}'` it applies and leaves no legacy column; with anon's GA4 grant
planted before it (U15's migration applied first) or a table-wide staff SELECT, the grant
guard refuses and nothing is dropped. pgTAP: `integrations` 47 of
47, `rls_sales_role` 66 (the catalog walk), `preview_dataset` 24, `rls_admin_cms` 25,
`help_catalog` 85, `help_centre` 64, and `grants_app_schema` to its section 8 (32; PGlite has
no pgtap schema for the deploy-guard role, as on `main`). Without 0110 the new assertions fail
(`integrations` 5, 6 and 16, `grants_app_schema` 26). The read-back (`readback_u11c.sql` in
the build's scratchpad, 19 expectations): every column but the server version.

## The readers of `site_integrations` (the proof the deployed Worker keeps working)

changes nothing under `src/` but one comment in the integrations route, so the readers on this
branch are the deployed ones, and `tests/lib/integrationsContract.spec.ts` holds each of them
to the columns the migrations leave and to the grants of the role that reads them:

- **The integrations route** (`src/pages/api/admin/integrations.ts`, the singleton kernel):
  driven through a recording client: GET, the first save (the version read, the insert with

  driven.
- **The public loader** (`src/lib/data/siteVerification.ts`): driven as anon; one column,
  `search_console_token`, inside anon's grant.
- **The preview dataset** (`src/lib/preview/dataset.ts`): reads a column-granted table with

- **The editor's fields** (`src/lib/admin/ui/integrations.ts`, which the tiles use): each

- **export-backup** (`BACKUP_TABLES`): does not list the table, and names its columns for

- **The seeds** (`supabase/seed.sql`, `supabase/seeds/`, `supabase/seed-data/`,

- **Everything else:** the files whose code (comments aside) names `site_integrations` under
  `src/`, `packages/`, `scripts/` and `supabase/functions/` are exactly the six the spec lists

## Departures, and why

- **The precondition refuses instead of switching to a revoke.** The brief decides revoke or
  drop from production's count, which was 0, so this is a drop. A migration cannot ask the
  owner at the push, so if a value was written in the window since 0105 it fails closed and
  drops nothing: the owner reads the rows and clears them, or asks for the revoke variant
  (Owner items). Dropping unread values would destroy what someone wrote; carrying on with a
  revoke silently would leave a value no one has read.
- **The lock.** Not in the plan: found by the self-review. Without it, a write committing
  between the precondition's count and the drop's lock would be dropped unread. The lock is
  the one the drop takes anyway, taken earlier; a reader queues behind it for the length of
  the migration (`lock_timeout` 5 s bounds the wait for it).
- **The grants are restated** although a drop alone would leave 0105's grants on the kept
  columns as they are: P-14's "stated, never inherited", and it lets the postconditions compare
  every list whole, under either grant regime.
- **The grant guard.** Not in the plan: found by the second self-review. A restatement from
  nothing reverts any grant a migration between 0105 and this one gave, and the
  postconditions (and the read-back) read the restatement back, so they would pass. U15's
  migration (built as the 0109 placeholder) widens anon's SELECT to `ga4_measurement_id`; the
  train orders this file first, but if that order ever flipped, this push would have taken
  the GA4 id away from the deployed U15 loader with every check green. The guard refuses
  instead, and the spec holds the grants it expects equal to the replay of the migrations
  before it (it fails without the guard).
- **CLAUDE.md's U11 bullet is amended, not joined by a U11c bullet**: the residual was stated
  there, and one place now says it is closed. U11.md is edited after its merge (its residual,
  its owner item, one note for U15), because the brief asks those places to say the residual
  is closed.
- **One `src/` comment** (the integrations route's, which said the contract step "revokes"
  the boxes) is updated; no code changes.

## Owner items

- **Before the push:** confirm the Worker deployed is #106 (U11) or later
  (`npx wrangler versions list`: its message carries `ci 1083159…` or a later commit). A
  Worker older than #106 selects the dropped columns, and its Integrations screen then fails
  (the rollback line, launch runbook §10, moves to #106 with this push).
- **At the push:** if the migration refuses with "N site_integrations row(s) hold legacy
  integration JSON", nothing is dropped. Read those rows in the dashboard. Treat any key or
  secret found there as exposed (CMS staff tokens could read the boxes before 0105, Admin and
  SEO after it, and a cleared value stays in point-in-time recovery and the nightly dump):
  rotate it at its provider, then set `ga4`, `search_console`, `calendly` and `recaptcha`
  back to `'{}'`, and push again. (Production counted 0 such rows at 0105's push.) To keep what is there instead, say so: the file becomes a revoke of every privilege of
  authenticated, anon and PUBLIC on the four columns. If it refuses with "the grants on
  public.site_integrations are no longer 0105's", a migration that changed them is already
  applied (U15's, if the order flipped): nothing is dropped; this file is renumbered below it
  or restates that change too.
- **After the push:** the read-back (`readback_u11c.sql`); then merge (the deploy guard needs
  the version recorded first).
