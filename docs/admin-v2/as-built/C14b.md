## Plan (written before the build)

- **Scope.** The contraction C14a prepared: the legacy lead columns and everything that keeps
  them alive go. No Worker code changes (C14a's code names none of the dropped columns); only
  the migration, the tests that name what it drops, and the docs.
- **The migration, in order** (one file, one transaction, `lock_timeout` 5 s, no `cascade`):
  1. Preconditions under the drop's own lock (a DO block, never a top-level `LOCK TABLE`),
     each a count, never a value: no lead holds a plaintext band without an encrypted
     timeline; no legacy `internal_notes` differs from its mirrored note (a field longer than
     the mirror's 5,000 characters differs too); no lead holds an `ip_inet`; no
     `crm_settings.timezone` differs from the studio's zone in force; every lead has a stage
     and every tenant exactly one initial stage.
  2. `app.tg_lead_pipeline()` restated from 0041 without the legacy steps: no band clause, no
     legacy sync, no `status` derivation; an INSERT with no stage takes its tenant's initial
     stage (the contact form's fallback insert sends none); `app.acting_for` is no longer read
     (its one setter goes in step 4).
  3. `app.tg_lead_timeline()` restated without the notes mirror. The mirror notes already in
     the thread stay, as notes.
  4. `public.crm_delete_lead_note` restated without the legacy branch and its
     `app.acting_for` bracket: a legacy note is deleted like any other.
  5. `public.crm_index_lead` restated with the same signature and no band case
     (`p_timeline_text_enc` kept, ignored, so a caller naming it still resolves).
  6. `app.backfill_lead_pipeline()` and `app.lead_stage_for_status(uuid, text, uuid)` dropped.
  7. `leads_safe` dropped, the columns dropped (`leads_status_check` and
     `leads_tenant_status_idx` named first), `leads_safe` re-created with
     `security_invoker = true` and its grants stated (authenticated SELECT only), in the same
     transaction.
  8. `crm_settings`' three column-list triggers re-created without `timezone`, then the column
     dropped.
  9. Postconditions under both grant regimes (MAINTAIN on 17+).
- **Tests.** pgTAP: `rls_leads` (the columns absent, `leads_safe`'s exact columns, invoker
  rights and grants), `rls_lead_pipeline` (the legacy sync and mirror cases replaced by the
  stage and spam writes that remain; an insert with no stage takes the initial one),
  `crm_ingest` (no band moved, the zone gone), `crm_leads_write` (a legacy note deleted like
  any other, nothing set), `crm_settings`, `crm_queries`, `lead_pipeline_backfill` (the
  function is gone), `rls_sales_role`, `release_apply` (only `apply_release` calls
  `set_config` among exposed functions), `grants_app_schema` (the restated functions' EXECUTE,
  the dropped ones gone); each `plan(n)` recounted. Vitest: whatever reads the migrations
  (the grant replay learns `drop column`, the zone list, the note door's text, the lead
  grants spec), run whole. The PGlite replay of every migration, with the precondition
  refusing on planted legacy rows. A read-back for production.
- **Docs.** This note, the README index line, CLAUDE.md §3 and §8 (the expand-window sentences
  become past), the launch runbook §10 (the rollback floor moves to C14a's merge, #109),
  `docs/retention.md` and `crm.md` only where they describe the dropped fields as live.

## What was built

- **One migration, `0113_crm_leads_contract.sql`**, in the order the plan gives: the
  preconditions under the locks, the BEFORE and AFTER phases restated, the note door and the
  index door restated, the two legacy helpers dropped, `leads_safe` dropped, the CHECK, the
  index and the four columns dropped and `leads_safe` re-created, `crm_settings`' three stamp
  triggers re-created and its `timezone` dropped, then the postconditions. No `cascade`
  anywhere: every drop is RESTRICT, so an object the catalog records as depending on a dropped
  column or function fails the push instead of going with it.
- **The locks** are taken inside the first DO block (`crm_settings` then `leads`, ACCESS
  EXCLUSIVE, the order arrival and a points change take them), never as a top-level
  `LOCK TABLE`, which the Supabase CLI's pipeline refuses (25P01;
  `tests/lib/integrationsContract.spec.ts` refuses one in any migration). The block sets
  `lock_timeout` itself as well as the file's first `set local`, so a busy table fails the push
  at 5 s rather than queueing every contact form behind it. The locks hold to the end of the
  file's transaction, so nothing is written between the counts and the drops.
- **The runner** must bypass row security (a superuser or BYPASSRLS; production pushes as
  `postgres`, which does): `leads`, `lead_stages` and the settings force it, so a runner bound
  by it would count nothing and drop the columns unread. The first DO block refuses any other
  runner before it takes a lock (review fix 3).
- **The preconditions** raise with a count, never a value: a lead with a plaintext band and no
  encrypted timeline; a lead whose non-blank notes field does not equal a mirrored note
  (source `legacy`) word for word, which also catches a field over the mirror's 5,000
  characters and a field written at INSERT (0034 mirrored on UPDATE only); a lead with an
  `ip_inet`; a tenant whose `crm_settings.timezone` is not Riyadh and who has no
  `site_settings` row (0102 copied the CRM zone to every row that existed, so only such a
  tenant could lose one); a lead with no stage, or a tenant without exactly one initial stage.
  Each message says what to do next. Production counted 0, 0 and 0 of 2 leads for the first
  three on 2026-10-25.
- **The words leave the rows** (section 6b, review fix 1). DROP COLUMN only hides a column:
  each row keeps the dropped value's bytes until it is next written, and after this file the
  note door writes no lead. So every lead still holding a notes field (each matches its
  mirrored note, or the preconditions refused) or a moved band is rewritten with both empty
  before the drop, after the AFTER phase lost the mirror (so the mirror notes stay). The
  BEFORE phase is switched off (`disable trigger leads_pipeline`) for that one statement,
  under the ACCESS EXCLUSIVE lock already held, so the rewrite is no edit: the lead keeps its
  `updated_at`, `updated_by` and `version`; the AFTER phase records nothing for these columns.
  A NOTICE names how many rows were rewritten (0 on production, which holds no field and no
  band), and a postcondition refuses a trigger on `leads` left switched off. Autovacuum then
  reclaims the old row versions, as it does for any deleted note.
- **`app.tg_lead_pipeline()`** is 0041's, step for step, less the band clause, the legacy sync
  and the derived `status`; a lead INSERTed with no `stage_id` takes its tenant's initial stage
  (the contact form's fallback insert names none and relied on the `status` default through
  the sync; NOT NULL on `stage_id` refuses a tenant with no initial stage). An edit's person is
  the session's; `app.acting_for` is no longer read (its one setter was the note door's legacy
  branch).
- **`app.tg_lead_timeline()`** is 0041's less the notes mirror. The notes the mirror wrote
  stay in the thread (source `legacy`), append-only like the rest.
- **`public.crm_delete_lead_note`** deletes any note the same way and records `note_deleted`
  with its source; it writes no lead and sets no setting. **`public.crm_index_lead`** keeps its
  six-parameter signature (an older cron named `p_timeline_text_enc`; C14a's does not) and
  ignores the last one. Both stay the service role's only, SECURITY INVOKER, grants restated.
- **Dropped:** `app.backfill_lead_pipeline()` (0034's one-off) and
  `app.lead_stage_for_status(uuid, text, uuid)` (the sync's helper), both readers of `status`.
- **`leads_safe`** is dropped and re-created in the same transaction with
  `security_invoker = true`, 0041's columns less `status` in 0041's order, and its grants
  stated for both privilege regimes (P-14): `authenticated` SELECT, nothing for PUBLIC, anon
  or the service role.
- **The postconditions** hold the column sets of `leads` and `crm_settings`, the CHECK and
  index gone, `leads_safe` (invoker rights, its exact columns, its grants), the staff column
  grants on `leads` (SELECT 0041's set less `status`, UPDATE the nine pipeline columns, no
  INSERT, REFERENCES or table-wide privilege), anon and PUBLIC holding nothing, the service
  role's CRUD, the three policies (each leading with the tenant predicate, the live one
  reading `app.live_role`), the four restated bodies naming no dropped column and no setting,
  no function in `app` or `public` naming the band, the address, the helpers or `acting_for`
  (`internal_notes` only in job-application code), the phases' execute rights and owners, the
  triggers on `leads` and the three stamp triggers on `crm_settings`, `crm_settings`' staff
  UPDATE columns, and every lead in the pipeline. MAINTAIN is checked only on PostgreSQL 17+.
- **No Worker code changes.** C14a's code names none of the dropped columns
  (`tests/lib/leadsContract.spec.ts`), so the Worker deployed when this is applied is the one
  that keeps running. **No help guide changes**: no guide describes a dropped field (the
  leads, Pipeline, CRM settings and Sales guides were read), so no `sort_order` is taken and no
  revision is named.
- **Docs.** CLAUDE.md §3 (the lead bullet's opening names the notes thread; the
  expand-window sentence is gone), §8 (the Data model line, the Leads v2 bullets in the past
  tense, C3's note-door attribution, C9a's zone, C10a's legacy grant, C14a's both-schemas
  sentence, a new C14b bullet), §9 (c) and §10 (notify-lead's field list); the launch runbook
  §10; `crm.md` §4.7 and the Tasks "today" rule (the studio's zone is `site_settings.timezone`);
  `deviations.md`'s U9 zone note; architecture §2.5 (a dated note that the four columns are
  gone).

## Departures, and why

1. **`LEGACY_LEAD_COLUMNS` stays in `src/lib/admin/leadFields.ts`** with its `stripSensitive`
   loop, though C14a said C14b "can" delete it. The plan for this PR is the migration and the
   tests that name what it drops, with no Worker code: the deployed Worker is unchanged across
   the apply, and the list now only keeps a never-granted name out of a response and gives
   `leadGrants.spec` its names. Deleting it is a one-line cleanup for any later lead slice.
2. **More preconditions than the plan's read-back.** C14a's plan stops on bands, notes and the
   zone; this file also refuses on an `ip_inet` (never written, so one would mean an unknown
   writer) and on a lead with no stage or a tenant without exactly one initial stage (the
   arrival default stands on it). The zone count is narrower than the plan's
   `zones_without_row`: a tenant with no `site_settings` row whose CRM zone is Riyadh loses
   nothing (`app.studio_time_zone` answers Riyadh), so it does not block.
3. **The notes comparison is exact, not on the first 5,000 characters.** The plan compared
   `left(internal_notes, 5000)` and counted long fields apart; comparing the whole field
   refuses in both cases with one count (and says how many were long), so no tail is dropped
   unread.
4. **`app.acting_for` goes with the legacy branch.** The plan restated the note door without
   its bracket; with no setter left, the BEFORE phase stops reading the setting too, so a
   service-role edit made for no one is attributed to no one (the manual add still names its
   creator through `created_by`). The postconditions refuse any function naming it.
5. **`leads_safe` is not granted to the service role**, and the postconditions hold that:
   nothing reads the view as the service role, and it is in `FORBIDDEN_BACKUP_TABLES`.
6. **The §5 row "Leads — budget/timeline/internal_notes/ip (PII)" keeps its label** (owner
   default, C14a's owner question 2): it names a class of data the notes thread inherits, and a
   relabel moves four places together (CLAUDE.md §5, architecture §3.4, its `ROLE_CAPS` block,
   §9.3) under the matrix snapshot test. §3 and §8 say what the columns are now.
7. **`docs/retention.md` is unchanged**: it names none of the dropped fields (the leads row
   already speaks of the notes thread and the timeline).

  this branch with `main` merged in (migrations.md, Pushing to production). The read-back is

  then to `0113`, with `scripts/renumber-migration.mjs` after each `main` merge. U15
  (`0113_ga4.sql`) and E1 (`0113_page_editor.sql`) hold the same placeholder; whichever merges
  second renumbers at the train.
- **What the renumber script leaves alone** (review fix 10). It rewrites the file name
  everywhere, but a bare number only while no other migration on `main` holds it. If U15 or
  E1 merges first as `0113_*`, a renumber of this file moves the file name and leaves every
  bare `0113` of this PR where it is: the CLAUDE.md C14b bullet ("0113, the migration alone"),
  the README index line, this note, and the migration's own header comment. Fix those by hand
  from the script's "left alone" list in the same commit. The read-back holds its number in
  one place (its `this_file` CTE): change that literal too.
- **R11's set_config check** (review fix 2). R11's migration (now `0112_release_schedule.sql`
  on `main`) ends with a postcondition that the exposed functions calling `set_config` are
  exactly `apply_release` and `crm_delete_lead_note`; this file restates the door without
  `set_config`, so R11 applied after it would refuse. R11 merged first (#111), so it runs
  before this file everywhere: in CI's replay, in PGlite here, and on production, where the
  train pushes it first. No sibling carries its own copy any more (R12, E1 and U15 all hold
  `main`'s `0112_release_schedule.sql`, and none of their migrations repeats the check). The
  remaining rule: no slice is pushed to production between this file's apply and this PR's
  merge unless its branch has replayed this file, and no later migration may re-assert that
  list without leaving `crm_delete_lead_note` out.
- **Expected conflicts.** `supabase/tests/release_apply.test.sql` (R11, R12 and E1 edit it;
  this PR changes one assertion's text and its comment) and

## Review fixes (2026-10-27)

Eleven low findings from the security and correctness reviews and one skeptic verdict, each
checked against the code before it was acted on.

1. **A dropped column's bytes stay in the lead row** (security; confirmed). Fixed in the
   migration, section 6b (What was built). Proof, a PGlite probe with `pageinspect`
   (scratchpad `c14b-fix/probe.mjs`): a lead whose notes field was mirrored and a lead with a
   moved band, then this file, then the note door deleting the mirror note, then `VACUUM`.
   Without the fix two row versions still hold the words after the vacuum (the live ones);
   with it none do, the NOTICE names 2 rows, the two leads' `updated_at`, `updated_by` and
   `version` are unchanged, the mirror note survived the file, and all three triggers on
   `leads` are switched on. Guarded by `leadsContractSql.spec` (the shape) and the
   postcondition (the triggers). `docs/retention.md` stays unchanged: no residue is left to
   describe.
2. **R11's set_config postcondition** (security, upheld by the skeptic). No code change: R11
   merged first (#111, `0112`), so its check runs before this file everywhere. The Merging
   section now says so, and what still binds between this file's apply and its merge.
3. **The preconditions did not check the runner** (security; confirmed). Fixed: the first DO
   block refuses a runner that is neither superuser nor BYPASSRLS, before any lock or count.
   The probe runs the real file as a role that can alter the tables (a member of their
   owner) but does not bypass row security: it is refused by the new check. Without the fix
   the same runner happened to be refused anyway, by the initial-stage count (it read the
   tenant but none of its stages) with a message naming the wrong cause, and that refusal
   rested on `tenants` being readable to it; the check makes it explicit.
4. **The note routes' comments** (security; also correctness 5). Fixed (comment only):
   `notes.ts` and `[noteId].ts` say the mirror's notes stay and a legacy note is deleted like
   any other, no lead row written and none holding the words.
5. **The read-back** (correctness; confirmed: `legacy_notes_kept` had no value, so the compare
   always failed on it). Fixed: the after query drops it; the "before the push" query counts
   the legacy notes (and says to count them again after, expecting the same), the tenants
   without exactly one initial stage, whether the runner bypasses row security and the rows
   the file will rewrite; the after query adds `leads_triggers_all_enabled`; the migration's
   number is written once, in a `this_file` CTE. On the replay: 43 expectations, the one
   mismatch `server_version_num` (PGlite).
6. **CLAUDE.md's U9 bullet** (correctness; confirmed). Fixed: the zone list was "copied from
   `crm_settings.timezone`, which C14b dropped with its CHECK".
7. **`.claude/rules/database-and-authz.md`** (correctness; confirmed). Fixed: lead PII is
   `budget`/`timeline` and the notes thread; `internal_notes` and `ip_inet` were dropped.
8. **`deviations.md`'s §6.1 row** (correctness; confirmed). Fixed: "which C14b dropped".
9. **`leadFields.ts`' comment** (correctness 5, the part not covered by 4). Fixed: the list is
   kept so `stripSensitive` still keeps the names out and the tests know what C14b removed;
   deleting it stays a later lead slice's cleanup (departure 1).
10. **The renumber note overstated the script** (correctness; confirmed against
    `scripts/renumber-migration.mjs`). Fixed in Merging: which bare numbers to move by hand.
11. **The missing review brief** (correctness, a process note). Skipped: nothing in the code
    to change; the reviews' checks stand.
