## Plan (written before the build)

Releases stay off in production until R14. With releases off every save is live, as every
staged editor saves today; with releases on the singleton kernel stages it (R3b). There is no
second write path.

### Storage: `public.form_settings`, a staged singleton

One row per tenant (key `tenant_id`, created on first save, as `seo_defaults`), holding only
what differs from the code's built-in forms (the F5b rule: store differences):

- `inquiry jsonb` and `application jsonb`: the two forms' overrides (below), each `'{}'` by
  default;
- `consent_revision int`: computed by the database, never written by a client or a release:
  a BEFORE trigger adds one whenever the Join consent wording in `application` changes;
- `version`, `created_at`, `updated_at`, `created_by`, `updated_by` and the standard triggers.

A CHECK (`app.form_copy_ok`) holds each column to a JSON object of at most 16 KB in which no
string carries `<`, `>` or a C0/C1 control character (no HTML in copy, no line breaks). The
shape itself is the Worker's Zod contract (`packages/schemas/forms.ts`), re-parsed by every
reader (the public renderer and both public endpoints), so a row written around the Worker
costs a field its built-in value, never a page.

RLS ENABLE + FORCE, the tenant predicate first in every policy: everyone reads the tenant's
row (it is public copy, and anon renders it), a RESTRICTIVE non-staff block for signed-in
tokens that are not CMS staff (0097's pattern, Sales), Admin and Developer insert and update
by the JWT role (`app.role_general_settings(app.current_role())`) and RESTRICTIVE by the live
profile (`app.live_role()`), as 0102 does for `site_profile`; nobody deletes. Grants stated
(P-14): anon SELECT on the three public columns; authenticated SELECT, INSERT, UPDATE; the
service role SELECT, INSERT, UPDATE, DELETE; no TRUNCATE, REFERENCES, TRIGGER or MAINTAIN.

Registry contract (releases.md §1.3): every CMS role reads it (#1), its write policies say who
authors it (#2), it has `tenant_id`, `version` and the standard triggers (#3), and it gets the
guard (`form_settings__release_guard`), the snapshot (`app.tg_snapshot_singleton('form_settings')`)
and the capture (`app.tg_release_capture('form_settings', 'tenant_id', '')`) in the same
migration (#4); its TS entry (#5); one capability (#6). Registry row: `form_settings`, area
`settings`, authors `{admin,developer}`, no removal, columns `{inquiry,application}`, apply
order 110.

### What the config holds (closed sets, Zod in `packages/schemas/forms.ts`)

- **Inquiry form** (home, Contact, services pages, each a variant of one form):
  - a label per field, English and Arabic both required (name, email, company, phone, service,
    budget, deadline, message);
  - visible and required for the OPTIONAL fields only (company, phone, service, budget,
    deadline). Name, e-mail and message stay required (the pipeline needs them). "Visible" can
    only hide: a variant never gains a field it does not ask for;
  - the order of the eight fields (each variant renders its own in that order);
  - the button text;
  - the five budget bands' labels (the bands themselves are closed: a lead stores the key).
- **Join form:**
  - a label per control (name, email, phone, city, role, experience, workType, availability,
    skills, portfolio, linkedin, cv, message);
  - visible and required for the optional ones only (skills, linkedin, cv); everything the
    schema requires stays required;
  - the order inside each of the three groups (about you, the role, your work);
  - the button text;
  - the two consent lines (this application, future roles), versioned (below).
- **Captcha:** shown as a switch that is off and says "Not set up" (O-19). Not stored: switching
  it on needs a §7 CSP amendment and a public budget check, which is O-19's slice.
- **Honeypot:** always on, shown as a fact, not a switch (deviations register).

### Consent copy is versioned

The Join consent wording is stored with the application today as `consent_version`
(`RECRUITMENT_POLICY_VERSION`, a code date). With the wording editable, a form whose consent
lines are overridden posts `<code version>.r<consent_revision>`, and the stored version names
both the notice and the exact wording (the wording of revision N is in `content_versions`, the
row's history). `/api/apply` accepts a code version on the list, or one with `.rN` where
`1 <= N <=` the published row's revision. `job_applications.consent_version`'s CHECK widens to
admit the suffix (expand only: every stored value still passes).

The inquiry form's consent line ("I agree to be contacted about my inquiry") stays code-owned
in this slice: a lead stores the answer, not a version, and versioning it needs a column
through `crm_ingest_lead` (owner question below).

### Server validation follows the config

- `/api/contact`: the form posts which variant it is (`form`: compact, full, hello). After
  `LeadInputSchema` (the floor), the route reads the published config (service client, the
  tenant resolved server-side) and drops every value of a field the variant does not ask for
  or the config hides, then answers 422 naming each field the config requires and the
  submission left empty. A submission that names no variant is held to what every variant
  asks. A config that cannot be read means the floor only (the inquiry form fails open, EXC-004).
- `/api/apply`: after `ApplicationInputSchema` (the floor), the published config decides the
  optional controls: hidden ones are dropped, required ones refused when empty (422 with the
  field names; a required CV that is missing is `invalid` on `cv`), and the consent version is
  checked against the revision. A config that cannot be read means `unavailable` (the Join form
  fails closed, as its limiter does).

### Public pages stay Tier A

`ContactForm.astro` and `ApplicationForm.astro` render server-side from the published config
(`src/lib/data/forms.ts`, one read per request through `contentClient()`, so the preview
overlays a pending change), with no client-side hydration. With no row the HTML is
byte-identical to today's (`tests/render/sections.spec.ts` snapshot). The four form sections
(`contact`, `contactInquiry`, `hello`, `joinApply`) and the service pages read `forms:all`,
which the registry entry purges.

### The screen

`/admin/forms` becomes the editor for `settings.general` holders (Admin, Developer): the two
tabs as today (links), and per tab one island (`AdminForms`) on `useEntitySave` and
`EditorForm` (so release mode, the savebar, 409s and the history button work as every
staged editor): the fields card (label EN and AR, Shown, Required, Move up and down), the
budget card (inquiry), the button card, the consent card (Join, with the version it will
post), and the protection card (honeypot always on, captcha off "Not set up", the limits).

### Out of scope

Adding fields, removing fields, new budget bands, the honeypot switch, turning the captcha on
(O-19), editing placeholders and the inquiry consent wording (owner question).
