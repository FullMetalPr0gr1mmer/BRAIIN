# H12: a move never writes an archived row it may not, and a refused reorder writes nothing

- **Lane:** hotfix
- **Design:** none. U7 found the same flaw in the collection screen and fixed it on its own
  branch (PR #90, `renumberable`); this is the ResourceTable lists' half and the route's
- **PR:** number at review
- **Migrations:** none

## As built

**The defects.** The archive gates let only an Admin write a row that stays archived, a new
`sort_order` included: 0001's `services_update` and `blog_update` (a term of the permissive
policy's WITH CHECK, `app.is_admin() or status <> 'archived'`) and the RESTRICTIVE
`<table>_archive_admin` policies of 0007, 0018, 0021 and 0028 (the same WITH CHECK).
- Move up / Move down on a ResourceTable list swapped a row with its neighbour. When the
  neighbour was archived and the person could not archive (a Content Creator), its update was
  refused (42501), so a move next to an archived row always failed. Live lists with reorder on
  an archive-gated table: services, portfolio, disciplines, ai-questions, ai-styles
  (certifications, statistics, team and testimonials, and the FAQ, now draw on U7's collection screen, which applies the same rule with `renumberable`; the route's pre-check covers every list). Latent while no Content Creator account is
  in use.
- `reorderRoute` updated the rows one at a time with no transaction. A refusal half way left
  the earlier rows moved (a partial order, answered as a 500), and the screen's comment said
  that could not happen. An id that was not a row of the caller's tenant matched nothing and
  the route answered 200.

**Rule 1, the screen.** A move only writes rows the person may write
(`src/components/admin/screens/resources/reorder.ts`, `swapTarget`). For a person who may not
archive, a move steps over archived rows to the nearest row that is not archived, an archived
row does not move, and a button with nothing to swap with is disabled (the `disabled`
attribute, so its styling and accessible state are the ones it had). An Admin's move swaps
with the next row, archived or not, as before. Who may archive is `canArchive`, read by each
list page from the session (`can(role, 'content.archiveDelete')`, as `canAdvanced` is on the
section form) and passed to the island; omitted, it is false, the safe side. A row with no
`status` (clients, sectors) is never archived.

A refused move re-reads the list before it shows the error (`load()` clears the error as it
starts, so the message is set after it). The likeliest refusal is a stale list: an Admin
archived the neighbour after the list loaded, so the buttons still offered it. After the
re-read the statuses, numbers and buttons are the stored ones, and an archive refusal (403
naming `content.archiveDelete`) says so in words (`MOVE_ARCHIVED`) instead of "Your role does
not allow that".

**Rule 2, the route.** Before writing anything, `assertReorderable` (`src/lib/admin/resource.ts`)
reads the named rows in one tenant-scoped query (`id`, and `status` where the entity has one)
and refuses the whole request when:
- an id is not a row of the caller's tenant (another tenant's, or deleted): 422, "Nothing was
  moved: …", field `items`;
- a row is archived and the caller lacks `content.archiveDelete`: 403, the capability refusal
  an archive itself gets (`assertStatusTransition`).

Only then do the updates run. A refusal at an update is now mapped by `translateWriteError`, as
every other kernel write's is (a 403 for a gate), not a 500. The ids are lowercased by the
route's schema: a uuid is case-blind and Postgres answers in lowercase, so an id sent in
capitals is the row it names, for the pre-check, the updates and the staged path alike.

**Releases on: the same rule, at stage time and at publish time.** `apply_release` runs as the
publisher (0051), so the archive gates bind the publisher, and a release holding one change they
refuse is refused whole. `keepsArchived` (`src/lib/release/caps.ts`) names that change: an
update of a row archived live that sets no status of its own (a sort order, a title). It needs
`content.archiveDelete` on top of the area's capabilities, as an archive does (`requiredCaps`),
so it waits for an Admin. A restore (any other status) is an edit, as an immediate save of it
is. Who sees it:
- staging: `stagedReorder` and `stagedUpdate` refuse a Content Creator's change to such a row
  (403, `content.archiveDelete`) before the one writer call, so nothing is staged
  (`stageKeepsArchived`); a pending status is judged by `stageTransition`, as before (a pending
  restore lets them change the row);
- publishing and the dry run: `assertMayPublish` reads the live rows first (`readLive`, the same
  read the check over the selection then uses, not a second one), so a change staged before the
  row was archived, or staged by an Admin, refuses a Content Creator by name and says who it
  waits for, instead of an apply refused whole;
- the pending summary (`publishableByMe`, `requiredCaps`, `waitingFor`): one extra read of the
  listed edits' ids that are archived live, per table and 100 ids;
- settling a conflict (`resolveDraft`, which rewrites the change): judged again once live is read.

An id that is neither a live row nor a pending create is still skipped by `stagedReorder`, as R3
built it, and the rest of the reorder is staged: unlike the live path, which refuses the whole
request.

**Residuals.**
- Live path: the read and the writes are not one transaction. A row archived by someone else
  between them can still leave half a swap: the first row lands on the archived row's number,
  the archived row's write is refused (a mapped 403), and the two rows now share one number.
  No later move parts them, because a swap only exchanges two numbers already stored; visitors
  never see the archived row, and setting either row's Sort order does part them. A row deleted
  in the same window matches nothing: the other row moves, and no number is shared. A database
  function doing the whole reorder in one statement would close it; not built (no migration in
  a hotfix for a race this narrow).
- Releases on: a row archived between the publish's live read and the apply is refused by the
  gate inside the apply (0051's BR422 `refused`, a 422 naming the change), and nothing of the
  release is applied; publishing again shows the change as waiting for an Admin.
