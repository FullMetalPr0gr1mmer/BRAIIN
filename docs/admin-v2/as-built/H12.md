# H12: a move never writes an archived row it may not, and a refused reorder writes nothing

- **Lane:** hotfix
- **Design:** none. U7 found the same flaw in the collection screen and fixed it on its own
  branch (PR #90, `renumberable`); this is the ResourceTable lists' half and the route's
- **PR:** number at review
- **Migrations:** none

## As built

**The defects.** The RESTRICTIVE archive gates (0001, 0007, 0018, 0021, 0028: `with check
(app.is_admin() or status <> 'archived')`) let only an Admin write a row that stays archived,
a new `sort_order` included.
- Move up / Move down on a ResourceTable list swapped a row with its neighbour. When the
  neighbour was archived and the person could not archive (a Content Creator), its update was
  refused (42501), so a move next to an archived row always failed. Live lists with reorder on
  an archive-gated table: services, portfolio, disciplines, ai-questions, ai-styles,
  certifications, statistics, team, testimonials. Latent while no Content Creator account is
  in use.
- `reorderRoute` updated the rows one at a time with no transaction. A refusal half way left
  the earlier rows moved (a partial order, answered as a 500), and the screen's comment said
  that could not happen. An id that was not a row of the caller's tenant matched nothing and
  the route answered 200.

**Rule 1, the screen.** A move only writes rows the person may write
(`src/components/admin/screens/resources/reorder.ts`, `swapTarget`). For a person who may not
archive, a move steps over archived rows to the nearest row that is not archived, an archived
row does not move, and a button with nothing to swap with is disabled (the `disabled`
attribute, so its styling and accessible state are the ones it had). An Admin's move swaps
with the next row, archived or not, as before. Who may archive is `canArchive`, read by each
list page from the session (`can(role, 'content.archiveDelete')`, as `canAdvanced` is on the
section form) and passed to the island; omitted, it is false, the safe side. A row with no
`status` (clients, sectors) is never archived.

**Rule 2, the route.** Before writing anything, `assertReorderable` (`src/lib/admin/resource.ts`)
reads the named rows in one tenant-scoped query (`id`, and `status` where the entity has one)
and refuses the whole request when:
- an id is not a row of the caller's tenant (another tenant's, or deleted): 422, "Nothing was
  moved: …", field `items`;
- a row is archived and the caller lacks `content.archiveDelete`: 403, the capability refusal
  an archive itself gets (`assertStatusTransition`).

Only then do the updates run. A refusal at an update is now mapped by `translateWriteError`, as
every other kernel write's is (a 403 for a RESTRICTIVE gate), not a 500.

**Releases on.** `stagedReorder` writes drafts, not live rows, in one all-or-nothing writer call,
but the apply runs as the publisher (`apply_release`), whom the archive gates would refuse. So
a row that stays archived (archived live, no pending status of its own) is now an Admin's to
move there too: 403 before the writer call, nothing staged. A pending status is judged by
`stageTransition`, as before (a pending archive refuses a Content Creator; a pending restore
lets them move it). The live read gains `status`. An id that is neither a live row nor a
pending create is still skipped, as R3 built it: nothing is written for it.

**Residual.** The check and the writes are not one transaction. A row archived (or deleted) by
someone else between the read and the updates can still leave a partial order: the rows before
it moved, it did not (two rows may share a number). The response says so (403 for an archive),
and the next move, made on the re-read list, repairs it. A database function doing the whole
reorder in one statement would close it; not built (no migration in a hotfix for a race this
narrow).

**Tests.** `tests/lib/resourceReorder.spec.ts` (the helper both ways, and every reorder list
with a lifecycle passes `canArchive`); the matrix gains "naming an archived row (Admin only)"
for services, portfolio, disciplines, both Style-Finder lists and services with releases on;
`tests/authz/reorder.spec.ts` drives the route over the in-memory database: a Content Creator
naming an archived row writes nothing (the live row it also named included), an Admin's
passes, another tenant's id and another tenant's caller are 422 with nothing written, a deleted
row is 422, and the residual race is a mapped 403; `tests/lib/stagedKernel.spec.ts` the staged
half; `tests/admin/reorder.e2e.ts` the screen and the server as content_creator.
