- **Lane:** UI (Wave 1)
- **Design:** [ui.md](../ui.md) "AV-11: Media uploads pipeline (A5)" and "Media library
  (AV-11/12)", Pipeline; README "Uploads (U3)"; plan defaults O-1 (the migration creates the

- **PR:** the `feat/u3-uploads` branch (its number is given at review)
- **Migrations:** 0045 (`0045_media_uploads.sql`), reserved for U3 in this wave; expand only,

## As built

**The pipeline.** `POST /api/admin/media/upload` and `POST /api/admin/media/[id]/replace`
(`defineAdminRoute`, `media.write` at full level: Admin, Content Creator, Developer; SEO's
"meta only" is a 403). The file is the raw request body and its details travel in one header,
`x-media-meta` (`encodeMediaMeta`: the JSON as UTF-8 in base64url, so Arabic alt text survives
at about 2.7 characters a letter), so the CSRF check stays header-only (middleware) and the
Worker never parses a multipart body. Every valid set of details fits the header's 8,192
characters: no detail takes a control character or a lone surrogate, so the schema's maximum in
the costliest script comes to about 7.4 KB (`MEDIA_META_LIMITS`, tested); a longer header is
refused as "too long". In order, each step refusing before the next costs anything
(`src/lib/admin/mediaUpload.ts`):

1. the details, through Zod (`MediaUploadMetaSchema`: alt in both languages required, tags,
   folder, the file's own name as `displayName`; strict, so `storagePath` cannot be smuggled);
2. Content-Length required and at most 20 MB, from the header (411, 413), before a byte of the
   body is read;
3. "Not set up" (503) when the Worker has no `IMAGES` binding or Supabase is unconfigured;
4. the live recheck (the service role writes the object, so a demoted editor is refused now);
5. the head sniffed through a clone of the request (`src/lib/media/sniff.ts`): JPEG, PNG or
   WebP stills by their bytes, never by name or Content-Type; SVG and any markup, GIF,
   animated PNG/WebP (flag or `ANIM`/`ANMF`/`acTL`), HEIC, AVIF and the rest are 415; the
   decompression guard (12,000 px a side, 40 MP) and a malformed or cut header are 422;
6. a slot under `MEDIA_UPLOAD_LIMITS` (50 a day per person, 100 per tenant, the privileged-op
   ledger; a refused file costs none);
7. the body streamed into the binding: scale-down to a 2,560 px long edge, one WebP frame,
   quality 85; the output is read back (`src/lib/media/webp.ts`): its own size, one frame, any
   `EXIF`/`XMP ` chunk stripped (Cloudflare says WebP output carries none; this makes it true
   by construction), no larger than the bucket's 10 MB;
8. the object, as the service role, under `<tenant>/<random uuid>_<w>x<h>.webp`, with a
   one-hour `cacheControl` (a year would keep a deleted file in Supabase's CDN for a year: on
   the Free plan a delete does not clear it);
9. the row, as the CALLER (so `media_write` RLS is the second layer); if it is refused, the
   object is deleted again;
10. the audit row (`media_asset.upload` / `.replace`): sizes and formats, never the file name.

Replace checks the version before the file is read and again in the UPDATE (409), writes a new
key, keeps the row's id, alt and tags, and leaves the old object for the daily sweep, unless the
details say `removePrevious: true`: then the old object is deleted at once (for an image that
must come down now), and the audit row names it (`previousFile`, `previousKey`).
`DELETE /api/admin/media/[id]` (Admin, refused while used) now removes an uploaded image's
object after its row, only under the caller's tenant prefix and only if no row still names it
(`removeObjectIfUnnamed`, the sweep's own question, asked as the service role), and says in its
audit row and response whether that worked or why the file was kept (`fileKept`). `GET /api/admin/media/[id]/download` streams the stored master
(`attachment` named after the upload with `.webp`, `nosniff`, `no-store`, CSP `sandbox`), and
`GET /api/admin/media/stats` returns "storage used" against a 1 GB constant (the Supabase Free
plan, shared with the CV bucket). The generic media routes can neither create a `storage` row
nor change an uploaded file's columns (`provider`, `storage_path`, size, MIME type…): the form
may restate them unchanged.

**The database (0045).** The `storage` provider with a shape CHECK: an image, WebP, the key's
tenant segment equal to the row's tenant and its `<w>x<h>` equal to the row's width and height,
at most 2,560 px, a size the bucket can hold, no `provider_ref`/`stream_uid`, wrapped in
`coalesce(…, false)` so a NULL fails rather than passes. One row per object: a unique index on
`storage_path` for `storage` rows (`media_assets_storage_object_key`), because a staff token
holds INSERT and UPDATE on the table and could otherwise make a second row name a live
poster's file. `display_name` (staff only: the anon column grant is unchanged, and a
postcondition says so); its CHECK names the characters it refuses (C0 and C1 controls, DEL,
U+2028/U+2029, both slashes) instead of a locale's `[[:cntrl:]]`, and `MediaDisplayNameSchema`
refuses the same set (a vitest reads the class from the migration). `set local lock_timeout =
'5s'`, as 0038: a busy table fails the push instead of queueing the site behind it.
`media_assets_public_read` is 0028's policy with `storage` added. `public.media_storage_stats(p_tenant)` (SECURITY INVOKER,
`authenticated` only, zero for any tenant but the token's) and
`public.media_orphan_objects(p_older_than_minutes, p_limit)` (service role only; it refuses a
caller that does not bypass RLS, because under RLS every object would look orphaned). The
bucket: public, 10 MB, `image/webp` only, plus a RESTRICTIVE belt on `storage.objects` for anon
and authenticated, as 0029 did. No new table, sequence or capability: §5 "Media — upload / edit
metadata" already decides who uploads. pgTAP `media_uploads.test.sql` (56) covers the bucket;
the belt, asserted wherever this role could add it and proven with a permissive policy that
opens every bucket to anon and authenticated (media stays shut, the other bucket opens); the
shape and the display-name set; one row per file (a staff token can neither add a second row
naming a file nor repoint one); admin/content_creator/developer writing, SEO refused and
editing alt only through `update_media_meta()`, other_tenant reading and writing nothing,
Admin-only hard delete, anon reading only what published content shows and never
`display_name`, the meter, and the sweep (its probe no longer turns into skips).

**Delivery.** `imageRef()` resolves a public `storage` row to image metadata whose `src` is
the object's public URL (`uploadedImage`), so `<Picture>` and every `getImage()` call site build
`/_image` URLs exactly as for a bundled still: same origin, so img-src gains nothing and §7 is
unchanged; a call site passing only a width gets the height from the aspect. `MediaImage`
gives an upload a WebP fallback (`uploadFallbackFormat`), not Astro's full-size PNG. The H3
guard admits a bucket key at the size its name states (`uploadedImageSize`), in the formats the
markup asks of an upload (avif, webp, and the share images' jpg), at one height per width (an
upload only reaches MediaImage and width-only `getImage()`, so Astro's height is within half a
pixel of the exact aspect; stills keep their two pixels), and no other remote.
`image.remotePatterns` comes from `scripts/media-remote-patterns.mjs`, an integration that pins
PUBLIC_SUPABASE_URL's protocol, host, port and the bucket path; `astro build` fails without a
usable URL, `dev`/`check`/`sync` warn.

**The `/_image` endpoint** (`src/lib/http/imageEndpoint.ts`, the H3 row's "custom endpoint wraps
the adapter", registered as `image.endpoint` by `scripts/image-endpoint.mjs` after the adapter
sets its own). It runs the guard on the route itself; a bundled still goes to the adapter's
endpoint unchanged; an upload is fetched from the bucket (`redirect: 'manual'`) and handed to
the Images binding only when the answer is a 200 `image/webp` (a missing key, a redirect or any
other type is a 404 with no binding call), and its derivative is cached for an hour (the
object's own lifetime), not the adapter's immutable year. The middleware keys the guard and the
maintenance exemption on the route Astro matched (`isImageEndpoint`: `context.routePattern`, with
the decoded, normalised path as the belt), because Astro routes `/_image/`, `/%5Fimage` and
`/_imag%65/` to the same endpoint; the guard was keyed on the spelling `/_image`. The endpoint is
exempt from maintenance: it is not a page, and the admin's thumbnails of uploads go through it.

**The sweep.** A fourth daily job, `media-orphans` (`src/lib/media/orphans.ts`), after the Join
retention and before the lead indexing: up to 100 objects older than an hour that no row names,
removed through the Storage API; budget 4 subrequests, the registry's sum 39 of 50.

**Measured.** Subrequests per upload: about 10 (session check 2, live recheck 1, the ledger 3,
the binding 1, the object 1, the row 1, the audit row 1); a replace about 12 (14 with
`removePrevious`: the lookup and the removal); a delete one more than before (the lookup); an
upload's derivative 2 on a cache miss (the object, the binding), 0 on a hit. Worker JavaScript
(Node, warm, the binding's work stubbed): the sniff 0.7 µs, the master's read-back 0.8 µs, the
whole route about 1.2 ms for a 0.15 MB photo; an EXIF strip, when it happens, 0.4 ms. A 17 MB
body costs 8 to 21 ms in Node, which moves it through JavaScript streams; in workerd the body,
its tee and the binding's input are native streams, so that cost should not be the Worker's.
Not measured in workerd here (no `wrangler dev` on this machine): the CI e2e exercises the real
path and the first production upload confirms the CPU (O-16).

**Tests.** `tests/lib/mediaSniff.spec.ts` (fixtures: truncated, polyglot, renamed SVG, animated
WebP/PNG, HEIC/AVIF, oversized, malformed), `mediaUploadApi.spec.ts` (order, refusals,
compensation, EXIF, the object's cache lifetime, replace and `removePrevious`, delete and a file
another row names, download, stats), `mediaResource.spec.ts` (the header at the schema's
maximum, the display-name set against the migration, the constraint fields),
`mediaDelivery.spec.ts` (guard, resolver, thumbnail, every transform `<Picture>` emits for an
upload, remote patterns), `imageEndpoint.spec.ts`, `middlewareImage.spec.ts` (each spelling of
the route, maintenance), `dailyJobs.spec.ts`, the endpoint cases in `tests/authz/cases/media.ts`,
pgTAP above, `tests/e2e/image-guard.e2e.ts` (the aliases on a public still) and
`tests/admin/uploads.e2e.ts` (through wrangler dev's local Images binding and CI's local
Storage: the aliases, a missing key's 404 and the hour-long Cache-Control too).

## Departures from the design

- **AVIF and HEIC are refused as input.** The design accepts AVIF. Cloudflare's limits page
  marks AVIF input "Available on an Enterprise plan", so an AVIF could never be processed here;
  HEIC is refused as the design says. Recorded in the deviations register.
- **20 MB, not 25 MB (README) or 10 MB (ui.md).** The Images binding's `.input()` limit
  (B7 item 2), counted in decimal megabytes. The bucket stays at 10 MB: it holds only the
  re-encoded master.
- **One WebP master, not "WebP/AVIF".** AVIF output stops at 1,200 px; `/_image` makes AVIF
  derivatives from the WebP master (B7 item 2).
- **The object key carries the size:** `<tenant>/<uuid>_<w>x<h>.webp`, not `<tenant>/<uuid>.<ext>`,
  so the public `/_image` guard bounds a transform without a database read; the CHECK holds the
  name equal to the row.
- **The body is the raw file, details in a header**, not a multipart form: it streams to the
  binding and keeps the CSRF check header-only. U4's dialog sends it this way (XHR progress
  still works on a raw body).
- **`dimensions.ts` is part of `sniff.ts`**: one pass over the head finds the type and the size.
- **`thumb_url` is written by hand**, not through `getImage()`: the same four parameters,
  so the media resource (an API module) needs no `astro:assets`; a test holds it to the guard.
- **The upload cap is 50 a day per person and 100 per tenant**, against the Images Free plan's
  5,000 unique transformations a month; the design named the cap, not the numbers.
- **The e2e keeps its uploaded row:** the per-role sweep opens the newest media row's edit
  screen, so a delete in the e2e could race it; the delete path is covered by vitest.
- **The ledger row:** `migrations.md` reserved 0040 for U3; this wave assigned 0045, and only
  U3's own row was corrected.
- **The details header is base64url JSON**, not percent-encoded: percent-encoding cost an Arabic
  letter 6 characters and valid details (about 11 KB at the schema's limits) were refused by
  the 8 KB ceiling (review).
- **`/_image` is our endpoint around the adapter's** (H3's design, built here): the adapter
  hands any upstream body to the binding and caches every derivative for an immutable year.
- **Erasure is not instant.** A deleted or replaced upload stays reachable for up to about two
  hours: Supabase's CDN copy and the `/_image` derivative live an hour each, the Free plan
  cannot purge the first, and purging the second needs the zone's purge token (O-3). Pages
  cached before the change keep pointing at the old derivative until purged. Recorded in the
  deviations register.

## Review fixes (2026-10-12)

u3-security-1 (the guard keyed on the spelling `/_image`), u3-security-2 (a deleted file stayed
on the web for a year), u3-security-4 and u3-correctness-3 (a second row could name a live
file, and deleting it removed the file), u3-security-8 and u3-correctness-9 (the belt's pgTAP
could not fail; the sweep's could skip), u3-correctness-1 (no lock timeout),
u3-correctness-2 (a well-formed key cost a binding call; png and jpeg were admissible for an
upload), u3-correctness-6 (valid details were refused as unreadable), u3-correctness-7 (a PNG
fallback), u3-correctness-8 (maintenance 503'd the admin's thumbnails), u3-correctness-11 (the
display-name CHECK and the schema disagreed), u3-correctness-12 (a comment named the wrong
test). Each is fixed with a test that fails without it.

Left open, by design or for the owner:

- **A random, well-formed key** still costs one Worker request and one Supabase fetch (a 404,
  never a transformation). Refusing keys the Worker never issued without that fetch needs a
  signed key (an HMAC in the name); not built.
- **The key's tenant segment is not pinned** at `/_image` (single tenant at launch; the CHECK
  pins it in the database).
- **The admissible set per upload** is the listed widths below its own plus its own width, in
  three formats: at most 57 unique transformations, where the markup emits about 10. Runbook
  §6i "Costs to watch" gives the budget.
- **Replace by a Developer** changes what a published page shows (u3-correctness-5, an owner
  decision); the orphan grace still runs from the object's creation (u3-correctness-4); a
  hand-made `media` bucket would be widened by the upsert (u3-correctness-10). Not in this
  round's list.
