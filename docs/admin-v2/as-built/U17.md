## As built

**The rule, once, in both layers.** A person must be at `aal2` when they have a VERIFIED factor
(any type: only TOTP is offered, and a phone factor, if ever switched on, must not weaken the
rule) or when their tenant's `admin_security_settings.require_mfa` is on. The database's copy is
`app.mfa_required(p_user, p_tenant)` (STABLE SECURITY DEFINER, empty search path, EXECUTE for
`supabase_auth_admin` only: it reads `auth.mfa_factors` and a FORCE-RLS table); the Worker's is
`secondStepNeeded` in `src/lib/auth/twoStep.ts`. The two case tables
(`supabase/tests/two_step.test.sql` on the hook, `tests/lib/twoStep.spec.ts` on the Worker)
name each other.

**The database layer: the access-token hook (0072 §3).** 0010's body, contract and kind kept
(SECURITY INVOKER, STABLE, reads `profiles` through `profiles_auth_admin_read`, strips role and
tenant for no profile or a switched-off one), plus one rule: role and tenant are stamped only
when the token's `aal` is `aal2` or `app.mfa_required` is false. Anything but `aal2`, missing
included, counts as below it, so a malformed event can only withhold the role. Every other
claim, and every other key of `app_metadata`, comes back untouched (pgTAP 15). No exception
handler (0011's warning: a hook that raises fails every sign-in; one that swallowed would fail
open or lock everyone out); the helper is two indexed lookups instead, and the first
postcondition block exercises the owner's SELECT and DELETE on `auth.mfa_factors` and calls the
rule before the push can commit. The search path moved from `public, pg_temp` to `''` with
every name qualified (P-14). Grants: EXECUTE for `supabase_auth_admin`, as 0010; P-14 also
revokes it from `service_role`, which 0010 left with Supabase's default (GoTrue calls the hook
as `supabase_auth_admin`; no code, test or job calls it as the service role).

**The Worker layer: `resolveAuthContext`'s fourth fact** (`src/lib/auth/context.ts`). Below
the required level a request gets no `AuthContext`, only `pending: { userId, tenantId, email,
role, mode, factorId }` with `mode` `challenge` (a verified factor) or `enrol` (the tenant
requires it and there is none: sent to set it up, never refused silently). Nothing changes for
anyone who needs no second step: every pre-U17 case of `tests/lib/authContext.spec.ts` is
unchanged. A token without a role claim (what the hook mints below the level) has its profile
read only when it is not `aal2`; a profile that cannot stand (switched off, locked by the fifth
wrong code, too old a sign-in) revokes it, as it does a full session; anything else stays the
anonymous answer it always was. A token that still carries a role (minted before the factor or
the switch) is held at the second step all the same, after the role and tenant comparison and
the session length. The tenant setting rides the profile read it already made
(`PROFILE_WITH_SETTING` embeds `require_mfa`); the plain-profile fallback reads "not required"
(logged once, as the session length's), while the hook still holds the database layer. A full
session's context carries `twoStep: { on, required, factorId }`.

**The middleware gate** (`src/middleware.ts`). A pending session reaches `/admin/2fa` and
`/api/admin/auth/logout` (both the path and the matched route must be one of the two) and the
pre-auth screens; anything else answers as if there were no session but points at the second
step: a page 302s to `/admin/2fa?next=<path>`, the API answers 401 `two-step-required`. It
passes the CSRF check, the body limit and `no-store` like any session; a stale or oversized
form on `/admin/2fa` goes back to the page (`expiredForm.ts`). The sign-in endpoint hands a
pending session to `/admin/2fa` without `registerSuccess` (it would reset the failure count
between the password and the code) and without an `auth.login` row; `/admin/login` sends a
pending visitor on to the second step.

**`/admin/2fa`** (`src/pages/admin/2fa.astro`, `src/components/admin/screens/twoStep/`,
`src/lib/auth/twoStepFlow.ts`, `public/styles/admin/two-step.css`). Zero JavaScript; every
action a form posting to the page (the intents `verify`, `start`, `confirm`, `off`, `signout`,
each allowed only for its kind of caller, 403 otherwise). Two frames: the sign-in shell for a
pending session (the code; a forced setup), the admin shell for a full one (set up when off,
manage when on). The setup step is rendered on the POST, never redirected, and the key is never
stored: a wrong code re-renders the same step from hidden fields (GoTrue verifies against its
own secret, so a tampered key only misleads whoever tampered). Wrong codes at the sign-in step
and for turning it off count toward the 5-in-15-minutes lockout; a wrong code while confirming
your own new setup does not (D7); the fifth signs the session out to the sign-in page's
"locked" copy; a locked account is refused before GoTrue is asked. `registerSuccess` and the
`auth.login` row (`detail.second_step: 'totp'`) come after the code. `auth.two_step_on` and
`auth.two_step_off` are audited as the person. GoTrue's MFA errors are read through one table
(`outcomeOf`): only `mfa_verification_failed` (or a 400/422 with no code) is the person's
wrong code; a rate limit, an outage or anything else counts nothing and is logged with its
status and code only, never the code or the key. The issuer label is the brand from
`site_profile` (P-12), the account label the e-mail.

**Turning it on for everyone.** `admin_security_settings.require_mfa` (NOT NULL DEFAULT false,
false for every tenant after 0072), saved by the existing versioned
`PUT /api/admin/users/security` with the card's other two settings. Turning it ON is refused
(422, `field: requireMfa`, "Turn on 2FA for your own account first.") unless the saving Admin's
own session uses 2FA (`auth.twoStep.on`, which a full session has only at `aal2`): D5. Omitted
from the body (a card loaded before U17), it keeps the stored value. The card's switch asks
first, with how many active members have not set it up, counted across the whole directory.

**Reset 2FA.** `POST /api/admin/users/[id]/two-step-reset` (`users.manage`, the live recheck,
never yourself) calls `public.reset_two_step(p_tenant, p_user)` (SECURITY DEFINER, empty search
path, EXECUTE for `authenticated` only), which checks it all again as the database sees it (a
live Admin of the token's tenant, 42501 otherwise, stale tokens included; the target in that
tenant, not the caller, not the account owner, holding a factor), then deletes the factors
(challenges cascade), every session and refresh token, and writes `user.two_step_reset`
(`detail.factors`) in the same transaction, so a reset whose audit row cannot be chained does
not happen. The route writes no row of its own and maps `owner_protected` to 422
`owner-protected`, `self` to 422, `nothing_to_reset` to 409, `not_found` to 404.

**The users screen and the account.** `public.staff_accounts` gains `two_step` and `is_active`
(drop and create: the result type changed; same checks, cap and grants). The table's "2FA"
column (On, Off, or Unknown when the directory cannot be read) and the drawer's subline read
it; "Reset 2FA" shows for a colleague with it on who is not the owner, behind a confirm. The
account drawer and page gain "Two factor authentication" (On, via authenticator app / Off,
with Set up or Manage to `/admin/2fa`).

**Site health.** `security.two_step` in the Security group, after G2's readings (the
prototype's "Admin and data" card follows its "Website" card): "N team members without two
factor sign in" / "Everyone uses two factor sign in", `users.manage` only, linking to Users &
roles, Unknown when the directory cannot be read. `loadHealthReport` reads the directory only
for a `users.manage` role: one more read for Admin (the dashboard's measured budget moves
26 to 27 page reads, 38 in all), none for Developer, who sees "not checked for your role".

**Help.** H11's catalog is not on `main` yet, so this slice does not restate
`app.help_article_set()` (the old rule 1 is retired). Its two guides are
`docs/admin-v2/guides/your-account.json` (a 2FA section; `/admin/2fa` among its screens) and
`docs/admin-v2/guides/roles-and-access.json` (Require 2FA for everyone; Resetting someone's
2FA), each the nine keys a put takes, places and titles unchanged (20 and 30). 0072 §6 holds the
marked TODO for the two `select app.put_help_guide($guide$ … $guide$::jsonb, N);` lines (N the
guide's revision on `main` at merge, 1 unless a sibling put it first). Until then
`tests/fixtures/pendingGuides.ts` lays the files over the migrations' set and
`tests/lib/helpCentre.spec.ts` holds them to every rule of the set (schema, screens, Arabic
block for block, copy rules, `PAGE_GUIDES`) and their claims to the code; a test refuses a file
no migration's `TODO(U…, H11)` names. The wiring deletes the files, after which the fixture
reads nothing.

**Corrections rule 4.** `PAGE_GUIDES` (`your-account` gains `/admin/2fa`), the sweep's
`EXTRA_LINKS` (`/admin/2fa`, `caps: []`: every role is swept on its full-session frame), the
guide's `screens`. The nav registry gains no line: like `/admin/account`, the page is reached
from the account row, not the menu, and the sweep expects the role's own sidebar there, which
the admin frame renders.

**`supabase/config.toml`** pins `[auth.mfa] max_enrolled_factors = 10` and `[auth.mfa.totp]`
enrol and verify on (`tests/lib/twoStepConfig.spec.ts`).

## Departures from the brief, and why

- **No QR code (D2's fallback).** The setup step shows the key, grouped in fours, and an
  `otpauth://` link that opens the authenticator on the phone the page is open on. Drawing a QR
  needs an encoder this repository does not carry (`uqr` or `qrcode-generator`), and a builder
  may not add a dependency (the lockfile is the owner's). GoTrue's own `qr_code` is a `data:`
  image the CSP refuses. Adding it later is `src/lib/auth/qr.ts` and one block in the setup
  step (owner question). The guide says "type the key the page shows", and its test refuses any
  mention of a QR code until there is one.
- **`/admin/2fa` has two frames, and is in the sweep.** The brief kept it in the sign-in shell
  and out of `EXTRA_LINKS`; the corrections' rule 4 puts it in `EXTRA_LINKS` with `caps: []`,
  and the sweep fails a page without the role's sidebar. So a full session (set up, manage)
  sees it in the admin shell and a pending one in the sign-in shell. Its sheet is its own,
  `two-step.css` (one line in `src/lib/admin/stylesheets.ts`), styling both frames with no
  login.css class (`tests/lib/adminStyles.spec.ts`: a class only one sheet styles renders only
  where that sheet is linked).
- **The guides are files, not a restatement** (the task's H11 rule, above).
- **`staff_accounts` also gains `is_active`**, so the confirm's count and the health check count
  active members across the whole directory (up to 200), not the list's page of 25.
- **`requireMfa` is optional in `SecuritySettingsSchema`** (still strict): a card open across
  the deploy saves without it and the stored value stays.
- **Copy.** Require 2FA's hint is "People without it are asked to set it up at their next
  click." (D6: the prototype's "at next sign-in" is untrue here). The reset confirm says they
  set 2FA up again "the next time they sign in if your team requires it, or from their
  account", since without Require a reset person simply signs in with the password. The
  account row's icon is `lock` (`shield` is "What you can do"'s).
- **`nothing_to_reset` answers 409 `in-use`** with the sentence as its detail (the kernel's
  409 with a detail; the brief named only the status).
- **The e2e account is a Developer**, not an Admin fixture: it proves the database layer by
  reading the activity log (Admin and Developer only) straight from PostgREST, refused at `aal1`
  and answered at `aal2`, and a Developer touches less of the shared run than an extra Admin.
- **`tests/a11y/axe.e2e.ts` and `tests/e2e/csp.e2e.ts` do not list `/admin/2fa`.** Without a
  session it only redirects to the sign-in page those lists already hold; every step with a
  session is checked by `tests/admin/twoStep.e2e.ts` (axe, overflow, CSP, console, no `style=`
  at 320, 390 and 1280) and the sweep. The forced setup (`enrol`) is checked by the render spec
  only (switching Require on in CI would hold every shared session at the second step).

## What the local stack showed

No container runtime on the build machine, so the brief's GoTrue assumptions are checked in CI's
e2e, not here: that the hook's `claims` carry `aal` (step 2 asserts an `aal1` token with no
role, and an `aal2` one with it), that `enroll` works at `aal1` with no verified factor (step
1), and that a reset ends the person's sessions (step 3). Read from auth-js 2.110.7's
`ErrorCode` union: `mfa_verification_failed`, `mfa_factor_not_found`,
`mfa_totp_enroll_not_enabled`/`mfa_totp_verify_not_enabled` ("Not set up"),
`over_request_rate_limit`; `mfa_challenge_expired` and `mfa_ip_address_mismatch` fall to
"unavailable" (logged with the code). Not verified, and not relied on by any copy: whether a
verified enrolment signs out the person's other `aal1` sessions (the Worker holds them at the
second step either way), and GoTrue's per-IP MFA verify limit (no `config.toml` key). To check
on staging after the push (owner item O-25): a sign-in with a code end to end, because
`challengeAndVerify` is two requests from the Worker and GoTrue refuses a verify from another
IP than its challenge (`mfa_ip_address_mismatch`); if a Worker's two subrequests ever leave
from different addresses, the page says "not available right now" and the system log names the
code.

## Deploy order and rollback

Apply 0072 first (owner-gated), then deploy. Between the two, the old Worker meets the new
hook: nobody has a factor (setting one up needs the new Worker) and `require_mfa` is false for
every tenant, so every token is stamped exactly as before (pgTAP 1 to 4 and 12). The old
Worker's `StaffAccountRowSchema` is a plain `z.object` (not strict), so it drops the directory's
two new keys; its session check selects `session_max_days` only. Never switch Require on before
the new Worker is live. Rollback (launch runbook §10): the Worker with `wrangler rollback` (it
reads a role-less `aal1` token as anonymous, so it never grants more than the hook stamped);
the hook alone by re-running 0010's body; the escape hatch
`update public.admin_security_settings set require_mfa = false`; one person's factor by
deleting it from `auth.mfa_factors`. The owner's lost phone: runbook §3a.
