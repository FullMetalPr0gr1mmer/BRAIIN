## What was built

### Job applications (U8a)

- `/admin/applications` on the kit (`screens/applications/ApplicationsPanel.tsx`): a DataTable
  (Name and Role as `dir="auto"` text, Experience in words, CV Yes/No, Received as a relative
  time with the full Riyadh time as its title, Status as a badge), status chips (All and the
  six), the pager, an empty state, and a row action "Open <name>'s application". The list's 403
  shows in the table's error line, which `refusals.e2e.ts` reads. The four API routes are
  unchanged (`applicationsAdmin.spec` passes as it was).
- `ApplicationDrawer.tsx`: the kit's wide Drawer, titled with the applicant's name, with
  cards: Message, Details (`detailRows`: labels from the option tables, never a contact field;
  crafts as badges; Portfolio and LinkedIn only through `safeLink`, opened with
  `noopener noreferrer`), Contact details (Reveal, then `mailto:` and `tel:` links with
  "Hide"), CV (the plain download link, its size, "Not virus-scanned", "Recorded against your
  account."), Status (a select, one PATCH per change; Spam asks first with
  `SPAM_RETENTION_DAYS`), Internal notes (5,000 characters with a count, "Save notes"), Consent
  and retention. Footer: "Erase application" (asks, then DELETE and "Application erased.")
  and "Close", which asks "Leave without saving the note?" when the note has unsaved text.
  Errors inline, successes as toasts, no `window.confirm`, no `style=`.
- **The double reveal is fixed.** A reveal is the one `?pii=1` GET (live recheck,
  `application.view_pii` written before the decrypt); its values stay in the drawer's memory.
  A status or notes PATCH answers with the row's detail columns and no contact details;
  `mergeAfterPatch` (`src/lib/admin/applicationView.ts`) takes them and keeps what was
  revealed. Before U8a every save re-opened the application with `?pii=1`: a second decrypt
  and a second audit row per save. The e2e counts the audit rows.
- `?status=` and `?open=<uuid>` are read on the server (`parseInitial`: a known status, a
  uuid, anything else ignored) and kept in step in the address (replaceState); the bell's
  "New application" links to `?open=<id>` (`notifications/applications.ts`). Opening writes
  the route's existing no-PII `application.view` row, as a click does.
- The closed-form note ("The Join form is closed, so no new applications arrive. An Admin can
  open it in General settings.") reads the identity AdminLayout already reads (memoised per
  request, no extra read), for `applications.manage` holders only.
- `public/styles/admin/applications.css` (the drawer's stack, the crafts row, wrapping links,
  the footer; tokens only), listed in `stylesheets.ts`.

### Style-Finder (U8a)

- A question's options are a repeater (`ui/aiQuestions.ts`): a short key (≤ 60) and its words
  in both languages, at most 20, as `AiQuestionWriteSchema` takes; "How visitors answer" is
  the input type. Styles keep `traits` as "Traits (advanced)" JSON with a help line saying its
  shape and that nothing reads it (D4); the image is "Image link" (D5: a URL column).
- Results & logic (`ui/aiConfig.ts`): plain labels, "Not read yet" hints, the two limits'
  hints naming today's fixed limits, `model` ≤ 80 and the instructions ≤ 8,000 as the schema
  caps them. `tests/lib/styleFinderUi.spec.ts` holds every number to `AI_IP_LIMIT`,
  `AI_SESSION_LIMIT` and `AiConfigSchema`.
- A server Note on the three screens (`src/lib/admin/styleFinderCopy.ts`), shown to the roles
  that edit each: the quiz is not on the site yet; on Results & logic, nothing is read, every
  request is turned away, nothing is spent, and the key is a server secret.
- **Pillar 1, for whoever wires the quiz:** the schema lets an Admin store up to 1,000 USD a
  day and 1,000 requests an hour. Nothing reads them today. The quiz must take the LOWER of a
  stored value and the code's ceilings (`AI_DAILY_USD_CAP`, `AI_IP_LIMIT`,
  `AI_SESSION_LIMIT`), so an edit here can only tighten them; the Durable Object cap stays the
  hard ceiling. Said in `ui/aiConfig.ts` and CLAUDE.md's U8a bullet.

### Tabbed and read-only editors (U8b)

- **The kit's `TabStrip`** (`kit/Tabs.tsx`): the tab list alone, controlled (`value`,
  `onChange`), ids `<idBase>-tab-<id>` controlling `<idBase>-panel-<id>`, `?tab=` kept in step
  (`param`, null for none), the roving keyboard as before, and a tab `cue` ("has errors"): a
  dot it shows and words its accessible name ends with, after the visible label (WCAG 2.5.3).
  `Tabs` is TabStrip plus its panels, its markup unchanged (the existing rows pass as they
  were).
- **`EditorForm` tabs** (`fields/EditorForm.tsx`): field tabs are tab panels inside the one
  form (all mounted, the others hidden, so a save sends every field); a panel tab
  (`panel: 'seo'`) is a tab panel after the form, never inside it (the SEO editor is its own
  form), and the form is hidden while it is current. An ErrorSummary link or "Next gap" that
  names a field in a hidden tab switches to it in the same turn (the reveal listener), before
  `revealAndFocus`'s frame focuses the field; a tab holding an error says so. `?tab=` follows
  the tab and is read on the server for the first paint. Without `tabs` (and without
  `readOnly` and `publicHref`) the output is byte for byte what it was (`editorForm.spec`'s
  rows pass unchanged, and a test compares `readOnly: false` with no prop).
- **Read-only**: the fields inside `<fieldset class="editor-ro" disabled>`, the rich text
  created not editable with no toolbar (`FieldsReadOnly` context in FormField, a `readOnly`
  prop on RichText, which still imports nothing new: it is the lazy `admin-rich` chunk), no
  Save, no save status, Ctrl/⌘+S and a submit do nothing, and a note. UX only: the server
  refuses as before.
- **Creative Knowledge** (`ui/blog.ts`): titled "Creative Knowledge"; tabs Content | SEO |
  Publishing; Author is a picker of PUBLISHED team members, Category a picker of categories;
  "Share image (https link)" with its help (D5); "Open on site" for a published post. The pages
  decide on the server from ROLE_CAPS (`src/lib/admin/editorAccess.ts`): `canWriteResource`
  (`blog.write`: "New post" and an editable form, else read-only), `seoAccess` (`seo.entityMeta`:
  full, view or none), `firstTab` (the address's `?tab=`, else SEO for a role that may only
  change SEO), and the SEO tab's setup (`loadSeoPanelSetup`, the caller's own reads; a failed
  read is logged and the tab says so). SEO opens a post on its SEO tab with the content
  read-only; Content Creator sees the SEO tab read-only (`SeoPanel readOnly`).
- **Two server fixes** (`resources/blog.ts`):
  - D11: a published (or scheduled) post's author must be a PUBLISHED team member: one read
    of `team_members.status` under the caller's RLS, tenant-scoped; anything else (a draft, an
    archived or an unseen member) is a 422 on `authorId`. The public page embeds its author
    through anon's published-only RLS, so a draft author rendered a post with no author and an
    Article with none (Pillar 3). R6 (#94) landed while this was built, so the rule reads
    through the rule context's `db` when one is given (a publish and its dry run: the state
    the release leaves behind, so a member published in the same release counts) and live
    otherwise (`liveDb`), as R6's poster rule does; the brief's "R6 must route it through the
    overlay" is done here rather than left as a note.
  - D12: `body: null` (an editor nobody touched: a post holding only `body_html`, as the
    seed's do, loads an empty editor and a full save sends null) is dropped from the save, so
    `body_html` is no longer blanked. An emptied editor sends a document, which still clears.
- `ResourceTable`: `canCreate` (no "New" and no "add the first one" without it), and a column
  that is a `select` of the form shows the option's words (the Style-Finder's Input column
  reads "Single choice"); additive.

## The tab API (frozen here for U5 and U6)

```ts
// src/lib/admin/ui/types.ts
interface EditorTabDef { id: string; label: string; icon?: IconName; fields?: readonly string[]; panel?: 'seo' }
ResourceUi.tabs?: readonly EditorTabDef[];        // every field in exactly one field tab
ResourceUi.seoEntity?: SeoEntityType;              // what `panel: 'seo'` edits
ResourceUi.publicHref?: (values) => string | null; // "Open on site"
```

- A field tab names its fields; a panel tab names its panel (only `'seo'` today). Ids are
  lowercase words and hyphens (the `?tab=` value), unique. `validateTabs` (editorTabs.ts)
  states the rules and `tests/lib/editorTabs.spec.ts` runs it over every ResourceUi, so a
  services or projects config that breaks one fails CI.
- The page decides access on the server with `canWriteResource(slug, role)`,
  `seoAccess(role)`, `firstTab(visibleTabs(ui.tabs, { seoAccess }), ?tab, { readOnly,
  seoAccess })` and `loadSeoPanelSetup(sb, session, type, id)`, and passes `readOnly`,
  `initialTab`, `seoAccess` and `seo` to `AdminResourceForm` (copy `src/pages/admin/blog/`).
- A screen that draws its own tabs uses `TabStrip` with its own panels (the ids from
  `tabIds(idBase, id)`).
- **Groups (U9a) compose inside tabs:** a field tab's card is where a group renders; a group
  never spans two tabs. U9a's `groups` was not on main while this was built, so the rule is
  stated here and in the code comment, for whichever lands second.
- **Read-only and Sortable (U5, U6):** a disabled fieldset does not stop a pointer-dragged
  Sortable handle; a repeater in a read-only editor must check `closest('fieldset:disabled')`
  in `useSortable`. Posts have no repeater, so U8b does not.

## Departures from the brief, and why

- **One PR, one migration** (the owner's folded-PR decision); the migration is a pair of
  `app.put_help_guide` calls, not a restatement of the set (H11, 2026-10-18), and its pgTAP is
  a file of its own (`help_u8_guides.test.sql`) rather than rows in `help_centre.test.sql`, so
  no shared plan count moves (H11 rule 3).
- **`style-finder` takes place 115, not 125:** U17 (in flight) holds 125.
- **The model is `src/lib/admin/applicationView.ts`** (the brief allowed either name), beside
  `userModel.ts`.
- **The address keeps `?status=` and `?open=` in step** (replaceState) as well as the server
  reading them, so a reload or a copied link opens the same view.
- **Escape and the drawer's own Close with an unsaved note:** the native dialog closes
  first (the kit's Drawer cannot veto), so the drawer asks after, and a "no" opens it again
  with the note as typed. The footer's Close asks before closing.
- **The closed-form note is left out on a database outage:** the identity is then the code
  fallback, which says "closed"; the real setting is unknown, so nothing is said.
- **A panel tab mounts the first time it opens** (then stays mounted, hidden): the SEO panel
  reads its row on mount, so an editor that never opens SEO makes no extra request.
- **The shared SEO editor joined the field kit's chunk** (`SeoPanel` and `GooglePreview` in
  `ADMIN_FIELDS`, `astro.config.mjs`): the brief asked to check it, and U10 had left it in the
  SEO screen's group, where every editor importing it would have imported `admin-screens`.
  U10's bundle-spec row follows.
- **The read-only note is generic** (`readOnlyNoteFor`: "You can read this post. Your role
  changes its SEO only." for SEO; "… Your role cannot change it." otherwise), so U5 and U6
  reuse it.
- **`/admin/blog/new` is read-only too** for a role without `blog.write` (it is not in such a
  role's menu or sweep; the API refuses a create).
- **The author rule reads through R6's `db`** (above): the brief left it as an R6 note; R6
  merged first, so it is wired, with a unit test for each path.
- **`releaseOffWrites` snapshot updated on purpose (D12):** `toRow({ body: null })` now writes
  nothing, where it wrote `body` and `body_html` as null. The staged path (`derivePatch`)
  shares `toRow`, so a staged draft records no body for an untouched editor either.
- **The e2e does not delete its post:** the sweep opens the first row of the posts list
  (newest first), and a post removed between its list and its open would 404 there; it is
  archived in `afterAll` instead (off the public site; the CI database is per run). The draft
  team member sorts last and is deleted.
- **A guard the brief did not ask for:** `validateTabs` refuses a record field named like one
  of the SEO panel's (`SEO_PANEL_FIELD_NAMES`, held to `seoPanelFields()`): with the SEO tab
  mounted both forms are on the page, and the ids would repeat (an error link would reach
  the wrong field). Posts have none; U5 and U6 are told by CI if theirs do.
- **`src/lib/release/links.ts` gains U10's two share-image links** (`entity_seo.og_media_id`,
  `seo_defaults.default_og_media_id`, media, RESTRICT). Not this slice's design: R6 (#94)
  merged to main with `releaseLinks.spec` requiring every `_id` column of the registry, and
  U10 (this branch's base) had added the two columns; the spec failed on the merged tree.
  U10's own merge of main needs the same two lines (whichever lands second keeps one copy).
- Kept as the brief decided: D2 (Categories stay a link tab), D3 (Style-Finder's link tabs),
  D4 (traits and scoring stay JSON), D5 (URL columns), D6 (status in the drawer only), D17 (no
  automatic "In review" on open).
