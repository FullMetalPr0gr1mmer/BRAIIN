## Plan (written before the build)

Releases stay OFF in production and in the required e2e job. Nothing below changes what a page,
route or write does while they are off; every product change is gated on the release mode the
server reports, and every test change holds in both modes or branches on `releasesOn()`.
`playwright.config.ts` keeps main's projects with `E2E_RELEASES` unset (held by
`tests/ci/releasesRehearsal.spec.ts`). The switch itself, and flipping the CI seed or the
required e2e job to release mode, are R14c (below), at the owner's go.

### 2. `tests/authz/releaseMatrix.spec.ts` reads the §5 table too

The spec parses CLAUDE.md §5's "Release —" rows as well as architecture §3.4's, requires the two
tables to be the same line for line, and checks each against `requiredCaps` / `ROLE_CAPS` as
today (P-2). No capability is added: `tests/authz/matrix.spec.ts` stays green unchanged.

### 3. `tests/lib/releaseWritePaths.spec.ts`

A static scan of `src/` (everything but `src/lib/release/`): every `.from(<table>)` chain that
inserts, updates, upserts or deletes, where the table is a registry table (from
`RELEASE_REGISTRY`, plus the case study's two link tables) or is not a literal, and every RPC
that writes a registry table. Each must be a named, sanctioned exception with its reason and a
guard the file must hold (the legacy kernels' releases-off branch, an immediate column); an
unlisted write fails, and so does a listed one the scan no longer finds.

### 4. The per-item schedule hidden in release mode, creates included

R12 hides the Scheduled for field and turns the status select into "Visible on the site" only
for a record whose server answer carries `draft` (an editor of an existing record). A create in
release mode (its SaveTarget says `staged`, R12b) still drew the select with Scheduled and the
Scheduled for field, which the staged create refuses (Zod: no `scheduled` in a staged payload).
`useEntitySave` exposes `stagedCreate` (a new record whose target is staged); EditorForm draws
the release form for `draftMode || stagedCreate`. Releases off: no target is staged, nothing
changes (`tests/lib/editorForm.spec.ts`).

### 5. The publishing guide

`saving-and-publishing` (the guide every content editor's head opens) is rewritten for both
modes: today a save goes live at once; once publishing in releases is switched on, Save keeps an
unpublished change, the bar at the bottom counts them, Publish puts them live as a numbered
version, a release is scheduled (never one item), History and Backups & versions restore. Through
the existing mechanism: one `app.put_help_guide` at its current revision in migration 0128, with
the help-centre tests.

### 6. Launch runbook §6p

Checked line by line against the code and completed: the code prerequisite names R14b's build and
migration, the drill's FAQ steps match the release-mode create form (item 4), the editors'
message points at the guide, and R14c's CI flip follows the production switch.

### 7. The e2e specs written for releases off, converted to both modes

Per R14a's rules: publish only the spec's own pending items (the publish route with the items
read from `GET /api/admin/releases/pending`), clean up drafts as the system before restoring
rows, per-mode copy from the producing function, named locators; skip only true releases-off-only
behaviour with a named reason. A shared helper module (`tests/admin/releaseSteps.ts`) holds the
steps. Specs: general, header, footer, visibility, theme, section-blocks (with a `blocks`
project in both modes), loading (E7), templates (E3), section-appearance (E9).

### Found while planning: page visibility is not staged

`PUT /api/admin/page-visibility` (and its alias, and the password door) write
`page_visibility` directly whatever the flag, while 0066's guard refuses any staff write to that
registry table once releases are on: in release mode the Page visibility screen could save
nothing. R3b left it "immediate until R5's guard and R14's static write-path test close it".
This slice stages it (the entity-SEO pattern: a full replace keyed by its target, a pending
create under a Worker-allocated id), and the screen follows the server's answer as every other
editor does. Details under "What was built".
