## Plan (written before the build)

Releases stay off in production until R14 (`app.release_tenants` is empty). Every new screen is
honest while they are off, and every write path sends exactly what it sends on `main`.

**Scope (what releases.md and the earlier as-builts assign to R13; nothing of R14, R15 or
R17).**

1. **Backups & versions, `/admin/backups`** (Settings; zero JS where it can be, P-1).
   - Who: any CMS role holding a release read capability (`PENDING_ANY_CAP`, at full, view or
     meta: Admin, Content Creator, SEO, Developer); Sales gets the server's 403 and the
     layout's refusal, having read nothing. Both layers: the page's own gate and RLS on the
     ledger (0038: CMS staff only).
   - **Versions card**, server-rendered from R10's list (`listVersions`'s reads, shared):
     releases off, it says so ("Publishing in releases isn't switched on yet …") and lists
     nothing (none exists). On: "{N} published versions"; scheduled releases on top
     ("Scheduled · {date}", Change time, Unschedule); failed ones ("Couldn't publish on
     {date}: {reason}", R11's `failureCopy.ts`, Review); then the timeline ("v{N} · live now",
     the note, by · date time, "{k} changes in {areas}"), older versions with Preview
     (`/admin/preview/?v=N`), Restore and Details; a purge that failed with Retry.
   - **Details** is a server render of one version's changes (`?details=N`, R10's
     `versionDetail` rules: an area the person does not read counted, never listed).
   - **Restore** (releases.md §7's confirm and toast) stages through R10's route; its
     refusals are said on the page (every item under its reason). A restore's open changes
     are read back on the server (`origin_kind = 'restore'`), so the version's row offers
     **Publish v{N} again**: R10's rollback publish (`kind: 'rollback'`, every open change of
     that restore, untouched), never a toast for a refusal.
   - **Backups card**: "Download content" (`export-backup`, Admin and Developer:
     `export.backup`), what the file never holds, and the hourly limit said back on the page
     (the route answers a navigation that hits it with a 303 to `/admin/backups?export=limit`,
     as U13's activity export does; it also refuses a link followed from another site,
     `isSameSiteGet`, since it becomes a link here). The other roles read that an Admin or a
     Developer downloads it. Disaster recovery in one honest line (the runbook's §9: Supabase's
     own backups only, restored by whoever runs the site).
   - Actions (Restore, Publish again, Change time, Unschedule, Retry) are one island,
     `AdminVersions`, in its own chunk group (`admin-versions`), never admin-ui.
2. **The purge retry by hand**, `POST /api/admin/releases/[id]/purge` (owed by R7 and R10): any
   role that publishes something; the release published and its purge failed (or still
   pending); its stored tags through R7's `purgeTags` (source `release`), recorded with
   `record_release_purge`, `release.purge` audited when a request was sent. 409
   `releases-off` while releases are off.
3. **`GET /api/admin/releases/status`** (releases.md §7's card): the live version (number,
   when, by, note, the cache's state), unpublished changes (mine to publish, waiting: the
   pending summary's own counts), the next scheduled release and its count, failed releases,
   whether a cache is connected (O-3), maintenance. Any CMS role that reads a release area;
   `enabled: false` and nothing else read while off.
4. **The dashboard's publish card** (U1's widget registry, `publish`): drawn only while
   releases are on (R12's rule for the savebar: with them off no markup, script or request; the
   flag the shell reads anyway is read once by the page and handed to the shell), filled by a
   small island (`AdminPublishCard`, in R12's `admin-release` group, which every screen loads
   anyway while releases are on) from the status route: the rows of releases.md §7, Publish
   now (opens R12's dialog), Retry, Manage and "Versions" linking to `/admin/backups`. The
   kit's Publishing card draws it over made-up status, so the sweep and an e2e see it before
   R14.
5. **The history drawer on every editor** (releases.md §7): a History button in EditorForm when
   its host names the record (`history`: entity type and id, mapped from the save's target);
   the drawer is its own lazy chunk (`admin-history`, reached through `import()` only). R10's
   `GET /api/admin/history`: the pending change on top (Preview, Discard), then each version
   ("v{k} · live now" / "in release v{N}" / saved while releases were off), Preview of the
   version that made a snapshot (`?v=N`, R10 departure 11), Restore (R10's
   `/api/admin/history/restore`, only when the server says `restorable`: releases on and a role
   that publishes the type). With releases off it lists the saves that exist and says that
   restoring arrives with releases.
6. **Links owed:** the dashboard's release attention rows (R5) and the bell's failed-release
   item (R11) link to `/admin/backups`.
7. **The guide** `backups-and-versions` (one `app.put_help_guide`, revision 0, place 125, for
   the release read capabilities), offered on `/admin/backups` (`PAGE_GUIDES`), true with
   releases on or off.
