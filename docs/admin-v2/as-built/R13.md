## Plan (written before the build)

Releases stay off in production until R14 (`app.release_tenants` is empty). Every new screen is
honest while they are off, and every write path sends exactly what it sends on `main`.

**Scope (what releases.md and the earlier as-builts assign to R13; nothing of R14, R15 or
R17).**

1. **Backups & versions, `/admin/backups`** (Settings; zero JS where it can be, P-1).
   - Who: any CMS role holding a release read capability (`PENDING_ANY_CAP`, at full, view or
     meta: Admin, Content Creator, SEO, Developer); Sales gets the server's 403 and the
     layout's refusal, having read nothing. Both layers: the page's own gate and RLS on the
     ledger (0038: CMS staff only).
   - **Versions card**, server-rendered from R10's list (`listVersions`'s reads, shared):

## What was built

### Releases off: what changes and what does not

Releases stay off for every tenant (`app.release_tenants` is empty until R14). With them off:

- **Backups & versions** (`/admin/backups`) renders for every CMS role, reads nothing but the
  flag, draws no script of its own, and says "Publishing in releases isn't switched on yet, so
  there are no versions to list. Until it is, what you save goes live straight away." The
  Backups card works as it will on: Download content for Admin and Developer, the line that
  says who can for Content Creator and SEO.
- **The dashboard** reads the flag once in the page (CMS roles only, as the shell did) and hands
  it to the shell (`ShellPreload.releases`), so the render's subrequests are unchanged (42 of
  50, `dashboardWidgets.spec.ts`); the publish widget leaves the board, Add widget and the role
  presets (`withoutWidgets`, `offered`), so the dashboard is what it was, and no status request
  is made.
- **The history drawer** is on every editor of a release-managed record and lists the saves
  that went live (every save writes a numbered snapshot, R10); it says restoring needs releases
  and offers no Restore (the server's `restorable` is false). It asks for nothing until it is
  opened, and its code loads only then.
- **Every write path** is as on `main`: no kernel, staged, draft, singleton or entity-SEO code
  changed; `releaseOffWrites.spec.ts`, `stagedKernel.spec.ts`, `overlayDb.spec.ts`,
  `releasePublish.spec.ts` and `releaseVersions.spec.ts` are unchanged and green. The one
  route whose behaviour moved is the content export, a read with audit rows (below).
- **The new routes** answer 409 `releases-off` (the purge retry) or `enabled: false` (the
  status) after the flag read and read nothing else.

### Backups & versions (`src/pages/admin/backups.astro`, `src/lib/release/versionsPage.ts`)

- **The gate** (B7.3): `mayOpenVersions`, any release read capability at full, view or meta
  (`PENDING_ANY_CAP`: every CMS role); Sales gets the page's 403 and Refused, having read
  nothing (LOCKED_SCREENS, `anyOf`). The menu link (Settings, after Activity log, icon `db`) is
  derived from the same list, written out client-safe as `RELEASE_READ_CAPS`
  (`src/lib/release/readCaps.ts`, held equal to `PENDING_ANY_CAP` and `PREVIEW_READ_CAPS`).
- **Versions** (the `AdminVersions` island, the `admin-versions` chunk; drawn only while
  releases are on): what is scheduled (its time on the studio's clock, Change time and
  Unschedule: R11's PATCH and DELETE, version-checked) or failed ("Couldn't publish on {date}:
  {reason} Its changes are waiting to be published again.", R11's `failureCopy.ts`, Review
  opens R12's dialog) on top; then the versions, newest first, 50 a page (Older versions:
  `?before=`), the live one marked, a rollback naming the version it restored, the baseline
  named; "Couldn't refresh the website cache." with Retry; Preview (`/admin/preview/?v=N`),
  Details and Restore on the older ones.
- **Restore** confirms in releases.md §7's words, stages through R10's route and toasts "vN
  restored. Publish to make it live."; a refusal is said on the row with every item it names.
  The page reads the open restores back (`content_drafts` with `origin_kind = 'restore'`, by
  the version they restore), so the row offers **Publish vN again** (R10's rollback publish:
  every open change of that restore, untouched) and Preview the restore (`?only=`). A restore
  edited since, or held by a scheduled release, publishes as an ordinary release instead, and
  the row says so.
- **Details** (`?details=<id>`): zero JS, R10's `versionDetail` (each change in an area the
  person reads, its fields in the editor's words, before → after for plain and bilingual
  values, "Changed" for the rest; the others counted).
- **Backups**: Download content is a plain link to `GET /api/admin/export-backup`, what the file
  never holds, and the database's own backups in one honest line (the runbook's §9: no PITR or
  off-platform dump is running yet, so the page claims neither).
- Actions answer with a flash (`version-published`, `release-moved`, `release-unscheduled`) and
  read the list again.

### The content export behind the link (`src/pages/api/admin/export-backup.ts`)

Now a link a person follows, so as U13's activity export: a GET from another site's page
(`isSameSiteGet`) is 403 before the live recheck, a limiter slot or an audit row; a person who
hits the hourly limit, or whose attempt row cannot be written, is sent back to
`/admin/backups?export=limit|unavailable` (303, `no-store`) instead of a JSON body. A script's
request answers as before (429, 403). `tests/lib/exportBackupLink.spec.ts`.

### The status and the purge retry

- `GET /api/admin/releases/status` (`src/lib/release/status.ts`): the live version (number,
  when, by, note, purge), the pending changes counted as the savebar counts them (R12's
  `buildRows` and `savebarCounts` over R3b's summary, so the card and the bar never disagree),
  the next scheduled release and how many are scheduled, failed releases in the dashboard's
  seven days, whether a cache zone is set up, maintenance (KV). The pending summary's gate.
- `POST /api/admin/releases/[id]/purge` (`src/lib/release/purgeRetry.ts`, owed by R7 and R10):
  any role that publishes some area; the version published, not the baseline, its purge
  `failed` (else 409 `not-owed`); its stored tags (none: `tenant:default`) through R7's seam,
  recorded with `record_release_purge` (the attempt counted; a failure due for the cron with
  the same backoff, none after the tenth), `release.purge` audited with `retry: true` when a
  request went out.

### The dashboard's publish card

nothing; `Publish.astro` draws `AdminPublishCard` (in R12's `admin-release` group, which every

### The history drawer (`src/components/admin/screens/history/`)

resource slugs the registry manages, held equal to it) and adds History to the action bar of a
saved record; ResourceForm, the collection drawer, the service and project editors, the case
study panel, the discipline and sector drawers and the redirects drawer pass it. The drawer

(R10's one-snapshot restore; a pending change blocks it). Team members say that history is not
kept for them yet (O-12).

## Departures from the design, each with its reason

1. **The route is `/admin/backups`** (plan B7.3, which wins over releases.md's
   `/admin/settings/versions` and R10's note that `/admin/backups` was R17's), for every CMS
   role holding a release read capability (ui.md's nav caps `export.backup, content.publish`
   left SEO out; verification 1029).
2. **The publish card is drawn only while releases are on** (as R12's savebar): with them off
   it would only say that nothing exists, on every CMS dashboard until R14.
3. **No "Publish now" on a scheduled release** (R12 departure 16 sent it here; releases.md §7's
   versions page lists Change time and Unschedule only). R12's dialog cannot yet publish a
   chosen set alone without unticking the rest by hand; Unschedule returns the changes to the
   savebar, whose Publish ticks them. Owner question 1.
4. **No new bell kinds** (ui.md §2.8's "releases published" and "changes waiting"): neither
   README's R13 row nor releases.md's R13 lists them, and each is one more read on every
   admin render of a CMS role (the dashboard sits at 42 of 50).
5. **The history drawer is on row editors only.** The two singletons (the identity on General,
   the SEO defaults) key their history by the tenant, which no editor holds; entity SEO and
   page visibility are edited inside other screens. Each needs its id passed from its page:
   left for R14 or E1 (owner question 2).
6. **History before releases**: the drawer lists the saves that went live while releases are
   off (each save writes a numbered snapshot since R10), says restoring needs releases and
   offers none. releases.md §7's drawer assumed releases on.
7. **Restore's rollback is published from the version's row**, not from R12's dialog: the
   pending summary does not say which changes a restore staged, the dialog would tick every
   other pending change too, and R10's rollback must be exactly that restore's changes.
8. **The DR card is one line**: ui.md's "PITR 28 days, nightly encrypted dumps and the media
   mirror" are not running yet (launch runbook §9), so the page says only that the hosting
   provider backs the database up and whoever runs the site restores it.
9. **The content export changed** (a cross-site refusal and the 303 back to the page): it
   becomes a link here, and §3 asks that of every export a person follows as a link.
10. **The status reads maintenance from KV** (one read in its own request) rather than taking it
    from the dashboard's render.
