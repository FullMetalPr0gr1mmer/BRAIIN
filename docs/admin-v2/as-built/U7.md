## Departures from the brief, and why

1. **One PR, not two** (D1): the owner approved folded PRs; the commits stay separable (U7a's,
   then U7b's).
2. **The help guide is one put, not a restated set** (H11). H11's catalog retired the
   restatement rule: a slice puts its own guide with `app.put_help_guide(jsonb, revision)`.
   While H11 was in flight the guide waited as `docs/admin-v2/guides/collections-and-faq.json`
   behind a `TODO(H11)`; once H11 (0069) reached `main` the JSON moved verbatim into the
   migration's put and the file was deleted (no test reads it: the spec reads the migration).
3. **`saving-and-publishing` is not edited** (the brief adds `/admin/faq` to its screens). Under
   H11 a slice changes only its own guide; that guide still names the five collection screens,
   so the help drawer lists it among their guides, and `PAGE_GUIDES` offers
   `collections-and-faq` as their page head's guide.
4. **The lists show the collection's icon, not a thumbnail.** The list endpoints return media
   ids, not URLs; a thumbnail per row needs a media read per screen (and the 0024 public-media
   fence does not cover staff-only assets). Deferred; the drawer's media field shows the image.
5. **Three list projections widened** (the brief says the resource configs are unchanged): the
   testimonials list now returns `quote` and `consent_obtained_at` (the row's words and the
   "Needs consent" badge), clients `logo_media_id` ("Logo" or "Text only"), certifications
   `issuer`. Without them every real quote read "Needs consent" and every client "Text only".
   `tests/lib/collectionScreen.spec.ts` runs every definition over a recording row and fails on
   any key its list does not return. The consent record (`consent_reference`) stays out of the
   list. The same caps read them already (the item GET returns the whole row).
6. **Copy changes beyond the brief:** the testimonial lock's three refusal messages name the
   drawer's switch instead of the old Placeholder box; the em dashes in the five forms' help
   lines are gone.
7. **e2e, the public side of U7b is not asserted in the admin suite.** The public suites pin the
   seeded rows (eight marquee names and three quotes on Home), and the admin project runs beside
   them on one database, so `collections.e2e.ts` works on its own unpublished rows (the quote is
   scheduled for 2099 with no placement, the client stays out of the marquee, the numbers are
   drafts) and checks the stored rows through the service role. What `visible` and a published
   quote do on the site is `home-sections.e2e.ts`'s and pgTAP's.
8. **e2e, the FAQ:** the 201-character question became an answer with a line break (the
   question input's `maxlength` stops typing at 200, so the refusal could not be reached by
   typing); the move is up with the keyboard, then back down with its arrow (the row is added
   last and moved one place at most, so the Contact suite's pinned first question holds).
9. **`orderChanges` numbers only the rows the list holds** (an unknown id took a place before).
10. **Duplicate renumbered the whole list** (pre-merge review): it ran a move's renumbering over
    every row, so copying a client rewrote all sixteen seeded clients one update at a time while
    the Home suite read the marquee's order. `duplicateChanges` keeps the rows above the original
    as they are and orders its updates so no row passes another on the way

11. **The `[id]` route answers 404 for a path that cannot be a uuid**, with the list and a note,

12. **A move or a duplicate renumbered archived rows** (found by the CI e2e): the island
    renumbered every row of the list, so a Content Creator's move over a list holding an

13. **D18 ("nothing for Sales") became one policy**: C10a reached `main` first and set a

## Security: the non-staff block (found at the merge with C10a)

C10a (0097 §4, CLAUDE.md §8) set the boundary: Sales is a signed-in token that is not CMS
staff, and it reads no more than anon outside the CRM. A GRANT cannot tell the app roles apart
(all of them are `authenticated`), so wherever `authenticated` holds more columns of a public
table than anon, a RESTRICTIVE `<table>_staff_columns` read (the tenant first, then
`app.is_staff()`) keeps a non-staff token from every row; `disciplines` is the one named
exception. `faq_items` is such a table (anon SELECTs six columns, `authenticated` the whole row:
`published_at`, `scheduled_for`, `version`, the stamps and the ids of the staff who wrote it),
and U7, built before C10a, had no block: a Sales token read its tenant's published questions
with those columns.

- **The fix (0098 §3):** `faq_items_staff_columns`, RESTRICTIVE FOR SELECT TO authenticated,
  `tenant_id = app.effective_tenant_id() and app.is_staff()`, as 0097 writes its three;
  postcondition 2 lists it and 3b holds its shape as 0097's postcondition holds theirs; the
  read-back gains `faq_staff_block`. Staff are untouched (they pass `faq_items_read` already)
  and anon is not named. Nothing reads the FAQ through a non-staff token: `getFaq` uses
  `contentClient()` (the anon key; inside a preview scope the person's own client, and
  `canPreview` refuses a role with no content capability), and the admin's readers (the FAQ
  resource, ⌘K, the activity log's titles, the backup) are staff-gated. A signed-in token with
  no role claim now reads no row either (it read the published ones, as anon); no caller sends
  one.
- **Why the tests missed it:** `rls_sales_role.test.sql` compares a Sales token of its own test
  tenant with anon over every readable relation, and that tenant held no FAQ row (the only ones
  were seed.sql's, in another tenant), so both read 0 and the extra-columns check saw nothing.
  Its "none passes empty" guard counted rows as the migration role across every tenant, so
  seed.sql's ten questions satisfied it.
- **The test fix:** the guard counts rows in the Sales test tenant, as the migration role for
  a relation with a `tenant_id` column and, for one without (today only
  `dashboard_attention`), as an Admin token of that tenant reads it, never whole. Run so, it
  found two relations vacuous: `faq_items`, now given a published and a draft question there
  (without them the guard names exactly `faq_items`), and `dashboard_attention`, which is named
  in the test's `_no_fixture()` list with its reason (Open, below). The block's catalog row
  names four tables; a new row holds anon 1, Content Creator 2, Sales 0.
  `rls_faq_items.test.sql` holds the policy's shape and the block per role (every CMS role
  reads all four fixtures, anon the published one, a Sales claim none and writes none);
  `preview_dataset.test.sql`'s Sales row reads `faq_items=0`. Without the policy the three
  files fail 3, 5 and 1 assertions, and the migration refuses a missing policy
  (postcondition 2) or another USING (3b). Replayed on PGlite 17.5 over 0001 to 0098 with
  `seed.sql`: `rls_sales_role` (65), `rls_faq_items` (76), `preview_dataset` (20),
  `rls_releases` (115), `release_apply` (101) and `help_catalog` (85) pass, and
  `grants_app_schema` stops at its section 8, the known harness artefact.
