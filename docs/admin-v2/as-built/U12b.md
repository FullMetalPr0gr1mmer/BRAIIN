## As built

**Accepting an invite** (`src/pages/admin/invite.astro`, `src/pages/api/admin/auth/invite.ts`,
`src/lib/auth/inviteToken.ts`). The invite e-mail's link opens `/admin/invite?token_hash=…
&type=invite`, a zero-JS page on `AuthLayout` that only checks the token's shape and carries
it in a hidden field (mail scanners fetch links, so a GET never spends it). The form posts to
`POST /api/admin/auth/invite`, which does everything on the server, in this order: the token's
shape and the admin's rule for a new password (typed twice) before anything is spent; the
limits (10 an hour per IP address, then 30 an hour for the tenant, on the EXC-004 counter,
failing closed); `verifyOtp({ type: 'invite', token_hash })` in a request-scoped client
(`recoveryClient()`), which confirms the address and spends the link; the account must still be
switched on (an Admin may have switched it off since: then nothing is set, the verify's session
is ended and the page says the invite is no longer open); the password set and the invite
message cleared from the user's metadata; signed out everywhere; audited
`auth.invite_accepted` by the service role against the account (the IP and whether the global
sign-out worked; never the token, the address or the message). Then `/admin/login?invite=ready`
says "Your password is set". A failure that keeps the link goes back to `/admin/invite?error=…`
with the token in `__Secure-braiin-invite` (HttpOnly, SameSite Strict, Path `/admin/invite`,
15 minutes), never the URL; a spent link says to ask the Admin to send it again.

**The middleware.** `PRE_AUTH_PATHS` grows from six to eight (`/admin/invite`,
`/api/admin/auth/invite`), still classified by both the path and `context.routePattern`. The
CSRF refusal of a sign-in form and the 16 KB pre-auth body limit learn the invite page
(`expiredForm.ts`, `bodyLimit.ts`): a refused or oversized invite form goes back to its page,
the token in its own cookie.

**Invites on the users screen** (`PendingInvites.tsx`, `InviteDrawer.tsx`, replacing U12a's
invite card). "Pending invites" lists every account invited and never signed in
(`isPendingInvite`: invited, not confirmed, no sign-in), wherever it falls in the people
table's pages (the API's `pending`, from `staff_accounts`), each with Resend and Cancel
(confirmed: "Cancel invite?", "<email> will not be able to join with this link."). "Invite
someone" opens the drawer: e-mail, role, an optional name and an optional message (plain text,
300 characters, `InviteMessageSchema`: line breaks become spaces, no control or format
characters, no `<` or `>`). The page passes `emailReady` from the server.

**Switched off until SMTP** (O-2, O-22). While `AUTH_EMAIL_READY` is false, `POST
/api/admin/users` (the live invite, switched off too) and `POST /api/admin/users/[id]/resend`
answer 503 `not-set-up` after the capability gate and before anything is read, counted or
sent; the card shows "Not set up" with the reason (e-mail delivery is not connected yet) and
both buttons are off. The list and Cancel work either way. The acceptance page works either
way too: a token can only come from an invite e-mail.

**The routes.** Switched on, the invite POST takes the message (GoTrue renders it from user
metadata, `invite_message`), passes `redirectTo` `/admin/invite`, refuses an address that
already has an account here (422 on `email`, pointing at Resend), counts against
`INVITE_LIMITS` (10 an hour per Admin, 30 per tenant, `privileged_ops` key `user-invite`,
shared with Resend) and keeps writing the profile. Resend (`users.manage`, live recheck) acts
only on a pending invite of the tenant read through RLS, never yourself or the owner, an
account that can sign in, an address the allowed domain admits now; it calls
`inviteUserByEmail` again (D8), which sends a fresh link. Cancel (`DELETE
/api/admin/users/[id]/invite`, `users.manage`, live recheck) the same checks, then GoTrue's
admin delete (the profile cascades; audit rows keep the id). Audited `user.invite` (`role`,
`withMessage`), `user.invite_resend` and `user.invite_cancel` (`role`): no address and no
message (D5: nothing stored, not even a hash; the entity id is the person). The activity log
has words for all four actions.

**The e-mail.** `supabase/templates/invite.html` for the local stack (`[auth.email.template.
invite]` in `supabase/config.toml`), its link `{{ .SiteURL }}/admin/invite?token_hash={{
.TokenHash }}&type=invite`, the message under `{{ if .Data.invite_message }}`; launch runbook
§2b gives the hosted projects the same template, the redirect URL and what to check. The link
lasts one hour (D1: `otp_expiry` stays 3600, because GoTrue has one expiry for invite and
reset links); the drawer, the card and the guide say "The link works for one hour. Resend it
if it runs out."

**The guide** (0056). `app.help_article_set()` restated from 0055's set, every guide byte for
byte, plus `inviting-people` (`users.manage`, so Admin alone is shown it; `/admin/users`;
after the roles guide), seeded into every tenant, with postconditions on the set, its seed and
`help_articles`' grants under both privilege regimes (MAINTAIN on 17+). `PAGE_GUIDES` is
unchanged: the users screen's head keeps the roles guide, which every member may read.

## Departures from the brief, and why

- **"Invite someone" is in the Pending invites card's head, not the page head.**
  `AdminLayout` has no actions slot, and the drawer it opens lives in the island; a
  server-rendered head button would need a script to reach it.
- **No schema, so no pgTAP file.** An invite is a GoTrue account (read through 0055's
  `staff_accounts`); cancelling deletes it. 0056 is the guide, and its postconditions are its
  test, with `tests/lib/helpCentre.spec.ts` (0055's guides kept byte for byte, the new guide's
  claims held to the code).
- **The invite POST refuses an address that already has an account here.** GoTrue would
  otherwise re-send an unaccepted invite under its first role (or refuse a joined one) while
  the form claimed a new invite with a new role. Resend is the way for the first.
- **Resend checks the allowed domain as it stands now, and refuses a switched-off account**
  (it could not accept). Cancel works for a switched-off pending invite.
- **Cancel and Resend refuse yourself** besides the owner (D7): yourself is never pending, and
  the rule keeps a crafted id from deleting the caller.
- **A switched-off account sets no password at acceptance** (`closed`): beyond the brief, but
  an Admin who switched an invitee off expects the link to be useless. The verify has spent the
  link by then; the outcome is logged to `system_logs` (`auth.invite`, the account id, never
  more).
- **The acceptance's limits** are reset's per-IP window plus a tenant window counted only for a
  request the first let through (as forgot's), since each request is a GoTrue verify.
- **The e-mail carries no brand name.** P-12 takes the brand from `site_profile`, which GoTrue
  cannot read; a hardcoded name would go stale at the next rename.
- **Resend is `inviteUserByEmail` again (D8), verified against GoTrue's source, not on a local
  stack** (no Docker here, and the CI preview has e-mail off, so no e2e sends one). If a
  GoTrue version refuses it, Resend answers 422 "The invite could not be sent again" and the
  fallback is Cancel and invite again. The owner's check after O-2 is in runbook §2b.
- **The e2e reaches the invite drawer by rewriting the page's `emailReady` prop** (the CI
  preview is built with e-mail off): the drawer gets axe and the overflow check at three
  widths, and its send proves the server still answers `not-set-up`.

## Tests

Vitest: `tests/authz/invite.spec.ts` (the acceptance: the token only at submit, the password
rule before the link is spent, the limits failing closed, verify, the closed account, set, sign
out, cookies, audit), `tests/authz/login.spec.ts` (the eight pre-auth paths, path and route),
`tests/lib/usersApi.spec.ts` (the 503 while off; switched on: the message, the redirect, the
existing address, the limit, D5; Resend and Cancel on pending, joined, owner, self, switched
off, another tenant; §9 (b) for both), `tests/lib/users.spec.ts` (pending, cancel and resend
rules, the message schema), `tests/lib/authScreens.spec.ts`, `tests/render/authPages.spec.ts`
(the page's outcomes), `tests/lib/inviteTemplate.spec.ts` (the template, the config, the page's
token reader and the runbook hold one link), the endpoint cases (resend, cancel; the acceptance
in `endpointCoverage`'s not-drivable list with its spec), `helpCentre`. E2E:
`tests/admin/invites.e2e.ts` (above), and the invite page in the zero-JS, CSP, no-`style=` and
axe sweeps of the signed-out screens.
