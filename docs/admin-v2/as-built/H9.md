# H9: lead notifications restored, signed, and never silent

- **Lane:** hotfix
- **Design:** none (found by a read-only production check, 2026-10-13: `app.tg_notify_lead()`
  existed, but no trigger called it, so no lead had ever been announced)
- **PR:** #63
- **Migrations:** 0048 (`0048_lead_notify_trigger.sql`), to be applied to production before
  the merge

## As built

**The missing trigger.** 0010 created `leads_notify` only if pg_net was already installed
when it ran. Production's was not, so `notification_log` never had a row and nothing said so.
0048 makes pg_net a requirement: it runs `create extension if not exists pg_net with schema
extensions`, a no-op on production. CI's Supabase stack ships pg_net available but not
created, which is why the first draft's pgTAP passed 20 of its 27 assertions as skips. 0048
then creates the trigger on every database, and its postconditions require the extension,
the trigger's shape and `net.http_post`'s signature everywhere. The suite has no skip
branch.

**Where the call goes, and how it is authenticated (beyond the first draft).** The review
found two problems:
- 0010 read the URL from `site_settings.identity`, which Admin and Developer write.
- 0010 put `Authorization: Bearer <secret>` in the request. pg_net keeps that request in
  `net.http_request_queue` until its worker sends it, and on Supabase PUBLIC may read that
  table (EXC-012).

So now:
- The URL is the Vault secret `notify_lead_url`, set by the database owner. pgTAP proves
  `site_settings.identity.notify_lead_url` is not read: with an https URL there and the
  Vault secret set, but no Vault URL, nothing is queued; once the Vault URL is set, the
  request goes to it, not to the site_settings one (pre-merge review).
- The request carries `X-Braiin-Timestamp` and `X-Braiin-Signature: v1=<HMAC-SHA-256 of
  "<ts>.<lead_id>.<tenant_id>">` under the shared key. The key is Vault's
  `notify_lead_secret`, equal to the Worker's `NOTIFY_LEAD_SECRET`.
- The canonical string is signed rather than the JSON, so no serializer can break it.
- The Worker (`src/lib/leads/notifySignature.ts`) checks the headers before reading the
  body, refuses a timestamp more than 300 s away, recomputes the HMAC over the body's ids
  and compares in constant time. Every failure is the same 401.
- The bearer path is gone. Nothing ever sent one, since the trigger never existed.
- A queued request is now good for one lead for five minutes, and a replay only announces
  that lead again.

**Never silent (beyond the first draft).** Configured but unable to announce a lead (a
non-https URL, no secret, any error), the trigger raises a WARNING and writes a
`system_logs` row: source `leads_notify`, a fixed message, and `{sqlstate}` as the only
detail. Both happen in their own handler, so the log cannot fail the insert. The replay
proved this matters: a first draft raised its WARNING outside the handler, and those leads
failed to save.

Not configured at all is not logged per lead. Instead the Worker's daily cron job
`lead-notify` calls `public.lead_notify_misses()` (definer, service role only) and writes
one line:
- off: notifications are not configured;
- clean: the check ran and found nothing;
- a warning with the count: leads with no `notification_log` row, created from 24 h 30 min
  to 15 min before the run. The window is 15 minutes wider than the day between runs (the
  pre-merge review found a 24-hour window ending 15 minutes back skipped the 15 minutes
  before every run), so each run reaches into the one before; a miss in that overlap is
  counted twice, which a warning can bear. pgTAP checks both edges to the microsecond and
  a lead 24 h 10 min old, which the first window never counted.

The hook writes one such row for every lead it accepts, recipients or not, so a lead
nobody was eligible to hear about is not a miss.

**What "never fails an insert" means.** No error the trigger can catch fails the insert:
every statement runs inside a handler. PL/pgSQL's WHEN OTHERS does not catch
`query_canceled` or `assert_failure`. The function asserts nothing, and a cancel ends the
insert as it would without the trigger.

**Every door notifies.** A lead from the form (through `crm_ingest_lead` or its fallback
insert) and a lead staff add by hand (source `manual`, 0041) are both announced. That is
kept on purpose.

**A trigger on pg_net's queue (pre-merge review).** On Supabase PUBLIC holds ALL on
pg_net's two tables, TRIGGER included, not the four privileges EXC-012 first listed (its
query asked about those four only). Since 0048 the queue is written as `postgres` (the
trigger function is a definer it owns, and `net.http_post` runs as its caller), so a
trigger anyone attached to the queue would run as `postgres` on the next lead. Nothing
can do that on production today: no login role outside the platform's holds CREATE on
any schema, and the queue has no trigger. 0048 now makes sure the lead path never runs one:
- the function locks the queue (ROW EXCLUSIVE, which CREATE TRIGGER's lock conflicts
  with), looks in `pg_trigger` for any trigger on it that is not internal, and if there is
  one queues nothing: a WARNING and a `system_logs` row (`lead notification skipped: a
  trigger is attached to pg_net's queue`, detail `{}`), the lead saved;
- a postcondition refuses to apply 0048 over such a trigger, and requires the owner's
  INSERT on the queue (what the lock needs);
- pgTAP attaches a spy trigger to the queue inside the test transaction and shows nothing
  is queued, the spy never runs and one row is logged (it fails four ways against the
  first 0048).

EXC-012 now states exactly what PUBLIC holds, why it is not exploitable today (including
what `deploy_guard`'s read-only default does and does not stop), and two new owner actions:
report the grants to Supabase, and check `deploy_guard`'s TEMPORARY privilege.

**The owner's privileges.** Since pg_net 0.10, `net.http_post` runs with its caller's
rights, here the trigger function's owner. The postconditions read `http_post`'s body and
require EXECUTE on every `net` function it calls and INSERT on every table it writes,
together with that table's sequence. They also require the owner to read
`vault.decrypted_secrets` and run `extensions.hmac`.

**Also in this PR: the `staleDomain` flake.** `tests/lib/staleDomain.spec.ts` walked the
directories and then read what it had listed. An editor's atomic save (a temporary file
created and renamed away) could land between the two steps, failing with ENOENT in full
parallel runs. It now scans `git ls-files` under the same roots, with every `GIT_*`
variable dropped from git's environment. A throwaway-repo test proves it still catches the
domain in a tracked file.

**Production.** Not yet applied. After the push, `readback_0048.sql` (kept with the
operator's notes, not in the repo) reads back the trigger, the function's rights, owner
and body, the owner's privileges on what `http_post` touches, the ledger, and the counts.

**Owner steps.** Notifications stay off until three things exist (launch runbook §5):
- the Vault secret `notify_lead_url` (https);
- the Vault secret `notify_lead_secret`;
- the Worker secret `NOTIFY_LEAD_SECRET` with the same value.

Then send one test inquiry. Separately, confirm in the dashboard that `net` is not an
exposed API schema (EXC-012).
