## What was built

Nothing in the app reads or writes the new objects: the ledger is inert, and releases are
off for every tenant until R14 switches them on.

- **`app.release_entities`**, the registry: one row per release-managed entity type (twenty:
  category, sector, client, team_member, statistic, certification, discipline, service,
  portfolio, service_case, testimonial, blog_post, page, page_section, nav_item,
  site_profile, custom_theme, entity_seo, seo_defaults, redirect). Each row names its table,
  key (`id`, or `tenant_id` for the two singletons), area, author roles, delete roles, the
  writable column allowlist (derived columns included), the self-references set in a second
  pass (`portfolio.next_portfolio_id`, `navigation.parent_id`), the unique flags
  (`navigation.is_key`), the columns that stay immediate
  (`site_profile.accepting_applications`), the apply order, whether it has a status, and
  its go-live flag. RLS forced; CMS staff read it; no API role writes it.
- **`app.release_tenants`**, the switch-on flag: a row per tenant with releases on. Empty.
  RLS forced, no policy, no grant to any API role; `app.releases_enabled(uuid)` (SECURITY
  DEFINER) reads it.
- **`public.content_drafts`**: one shared pending change per entity, with its own version,
  the `base` for the column-level conflict check, a 512 KB payload cap, and the claim of a
  scheduled release. Staff may stage a change only to entity types their role authors
  (`app.can_author`), a removal only where their role may remove (`app.can_stage_delete`),
  an archive only as Admin, and never touch a claimed draft. A claim-lock trigger refuses a
  staff claim even past RLS.
- **`public.content_releases`**: the site versions, numbered per tenant once live. Staff
  read; the service role writes (no DELETE for anyone).
- **`public.content_release_items`**: append-only before/after images. Staff read; the
  service role inserts; the capture trigger (R4) gets an insert policy valid only inside a
  release.
- **`content_versions`**: `release_id`, set only while this transaction's release token is
  valid (`app.release_token_valid()`, `app.current_release_id()`). Snapshot triggers added
  on team_members, certifications, statistics, categories, navigation, redirects,
  entity_seo and custom_themes; `app.tg_snapshot_singleton` on site_profile and
  seo_defaults. Every registry table now has history.
- **`custom_themes_delete_admin`**: the RESTRICTIVE admin-only delete gate (releases.md
  §12.7). The Worker already required `content.archiveDelete` for a theme delete; RLS let a
  Developer delete one through PostgREST. Registry contract #2 needs RLS to say what the
  registry's delete roles say, so it is added here.
- **`packages/schemas/release.ts`**: the ledger vocabularies, the publish request, the
  draft payload envelope, the row shapes.
- **Tests:** pgTAP `rls_releases.test.sql` (74) and `snapshot_coverage.test.sql` (19), five
  rows added to `grants_app_schema.test.sql`; vitest `tests/schemas/release.spec.ts`
  (limits, control characters, uuids, strictness, the vocabularies against the SQL) and
  `tests/authz/releaseRegistry.spec.ts` (author and delete roles equal `ROLE_CAPS`, tables
  equal the resource configs). The migration's postconditions check the grants under both
  regimes, the tenant predicate on every policy of the three public tables, the function
  ACLs, every registry column and snapshot trigger, and that the flag table is empty.

## Departures from the design, and why

- **The flag is a table, not a column.** The design put `releases_enabled` on
  `site_settings`; the verification found Admin and Developer can write that row through
  PostgREST, which would disarm the guard. The README moved it to `app.release_tenants`,
  read by a definer. Consequence for R3: the design's `releasesEnabled()` read
  `site_settings` with the staff client, which can no longer see the flag (see Open).
- **No `app.is_cms_staff()`.** P-6 keeps `app.is_staff()` exactly the four CMS roles, so
  the drafts, releases, items and registry policies use it, and `content_versions_read`
  (already `app.is_staff()`) is unchanged; a postcondition holds it.
- **`content_versions` INSERT was already revoked** by H6 (0032), with the owner-only
  insert policy. R1 builds on it: the new singleton snapshot function has the same owner,
  checked by a postcondition.
- **Twenty registry rows, not the design table's twenty-two.** `faq_items` (U7) and the
  appearance tables (E5) do not exist yet; their slices add their rows with their tables
  (registry contract #4), as do page visibility (U14), forms config (E8) and template copy
  (E3).
- **Tenant-fenced release references.** Every reference to a release
  (`content_drafts.release_id` and `origin_release_id`, `content_release_items.release_id`,
  `content_releases.restores_release_id`, `content_versions.release_id`) is a composite key
  to `content_releases (tenant_id, id)`, so a row can only name a release of its own tenant
  (the 0034 pattern). The design had single-column keys.
- **The release item insert policy names the tenant** (verification claim 18) and is
  granted to the snapshot functions' owner only (the 0032 pattern), not to PUBLIC.
- **The writable allowlist leaves out `published_at` and `scheduled_for`** on every table:
  the apply stamps `published_at` on a first publish, and scheduling belongs to releases.
  `pages.nav_visible` stays a staged column, since the pages editor writes it; what happens
  to the Developer's visibility endpoint once the guard is armed (verification claim 7) is
  for R5 and U14.
- **`publish_flag` is `visible` on sectors, clients, page sections and navigation**, the
  four the design's §2.8 lists. The resource configs name `publishFlag` on clients and
  sections only today; the test checks agreement where a config names one, and R2
  reconciles the rest.
- **The release token** compares `app.release_apply` with
  `pg_current_xact_id_if_assigned()` (the verification prefers `pg_current_xact_id()` over
  `txid_current()`; the `_if_assigned` form never assigns an id just to check). R4 must set
  the GUC to `pg_current_xact_id()::text`. A new helper, `app.current_release_id()`, gives
  the snapshot trigger (and R4's capture trigger) the release id, and fails the write
  (22023) when the token is valid but the id is unreadable, rather than recording history
  with no release.
- **The snapshot functions pin `search_path = ''`** with every name qualified (P-14); their
  bodies are 0009's plus `release_id`.
- **`app.tg_draft_claim_lock` is SECURITY INVOKER**, where §2.7 lists the trigger functions
  as definers: it reads `current_user` and nothing protected. It allows the service role and
  requests with no role claim, and refuses an API role or any other role carrying a staff
  claim.
- **Release items use an identity column**, not `bigserial`, so no sequence grant is needed.
- **Small CHECKs added:** an item's before/after shape matches its op; a release note has no
  control characters; release areas are registry areas; counters are not negative; `base`
  and `label` have size caps. The design's `(tenant_id, entity_type)` draft index is left
  out: the unique `(tenant_id, entity_type, entity_id)` index serves it.
- **The publish request** caps a release at 60 changes (P-15, not the design's 500), is
  strict, and has no `scheduleAt`: a scheduled publish is refused until R11 adds and handles
  it. `kind` defaults to `publish`.
- **Backups unchanged.** §4.6 adds the ledger tables to `BACKUP_TABLES`; that changes what
  `export-backup` returns, so it waits for the slice that uses the ledger (R10 or R17).
- **pgTAP adds a `sales` claim row** where the role list matters (the policies read the role
  from the claim, so Sales' denial is provable before C10). No stale-token row: no definer
  here relies on `app.live_role()`.

## Open

- **R3 needs a staff-callable flag reader.** `app.releases_enabled(uuid)` is executable by
  no API role. Proposed for R3 (or R4): `public.releases_enabled()`, SECURITY DEFINER,
  answering for the caller's own tenant only, EXECUTE for authenticated and service_role.
- **Out-of-band capture (R5).** `content_release_items.release_id` is NOT NULL, as designed.
  If R5 records writes made outside any release as system items with no release, it relaxes
  that (an expand change).
- **Singleton drafts** are keyed by the tenant id; the database does not check that a
  `site_profile` or `seo_defaults` draft's `entity_id` equals its tenant. R3 writes it and
  R4 must refuse anything else.
- **PDPL.** History now also keeps team members' names and bios after an edit or deletion;
  redaction is R16 (owner item O-12).
