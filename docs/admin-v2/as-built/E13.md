## Plan (written before the build)

O-21 is open, so the catalogue can hold only Archivo (English) and Almarai (Arabic), the
brand's own. This slice builds the whole mechanism around them, so that adding a family later is
data plus a migration, and every page stays byte for byte as it is: no theme can choose anything
but the brand's fonts until a second family exists, and the brand's choice writes no token.

**What a family is** (`packages/theme/fonts.ts`, code-owned and closed, never a row): an id, its
name, the script whose pages it sets (`latin`: the English pages' `--bs-font-sans`; `arabic`: the
Arabic pages' `--bs-font-ar`, with a Latin subset of its own for the Latin words in Arabic
copy), its licence, its full CSS stack (the family, its fallback families, the generic tail), its
web faces (each a pre-subset woff2 in `public/fonts/`, a weight or a variable range, the
unicode-range its file holds, `font-display: swap`) and its metric-override fallback faces (per
weight, per script for an Arabic family, and per platform: Arial on Windows and macOS, Liberation
Sans and DejaVu Sans on Linux, as docs/fonts.md 2b and 2c measured them). One renderer writes a
family's `@font-face` blocks from that data.

1. **The catalogue is the source of the faces.** The brand's two families render exactly the
   `@font-face` set global.css and admin.css hold today (a test compares the three, block by
   block); global.css is not edited. admin.css declares every family of the catalogue (today the
   same set), so the editor can draw each family in itself.
2. **Settings v3** (`packages/schemas/theme.ts`): `fonts {latin, arabic}`, each one of the
   catalogue's family ids for its script, strict. v1 and v2 are read and answered as v3 at the
   brand's fonts through the one upgrade (`upgradeThemeSettings`), so the editor, `toRow`, a
   release's publish and the release lane's comparisons see one shape; the next save stores v3.
3. **Two tokens**, `--bs-font-sans` and `--bs-font-ar`, join the closed set: each takes exactly
   the stacks of the catalogue's non-brand families for its script, and the brand's family writes
   none (the stylesheets' own `:root` values are the brand's). With no non-brand family the
   pattern accepts nothing (`^(?!)`, valid and equal in JavaScript and Postgres). `compileTheme`
   writes a font token only for a non-brand family.
4. **theme.css follows the choice**: when a font token is set, the chosen family's faces (web and
   fallback, from the catalogue, code text keyed by the closed token, never row data) come first,
   then the `:root` rule; the page's own `--bs-font-*` is then the family's stack. No token: the
   body is exactly what it is today.
5. **The preload follows the choice**: the one hero-face preload is the chosen family's file at
   the weight the route's heading renders in (`heroFontPreload` reads the theme's font token; a
   route's `heroFace` names the weight; E12's Bold rule still applies). No token: the same href.
6. **The fallback faces follow the choice** by construction: each family's stack names its own
   fallback families, and they ride with its faces.
7. **Rules every family must pass** (a spec over the catalogue, with a test-only family proving
   each rule fires): the files exist; every web face is `swap`; a variable family has fallback
   faces at every weight the public stylesheets paint, a static family at each of its weights;
   an Arabic family per script; both platforms; its stack starts with the family and its
   fallback families, each declared; the heading weights a theme offers (800, 700) are real
   faces; the hero files are within 35 KB (Latin) and 45 KB (Arabic); every pairing of a Latin
   and an Arabic family, plus any family an Arabic stack names, is within 180 KB per route; no
   family loads from anywhere but `/fonts/`.
8. **Database** (0125): `app.theme_row_ok` restated: v1 and v2 as E12 held them (no font token),
   v3 with the closed `fonts`, the token set grown by the two keys, and each font token exactly
   what its choice writes (none for the brand's). Generated blocks from `packages/theme/sql.ts`
   (the token rules; a new font rules table). The CHECK keeps its name. The `theme` guide is put
   again (revision 3: the Fonts card; its tip no longer says the fonts are fixed).
9. **Editor**: a Fonts card on `/admin/appearance/theme`: "English pages" and "Arabic pages", a
   tile per family (its name, its licence, "Aa" or "أب" drawn in it, as the prototype's tiles),
   native radios; the site sample draws its English and Arabic lines in the chosen families. With
   one family per script the card shows the brand's two, chosen, and says how a font joins the
   catalogue. Reset brings the brand's fonts back. Staged with the theme: the fonts are part of
   its settings, so they ride the same save, live or pending.
10. **Docs**: fonts.md (the catalogue and how a family joins it), CLAUDE.md (§6, E13 entry),
    README, migrations.md, the launch runbook's rollback line, deviations.

Rollback (rule 5): a Worker older than E13 reads a theme's tokens through E12's set; no font
token can be written while the catalogue holds only the brand's, so a rollback needs no step. Its
editor reads a v3 row's colours, motion, shapes and type and saves v2, which the restated
function accepts.

## Departures

1. **The catalogue holds the brand's two families only.** O-21 (the families, with web
   licences) is open, and adding a family is the owner's choice plus a licence check (L-1), the
   files, measured fallbacks and a migration (docs/fonts.md "Adding a family"). The prototype's
   five Google families per script and "Add custom font" are not offered (deviations.md §5.5).
2. **A font token accepts nothing yet.** Each pattern is `^(?!)` (fails at every position, in
   JavaScript and in Postgres alike, both tested), rather than leaving the two keys out: the
   compiler, the stylesheet, the preload, the schema and the database all carry the font path
   now, and a family joining changes data, a literal and a migration only.
3. **A route names its heading's CSS weight (`heroWeight`), not an Almarai file
   (`heroFace="almarai-700"`).** A face name cannot follow a chosen family; a weight can, and the
   family resolves it as the browser does (About's 600: Almarai 700, Archivo's one file). The
   hrefs are unchanged.
4. **The route budget is counted per page family.** The public stylesheets name no family but
   through the two stacks (checked), so an English route loads its Latin family and an Arabic
   route its Arabic family plus any family that stack names (Almarai's names Archivo, counted
   though it is almost never reached). Today: English 34,928 B, Arabic 141,684 B, of 184,320.
   Summing a Latin and an Arabic family per route would refuse any static Latin family, which no
   route ever loads together with Almarai.
5. **A chosen family's faces ride in theme.css, not in global.css.** Every route would otherwise
   carry every family's rules in its render-blocking stylesheet; this way only a themed site
   pays, about 2 to 4 KB for one family, and theme.css passes its "under 1 KB" only while no
   family is chosen. admin.css declares every family (the admin is exempt from the font budget,
   and the editor's tiles need them).
6. **The admin chrome keeps the brand's fonts,** as E12's chrome keeps its shapes: admin.css's
   `--ad-font` and `--ad-font-ar` do not read the font tokens. The tiles and the site sample draw
   each family; the releases preview (the public page) wears the pending theme's.
7. **Pages outside the layout keep the brand's fonts:** the maintenance page
   (`src/lib/maintenance/page.ts`, its own inline faces) and the page-visibility gate (system
   fonts) are not themed.
8. **Licence text is not shipped with the files.** The woff2 files carry the copyright notice and
   the OFL's address (name records 0 and 14), not record 13; whether that meets the licence's
   notice condition is a question for the lawyer (docs/legal/review-register.md, L-1, LOW), and
   the catalogue records each family's licence and notice.

## Rollback

The database stays at this migration (forward only), and the restated function still accepts
v1 and v2, so the forward window is safe: the deployed E12 editor sends v2. The reverse is safe
too while the catalogue holds only the brand's families: no row can hold a font token, so an E12
Worker reads every theme's tokens as before; its editor reads a v3 row's colours, motion, shapes
and type (`settingsOf` ignores `fonts`) and saves v2, which 0125 accepts. With releases on, a
pending change staged by an E13 Worker carries v3 settings, which an E12 Worker's publish would
refuse; releases are off until R14. The slice that adds a family inherits E12's step: save the
theme at the brand's fonts, then purge `site:chrome`, before rolling the Worker back past it
(launch runbook §10).
