# R14e: page passwords in release mode (owner item B1, option b)

- **Lane:** Releases
- **Design:** [R14B.md](R14B.md) "Owner item B1" (option (b), proposed there and chosen by the
  owner), [U14b](U14b.md) (`page_passwords`, `set_page_password`, `page_password_check`, the
  gate), R14b's staged page visibility (`src/lib/release/stagedPageVisibility.ts`) and the
  password door (`src/pages/api/admin/page-visibility/password.ts`), CLAUDE.md §3 page
  visibility and §8 (the U14b and R14b lane bullets), P-3 (a secret is immediate, never
  staged), P-14 (grants stated, both layers)
- **Branch:** `feat/r14e-page-passwords` from main `b6e2dd1e`
- **Migration:** `0130_page_password_release.sql` (placeholder, renumbered at the merge train)

## The problem

With releases on (R14b), a page cannot newly go behind a password. The secret must be immediate
(no release, draft, version or audit row may ever carry it), but the mode and the message above
the box are registry columns of `page_visibility`, which 0066's guard lets change only inside a
release. R14b's door therefore set a password at once only on a page already behind one, with
nothing pending and its message unchanged (only the exempt `password_version` moved), and
refused everything else in words.

## Plan (written before the build)

Option (b): the secret is stored at once, the mode and the message are staged as the page's
visibility change, and the page asks for the password only once that change is published.
Releases off, everything is main's.

### 1. The database (0130)

- `public.store_page_password(p_page_id uuid, p_password text) returns jsonb`: SECURITY DEFINER,
  `search_path = ''`, EXECUTE `authenticated` only (revoked from public, anon, service_role).
  The caller must be live (`app.live_role()`, H16's rule: active, unlocked, the token's role,
  the token's tenant) and manage visibility (`app.role_manages_visibility`: Admin, Developer);
  the tenant is the caller's PROFILE's, never an argument; releases must be on for it (55000
  otherwise: with releases off the door keeps calling `set_page_password`); the page must be
  in that tenant and not the homepage; the password 8 to 72 bytes. It writes only
  `public.page_passwords` (the bcrypt hash, cost 10, as 0061) and, when the page asks for a
  password on the live site, that row's exempt `password_version + 1` (so every unlock cookie
  of the old password stops verifying, as a password change does today; 0066's guard lets an
  exempt-only update through). Its audit row (`page_visibility.password_stored`) names the page,
  whether the live gate changed and the new version: never the password, the hash or the
  message.
- `public.page_password_stored(p_page_id uuid) returns boolean`: SECURITY DEFINER, STABLE,
  `search_path = ''`, EXECUTE `authenticated` only, the same live check and profile tenant;
  whether a hash is stored for that page. The release check asks it (below).
- `app.tg_page_password_sync` restated with one addition: a row ENTERING password mode (an
  insert, or an update from another mode) whose `password_version` did not move gets
  `old + 1`. A release writes the staged mode and message but never the exempt version, and
  0061's CHECK needs a version above 0 in password mode. Every writer that already moves it
  (`set_page_password`: insert at 1, update at old + 1) is unchanged, so releases off nothing
  differs. Still: no writer puts a page into password mode without a stored hash (23514), and
  leaving it deletes the hash, clears the message and moves the version.
- `page_password_check` is NOT changed: it already joins `page_visibility ... mode =
  'password'`, so a stored hash on a page whose live mode is not password admits no one (an
  inert hash). pgTAP holds that.
- The page-visibility guide, revision 2 to 3 (H11's catalog): the release-mode paragraph says
  what is true now.
- Postconditions: both functions' settings, owners and exact ACLs; the trigger body; the
  registry row unchanged (`page_passwords` never a registry table, `password_version` exempt);
  the guide in the catalog and every tenant.

### 2. The Worker

- `packages/schemas/visibility.ts`: `PagePasswordDraftSchema`, the staged change the door writes
  (a page target, mode `password`, the message, no redirect or days). No password field.
- `PAGE_VISIBILITY.parseDraft` / `draftRow`: what a release reads from a visibility draft (the
  list's save, or the door's password change). `derivePatch` uses them, so the overlay, the
  dry run and the apply accept a password draft; the list's PUT keeps refusing `password` (it
  has no secret to set).
- `stagedPasswordWrite` (stagedPageVisibility.ts), the door with releases on, after the route's
  live recheck: the same checks a staged save makes (the page, the homepage, the pending change
  named, a scheduled one refused, the live version), then the secret at once
  (`store_page_password`), then the mode and the message staged as the setting's full replace
  (a no-op against live, a page already asking for one with its message kept, stages nothing
  and discards a pending change it replaces). The edge is synced only when the live gate's
  version moved. Replaces `assertPasswordImmediate`.
- The release check (`validate.ts`): a change that leaves a page in password mode with no stored
  hash is refused with a plain sentence; the apply's own refusal of the same thing (the trigger's
  `page_visibility_password_required`) gets the same words (`apply.ts dbIssue`).
- A restore of a version in password mode stays refused (`restorePatch`): a version cannot carry
  the secret, and only the door may put a page behind one.
- The screen: "Behind a password" offered on every page in release mode; the door's body names
  the pending change; the drawer, the confirm and the toast say what is immediate and what waits.
