# H13: the attention list is for CMS staff

- **Lane:** hotfix (security lane), C10a's follow-up
- **Design:** none as a slice. Found by U7's adversarial check of C10a's non-staff block
  ([U7.md](U7.md), Open): the rule is C10a's (0097 §4, CLAUDE.md §5, architecture §3.4), Sales
  is a signed-in token that is not CMS staff (`app.is_staff()` is the four CMS roles, P-6) and
  reads no more than anon outside the CRM
- **PR:** the `fix/h13-attention-staff` branch, cut from U7 (#90), which merges first (its
  number is given at review)
- **Migration:** built as `0100_attention_staff.sql`; its number is assigned at merge
  (`scripts/renumber-migration.mjs`). Push, then merge: nothing deployed relies on the rows it
  removes. Read-back: `readback_h13.sql` in the build's scratchpad (19 expectations; all but
  `server_version_num` checked in the PGlite replay)

## As built

**The gap.** `public.dashboard_attention` (v4, 0066) is a security_invoker view granted to
`authenticated`, so the RLS of the tables under it decided its rows, and those tables give every
signed-in token their published rows. A Sales token therefore read rows over public content: a
`missing_image` row for a published post with no cover, a `placeholder_live` row for a published
sample project. Anon holds nothing on the view and reads none. Every fact in those rows anon
reads from the tables themselves, so nothing private leaked, but it broke the rule, and the list
is a CMS staff feature. A signed-in token with no role claim read them too (37 rows of seed.sql's
launch tenant in the replay), and so did `public.content_health` when a Sales token called it
directly: it is INVOKER, granted to `authenticated`, and counts three of the list's kinds.

**The fix (`0100_attention_staff.sql`).** The view is restated as 0066 left it, byte for byte,
between two marker comments, inside one outer `select a.kind, a.entity_type, a.id, a.slug,
a.title, a.at from (...) a`, whose WHERE is the staff test, applied once over the whole union
rather than in each of its eighteen branches. Same six columns, order and types (the postcondition
reads them; `create or replace` would refuse a change anyway); security_invoker kept, so RLS
still scopes a staff member's rows to the tenant. The test:

```sql
 where app.is_staff()
    or (pg_catalog.current_setting('role') = 'none'
        and (nullif(pg_catalog.current_setting('request.jwt.claims', true), '')::jsonb
               #>> '{app_metadata,role}') is null)
```

- **`app.is_staff()`**, as 0097's block uses it.
- **The second arm, the owner's session.** 0097's block is a policy `TO authenticated`, which
  never binds the owner. A view has no TO clause, so the staff test alone would also empty the
  owner's psql reads: the launch runbook's §6b check ("expect none", which would then pass on
  nothing), §6c's two checks and `round2-cutover.mjs`'s verify step all read the view as
  `postgres`. The arm is 0066's trusted context (the release guard: no switched role, no staff
  claim), narrowed to no role claim at all (0097 §5, the sample lock). PostgREST switches role on
  every request and a SECURITY DEFINER call does not change the role setting, so no API token
  reaches it; a session that sets any role claim is judged by it (pgTAP: the migration role with
  a Sales claim reads no row). It never reveals more than the session reads from the tables: the
  view is security_invoker.
- **Not security_barrier.** A caller's own filter evaluated before the staff test sees only rows
  the tables' RLS already gives that caller.

Grants are stated for both Supabase regimes (P-14), exactly as 0066 left them: everything
revoked from PUBLIC, anon, authenticated and service_role, then SELECT to `authenticated`.
Postconditions: still a security_invoker view with the six columns; the definition names
`is_staff` once, right after the union's closing alias, and the claim test closes that WHERE;
every privilege (MAINTAIN on 17) as stated, table-wide and per column; and the view read under a
Sales claim in the migration's own session answers no row. Mutations checked in the replay: the
WHERE replaced by `true`, an extra `grant select ... to anon`, and the second arm without its
claim test each make the migration raise.

**Readers checked.**
- **The dashboard** (`src/lib/admin/dashboard/loaders.ts`): the attention widget and the
  placeholder banner read the view only for a role holding `blog.write`, `services.write` or
  `seo.entityMeta` in full (`ATTENTION_CAPS`): Admin, Content Creator and SEO, all CMS staff.
  Developer and Sales never ask, whatever their stored layout names.
- **Site health** (`src/lib/admin/health/summary.ts`): `content_health` through `siteHealth.view`,
  Admin and Developer, both CMS staff, so no count moves. Called by a Sales token directly, it now
  counts no live placeholder, missing alt or missing consent; its other counts read the tables
  under the caller's RLS, as before.
- **The bell and the shell's counters** (`src/lib/admin/notifications/`,
  `src/lib/admin/shell.ts`) do not read the view; `loaders.ts` is its only reader in `src/`.
- **Sales** has no screen that reads it, so no screen of a non-staff role depends on the empty
  answer.
- **The owner** (runbook §6b, §6c, the round-2 verify step): unchanged, through the second arm.

No CMS role loses a row: pgTAP reads the published post's row as the tenant's Admin, Content
Creator, SEO and Developer.

**Tests.**
- `supabase/tests/rls_sales_role.test.sql` (66): `dashboard_attention` is off `_no_fixture()`
  (now empty), the Sales tenant holds a published post with no cover, and a new assertion holds
  `anon=0 sales=0 admin=1` (an Admin token of that tenant reads its one row).
- `supabase/tests/release_attention.test.sql` (26), section 4, per role class: Admin, Content
  Creator, SEO and Developer of the tenant read the row; a Sales claim reads the post itself but
  no row of the list; a token with no role claim none; another tenant's Admin none; anon none (no
  privilege); the owner's session reads it, and none once it carries a Sales claim.
- `supabase/tests/stats_health_rollups.test.sql` (81): a Sales claim reads the published sample
  project, but `content_health` counts no live placeholder for it.
- `tests/lib/attentionKinds.spec.ts`: the newest definition carries the wrapper (a restatement
  copied from an older one fails), this file's text is 0066's verbatim between its markers with
  0066's two grant lines, and every role whose screens read the list (the attention widget's
  capabilities, `siteHealth.view`) is CMS staff. `tests/lib/dashboardWidgets.spec.ts`: per role,
  the dashboard asks the view only as Admin, Content Creator or SEO.
- Without the migration (reverted with `git apply -R`, replayed, restored): `rls_sales_role`
  fails 3 (Sales `1>0` rows, the view's columns, `sales=1`), `release_attention` 3 (Sales 1 row,
  no claim 37, the owner with a Sales claim 83), `stats_health_rollups` 1 (`1/1`), and
  `attentionKinds.spec.ts` 3. The Admin, Content Creator, SEO, Developer, other tenant and anon
  assertions hold either way, by design: they pin what the fix must not take away.
- Replayed on PGlite 17.5 over 0001 to `0100_attention_staff.sql` with `seed.sql` (pg_net at
  0048): `rls_sales_role` (66), `release_attention` (26), `placeholder_guard` (49),
  `stats_health_rollups` (81), `rls_releases` (115) and `preview_dataset` (20) pass.
